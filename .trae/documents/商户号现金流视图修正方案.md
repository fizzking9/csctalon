# 商户号现金流视图修正方案（v3全域统一核算版）

## Context（背景 · v3 重新梳理 · 2026-08-02）

**业务关系彻底澄清（用户纠正了 v1/v2 的错误理解）：**

| 路线 | 表 | data_source 类型 | 语义 | 来源 |
|------|----|----|----|----|
| **A. 退费单线上直退** | `refunds` WHERE refund_method='线上' | business（经营报表导出） | 经营侧可登记退款（**严格按用户要求：退费单管理里只有这条算退款路线**） | 运营平台导出 xlsx |
| **B. 钱包用户取现** | `wallet_withdrawals` WHERE op_type='用户提现' | business（经营报表导出） | 经营侧可登记提现（钱从钱包真实提出到用户银行卡） | 运营平台导出 xlsx |
| **C. 闪猫退款** | `shenmao_refund` 独立业务表（暂未建，data_source.code=shenmao_refund 已占位） | business（经营报表导出） | 经营侧可登记的闪猫专项退款（独立表，C/D不是商户号流水分桶！） | 后续对接导入 |
| **D. 其他退款** | `other_refund` 独立业务表（暂未建，data_source.code=other_refund 已占位） | business（经营报表导出） | 经营侧可登记的其他退款（独立表，C/D不是商户号流水分桶！） | 后续对接导入 |
| **E. 商户号现金流** | `merchant_refunds` WHERE refund_status='SUCCESS'（不分 refund_type 桶） | financial（财务对账基准） | 微信侧**真金白银实际扣款**（第五张独立表，对账基准），**不再拆成 C/D 桶** | 商户号款项.xlsx 导入 |

**合计口径（v3 全局统一）：**
- **经营估算**（经营侧四路总登记出款）= **A + B + C + D**（C/D 独立表未建 → 暂 = A+B，建表后代码零改动自动并入）
- **实际现金流**（财务侧商户号真扣）= **E**（merchant_refunds.refund_status='SUCCESS' 全部合计，**不区分 ORIGINAL/BALANCE**，不分桶）
- **对账偏差** = 经营估算 − 实际现金流 = **(A+B+C+D) − E**（正值 = 有未登记的商户侧退款）

### v1/v2 错误（已废弃）
- ❌ v1 错误：把 C/D 当成 merchant_refunds.refund_type 分桶（ORIGINAL/BALANCE），认为 "财务实际 = C+D = ORIGINAL+BALANCE"
- ❌ v2 错误：认为 "经营估算 = A+B"，"偏差 = (C+D) − (A+B)"
- ✅ v3 纠正：**C/D 是独立的两张业务表**（闪猫退款 / 其他退款，data_source 已注册占位），**merchant_refunds 只对应 E = 实际现金流（独立第五张表，对账基准）**

**历史数据验证（6/30~7/20 窗口，C/D 未建表时）：**
- 经营估算（A+B）：¥734,568.95
- 实际现金流 E（merchant_refunds SUCCESS 合计）：¥783,183.57
- 对账偏差（经营 − 实际）= +¥48,614.62 ≈ **待补齐的 C（闪猫退款）+ D（其他退款）**（C/D 建表导入后，偏差应收敛）

## 改动清单（v3 最终版）

### 1. 后端 analytics.py — `backend/app/services/analytics.py`

#### 统一核算块注释（L83-L122）
在文件最开头的看板2区域定义【全域统一退款核算规范 v3】，所有看板/接口/指标必须严格遵守，禁止局部私自改写。

#### 统一聚合器 `_cash_routes_total()`（L203-L288）
**单一真相源**（Single Source of Truth）：全局所有看板的四路拆分、经营估算、实际现金流、对账偏差，全部调用此函数派生，**禁止局部重写筛选条件**。
```
返回字段:
  route_a/b/c/d: {count, amount}      四路经营出款
  operational:   {count, amount}      经营估算 = A+B+C+D
  actual_cashflow: {count, amount}    实际现金流 E = merchant_refunds SUCCESS 合计
  financial:    = actual_cashflow      向后兼容保留键(语义=财务实际)
  diff:         {count, amount}       对账偏差 = 经营 − 实际
```

#### 各看板函数（全部迁移到 _cash_routes_total 派生，不再局部写 SQL）
- **`cash_out_trend`**：四路 A/B/C/D 单独按日堆叠（direct/withdraw/shanmao/other_refund + total_count） + 实际 E（merchant/merchant_count）独立曲线 + 对账 diff。C/D 表未建 → 读 0。
- **`cash_out_breakdown`**：`total=A+B+C+D`（经营估算），`actual_cashflow=E`，`merchant_cash=actual_cashflow`（兼容旧键），`diff=经营−实际`，附 _spec 口径说明。
- **`merchant_cash_summary`**：filter 从 ❌ trade_status='REFUND' 改为 ✅ refund_status='SUCCESS'（不分 refund_type 桶），作为对账基准。
- **`dashboard_summary`**：退款总额/笔数 = A，cash_out_total = 经营估算 A+B+C+D，新增 cash_routes 结构化数据（前端直接渲染卡片）。
- **`today_kpi`**：今日退款 = A，cash_out = 经营估算 A+B+C+D，新增 actual_cashflow、cash_routes_today 结构化数据。
- **`refund_withdraw_full_chain`**：保留链路基类方法（单退费单匹配提现流水），与全域核算的聚合口径正交，互不冲突。
