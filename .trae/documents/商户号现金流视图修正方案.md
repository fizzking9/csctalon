# 商户号现金流视图修正方案（v4 全域统一核算版）

## Context（背景 · v4 落地 · 2026-08-23）

**业务关系彻底澄清（v1/v2 错误 → v3 纠正 → v4 落地）：**

| 路线 | 表 | data_source | 语义 | 来源 |
|------|----|----|----|----|
| **A. 退费单线上直退** | `refunds` WHERE refund_method='线上' | refund | 经营侧可登记退款 | 运营平台导出 xlsx |
| **B. 钱包用户取现** | `wallet_withdrawals` WHERE op_type='用户提现' | wallet | 经营侧可登记提现（钱从钱包真实提出到用户银行卡） | 运营平台导出 xlsx |
| **C. 闪猫退款** | `shanmao_refunds` WHERE status='已退款'（独立业务表，已建表有数据） | shanmao_refund | 经营侧可登记的闪猫专项退款 | 闪猫导出 |
| **D. 手动退款** | `manual_refunds` WHERE is_refunded='是'（独立业务表，2026-08-23 建表导入） | manual_refund | 客服在商户号后台手动操作的退款登记台账（商户号手机退款处理登记.xlsx），is_refunded='否' = 登记蓄水 | 商户号手机退款处理登记.xlsx |
| **E. 商户号现金流** | `merchant_refunds` WHERE refund_status='SUCCESS'（不分 refund_type 桶） | merchant_refund | 微信侧**真金白银实际扣款**（第五张独立表，对账基准），**只作对账，不与经营四路累加** | 商户号款项.xlsx 导入 |

**合计口径（v4 全局统一）：**
- **经营估算**（经营侧四路总登记出款）= **A + B + C + D**
- **实际现金流**（财务侧商户号真扣）= **E**（merchant_refunds.refund_status='SUCCESS' 全部合计，**不区分 ORIGINAL/BALANCE**，不分桶）
- **对账偏差** = 经营估算 − 实际现金流 = **(A+B+C+D) − E**（正值 = 商户侧已扣款但尚未登记到四路的退款）

**核心原则：商户号款项（E）属于现金流，不能与经营数据（A/B/C/D）累加。**

### v1/v2 错误（已废弃）
- ❌ v1 错误：把 C/D 当成 merchant_refunds.refund_type 分桶（ORIGINAL/BALANCE），认为 "财务实际 = C+D = ORIGINAL+BALANCE"
- ❌ v2 错误：认为 "经营估算 = A+B"，"偏差 = (C+D) − (A+B)"
- ✅ v3 纠正：**C/D 是独立的两张业务表**（闪猫退款 / 手动退款），**merchant_refunds 只对应 E = 实际现金流（独立第五张表，对账基准）**

### v4 落地（2026-08-23）
- **D 路物理表 manual_refunds 已建并导入**《商户号手机退款处理登记.xlsx》（1,896 行，已退款 1,858 笔/¥156,555.50），不再依赖占位表返回 0
- **决策概览（refund_decision_overview）修正**：原 v1/v2 遗留把 E 当"D 商户号直退"加进四路合计（重复计算），现改为 D=手动退款，E 独立作为对账基准展示
- **新增手动退款登记水位**（类比钱包水位）：登记 − 已退款完成 = 蓄水（已登记未退部分）
- **E 数据截止标注**：商户号现金流为快照（trade_time 截止 2026-07-20），对账区域明确标注截止日，截止日后偏差仅供参考

**历史数据验证（6/30~7/20 窗口，E 有完整数据时）：**
- 经营估算（A+B+C+D）：¥665,692（A ¥476,412 + B ¥180,070 + C ¥3,081 + D ¥6,129）
- 实际现金流 E（merchant_refunds SUCCESS 合计）：¥750,643
- 对账偏差（经营 − 实际）= −¥84,951（负值 = E 中有未在四路登记的商户侧退款，属正常对账差异）

## 数据校验（D 与 E 的关系，2026-08-23 实测）

- Excel 商户ID 22/27（81.5%）存在于 E 中
- E 覆盖窗口（6/29~7/24）：Excel 307 笔已退款，按订单号命中 E 退款流水 44.6%，命中中金额一致 79.7%
- 结论：**D（手动退款）⊆ E（商户号现金流）**——手动退款是商户号真实退款的一部分，E 天然覆盖 D，故 E 绝不能再与 D/A/B/C 累加

## 数据质量校验与审核（2026-08-23 增补）

### 背景
《商户号手机退款处理登记.xlsx》为人工录入台账，时间字段易出错。实测发现：
- 7 行登记日期年份错位（2002/2029/2032/2035），但操作时间均为正常 2026 年 → 可按操作时间佐证自动纠错
- 1 行备注="示例"的模板数据 → 应剔除
- 3 对 refund_amount=NULL 行因唯一索引对 NULL 不去重而重复导入 → 已改表达式索引

### 校验规则（L2，导入时）
| 规则 | 判定 | 处理 |
|---|---|---|
| R1 示例行 | 备注 strip 后 == "示例" | 跳过导入（warning） |
| R2 年份/范围异常 | 登记日期超出 [当前年-2 的1/1, 今天+3天] | 有操作时间佐证 → 年份按 op_time 修正（auto_fixed）；无佐证 → pending |
| R3 时间倒挂 | 操作时间早于登记日期超过 1 天 | pending（待人工确认） |

- 校验函数：`_manual_refund_quality_check`（upsert.py），结果写入 `manual_refunds.quality_status`（ok/auto_fixed/pending）+ `quality_note`
- 导入结果新增 `warnings` 字段（提示/纠错类，非失败），uploads API 一并返回
- 去重键改为表达式索引 `(register_time, order_no, COALESCE(refund_amount,0))`，空金额归一参与去重

### 审核视图（L3，人工确认兜底）
- 入口：管理 → 数据质量 → 「手动退款质量审核」tab（DataQuality.vue + ManualRefundQuality.vue）
- 顶部统计卡：待确认/自动纠错/已确认/全部（可点击筛选）
- 表格：登记日期/操作时间/金额/订单号/设备/人员/质量状态/质量说明
- 操作：`确认通过`（pending → ok）、`编辑修正`（弹窗改时间/金额/状态后置 ok）
- API：GET `/analytics/manual-refund/quality`、POST `/{id}/confirm`、POST `/{id}/fix`
