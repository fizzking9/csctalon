## Engineering Conventions
- 被投诉主体归一化规则(2026-08-26): 仅在被投诉主体聚合统计时使用 _norm_subject_entity 函数合并同名主体——"深圳市云客猫科技有限公司"与"云客猫"合并为"云客猫"。商户号投诉维度仍按原始 registrant 字段细分呈现
- 外部投诉平台分布图数据格式(2026-08-26): ECharts 饼图数据必须使用 {name, value} 格式, 禁止使用 {name, count} 格式
- 商户号投诉趋势图要求(2026-08-26): 必须包含不同主体的堆叠柱趋势图, 按日聚合, 主体各自成系列
- 退款人=审核人口径(2026-08-26): 退款工单中的"退款人"字段以审核人(auditor)为准，无审核人时回退至操作人(operator)
- 数据压缩函数规范(2026-09-15 新增): 为防止 AI 报告 token 超限（feed 限 6000 字符），需使用 _compact_reception_breakdown、_compact_refund_breakdown、_compact_queue、_compact_staff_efficiency 四个压缩函数处理数据
- LLM 时间解析输出规范(2026-09-15 新增): LLM 时间解析需输出结构化 JSON 格式{"start":"YYYY-MM-DD","end":"YYYY-MM-DD","confidence":0.9}，后端需校验日期合法性、不晚于今天且start≤end
- trigger_at 格式设计规则(2026-09-16 新增): trigger_at 三格式: daily=`HH:MM`(如 "09:00")/weekly=`wday-HH:MM`(如 "1-09:00"=周一9点, wday=1..7 ISO)/monthly=`day-HH:MM`(如 "1-09:00"=每月1号9点)。用 `-` 分隔前缀与 HH:MM, 与 daily 的纯 HH:MM 区分明显
- AI 调度真优先级队列(2026-09-16 #127 完成): llm_scheduler 升级为**进程级线程安全优先门闸**_Gate(threading.Condition + heapq 按 (level,seq)), 任一时刻仅 1 个 LLM 调用在飞(互斥锁仍有效)。**优先级按工单定死**: L0=后台定时预生成(数值最小最高优) > L1=admin 手动触发 > L2=用户实时问答; 高优先级经 `holder.loop.call_soon_threadsafe(task.cancel)` **抢占**在飞低优先级(跨 asyncio 循环)。被抢占**不恢复现场**(取"可重试"): ai.py/ai_report_worker 捕 CancelledError, ai_task_manager 置"被更高优先级抢占, 请稍后重试"。API: 原 register/deregister 升级为 async `acquire(level, *, provider_code)/release(handle)`, 用 asyncio.to_thread 线程桥入队(不占事件循环), 但 LLM 协程仍在**调用方线程自己的 loop**跑(db 不跨线程)。queue_status 新增 running_level/running_name/run_s/queued/providers, queue_length 真实化。**多 provider 独立队列**(commit 0f4d7b1): 全局单门闸改 `_gates: dict[provider_code,_Gate]`, 同 provider 内排队+抢占, 不同 provider 并行不互斥; 预生成用 template.llm_provider_code, 用户实时 None 走 default。
- 日报随高频同步刷新节奏(2026-09-16 #129): **周报/月报维持 trigger_at 一天一次**; **日报跟随高频数据同步**(生产 8-24 点每 30min 一轮): sync_task_manager._run_background finally(success/partial) 与 complaint_sync(推送入库后)均调 warm_on_sync_complete; daily 有 **20min 最小间隔节流**(_daily_generated_recently 查当日 template_id+snapshot_date+is_public 最新 created_at; 同步周期30min, 正常每轮触发, 挡手动频繁同步)。落库用户确认**每次新增留痕**(不覆盖, matcher 按 created_at DESC 取最新)。单飞锁 _worker_lock 挡重叠。
- 122b 专供 AI 报告预生成(2026-09-17 #131): **qwen3.5:122b(q4_K_M 81GB, qwen35moe family 125.1B 总参/~10B 激活)装在 gmk-evo=192.168.10.21(124GB 统一内存 APU, 磁盘余 189GB), 仅供预生成; 用户实时问答/时间解析仍走 qwen3.8:27b**。provider code `talon-gmk-qwen3.5-122b`(base_url 4080, priority=3, enabled=true, **pregen_only=true, timeout_s=600, retry_max=0**); daily_general_morning/weekly_compare_last/monthly_overview 三模板绑此 code。机制(commit 8f9df14, 迁移 e2f3a4b5c6d7): llm_providers.pregen_only=true → 被 get_active_providers(实时链)与 llm_warmup(启动预热)排除; get_provider_chain(db, provider_code) 指定方置顶+常规链 transient 降级兜底, 指定方 disabled/不健康/不存在自动退回常规链; chat_completion 新增 provider_code 形参; ai_report_worker 透传 template.llm_provider_code, 预生成超时 180→600s。**防坑: 缺失模型 ollama 返回 404=permanent 不降级, 故 provider 初始 enabled=false, 拉取+冒烟通过才 enable**。实测: 完整日报 78s/report 1309 字, 热模型 2.5s, 冷加载 81GB 约 35s, keep_alive 5min 空闲自动卸载(available 恢复 86GB)。**关键坑: 直连 ollama 自带 /v1 发 think:false 三件套会 content 空(thinking 不被识别); 必须经 talon-api 4080(透传 /api/chat think=false)才正常, 与 #113 设计一致**。llm_scheduler 门闸按 provider_code 分桶, 预生成与实时并行不互斥。qwen3.8 家族最大 27b, 122b 在 qwen3.5 线。
- 刷新节奏模板化 refresh_on_sync(2026-09-16 #130): ai_report_templates 新增 `refresh_on_sync BOOLEAN NOT NULL DEFAULT FALSE`(迁移 d1e2f3a4b5c6, 回填 daily/sync-triggered/period=daily→true)。warm_on_sync_complete 候选**不再硬编码 frequency**, 改为 `is_active AND refresh_on_sync=TRUE`, 20min 节流统一作用于所有随同步刷新模板。admin 新建缺省由 `_auto_refresh_on_sync(period,frequency)` 自动识别(period=daily 或 freq in daily/sync-triggered→true); **PATCH 仅显式传值才更新, 改 period/frequency 不重算**(尊重手动选择)。前端 AiTemplates.vue 有开关+口径说明, 新建切周期联动, 列表 tag「随同步刷新/每日定时」。注意 alembic revision id 手写易撞车(本次 a5b6c7d8e9f0 已被 manual_refunds 占用致 Cycle), 新建迁移前必须 grep versions 确认 id 唯一。

## Lessons Learned
- **PG 唯一约束对 NULL 不去重(2026-09-19 C-P1-7 事故, 工单 #160/#161)**: `wallet_withdrawals` 唯一约束 `uq_wallet_withdrawals_business` 含 `device_sn`(可空), 而 **PostgreSQL 唯一约束/唯一索引对含 NULL 的行不去重(NULL≠NULL)** → device_sn 为 NULL 的行(生产占 62.5%)完全不受保护。`upsert_wallet` 用 `on_conflict_do_nothing(constraint=...)` 匹配不上 → 高频同步(30min/轮)对同一笔反复插入。**生产累积 40603 行重复**(其中 38458 行备注「提现申请-冻结 WD...」= 提现失败/冻结记录), 全表 28852→69455 虚胖 2.4 倍。**修复两层**: ①#160 止损: 按 `(account_id,op_type,op_time,operator,op_amount,coalesce(device_sn,''))` 保留每组 1 行, DELETE 40603(单事务), 备份=表 `wallet_withdrawals_bak_20260919` + pg_dump `/opt/csctalon/backups/`; ②#161 治理: 迁移 `h3i4j5k6l7m8` 建**部分唯一索引** `uq_wallet_withdrawals_null_sn (account_id,op_type,op_time,operator,op_amount) NULLS NOT DISTINCT WHERE device_sn IS NULL`(PG15+ 的 NULLS NOT DISTINCT 让其余列含 NULL 也按 NULL 相等去重), 模型 `wallet.py` 用 `Index(..., postgresql_where=text(...), postgresql_nulls_not_distinct=True)` 镜像声明, `upsert_wallet` **按 device_sn 是否为空分流两个冲突目标**(非空→原 constraint, 空→index_elements+index_where)。**关键教训**: ①可空列进唯一键 = 去重形同虚设, 必须配部分唯一索引或 `NULLS NOT DISTINCT`; ②排查此类问题先查 `count(*) FILTER (WHERE col IS NULL)` 与 `GROUP BY ... HAVING count(*)>1`; ③建索引会暴露既有脏数据(测试库也撞出 154 行重复, 宽表测试 fixture 也撞), 建前必须先清理; ④**裸表口径 ≠ 经营口径**: 我最初按 `op_type='用户提现'` 裸算 B 路 597.89 万得出"虚高 3.5 倍"是误判, 真实经营 B 路有 `_route_b_withdraw_filter`(排除 冻结/退款失败/提现失败/超期订单不允许退款/驳回/拒绝/未到账 七关键词), 宽表重建前后**完全不变**(10935/1396578.62) → 证明重复行从未进经营统计; 报口径问题前必须先确认用的是哪套口径。
- **Edit 工具在中文路径文档上静默失败(2026-09-19 踩坑)**: 对含中文文件名的 markdown(如 `docs/design/AI数据接入助手设计-20260919.md` / `docs/README.md`)执行 Edit 时, 工具**返回成功快照但磁盘未变**(Read 随后也返回缓存内容, 造成"已改"的假象)。实测: #157 时对设计文档 §七 的改动与 docs/README 状态更新**均未落盘**, 直到 #158 才发现(设计文档 §七 仍是旧端点表、README 仍写「评审中」)。**规则**: 中文路径文档一律用 `python3 - <<'PYEOF'`(读→replace→写)或 Write 落盘, 并**立刻用 `grep -c 关键标记` 核验**; git add 后用 `git show --name-only` 确认文件真进了 commit(不能只看 `git status` 干净)。排查手法: `ls -la` 看 mtime 是否变化 + `python3 -c "open(p).read().count(kw)"` 直读磁盘。
- **生产部署与实测通路(2026-09-19 固化)**: ①生产 SSH: `ssh evox2`(tanzk@192.168.10.21)**免密** + `sudo -n true` **免密 sudo** 可用; 升级用 `ssh evox2 "sudo bash -lc '/opt/csctalon/current/deploy/upgrade.sh --git'"`(自动备份→切版本→重建→健康检查)。②Gitea API: 读 issue 匿名可(**`/api/v1/repos/tanzk/csctalon/issues/N`**), **写评论/关单必须认证** → 用 `~/.netrc` 里 `10.147.17.41` 的 login/password 做 **basic auth**(python `netrc.netrc().authenticators()` + base64), 比找 token 可靠。③容器内跑自测脚本: 宿主机 `scp` → `docker cp` → `docker exec -w /app -e PYTHONPATH=/app csctalon-backend python /tmp/x.py`(容器无 curl, 生产容器内 httpx 0.28.1 可用)。④**容器内 httpx 必须禁用 keep-alive**(`limits=httpx.Limits(max_keepalive_connections=0)` + `Connection: close`), 否则 uvicorn 关闭空闲连接导致轮询时 `ReadError: Connection reset by peer`。⑤容器内 `127.0.0.1` 只有后端(8000), nginx 在 csctalon-web 容器 → 前端可达性在宿主机 curl 验证。⑥升级后用 `docker exec csctalon-backend grep -c 新函数标记` + `alembic_version` 证实容器内代码/迁移已更新(不能只看 upgrade 输出)。

- 凭证核验铁律(2026-09-16 #116 教训): "代码侧完成"≠"验收通过"。手写 SQL 必须在 docker exec 里跑一次真实查询贴进评论, 涉及新表/新路由必须用真实 token 调一次 HTTP API。AGENTS.md「禁止『已测试通过』不可验证」铁律的变种说法(如"代码侧完成" "静态侧已验证")同样违规。工单关闭前 9 条验收条件逐条必须可复现核验, 不许用"代码完成"遮掩"运行时未测"。#116 一次部署即因 `end` PostgreSQL 保留字触发 500, 就因为没在凭证前跑过真实 SQL。
- PostgreSQL 保留字陷阱(2026-09-16 #116): 列名含 `end`/`start`/`date` 等保留字时, ORM (SQLAlchemy) 自动 quote 不报错, 但手写 `text("SELECT ... end, ...")` 会触发 syntax error。规则: 手写 SQL 中所有可能冲突的列名一律 `"col"` 双引号化, 不依赖"看起来没报错就安全"
- 凭证评论脚本教训(2026-09-16): 用 `curl --data-binary @file` POST 凭证评论**未包装 JSON {"body":...}** 导致 5 评论全 FAIL, 但工单已先关闭(违反"禁止无凭证关闭"铁律)。修复: 用 python json.dumps(body) 正确包装后补记凭证评论 id 978-983。教训: 凭证评论脚本必须先验证 POST 成功再关闭工单, 顺序不能反; markdown 含特殊字符必须用 json.dumps 转义非 --data-binary 直传
