## 【父工单】BMS 五源数据扩容（采集 + 对账 + 设备审计）

**标签**：`feature` `backend` `ops`（或按需）
**标题**：BMS 平台五类数据扩容：退款记录报表/订单/退货 采集 + 对账回填 + 设备月流量审计 + 设备档案

### 背景
为支撑"商户号退款对账闭环"与"设备审计"，需从 BMS(wifi.cloud-cat.cn/bms) 补充 5 类数据：
1. 退款记录报表 `/settle/refund-record-report`（= E 路线上退款水单，含精确退款时间/商户号/设备号 → 对账）
2. 订单管理 `/pay/pay-manage`
3. 退货跟踪 `/user/returnTracking`
4. 设备流量 `/device/device-flow`（单 SN × 按月，HTTP JSON API）
5. 设备管理 `/device/device-manage`（激活时间窗 → 补 devices 档案）

### 用户已拍板决策（2026-09-05）
- D1 设备流量仅建月汇总表 `device_flow_usage`（SN×月）
- D2 对账一期 = 采集入库 + D 路时间回填 + E/ABCD 逐笔勾稽视图
- D3 退款/订单/退货 先按需手动采集，不纳入定时
- D4 设备管理复用 `devices` 主表补字段，不新建扩展表
- D5 工单以本文档正文落地

### 子工单清单（依赖）
- #P1 采集框架接入前 3 源（退款记录报表/订单/退货）
- #P2 退款记录报表 → E 路/D 路对账回填（依赖 P1）
- #P3 设备月流量采集 + 设备审计工具
- #P4 设备管理档案回填 devices
- #P5 文档/缓存/验证（依赖 P1-P4）

### 关闭条件
所有子工单关闭且通过阶段 Gate（架构 LOCKED / CI / 审查无 CRITICAL）。

## 【子工单 P1】采集框架接入前 3 源（退款记录报表 / 订单 / 退货）

**标签**：`feature` `backend`
**标题**：新增 BMS 数据源：退款记录报表 / 订单管理 / 退货跟踪（Playwright 采集 + 入库）

### 背景 / 影响范围
3 个新源同属 wifi.cloud-cat.cn 域，自动归入 `bms-wifi` 组共享凭证，不需要重复配账号密码（本地 .env 已配 YKM-TZK 可测）。

### 架构文档路径
（待架构阶段产出 LOCKED 文档后回填，如 `docs/arch/A-20260905-00X-xxx.md`）

### 改动清单
按《数据源接入与缓存加速规范》§7.1：
1. `alembic/versions/` 新迁移建表：`refund_record_reports`（退款记录报表）/ `bms_orders`（订单）/ `return_trackings`（退货）——字段见规划文档 §4.1-4.3
2. `models/` 3 个新模型 + `models/__init__.py` 注册
3. `services/bms_fetcher.py` `BMS_DATA_SOURCES` 加 3 源（name/base_url/page_path/time_labels/time_format）
4. `services/data_parser.py` `COLUMN_TEMPLATES` 加 3 块
5. `services/upsert.py` 写 upsert + `UPSERT_DISPATCH` 加 3 键
6. `services/data_source_registry.py` `DATA_SOURCE_SEEDS` + FIELD_OVERRIDES + refresh
7. `services/bms_sync.py`/`api/v1/fetch.py` `valid_types`（L239/L383）加 3 源
8. **default_sync 先不设 True**（D3：手动跑通验证后评估）

### 约束
- 时间字段 naive-北京→UTC 入库（`_to_datetime`）；退款报表时间口径待样本确认
- 金额"元"(2位小数)；禁止裸 print/console.log
- BMS 65s 操作间隔遵守

### 测试要求
- pytest：每源 ≥1 正向 + 2 边界（映射/去重/时间），ruff 过
- 手动：3 源各触发一次同步，入库行数与 BMS 页面对得上

### 关闭条件
3 源可手动同步入库且数据正确；pytest+ruff 全绿；`fetch/data-sources` 列表可见。

## 【子工单 P2】退款记录报表 → E 路 / D 路对账回填

**标签**：`feature` `backend`（可能含 `bug` 若对账暴露既有问题）
**标题**：退款记录报表接入对账：E 路线上水单 + D 路手动退款时间回填 + ABCD/E 逐笔勾稽

### 背景
退款记录报表含平台订单号/商户号/设备号/精确退款时间 → 是"对账水单"。现 E 路 `merchant_refunds` 为 Excel 快照（7/20 截止、wx_refund_no 损坏）；D 路 `manual_refunds.op_time` 人工台账常缺失/不准。

### 一期范围（D2）
1. `refund_record_reports` 作为线上退款水单明细与 merchant_refunds 并存
2. **D 路 op_time 回填**：按 (device_sn/order_no, refund_amount, 时间窗) 可信匹配 → 回填 manual_refunds.op_time，带 `quality_status=auto_filled` + 溯源
3. **逐笔勾稽视图**：退款记录报表每行 → 尝试匹配 A/B/C/D → 标记 matched/未登记（= 商户实扣未记账的对账差异下钻）
4. E 路 merchant_refunds 缺失/损坏字段按可信键更新补全（对接键 merchant_refund_no）

### 约束
- 回填必须质量护栏（唯一命中才写、金额±容忍、多候选挂 pending）
- 不改变已 LOCKED 的 v4 核算口径（A+B+C+D 与 E 独立对账）；新增能力是叠加不是推翻
- 金额单位、时间换算遵循规范

### 测试要求
- 构造合成数据：D 路缺失 op_time 行被正确回填；多候选不误写；勾稽 matched/未登记分类正确
- pytest + ruff + 前端 build

### 关闭条件
对账勾稽视图正确；D 路回填带质量标记且可审计；不破坏现有 v4 对账展示。

## 【子工单 P3】设备月流量采集 + 设备审计工具

**标签**：`feature` `backend` `ops`
**标题**：设备月流量采集（单 SN×月，HTTP API）+ 设备审计查询工具

### 背景
设备流量页走 HTTP JSON API（已实测）：`GET /bms-portal/deviceFlow/sn/pageList?sn=&flowDate=YYYY-MM&timeType=2` → `{code, data:{total,totalFlow,items}}`。用途 = 设备审计时单 SN 按月汇聚记录到独立流量表；当月未完整月份可反复重取更新（9/5 取 9 月 9G，10 月可能更新）。

### 一期范围（D1 仅月汇总 / D3 按需触发）
1. 建表 `device_flow_usage`（device_sn + stat_month 唯一，flow_gb/day_count/last_date/month_complete/fetched_at）
2. 新增 `services/device_flow_sync.py`：复用 bms-wifi 登录态 cookie，封装单 SN×月拉取 → 聚合(若逐日) → 幂等 upsert
3. 后端 API：手动触发拉取（POST）+ 本地历史查询（GET 列表，分 SN/月/商户筛选）
4. 前端"设备审计"工具页：输入 SN + 选月份（默认按月）→ 查询上游→入库→展示本地月流量历史；补"重取更新不完整月"
5. 与现有 `/recharges/traffic/upstream` 占位打通或新增端点（不重复）

### 约束
- 一次一个 SN 调用上游（用户限制）；遵守 BMS 限流
- 幂等 upsert；month_complete=false 的月份可覆盖
- 登录态复用 bms-wifi 组凭证

### 测试要求
- HTTP fetcher 单测（mock 上游）+ upsert 幂等（同 SN×月重取不新增行只更新）
- pytest + ruff + 前端 build

### 关闭条件
工具页可对单 SN 选月查询并正确入库/更新；历史列表可查；幂等无重复。

## 【子工单 P4】设备管理档案回填 devices

**标签**：`feature` `backend`
**标题**：设备管理页（激活时间窗）采集 → 复用 devices 主表补齐档案

### 背景
`devices.sn` 主表多为采集自动建的空壳，缺 active_time/设备类型/商户/状态/ICCID/批次等。

### 一期范围（D4 复用主表）
1. `BMS_DATA_SOURCES` 加 `device_profile` 源（激活时间窗导出）
2. 解析/upsert → `devices` 主表 on_conflict_do_update(sn) 补齐 active_time/device_type/device_type_remark/merchant_name/status；若 devices 缺列（如 ICCID/批次/市场名称），架构阶段评估加列或另建精简扩展表
3. 手动触发（激活时间可回看历史区间分批）

### 约束
- 复用 `_sync_devices` 逻辑、不产生重复 SN
- 时间字段按规范入库

### 测试要求
- upsert 同 SN 补字段不新增；pytest + ruff

### 关闭条件
设备档案补全可用；无重复 SN；历史激活区间可回补。
