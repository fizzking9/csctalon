## 〇、一句话概括

**把「AI 报告/提示词用得好不好」从只有后台日志（system_events）变成生产可见的评估中心**：两级评估（规则级 + 提示词段）+ 跨链路关联（智能助手摘取提示词 ↔ 模板报告生成提示词）给出「不命中」归因，AI 产建议 → 人工一键确认 → 半自动写入（留版本、可回滚）。

## 一、背景与目标

### 1.1 用户诉求（原话要点）

> 「提示词的评估、迭代、升级，希望可以依照执行的结果、记录、评估分析后能够半自动来执行。为什么生产环境的页面没有对应的展示实现呢？是前端页面没有菜单链接显示吗？」
> 「规则级评估 + 提示词段评估 + 半自动执行 都要有」
> 「智能助手的提示词（报告的裁剪与整合输出）与模板报告（预处理报告）的提示词应该有很强的关联性吧，不然很容易不命中」

### 1.2 现状痛点

| 环节 | 现状 | 问题 |
|---|---|---|
| 执行结果记录 | 已有：`ai_reports.hit_mode`(full/section/live/rule)、`matched_count`、`latest_missing`；`governance_rules.hit_count` | 记录在，**无生产页面可看** |
| 评估分析 | `ai_feedback_service.build_health_report` 已产出三层建议（feed/模板/提示词） | 只落 `system_events` 事务通知中心，无独立 API/页面；**只出建议、无迭代执行路径** |
| 提示词关联 | 生成侧 `_SYSTEM_PROMPT`（H2 锚点纪律 + `**<维度>**：` 二级锚点行）与摘取侧 `_EXTRACT_SYSTEM`（按 H2 切分 + scope→H2 映射）各自独立演进 | **无一致性检查**：锚点漂移/关键词不贴 → 模板匹配不命中（走 LLM 兜底，贵且不可控） |
| 迭代升级 | 改 `question_keywords`/`question_template` 靠人工去 AiTemplates 页手改 | 无「建议 → 确认 → 应用」半自动通道；无版本留痕 |

### 1.3 目标

1. **评估中心页面**：近 N 天命中/兜底分布、模板命中率、治理规则健康度、高频未答好问题，全部可下钻。
2. **跨链路关联评估**：生成侧 vs 摘取侧锚点约定一致性检查 + 模板关键词命中率 + 「不命中」归因（关键词不贴 / 锚点漂移 / feed 缺失 / scope 覆盖不全）。
3. **半自动执行**：AI 产出结构化建议（补关键词 / 建模板 / 调规则动作）→ 人工一键确认 → 写入模板/规则，**每次写入留痕（谁改、何时、版本递增）**。
4. **规则健康度**：`governance_rules` 增加效果回填（执行成功 / 人工驳回 / 误报），支撑规则级评估。

### 1.4 非目标（取舍，评审重点）

- **不自动直接改代码常量**：`_SYSTEM_PROMPT` / `_EXTRACT_SYSTEM` 是提示词铁律，评估只给差异报告 + 人工落地指引（写入 `prompt_iterations` 留痕，人工按指引改代码）。
- **不做全自动执行**：一切写入必须人工确认；半自动 = AI 出建议 + 一键落地，人只做确认这一步。
- **不合并两条提示词链路存储**：`ai_report_templates`（模板）与 `governance_prompts`（治理研判）各自独立，评估中心是**只读聚合视图 + 各自写入**。
- **不做实时逐问评估**：评估窗口 = 近 N 天（默认 7 天），与 #153 健康报告同口径；不做请求级埋点改造。

## 二、总体设计：两级评估 + 跨链路关联 + 半自动闭环

```
┌─ 执行结果记录层（已有，本设计补 governance 效果回填）────────────┐
│  ai_reports.hit_mode / matched_count / latest_missing / llm_model │
│  governance_rules.hit_count + 【新增】effect_executed/rejected/fp │
└───────────────▲────────────────────────────────────────────────────┘
                │ 读
┌─ 评估分析层（本设计新增：评估服务 + 页面）─────────────────────────┐
│  ① 规则级评估：模板命中率(snapshots vs matched)、规则健康度(hit+效果)│
│  ② 提示词段评估：question_keywords 命中率 / 高频 live 兜底问句     │
│  ③ 跨链路关联（不命中归因）：                                      │
│     · 锚点一致性：H2_ANCHORS(摘取) vs _SYSTEM_PROMPT 铁律3(生成)   │
│                    vs 报告实际 H2 分布 → 漂移检测                  │
│     · 关键词覆盖率：高频问句 vs 模板 keywords → 未覆盖归因         │
│     · scope 映射覆盖：_SCOPE_TO_H2 键 vs 模板维度域 → 覆盖缺口      │
│  产出：suggestions[]（结构化，带建议类型/目标/理由/新值）          │
└───────────────▲────────────────────────────────────────────────────┘
                │ 建议(proposed)
┌─ 半自动执行层（本设计新增：prompt_iterations 留痕）────────────────┐
│  AI 建议 → 人工确认(confirm) → 应用(apply)：                       │
│  · 模板：追加 question_keywords / 改 question_template（版本递增） │
│  · 规则：调 governance_rules 动作/启停（效果回填联动）             │
│  · 代码常量差异：只记建议 + 落地指引，不自动写                     │
│  全部写 prompt_iterations（谁改/何时/old→new/状态机）              │
└──────────────────────────────────────────────────────────────────────┘
```

**关键原则：**

1. **评估只读、写必留痕** —— 评估中心全是聚合读；任何写入走 `prompt_iterations` 状态机（proposed → confirmed → applied / rejected）。
2. **「不命中」归因要能追到根** —— 同一问句重复走 live 兜底 = 关键词不贴；模板 0 命中 = 关键词覆盖缺；报告 H2 与摘取锚点不符 = 锚点漂移；三者归因不同、建议不同。
3. **半自动 ≠ 全自动** —— 每条建议落到页面，人工点「确认应用」才写；但写入是服务端一键完成（不用人去 AiTemplates 手翻）。

## 三、数据模型

### 3.1 `governance_rules` 扩效果字段（迁移 A）

| 列 | 类型 | 说明 |
|---|---|---|
| `effect_executed` | INT NOT NULL DEFAULT 0 | 按规则执行成功次数（execute 时 +1） |
| `effect_rejected` | INT NOT NULL DEFAULT 0 | 人工驳回次数（规则命中但人工否定建议） |
| `effect_fp` | INT NOT NULL DEFAULT 0 | 误报次数（规则命中但确认业务允许/无问题） |
| `last_effect_at` | TIMESTAMPTZ NULL | 最近一次效果事件时间 |

健康度口径：`fp_ratio = effect_fp / (effect_executed + effect_rejected + effect_fp)`；`fp_ratio > 0.5` → 建议停用/降级。

### 3.2 `prompt_iterations` 表（新增，迁移 B）—— 半自动执行留痕

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `scope` | VARCHAR(32) | `template_keyword` / `template_question` / `new_template` / `rule_adjust` / `anchor_guide` / `human_opinion`（#174 人工意见，只记录） |
| `target_id` | INT NULL | 模板 id / 规则 id |
| `target_name` | VARCHAR(255) | 快照名（模板 name_cn / 规则 code） |
| `suggestion` | TEXT | AI 建议内容（建议的新关键词/新问句/规则调整） |
| `reason` | VARCHAR(255) | 建议理由（如「近 7 天快照 3 份 0 命中」/「问句 X 重复 5 次走 live」） |
| `old_value` | TEXT NULL | 旧值（应用时对比） |
| `new_value` | TEXT NULL | 新值 |
| `status` | VARCHAR(16) | `proposed` / `confirmed` / `applied` / `rejected` |
| `created_by` / `confirmed_by` / `applied_by` | INT NULL | 各环节操作人 |
| `created_at` / `confirmed_at` / `applied_at` | TIMESTAMPTZ | |
| `result` | VARCHAR(64) NULL | 应用结果（success / skipped / error + 摘要） |

状态机：`proposed`（评估自动产出）→ `confirmed`（人工点确认）→ `applied`（服务端写入成功）；人工点「不采纳」→ `rejected`（可记原因）。

## 四、后端接口（挂 `/admin/ai/prompt-eval`，AdminUser，`{code,data,message}`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/summary?days=7` | 总览：命中分布(hit_mode)、命中率、live 占比、模板命中热度 Top、治理规则健康度、高频兜底问句 Top |
| GET | `/templates?days=7` | 模板级：snapshots/matched/命中率/question_keywords/latest_missing 聚合（复用 build_health_report 数据源） |
| GET | `/anchor-check` | 跨链路锚点一致性：静态比对 `H2_ANCHORS`(摘取) vs `_SYSTEM_PROMPT` 锚点常量 vs 报告实际 H2 分布（漂移清单） |
| GET | `/governance-rules` | 规则健康度：hit_count + 效果回填 + fp_ratio 排序 |
| POST | `/suggest` | 生成半自动建议：基于上面四路信号产结构化 suggestions（可 LLM 提炼关键词 / 纯规则提取，见 §六） |
| POST | `/iterations` | 人工对建议拍板：`confirm` / `reject` |
| POST | `/iterations/{id}/apply` | 服务端应用：写模板/规则，版本递增，回填 result |
| POST | `/opinions` | 人工意见输入（#174）：内容(必填)+分类+关联对象，落 human_opinion 行，只记录不自动执行 |

`/suggest` 与 `/iterations` 依赖 `llm_scheduler` L1（如走 LLM 提炼关键词）；纯规则路径不调 LLM。

## 五、前端页面设计（界面设计说明规范 · 五要素）

### 5.1 目的（替谁 / 答何决策）

**替 admin** 回答：「AI 报告/提示词的命中链路健不健康？哪里在漏？要不要迭代、迭代成什么？」—— 把 #153 只落通知中心的结果搬到决策可见的页面，并给出可执行路径。

### 5.2 逻辑（为何这样组织）

- 独立菜单「提示词评估中心」（`/system/ai-prompt-eval`，roles=admin），归「AI 与分析」分组，与「AI 管理(配置侧)」「AI 报告历史(查看侧)」并列 = **评估侧**。不塞进 AiAdmin 3 Tab（配置侧已满，评估是另一语义；同 #141 报告列表拆出独立页的先例）。
- 页面五个区块 + 一个「迭代建议」抽屉：
  1. **总览卡片**（4 卡 + 1 表）：命中率 / live 兜底占比 / 模板 0 命中数 / 规则预警数 + 高频兜底问句表（可下钻到近 N 天明细）
  2. **模板评估表**：模板 × (快照/命中/命中率/关键词/缺失维度)，按命中率升序（问题模板在前）
  3. **跨链路关联卡**：锚点一致性结果（生成约定 vs 摘取锚点 vs 实际报告 H2）+ 覆盖缺口
  4. **规则健康度表**：规则 × (hit/执行/驳回/误报/fp_ratio)
  5. **人工意见区块**（#174）：表单（意见内容必填 + 分类[分析异常/不合理/业务深化/其他] + 关联对象可选）
     + 意见列表（分类标签 + 状态 + 提交人/时间），待处理意见可「采纳 / 不采纳」——
     它是「人补充评估」的输入口：机器评估只认规则，业务直觉/异常判断无处落账，
     会导致「看出来了但没记录、下次还要重新发现」
  6. **迭代建议抽屉**：列出 suggestions[]，每条带「理由 + 新值预览」，按钮 确认应用 / 不采纳
- 布局贴近用户偏好：紧凑、问题优先（命中率最低排最上）、ⓘ 数据说明 + 可下钻。

### 5.3 口径

- 评估窗口 = 近 N 天（默认 7，可切 1/7/30），北京时间 `created_at AT TIME ZONE 'Asia/Shanghai'`（数据时间规范）。
- 命中率 = `(full + section) / 本人私有问答总数`（与 #153 build_health_report 完全同口径，页面标注「与健康报告同源」）。
- 模板命中率 = 窗口内快照的 `matched_count` 合计 / 快照数（快照级口径，近似值，页面注明）。
- fp_ratio、规则健康度见 §3.1。
- 「空」的含义：无问答 → 命中率显示 `-` 并说明「本期无用户问答」；模板无快照 → 命中率 `-` 说明「本期未生成」。

### 5.4 取舍（不做什么及原因）

- **不自动改代码常量提示词**（提示词铁律）：锚点漂移只出差异报告 + 落地指引，不提供写入口。
- **不做全自动**：所有写入必须人工点确认（半自动的「半」字）。
- **不做治理研判提示词(governance_prompts)的迭代入口**（本期）：那是研判链路，先不混入报告链路评估；规则级评估只覆盖 governance_rules 健康度。
- **不做请求级实时埋点**：复用已有 `ai_reports`/`system_events` 留痕，评估窗口化。
- **人工意见只记录 + 采纳/不采纳跟踪，不自动转执行**（#174）：自由文本不可靠，不解析、不自动改模板/规则；采纳仅打标记(confirmed)，落地走现有「AI 管理」或迭代抽屉。

### 5.5 工单

#173（本设计）；三层落地：本文件（设计）+ 页面 ⓘ 说明 + 代码头部 Design Rationale 注释块 + review-checklist 过审。

## 六、跨链路关联评估与半自动建议（核心）

### 6.1 两条提示词链路的关联点（回答用户「应该有强关联」）

| 关联点 | 生成侧（模板报告·预处理） | 摘取侧（智能助手·裁剪整合） | 评估 |
|---|---|---|---|
| H2 锚点 | `_SYSTEM_PROMPT` 铁律 3：周报/月报必须按 5 锚点结构化 | `H2_ANCHORS` 常量 + `split_sections` 按 `##` 切分 | 静态比对两处锚点集合 + 报告实际 H2 分布 → 漂移清单 |
| 维度二级锚点行 | `【维度输出格式】`：`**<维度>**：<数据>` | 摘取识别 `**<维度>**：` 锚点行 | 比对两端常量约定是否一致（本期只读展示） |
| 关键词 | `question_keywords`（匹配用户问句） | 无独立关键词（靠 scope→H2） | 高频兜底问句 vs 关键词 → 覆盖率 |
| 问句→维度 | `question_template` + `required_dimensions` | `_SCOPE_TO_H2`（退款/投诉/接待→H2 段） | 模板维度域 vs scope 键覆盖缺口 |

### 6.2 「不命中」归因规则（确定性规则，不依赖 LLM）

| 信号 | 归因 | 建议 |
|---|---|---|
| 模板 snapshots>0 且 matched==0 | 关键词不贴用户问法 | 建议：从高频问句提取候选词补 `question_keywords` |
| 同问句+同窗口 live ≥2 次 | 关键词/模板覆盖缺 | 建议：新增模板或补关键词（含问句样本） |
| live_ratio ≥ 0.5 | 提示词层整体失灵 | 建议：锚点对齐检查 + 逐模板排查 |
| 报告实际 H2 ⊄ 约定锚点 | 锚点漂移（生成侧/模板问句导致） | 建议：落地指引（改 question_template 或代码常量，记 anchor_guide） |
| 模板 required_dimensions 含 scope 无映射 | scope 覆盖缺口 | 建议：补 `_SCOPE_TO_H2` 映射（代码侧，记落地指引） |
| 规则 fp_ratio > 0.5 | 规则误报率高 | 建议：停用/降级规则（可半自动：确认后置 enabled=false） |

### 6.3 建议产出

`/suggest` 产出 suggestions[]（每条 = scope/target_id/suggestion/reason/old_value/new_value）：
- **补关键词**：优先从高频兜底问句做词频提取（规则路径，快）；可选 LLM 提炼（L1 调度，27b）。
- **新模板**：高频兜底问句聚类（按问句窗口聚合，规则路径）。
- **规则调整**：fp_ratio 阈值驱动。
- 锚点漂移/scope 缺口：只产 `anchor_guide` 落地指引，不产可写值。

### 6.4 应用动作（apply）

| scope | 应用动作 | 留痕 |
|---|---|---|
| template_keyword | `UPDATE ai_report_templates SET question_keywords = old || new`（去重） | prompt_iterations + version 递增（复用 #130 迁移范式） |
| template_question | 更新 question_template（人工确认时含新值全文） | 同上 |
| rule_adjust | 置 enabled=false / 改 disposition | governance_rules 变更 + 记录 |
| new_template | 本期只记录建议，不自动建模板（建模板需人工去 AiTemplates 补全 required_dimensions） | 建议留存 |

## 七、约束与禁止事项

1. 表结构变更必须走 Alembic 迁移（单 head；新 revision id 前先 `grep alembic/versions` 确认唯一）。
2. SQL 一律 `text()` + 绑定参数；`"start"/"end"` 等保留字必须 `""` 引号化（#116 教训）。
3. 时间窗口北京时间 `AT TIME ZONE 'Asia/Shanghai'`；`jsonb_typeof(latest_missing)='array'` 守卫（#153 约束 4）。
4. 响应格式 `{code, data, message}`；错误走 HTTPException（error-code.md）。
5. **禁止自动修改 `_SYSTEM_PROMPT` / `_EXTRACT_SYSTEM` 代码常量**（提示词铁律；只出差异报告与落地指引）。
6. 禁止无工单开发（#173 已建）；提交信息必须带 `#173`。
7. 前端禁止裸 `console.log`，后端禁止裸 `print`（logger）。
8. 中文路径文档落盘后必须立刻 `grep -c 关键标记` 核验（Edit 中文路径静默失败教训）。
