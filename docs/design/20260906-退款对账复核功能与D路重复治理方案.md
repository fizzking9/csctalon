## 一、背景与问题（来自生产对账分析）

### 1.1 业务分层（用户确认，与数据吻合）

| refund_method | 语义 | 与 E(退款记录报表) 关系 |
|---|---|---|
| **线上** | 商户号直接扣款退款（不进钱包） | 命中率 98.1%，即 **A 路** |
| **转入提现账户** | 先退到用户钱包（79% 也走商户号扣款进钱包） | 命中 E 79.1%，其后用户再提现 → **B 路** |
| **线下**（BR/SP）| 非商户号微信退款 | 仅 4.2% 在 E，不应对账 E |

- E（`refund_record_reports`）= 商户号微信退款水单（仅 WX/WS/WN，无 WD 提现单），是"真金白银扣款"对账基准。
- B（`wallet_withdrawals` 用户提现 WD 单）是"转入提现账户"的第二层，与 E 不同源。

### 1.2 核心缺陷：D 路手动退款重复登记

- `manual_refunds` 全表 **5,829 行 / 仅 2,878 个去重 order_no**（超额 2,951 行 / ¥444,066）。
- 典型脏数据模式：同一 `order_no` 两行——
  - ① 无SN行：`device_sn` 空、金额恒 100、`register_time` 为乱年份（2001~2005/2031）的 09-26、`remark`="余额已清除/押金"；
  - ② 有SN行：真实设备、真实金额、真实登记日期/客服。
- **回填放大缺陷**：`backfill_d_op_time`（`reconcile.py`）L1(order_no) 匹配把同一 E 水单 report **回填到 2~5 行 manual**（1,594 个 report → 3,201 行 / ¥365,177），使无SN历史残留行也被 `COALESCE(op_time,register_time)` 拉进近期统计窗口 → 重复计入 D 路经营。

### 1.3 对账差量化（修复 D 重复后收敛）

| 窗口 | A+B+C+D 原始 | E | 差 | D 重复超额 |
|---|---|---|---|---|
| 8月 | ¥1,208,648 | ¥1,004,962 | **+¥203,686** | **¥202,970** |
| 9/1~9/5 | ¥247,942 | ¥199,723 | **+¥48,219** | **¥49,228**（348行, 97%无SN）|

全窗口（06-01~09-05）原始差仅 +¥9,590（0.28%），因 6-7 月 E>经营 与 8-9 月 经营>E 对冲；**逐月/近期差异主体 = D 重复**。

## 四、方案 A：D 路重复治理

### 4.1 修复 `backfill_d_op_time`（reconcile.py，代码缺陷）

**现状缺陷**：`_match_report` 的 L1(order_no) 一旦匹配到 report 就回填，未限定 manual 行本身的质量特征；同一 report 可被多条 manual 命中（无SN残留行 + 真实行）。

**修复规则**（不推翻 LOCKED 的匹配优先级，仅加护栏）：
1. **候选 manual 限定**：回填候选排除"无SN + register_time 年份异常(非近2年)" 的疑似残留行（`device_sn` 空 且 `register_time` 不在 2025~2026 区间 → 不自动回填，标 `quality_status=pending` 待人工）。
2. **唯一候选强制**：L1/L2 命中 >1 条 manual 时**不写**，标 pending（现逻辑已有多候选判 pending，但未对"同 report 已回填其他行"去重 → 补：同一 report 只允许回填一条 manual，即 `backfill_manual_refund_id` 已置位则跳过）。
3. **幂等/溯源保持**：沿用 `quality_status=auto_filled` + `backfill_refund_record_report_id` 双向溯源，可回滚。

### 4.2 历史脏数据清理（一次性治理脚本）

**目标行**：`manual_refunds` 中
- `device_sn IS NULL OR device_sn=''`
- AND `is_refunded='是'`
- AND `register_time` 年份 ∈ [2001..2024] ∪ {2031}（乱年份残留，且与同 order_no 的真实行成对）
- AND `remark` ∈ {余额已清除, 押金, 退电池费用, ...}（业务判断为非微信实扣的"占位/补录"行）

**处理策略（三选，建议 A）**：
- **A（推荐）**：不物理删除，先标 `quality_status=duplicate_residual` + `quality_note`（写 reason/对应对账 report id），统计口径 D 路 `_route_d_other_agg` 增加排除 `quality_status='duplicate_residual'` 的条件（口径调整需架构评审，因为涉及 LOCKED 聚合函数）。→ **风险最小、可回滚**。
- B：物理删除（先导出备份）。
- C：仅出报告，人工在 ManualRefundQuality 页面逐条确认。

> 因 4.2 涉及 `_route_d_other_agg`（analytics.py LOCKED 引用）的统计口径变化，**必须走架构评审 + 更新 LOCKED 文档版本**，不得静默改。

### 4.3 防复发
- `upsert_manual_refunds` 去重键已含 (登记日期, order_no, device_sn, 登记人)；对"无SN + 乱年份"入参增加质量校验（`quality_check`）标 pending 或拒收，防再次混入。
- 每日/定时巡检：`manual_refunds` 异常年份行计数告警（可挂 A-20260904-001 健康告警扩展）。

## 五、方案 B：手动对账复核功能

### 5.1 数据模型（ER 增量）

新表 **`reconcile_checks`**（对账复核批次，仅留痕不参与统计）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| check_no | varchar(32) unique | 复核单号 `RC+日期+序号` |
| window_start / window_end | timestamptz | 对账时间窗（北京时间 naive → UTC aware 存） |
| grain | varchar(8) | 复核粒度 day/week |
| route_snapshot | jsonb | **时点快照**：{A:{cnt,amt},B:...,C:...,D:...,E:{cnt,amt},operational,actual_cashflow,diff}（复用 `_cash_routes_total` 口径，冻结留痕） |
| detail_stats | jsonb | 勾稽汇总：E 命中 A/B/C/D/unmatched 笔数金额（复用 water_statement 分类逻辑） |
| dupe_detect | jsonb | 本窗 D 路同 order_no 多行/无SN乱年份 检出数（辅助复核） |
| conclusion | varchar(16) | 结论：`一致` / `差异已确认` / `存疑待查` |
| note | text | 复核备注（客服/财务填写差异原因） |
| reviewed_by / reviewed_name | int / varchar | 复核人（Admin/Supervisor） |
| reviewed_at | timestamptz | 复核时间 |
| created_at / updated_at | timestamptz | TimestampMixin |

> 复用项目既有模式：`IDMixin + TimestampMixin`（同 MetricDailySnapshot），JSONB 存明细快照，避免逐笔冗余表。

### 5.2 接口契约（挂现有 `/reconcile` router）

| 端点 | 方法 | 权限 | 说明 |
|---|---|---|---|
| `GET /reconcile/check/run?start=&end=&grain=` | GET | CurrentUser | 生成某窗口对账预览（不落库）：五路合计+差异+逐笔勾稽分类+D重复检出 |
| `POST /reconcile/check/confirm` | POST | Admin/Supervisor | 对窗口发起复核：落库 reconcile_checks（含快照+结论+备注） |
| `GET /reconcile/check/list?page=&page_size=` | GET | CurrentUser | 复核批次列表（可按窗口/结论过滤） |
| `GET /reconcile/check/detail?id=` | GET | CurrentUser | 批次详情（快照 + 勾稽明细分页 + 差异明细下钻） |
| `POST /reconcile/check/{id}/conclusion` | POST | Admin/Supervisor | 补/改结论与备注（留痕更新） |

参数约定：`start/end` 按北京时间传入（`YYYY-MM-DD` 或 ISO），后端 `_to_utc_aware` 归一（复用 reconcile.py 现函数）。金额单位**元**（与退款报表一致，不分/元换算）。

## 七、风险清单

1. **D 路治理影响统计口径**：`_route_d_other_agg` 加排除条件改变经营估算 → 属 LOCKED 口径变更，必须走架构评审 + 更新 A-20260902-011 版本号，否则 A/B/C/D 与历史不可比。缓解：默认方案 A 仅加 `quality_status` 标记不参与统计前先评审。
2. **回填修复误伤真实低精度行**：排除"无SN+乱年份"可能漏掉真实但无SN的退款登记。缓解：不自动回填转 pending，人工复核（ManualRefundQuality 页面已有 confirm/fix 能力）。
3. **对账复核快照口径漂移**：若复核页复用的聚合函数与展示页不同步（如时间换算/状态过滤）→ 复核结论失真。缓解：复核快照**强制复用 `_cash_routes_total`/`water_statement` 同一函数**，加回归测试断言与展示页一致。
4. **复核标识被误用为"已对平"的免责标记**：conclusion=一致 不代表数据无误，仅代表该窗口人工核对过。缓解：UI 文案明确"复核=人工确认口径与数据，非数据正确性保证"，并记录 reviewed_by/reviewed_at 可审计。
5. **大量历史脏行治理的误删风险**：2001-2025 部分 register_time 可能是真实历史台账（记忆：register_time 2001-2025 大量历史台账为真实数据逐年递减）。缓解：**绝不按 register_time 年份一刀切删除**；治理仅针对"与同 order_no 真实行成对 + 无SN + 金额100占位"的残留特征，先预览报告再执行。
