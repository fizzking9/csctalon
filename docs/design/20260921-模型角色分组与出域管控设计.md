# 模型角色分组与出域管控设计（2026-09-21）

> **性质**：需求（REQ）—— 待人工锁定后实施。
> **背景**：`docs/design/20260921-*.md` 讨论产出。
> **关联实测**：[talon 模型能力矩阵](../../../talon/docs/reports/模型能力矩阵与任务分流-20260920.md)

---

## 一、问题陈述

### 1.1 现状

| 问题 | 证据 |
|---|---|
| **P1. 业务代码硬编码模型名** | `ai_semantic_matcher` 曾写死 `talon-gmk-qwen2.5-7b`，实测该模型 5/5 全错，修它必须改业务代码 |
| **P2. 管理界面按扁平列表展示** | `LlmProviders.vue` 是一张扁平表格（按 priority 排序），**看不出「谁为哪个角色服务」** |
| **P3. 档位绑定在代码里** | 三档位（assistant/specialist/expert）的 primary/secondary 写在 `llm_tiers.py` 常量中，**管理员无法在界面调整** |
| **P4. 云端静默兜底，无出域管控** | `CLOUD_FALLBACK="deepseek-v4-flash"` 硬编码进所有档位链尾部；本地 transient 失败**自动出网**，且**无任何开关、提示或审计标记** |

### 1.2 P4 的危害（最重要）

用户明确的核心价值主张（talon 定位文档 §2）：

> 「**数据不出内网**将会是很多企业主的刚需。另外他们会对**不可预知的账单恐慌**。」

而当前实现：
- 本地模型超时（实测 27b 过去 30% 概率超时）→ **静默把客户工单数据发到 api.deepseek.com**
- 无开关、无日志标记、无用户确认

**这是「为可用性牺牲数据边界」，且违背定位。必须修。**

## 二、设计目标

| # | 目标 | 验收判据 |
|---|---|---|
| G1 | 模型**按角色分组**展示与配置 | 管理界面按「助理/专员/专家」分区，每区显示成员与其兜底顺序 |
| G2 | 每角色支持**多个模型兜底** | 有序列表，界面可上下调整顺序；运行时按序降级 |
| G3 | **出域策略参数化** | 管理员可在界面设置 `never / explicit_only / auto`；`never` 时云端从所有链中移除 |
| G4 | 出域**可审计** | 每次出网调用在 `llm_call_logs` 有明确标记（如 `is_cloud=true`） |
| G5 | 与 talon「能力级路由」(P1-1) 方向对齐 | 档位语义可映射为 `capability:xxx` |

## 三、数据模型

### 3.1 `llm_providers` 增列

| 列名 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `is_cloud` | bool | `false` | **是否出域**（云端/公网）。`true` 时受出域策略管控 |
| `role_scope` | varchar(32) | `NULL` | **显式归属角色**（`assistant`/`specialist`/`expert`/`NULL`=不限） |
| `role_order` | int | `100` | **角色内兜底顺序**（小=先尝试）。仅 `role_scope` 非空时有意义 |

> **设计取舍：为什么用 `role_scope` 而非新建 `llm_roles` 表？**
>
> 方案 A（新表 `llm_roles` + 关联表）：规范化，支持一模型多角色。
> 方案 B（**采用**）：`llm_providers` 加两列。
>
> **选 B 的理由**：实测模型能力差异明显且互斥（MoE 有数值缺陷、Dense 慢），
> **一个模型服务多个角色的场景在当前集群不存在**；且 provider 数量仅 5 个。
> 加表会引入 JOIN 复杂度而收益为零。**若将来出现多角色需求，再迁移到 A。**

### 3.2 新增 `llm_role_config`（角色定义，单行一角色）

| 列名 | 类型 | 说明 |
|---|---|---|
| `role_key` | varchar(32) unique | `assistant` / `specialist` / `expert` |
| `display_name` | varchar(32) | 助理 / 专员 / 专家 |
| `description` | varchar(255) | 用途说明（含实测依据） |
| `enabled` | bool | 角色总开关 |
| `allow_cloud` | bool | **该角色是否允许出域**（细粒度控制） |
| `tier_order` | int | 全局档位顺序（供 UI 排序） |

> `llm_role_config` 仅 3 行，用于**界面文案与角色级开关**，避免把提示语写死在前端。

### 3.3 新增系统设置项（全局出域策略）

复用现有系统设置机制（`app/core/config.py` 的 settings + 可能需要 `system_settings` 表）：

| 键 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `LLM_CLOUD_POLICY` | `never` / `explicit_only` / `auto` | **`explicit_only`** | 全局出域策略 |
| `LLM_CLOUD_REQUIRE_CONFIRM` | bool | `true` | `explicit_only` 下是否需用户确认 |

**策略语义**：

| 取值 | 行为 | 适用 |
|---|---|---|
| `never` | 云端 provider **从所有链中移除**（等效禁用） | 数据绝对不出域 |
| `explicit_only` | 仅当**调用方显式指定**云端（或用户确认后）才用 | ✅ **默认**：兼顾体验与合规 |
| `auto` | 本地失败自动降级云端（**当前行为**） | ⚠️ 需管理员明确选择 |

## 四、运行时逻辑改造

### 4.1 `llm_tiers.resolve_tier()` 改为读 DB

```python
def resolve_tier(db: Session, role_key: str) -> list[str]:
    """按角色查 DB，返回按 role_order 排序的 provider_code 链。

    云端过滤由 LLM_CLOUD_POLICY 决定：
      never        → 排除所有 is_cloud=true
      explicit_only→ 排除（除非调用方传 include_cloud=True）
      auto         → 保留在链尾
    """
```

**保留** `llm_tiers.py` 的常量作为**兜底默认值**（DB 无配置时使用），避免首次部署即失效。

### 4.2 `get_provider_chain()` 增加出域过滤

```python
def get_provider_chain(db, provider_code=None, *, allow_cloud=None):
    """allow_cloud=None 时按全局策略决定；False 时强制排除云端。"""
```

### 4.3 `llm_call_logs` 增加出域标记

| 列名 | 类型 | 说明 |
|---|---|---|
| `is_cloud` | bool | 本次调用是否出域（便于事后审计"数据去过哪") |

## 五、管理界面改造（`LlmProviders.vue`）

### 5.1 版式：从「扁平列表」改为「角色分区」

```
┌─ 出域策略 ────────────────────────────────────┐
│  ○ 禁止出域 (never)                            │
│  ● 仅显式允许 (explicit_only)   ← 推荐          │
│  ○ 自动降级 (auto)                              │
│  ⚠️ 当前有 N 个云端 Provider 受此策略约束        │
└────────────────────────────────────────────────┘

┌─ 助理 assistant ──────────────────────────────┐
│  速度优先：分类打标 / 语义匹配 / 摘取排版        │
│  ┌────┬──────────────────┬──────┬────┬─────┐  │
│  │ 顺序│ 模型              │ 类型 │健康│ 操作│  │
│  ├────┼──────────────────┼──────┼────┼─────┤  │
│  │ 1  │ qwen3-coder:30b  │ 本地 │ ✅ │↑↓ ⚙│  │
│  │ 2  │ qwen2.5:7b       │ 本地 │ ✅ │↑↓ ⚙│  │
│  │ 3  │ deepseek-v4-flash│ 云端 │ ✅ │↑↓ ⚙│  │
│  └────┴──────────────────┴──────┴────┴─────┘  │
│  [ + 添加模型到本角色 ]                         │
└────────────────────────────────────────────────┘
（专员 / 专家 同构）
```

### 5.2 关键交互

| 交互 | 说明 |
|---|---|
| **上下箭头** | 调整 `role_order` → 改变兜底顺序 |
| **云端行标注** | 单独底色 + 「云端」标签，出域策略为 `never` 时显示为**禁用态** |
| **添加模型** | 从已有 provider 中选（不重复创建），或新建 |
| **角色级开关** | 每个分区右上角可整体启停 |

### 5.3 后端 API 增补

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/llm-providers/roles` | 角色列表 + 各角色成员（按序） |
| `PUT` | `/llm-providers/roles/{role_key}` | 更新角色（含成员顺序、allow_cloud） |
| `GET` | `/llm-providers/cloud-policy` | 读全局出域策略 |
| `PUT` | `/llm-providers/cloud-policy` | 写出域策略 |

> **不破坏现有 API**：`GET /llm-providers` 保持原样（扁平列表），供调用日志页等复用。

## 六、实施顺序（分 3 批，每批可独立发布）

| 批次 | 内容 | 验收 | 风险 |
|---|---|---|---|
| **B1 出域管控**（最高优先） | 增 `is_cloud` 列 + 策略参数 + 链过滤 + 日志标记 | 设 `never` 后调本地失败**不出网**；日志可见 `is_cloud` | 低（纯新增） |
| **B2 角色落库** | 增 `role_scope`/`role_order` + `llm_role_config` 表 + `resolve_tier` 读 DB | 改 DB 即可调整档位，无需改代码 | 中（涉运行时选型） |
| **B3 界面分组** | `LlmProviders.vue` 改为角色分区 + 出域策略面板 | 管理员可在界面完成 B2 的配置 | 中（前端） |

**B1 必须最先做** —— 它是当前唯一**已经存在且正在静默生效**的风险。

## 七、风险与取舍

| # | 风险 | 缓解 |
|---|---|---|
| R1 | `auto` 策略下仍会静默出网 | 默认改为 `explicit_only`；`auto` 需管理员显式选择并在界面标红警示 |
| R2 | 出域策略改 `never` 后，若本地全挂则**无兜底** | 这是**预期行为**（数据边界优先于可用性）；界面需明示此代价 |
| R3 | 角色落库后 DB 与 `llm_tiers.py` 常量可能不一致 | 常量降级为「DB 无配置时的默认值」；界面展示实际生效值 |
| R4 | 一模型多角色的需求可能出现 | 当前实测不存在；若出现则迁移到关联表（已在 §3.1 说明） |

### 明确不做

- ❌ **不做用户级出域确认弹窗**（B1 只做策略与审计；确认交互归 B3 之后的迭代）
- ❌ **不做模型自动优选**（不根据实时成功率自动排序 —— 实测数据量不足，会引入抖动）
- ❌ **不做成本预测**（云端账单预测需要单价与历史，当前无）
