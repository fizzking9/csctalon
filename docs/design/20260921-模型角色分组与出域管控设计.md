# 模型角色分组与出域管控设计（2026-09-21）

> **性质**：需求（REQ）—— 待人工锁定后实施。
> **背景**：`docs/design/20260921-*.md` 讨论产出。
> **关联实测**：[talon 模型能力矩阵](../../../talon/docs/reports/模型能力矩阵与任务分流-20260920.md)

## 一、问题陈述

### 1.1 现状

| 问题 | 证据 |
|---|---|
| **P1. 业务代码硬编码模型名** | `ai_semantic_matcher` 曾写死 `talon-gmk-qwen2.5-7b`，实测该模型 5/5 全错，修它必须改业务代码 |
| **P2. 管理界面按扁平列表展示** | `LlmProviders.vue` 是一张扁平表格（按 priority 排序），**看不出「谁为哪个角色服务」** |
| **P3. 档位绑定在代码里** | 三档位（assistant/specialist/expert）的 primary/secondary 写在 `llm_tiers.py` 常量中，**管理员无法在界面调整** |
| **P4. 云端静默兜底，无出域管控** | `CLOUD_FALLBACK="deepseek-v4-flash"` 硬编码进所有档位链尾部；本地 transient 失败**自动出网**，且**无任何开关、提示或审计标记** |

### 1.2 P4 的危害（最重要）

用户明确的核心价值主张（talon 定位文档 §2）：

> 「**数据不出内网**将会是很多企业主的刚需。另外他们会对**不可预知的账单恐慌**。」

而当前实现：
- 本地模型超时（实测 27b 过去 30% 概率超时）→ **静默把客户工单数据发到 api.deepseek.com**
- 无开关、无日志标记、无用户确认

**这是「为可用性牺牲数据边界」，且违背定位。必须修。**

## 二、设计目标

| # | 目标 | 验收判据 |
|---|---|---|
| G1 | 模型**按角色分组**展示与配置 | 管理界面按「助理/专员/专家」分区，每区显示成员与其兜底顺序 |
| G2 | 每角色支持**多个模型兜底** | 有序列表，界面可上下调整顺序；运行时按序降级 |
| G3 | **出域策略参数化** | 管理员可在界面设置 `never / explicit_only / auto`；`never` 时云端从所有链中移除 |
| G4 | 出域**可审计** | 每次出网调用在 `llm_call_logs` 有明确标记（如 `is_cloud=true`） |
| G5 | 与 talon「能力级路由」(P1-1) 方向对齐 | 档位语义可映射为 `capability:xxx` |

## 三、数据模型

### 3.1 `llm_providers` 增列

| 列名 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `is_cloud` | bool | `false` | **是否出域**（云端/公网）。`true` 时受出域策略管控 |
| `role_scope` | varchar(32) | `NULL` | **显式归属角色**（`assistant`/`specialist`/`expert`/`NULL`=不限） |
| `role_order` | int | `100` | **角色内兜底顺序**（小=先尝试）。仅 `role_scope` 非空时有意义 |

> **设计取舍：为什么用 `role_scope` 而非新建 `llm_roles` 表？**
>
> 方案 A（新表 `llm_roles` + 关联表）：规范化，支持一模型多角色。
> 方案 B（**采用**）：`llm_providers` 加两列。
>
> **选 B 的理由**：实测模型能力差异明显且互斥（MoE 有数值缺陷、Dense 慢），
> **一个模型服务多个角色的场景在当前集群不存在**；且 provider 数量仅 5 个。
> 加表会引入 JOIN 复杂度而收益为零。**若将来出现多角色需求，再迁移到 A。**
>
> ---
>
> ### ⚠️ 2026-09-21 实测证伪（部署后立即发现）
>
> **上述「一模型一角色」的假设是错的。** 配置生产角色成员时立即暴露：
>
> `qwen3-coder:30b` 需要**同时**服务两个角色：
> - `assistant` 的首选（实测语义匹配 6/6 全对、快 3x）
> - `specialist` 的备选（27b 失败时的降级目标）
>
> 但 `role_scope` 是单值列，两次 UPDATE 后者覆盖前者 → 实测得到：
> ```
> assistant   talon-gmk-qwen2.5-7b          ← 降级为 7b（而它实测语义匹配 5/5 全错！）
> specialist  talon-gmk-qwen3-coder-30b     ← 错位
> ```
> **比源码常量更差** —— 等于把实测已知会错的模型放到了首选位。
>
> **结论：方案 B 不成立，需迁移到方案 A（关联表）。**
>
> **临时缓解**（已应用）：把 `coder-30b` 归入 `assistant`（它是 7b 的上位），
> `specialist` 只声明 27b 为首选，`coder-30b` 通过**常规链尾巴**仍可兜底
> （`get_provider_chain` 会把其余 provider 按 priority 追加）。行为与源码常量等价。
>
> **正式修复**（待办）：新增 `llm_role_members(role_key, provider_code, sort_order)`
> 关联表，`role_scope`/`role_order` 降级为兼容字段（保留一版本后删除）。

### 3.2 新增 `llm_role_config`（角色定义，单行一角色）

| 列名 | 类型 | 说明 |
|---|---|---|
| `role_key` | varchar(32) unique | `assistant` / `specialist` / `expert` |
| `display_name` | varchar(32) | 助理 / 专员 / 专家 |
| `description` | varchar(255) | 用途说明（含实测依据） |
| `enabled` | bool | 角色总开关 |
| `allow_cloud` | bool | **该角色是否允许出域**（细粒度控制） |
| `tier_order` | int | 全局档位顺序（供 UI 排序） |

> `llm_role_config` 仅 3 行，用于**界面文案与角色级开关**，避免把提示语写死在前端。

### 3.3 新增系统设置项（全局出域策略）

复用现有系统设置机制（`app/core/config.py` 的 settings + 可能需要 `system_settings` 表）：

| 键 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `LLM_CLOUD_POLICY` | `never` / `explicit_only` / `auto` | **`explicit_only`** | 全局出域策略 |
| `LLM_CLOUD_REQUIRE_CONFIRM` | bool | `true` | `explicit_only` 下是否需用户确认 |

**策略语义**：

| 取值 | 行为 | 适用 |
|---|---|---|
| `never` | 云端 provider **从所有链中移除**（等效禁用） | 数据绝对不出域 |
| `explicit_only` | 仅当**调用方显式指定**云端（或用户确认后）才用 | ✅ **默认**：兼顾体验与合规 |
| `auto` | 本地失败自动降级云端（**当前行为**） | ⚠️ 需管理员明确选择 |

## 四、运行时逻辑改造

### 4.1 `llm_tiers.resolve_tier()` 改为读 DB

```python
def resolve_tier(db: Session, role_key: str) -> list[str]:
    """按角色查 DB，返回按 role_order 排序的 provider_code 链。

    云端过滤由 LLM_CLOUD_POLICY 决定：
      never        → 排除所有 is_cloud=true
      explicit_only→ 排除（除非调用方传 include_cloud=True）
      auto         → 保留在链尾
    """
```

**保留** `llm_tiers.py` 的常量作为**兜底默认值**（DB 无配置时使用），避免首次部署即失效。

### 4.2 `get_provider_chain()` 增加出域过滤

```python
def get_provider_chain(db, provider_code=None, *, allow_cloud=None):
    """allow_cloud=None 时按全局策略决定；False 时强制排除云端。"""
```

### 4.3 `llm_call_logs` 增加出域标记

| 列名 | 类型 | 说明 |
|---|---|---|
| `is_cloud` | bool | 本次调用是否出域（便于事后审计"数据去过哪") |

### 5.2 关键交互

| 交互 | 说明 |
|---|---|
| **上下箭头** | 调整 `role_order` → 改变兜底顺序 |
| **云端行标注** | 单独底色 + 「云端」标签，出域策略为 `never` 时显示为**禁用态** |
| **添加模型** | 从已有 provider 中选（不重复创建），或新建 |
| **角色级开关** | 每个分区右上角可整体启停 |

### 5.3 后端 API 增补

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/llm-providers/roles` | 角色列表 + 各角色成员（按序） |

| 批次 | 内容 | 验收 | 风险 |

## 七、风险与取舍

| # | 风险 | 缓解 |
|---|---|---|
| R1 | `auto` 策略下仍会静默出网 | 默认改为 `explicit_only`；`auto` 需管理员显式选择并在界面标红警示 |
| R2 | 出域策略改 `never` 后，若本地全挂则**无兜底** | 这是**预期行为**（数据边界优先于可用性）；界面需明示此代价 |
| R3 | 角色落库后 DB 与 `llm_tiers.py` 常量可能不一致 | 常量降级为「DB 无配置时的默认值」；界面展示实际生效值 |
| R4 | 一模型多角色的需求可能出现 | 当前实测不存在；若出现则迁移到关联表（已在 §3.1 说明） |

### 明确不做

- ❌ **不做用户级出域确认弹窗**（B1 只做策略与审计；确认交互归 B3 之后的迭代）
- ❌ **不做模型自动优选**（不根据实时成功率自动排序 —— 实测数据量不足，会引入抖动）
- ❌ **不做成本预测**（云端账单预测需要单价与历史，当前无）

## 九、执行记录：talon 入口与调用方身份收敛（2026-09-21）

> 本节记录**已实际执行**的生产改动，与前面 draft-1 的设计草案分开，
> 避免把「已做」和「计划做」混在一起。

### 9.1 背景：三个此前未被发现的问题

| # | 问题 | 实测证据 |
|---|---|---|
| A | **有 1 个 provider 绕过 talon** | `talon-macmini-qwen2.5-7b` 的 `base_url` 直指 `http://10.147.17.20:11434/v1`（mac-mini 上的 Ollama）。实测调用前后 `audit_logs` max id 不变 → **无鉴权/无审计/无熔断/无降级** |
| B | **csctalon 复用 ADMIN key** | `TALON_API_KEY` = talon 的 `TALON_ADMIN_KEY`。审计里 csctalon 的推理与运维操作**混记为同一个 `ADMIN`**，无法按调用方拆分计量 |
| C | **talon 侧的调用方映射命名错误** | `TALON_TRUSTED_CALLER_NAMES=192.168.10.38=csctalon-admin` —— 但 `192.168.10.38` 实为**开发机**，其调用路径是 `/admin/nodes`(41次) + `/metrics/dashboard`(30次)，是**管理界面轮询**，不是 csctalon |

> ⚠️ 问题 C 是 talon 侧当天早些时候引入的：命名时把「常出现在审计里的 IP」误判为 csctalon。

### 9.2 ⚠️ 推翻一条此前的建议

**原建议**：「删掉 `talon-macmini-qwen2.5-7b` provider（无用配置）」。

**这是错的。** 该 provider 的 `note` 明确写着：

```
Mac mini M4 24G; 实测 prefill 117.7 / decode 23.2 t/s; L3 备用(给 gmk-evo 减负)
```

`priority=25` 且 `enabled=true` → **它在常规链里**，是有意的**节点亲和策略**
（把部分流量导向 mac-mini 以减轻 gmk-evo 负载），不是废弃配置。
删掉它会破坏这个意图。

**正确做法**：保留 provider，只把 `base_url` 改为经 talon（`4080`），
让「减负」意图由 **talon 侧的 `TALON_CLUSTER_NODES` 权重**体现。

> 实测确认这样可行：`qwen2.5:7b` 连发 6 次 → node-3060 × 5、**mac-mini × 1**
> —— mac-mini 仍分到流量，且现在全程纳入审计与熔断。

### 9.3 实际改动

| # | 动作 | 内容 |
|---|---|---|
| 1 | 签发 csctalon 专属 key | `POST /admin/keys {"name":"csctalon"}` → `SN-7B884E144377` |
| 2 | csctalon 改用专属 key | `/opt/csctalon/.env` 的 `TALON_API_KEY` 由 ADMIN key 改为专属 key（备份 `.env.bak-fix`），`docker compose up -d backend` |
| 3 | mac-mini provider 改经 talon | `base_url` → `http://192.168.10.21:4080/v1`，**同时补写加密后的 key**（原 `api_key_cipher` 为空，靠免密直连；4080 已要求鉴权）|
| 4 | 修正 talon 侧命名 | `192.168.10.38=dev-workstation`（原 `csctalon-admin`，命名错误）|

**改动方式说明**：第 3 步**通过 `update_provider()` service 层**执行，
而非直接 `UPDATE` SQL。原因：该函数会
① 用 `encrypt_secret()` 正确加密 key ② 调 `invalidate_cache()` 刷新 30s 进程缓存。
裸改 SQL 会漏掉这两步，导致「改了库但进程仍用旧缓存」的静默问题。

### 9.4 验证结果

```
【provider 统一】6 个 provider 中 5 个 talon 全部指向 http://192.168.10.21:4080/v1
【业务可用】    qwen3.8:27b / qwen3-coder:30b / qwen2.5:7b  →  全 200
【身份可辨识】  审计: SN-7B884E144377（csctalon） / ADMIN（运维）分列
【减负未丢失】  qwen2.5:7b 6 次 → node-3060×5、mac-mini×1
【回归】        talon 243 tests passed；ADMIN key 运维通道仍 200
```

### 9.5 仍未做（与本设计草案的关系）

- **入口数量仍是 1 个但经宿主 IP**：csctalon 走 `192.168.10.21:4080`（宿主 LAN IP）。
  从容器视角该地址会被 SNAT，但**因为现在带 key，鉴权与审计均正常**。
  是否改为经内部网络（`172.22.0.5:4080`）属可选项，当前无需动。
- **出域管控（P4）未受影响**：`llm_cloud_policy` 仍按 provider 判定，
  本次改动**未触及** `deepseek-v4-flash` 的 `is_cloud` 语义。
  但注意：**若将来把多个 provider 收敛为单个 `capability:*`，出域判定将失去依据**
  （见 draft-1 §4.2）—— 故本次**刻意不做**该收敛。
- **调用方名称映射只解决了「人读得懂」，未解决「计量可结算」**：
  `ZT-dev-workstation` 仍是免密（无 key），无法作为计费主体。
  若需结算级计量，须给每个免密调用方改签发 key（本次已对 csctalon 示范）。
