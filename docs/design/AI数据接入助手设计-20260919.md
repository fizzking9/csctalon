## 〇、一句话概括

**接入一个新数据源 = 上传样例 → AI 起草「接入声明」（字段语义/命名/分组/去重建议）→ 校验器对照既有规范拦截违规 → 人工确认 → 生成落地包走现有流程。AI 只当「建议者与初稿起草者」，全部产出是配置，不是代码，不是规则。**

## 一、背景与目标

### 1.1 现状痛点

| # | 痛点 | 表现 |
|---|---|---|
| 1 | 新数据源接入全靠人工 | 每个数据源要人写：字段语义映射（`FIELD_OVERRIDES`）、`name_cn` 命名（带域前缀）、分组归属、去重键、description；对照 3 份规范逐条自查 |
| 2 | 规范是"断言"但无工具辅助 | 命名/分组规范 §五 的断言（name_cn 唯一、前缀白名单、同表双注册禁止）只在 CI 测试里拦截，起草阶段没有辅助 |
| 3 | 字段语义是隐性知识 | 哪些列是金额（分）、哪些是时间（需时区）、哪些是 SN，靠人肉识别，新人容易把 dimension/category 标错 |
| 4 | 去重键是红线 | 去重键错 = 重复入库（规范 9 条），但建议去重键时无任何机制辅助 |

### 1.2 目标

1. 数据源接入从「人肉写配置」变为「AI 起草 + 人工确认」，起草质量对齐既有规范。
2. 校验器把规范断言变成**起草阶段的实时拦截**，违规在确认前暴露，而不是 CI 时才暴露。
3. 全流程留痕可审计，AI 建议可追溯、可回滚。
4. **框架面向所有未来数据源**，不绑定当前 24 个数据源 —— 数据源越多，收益越大。

### 1.3 非目标（取舍，评审重点）

- **不做**自动建表 / 自动改 `DATA_SOURCE_SEEDS` 代码 —— 落地仍走「建表迁移 + registry 种子 + CI 测试」现有流程，本设计只产出**落地包**（建议，非执行）。
- **不做**自动决定去重键 —— AI 只给建议，去重键按 [数据采集合并去重机制说明](../standards/数据采集合并去重机制说明.md) 由人工确认（红线）。
- **不做**口径分类自动固化 —— 投诉三源等口径兜底属 P3（运行期治理），不在 P1。
- **不做**页面改版自适应 / 登录容错 —— 那是 P4（多模态），不在 P1。
- **不做**AI 直接写库 —— 所有 AI 产出物先转声明式配置，人工确认后生效。

## 二、总体设计：三层 + 一闭环

```
┌─ L0 规则层（运行期 · 现有机制不动）──────────────────────┐
│  data_source_registry / 去重键 / FIELD_OVERRIDES / 缓存   │
└──────────────▲────────────────────────────────────────────┘
               │ 确认后走现有流程落地（人工 + CI）
┌─ 接入声明层（本设计新增 · 配置化）───────────────────────┐
│  data_source_specs 表：code/table_name/name_cn/分组/       │
│  时间字段/SN/去重建议/字段语义映射/校验报告/落地包          │
└──────────────▲────────────────────────────────────────────┘
               │ 草稿 + 校验报告
┌─ AI 起草层（本设计新增 · 异步 · 留痕）───────────────────┐
│  起草服务：样例 → 结构化 spec 草稿（含 confidence）         │
│  校验器：规范断言实时拦截（纯规则，无 AI）                  │
│  （复用 llm_providers + llm_scheduler + system_events）     │
└────────────────────────────────────────────────────────────┘
```

**关键原则：**
1. **AI 起草、规则校验、人工确认** —— AI 负责"从样例里读信息"，校验器负责"按规范拦截"，人负责"最终决定"。三者解耦，任一层出错可单独追责。
2. **校验器是纯规则、确定性** —— 与 LLM 无关，可单测 100% 覆盖，是防幻觉的闸门。
3. **产出物全是配置** —— spec 落库为声明式数据，不产生解析器/分类器代码。这是"机制而非硬编码"的落点。

## 三、数据模型

### 3.1 `data_source_specs` 表（新增）

```python
class DataSourceSpec(IDMixin, TimestampMixin, Base):
    """数据源接入声明（草稿态 + 已确认态），一行 = 一次接入意图"""

    __tablename__ = "data_source_specs"

    # ── 声明主体（对齐 DataSource 字段，确认后可直接映射）──
    code: str            # 建议 code（须全局唯一，不与现有 registry 撞）
    table_name: str      # 物理表名（须与 model.__tablename__ 一致，AI 建议 + 人工核）
    name_cn: str         # 中文名（须过前缀白名单 + 全树唯一 + 禁 code 原文）
    category: str        # 分组（须命中 CATEGORY_ORDER）
    sort_order: int
    time_field: str | None
    sn_field: str | None
    pk_field: str | None
    pk_strategy: str     # primary_key / none / upsert（去重策略，红线，人工必核）
    sync_source: str | None
    description: str | None

    # ── 流转状态 ──
    status: str          # draft / confirmed / applied / rejected
    issue_no: str | None # 落地工单号（确认后填写，按 issue-workflow）

    # ── AI 与校验产物 ──
    sample_summary: JSONB        # 样例摘要：列名/类型/行数/每列前 5 个样例值（脱敏）
    field_specs: JSONB           # 字段语义映射数组（含 per-field confidence）
    dedup_recommendation: JSONB  # 去重建议：strategy + 字段 + 依据（引用去重规范条款）
    validator_report: JSONB      # 校验报告：{pass: [], warn: [], fail: []}，warn/fail 必须人工处置
    apply_package: JSONB         # 确认后生成的落地包（见 §六）

    # ── 审计 ──
    created_by: int
    confirmed_by: int | None
    confirmed_at: datetime | None
    applied_at: datetime | None
```

### 3.2 `field_specs` 结构（JSONB 数组元素）

```json
{
  "field_name": "refund_amount",
  "name_cn": "退款金额",
  "data_type": "numeric",
  "semantic_role": "amount",
  "agg_func": "sum",
  "is_filterable": true,
  "is_pk": false,
  "enum_values": null,
  "time_zone_note": null,
  "confidence": 0.95,
  "evidence": "列名含 amount + 样例为两位小数正数 → amount(分)"
}
```

- `confidence < 0.7` 的字段强制人工核（校验器置 warn）。
- `time` 角色字段强制要求 `time_zone_note`（默认 `Asia/Shanghai`，对齐数据时间字段使用规范）。
- `amount` 角色字段默认单位"分"，`evidence` 需说明依据（样例/列名/已知口径）。

### 3.3 留痕

AI 每次起草/重试记 `system_events`（category=`ai_governance`，action=`onboarding_draft`，detail=输入样例摘要+输出 spec 摘要+provider），复用 [record_system_event](../../backend/app/services/system_event_service.py)（如文件名），不新建日志表。确认/拒绝/应用动作也记事件。

## 四、校验器（纯规则，防幻觉闸门）

### 4.1 校验规则表（v1，规则本身后续可配置化）

| # | 规则 | 级别 | 依据 |
|---|---|---|---|
| R1 | `code` 与现有 `DATA_SOURCE_SEEDS`/`PROJECTIONS` 不重复 | fail | 命名规范 §3.4 |
| R2 | `table_name` 与现有注册表不重复（禁止同表双注册） | fail | 命名规范 §3.4 / 去重规范 |
| R3 | `name_cn` 全树唯一（含投影） | fail | 命名规范 §3.4 |
| R4 | `name_cn` 前缀命中白名单（A~E/聚合/视图/投诉/工单/客服/SCRM/订单/售后/设备/旧） | fail | 命名规范 §3.2 |
| R5 | `name_cn` 不含 code 原文（refund/wallet 等） | fail | 命名规范 §3.2 |
| R6 | `category` 命中 `CATEGORY_ORDER` | fail | 命名规范 §二 |
| R7 | 停用/口径易误用 → `name_cn` 必须含 ⚠️/停用/对账基准 标注 | warn | 命名规范 §3.3 |
| R8 | `pk_strategy=upsert` 时必须给出 dedup 建议字段，且引用去重规范条款 | fail | 去重规范（红线） |
| R9 | `sn_field` 若存在，须能在 `devices` 关联口径下成立（提醒） | warn | 引擎 SN 关联 |
| R10 | `time_field` 必须带时区说明 | warn | 数据时间字段使用规范 |
| R11 | `field_specs` 每字段角色命中枚举（dimension/measure/amount/time/person/sn/category） | fail | 模型约束 |
| R12 | `confidence < 0.7` 的字段数 > 阈值 → warn（人工重点核） | warn | 防幻觉 |
| R13 | `amount` 角色字段必须标注"分"单位 | fail | AGENTS.md 金额单位铁律 |
| R14 | 字段名与现有任一数据源的字段语义角色冲突（同名不同角色）→ warn | warn | 语义一致性 |

- `fail` 未清零禁止确认；`warn` 需人工逐条备注处置理由后放行（记录进 `validator_report.warn_resolutions`）。

### 4.2 校验器实现要点

- 纯函数 + 现查 registry（`ensure_data_sources_registered` 已把种子落库，校验直接查 `data_sources`/`data_source_fields` 表）。
- 单测覆盖每一条规则的正反用例（对齐命名规范 §5.1 的既有测试风格）。
- 规则集先用代码实现（一个 `validate_spec(spec, registry_snapshot) -> Report`），框架承诺：**规则是声明式可扩展的**（每条规则 = 一个函数，注册进规则列表），新规则只加函数不碰流程。

## 五、AI 起草服务

### 5.1 输入

```
{
  "table_hint": "bms_order"（可选）,          # 用户已知的表名/来源
  "business_note": "BMS 支付管理订单台账"（可选）,
  "samples": [                                # 表头 + 若干行（≤50 行，脱敏后）
    {"order_no": "...", "device_sn": "...", "combo_name": "..."},
    ...
  ]
}
```

### 5.2 输出（强制结构化 JSON，schema 校验，非法输出整体重试一次）

```json
{
  "spec": {
    "code": "bms_order", "name_cn": "订单·支付台账", "category": "交易与售后",
    "sort_order": 10, "time_field": "create_date", "sn_field": "device_sn",
    "pk_field": "order_no", "pk_strategy": "primary_key",
    "sync_source": "bms", "description": "BMS 支付管理订单台账（...）"
  },
  "fields": [ { ...per-field 结构见 §3.2... } ],
  "dedup_recommendation": {
    "strategy": "primary_key",
    "fields": ["order_no"],
    "rationale": "订单号唯一，参照去重规范 §X 主键策略",
    "requires_human_confirm": true
  },
  "risks": ["create_date 可能非真实业务时间，需人工确认"],
  "unknown_fields": ["merchant_note"],
  "overall_confidence": 0.85
}
```

### 5.3 提示词要点（v1，存 DB 可迭代，复用 #153 反馈闭环思路）

- **角色**：你是数据源接入助手，把样例表结构翻译成符合项目规范的接入声明。规范原文注入（命名规范 §三、去重规范 §去重键、字段角色枚举）。
- **铁律**：
  1. 只做语义推断，不做业务断言（禁止编造"这是对账基准"类结论）。
  2. 金额列一律判 `amount`（分），拿不准时 `confidence < 0.7` 而非硬猜。
  3. `code` 用英文蛇形，`name_cn` 用中文业务词且必须带域前缀。
  4. 时间列判 `time` 并给出时区说明；SN 列判 `sn`。
  5. `dedup_recommendation` 必须给出依据并标注 `requires_human_confirm: true`（红线，AI 永不自决）。
  6. 不确定的列进 `unknown_fields`，不进 field_specs 硬猜。
- **输出**：只输出 JSON，禁止任何解释文本（便于 schema 解析）。
- **Provider/调度**：走默认实时链（27b），经 `llm_scheduler` L1 级别异步执行（admin 手动触发级，不占用户问答），超时 60s，失败重试 1 次后返回错误，不降级到 122b（122b 仅预生成）。

### 5.4 起草后处理

1. schema 校验（`spec`/`fields` 必填字段齐全，角色枚举合法）。
2. 落 `data_source_specs`（status=draft）存 `field_specs`/`dedup_recommendation`。
3. 跑校验器 §四 → `validator_report` 存入。
4. 记 `system_events`（含 provider、耗时、校验 fail 数）。
5. 返回草稿 id + 校验报告 → 前端/接口展示，进入人工确认。

## 六、落地包（apply 产物）

人工确认（`confirm`）后再跑一次校验（fail 必须清零），通过后生成 `apply_package`：

```json
{
  "migration": "新增表迁移建议：CREATE TABLE ...（列清单来自 field_specs，供 DBA 核）",
  "registry_seed": {
    "code": "bms_order",
    "model": "BmsOrder",            // 提示：需新增 ORM 模型
    "name_cn": "订单·支付台账",
    "time_field": "create_date",
    "sn_field": "device_sn",
    "pk_field": "order_no",
    "pk_strategy": "primary_key",
    "sync_source": "bms",
    "category": "交易与售后",
    "sort_order": 10,
    "description": "..."
  },
  "field_overrides": [              // 需人工 review 后进 FIELD_OVERRIDES
    {"field": "combo_price", "role": "amount", "agg": "sum", "name_cn": "套餐价格"}
  ],
  "cache_keys": ["数据源接入缓存铁律：写入入口须失效 pattern，key 逐字符对齐"],
  "test_tasks": [
    "backend/tests/test_data_source_naming.py 命名断言",
    "backend/tests/test_data_source_tree_api.py 树接口断言"
  ]
}
```

`apply` **不执行任何写库/写码**，只产出 JSON；人工按 issue-workflow 走「建表迁移 → registry 种子 → 测试 → 凭证关闭」。

## 七、接口契约

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/ai-onboarding/drafts` | 上传样例 → 异步起草（202 + draft_id），任务经 llm_scheduler |
| GET | `/api/v1/ai-onboarding/drafts/{id}` | 轮询草稿：status(drafting/ready/failed) + spec + 校验报告 |
| PUT | `/api/v1/ai-onboarding/drafts/{id}` | 人工编辑草稿字段（改后重跑校验，fail 清零才可确认） |
| POST | `/api/v1/ai-onboarding/drafts/{id}/confirm` | 确认（重跑校验 → confirmed，填 issue_no） |
| POST | `/api/v1/ai-onboarding/drafts/{id}/apply` | 生成落地包（不写库，输出 apply_package） |
| GET | `/api/v1/ai-onboarding/drafts` | 列表（status/issue_no 筛选） |
| GET | `/api/v1/ai-onboarding/registry-snapshot` | 校验器对照的 registry 快照（前端辅助展示冲突） |

响应格式遵循 [error-code.md](../standards/error-code.md)（`{code:0,data,message}`，错误走 HTTPException）。
权限：draft 仅创建者 + admin；confirm/apply 仅 admin。
前端：P1 先做 admin 管理页（列表 + 草稿详情 + 确认 + 落地包下载），走界面设计说明规范三层落地。

## 八、验收标准 / 关闭条件（供工单用）

1. `data_source_specs` 表迁移 + 模型落地，`data_sources` 不受影响。
2. 校验器覆盖 §四 全部 14 条规则，正反用例单测通过（`pytest backend/tests/test_onboarding_validator.py`）。
3. 起草服务：上传样例（mock LLM 固定响应）→ 生成结构化 spec 落库 → 校验报告生成 → status 流转正确。
4. 非法 LLM 输出（非 JSON/schema 不合法）被捕获并重试，失败可复现。
5. confirm/apply 全流程走通：确认后 apply_package 生成，且**未写任何库、未改任何代码**（测试断言）。
6. 全部 AI 动作在 `system_events` 留痕（category=ai_governance）。
7. 端到端（真实 LLM）：用一份模拟新数据源样例跑通「起草 → 校验 → 人工改 → 确认 → 落地包」。
8. 文档：本设计评审通过后按 docs/README §六 登记 + review-checklist 无 CRITICAL。

## 十、边界与风险

| 风险 | 缓解 |
|---|---|
| AI 幻觉（编造字段语义/口径结论） | confidence 机制 + R12 阈值 + 校验器 fail 拦截 + 只出配置不出代码 |
| 去重键红线被绕 | R8 fail + `requires_human_confirm: true` 恒真 + 人工确认必填 |
| 落地包被误执行 | apply 只产 JSON，写库/写码必经人工 + issue-workflow |
| LLM 成本/延迟 | 异步 llm_scheduler L1，27b 本地，失败不降级 122b |
| 校验规则漂移 | 规则 = 函数清单，新增规则只加函数；与命名规范测试共用断言 |
