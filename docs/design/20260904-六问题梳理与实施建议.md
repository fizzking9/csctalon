## 问题 1：首页「今日工作效率」同一人多次出现（如董梦玲）

### 现状
- 展示：`web/src/views/dashboards/Today.vue` 模块7（L459 标题"今日/本周工作效率值"，L465 `el-table :data="topStaffList"`）；姊妹页 `OperationDashboard.vue` 模块4（L115 附近"工作效率值排名"）同源。
- 数据源：`GET /analytics/today/staff`（`analytics.py` L251 `today_staff`，`aggregate_by` 默认 `person`）→ `A.today_staff_efficiency`（`backend/app/services/analytics.py` ~L4730）。
- 根因（已定位）：
  1. SQL 侧各 CTE（`cs_q`/`rf_q`/`cm_q`/`tk_all_q` 等）**按源表原始 operator/handler 字符串 `GROUP BY`**；
  2. `ops_union` 再与 `PersonAlias.alias` **等值 join**（`_operator_to_person_cte`，analytics.py L1476）；同一人若在 `cs_records.operator` / `refunds.operator` / `service_tickets.handler` 三套文本里写法不一致（带空格、前缀、工号、别名未登记），或 PersonAlias 对同一人有两条 alias → join 出多行 / `person_id=None` 兜底行；
  3. `_aggregate_records(recs, mode)` 在 `mode == "person"` 时**直接原样返回，不做按人合并**（analytics.py L5590-5592）；
  4. 前端 `topStaffList`（Today.vue L1210）只 filter+sort，**无二次按 name/person_id 归并**。

### 建议（用户已选：后端按 person_id 归并）
在 `today_staff_efficiency` 内、`out` 生成后（`_aggregate_records` 的 person 分支或其后）按归一化人键归并：
- 归并键：`person_id`（非空时）→ 兜底 `name`（归一化后，如去 `企微-` 前缀 / strip）；同一人合成一行。
- 需合成的字段：`SUM_KEYS`（reception_count/reception_device_count/refund_op_count/sp_*/pp_* 等）+ 6 桶 `breakdown{sessions,people,work_contrib,eff_contrib}` + `work_score/eff_score`（分数=加总后 round）。
- 人员属性（name/person_id/department/group/position/qw_user_id/current_specialty）：取非空优先；`person_id` 为 None 的多行若归一名相同也可合成（同名不同人风险小，可用 person_id 优先、别名库已兜底大部分）。
- ⚠️ 关联影响：`external.py` 的 `_reception_specialty()` 复用 `today_staff_efficiency(..., aggregate_by="person")` 并把 `person_rows` 以 `name` 为键取 `sp_*/pp_*`。若归并后人行仍以 `name` 为主键且保持 6 桶字段，则该处不受影响；需回归。
- ⚠️ 绩效口径：`work_score/eff_score` 的合成必须与 `specialty/group` 聚合分支一致（加总再 round），避免分数口径不一致。
- ⚠️ 有回归测试 `test_*`（含 staff/efficiency 相关），改后需跑 pytest + web build。

### 涉及文件
- `backend/app/services/analytics.py`（`today_staff_efficiency` 归并逻辑）
- `backend/app/api/v1/analytics.py`（无大改，仅确认 key/参数）
- 前端 Today.vue / OperationDashboard.vue（如归并后仍有空行/排序，微调，一般无需改）
- 回归：backend tests + web build

## 问题 2：投诉统计三源应为「当日登记 / 当日处理」双值 + 双柱 + 明细扩充

### 建议（用户已选：首页/运营看板 + 投诉分析两处都改；当日处理=finish 落当日）
1. **后端口径扩展（单一事实源，避免各处手写口径漂移）**：

   - `period` 语义："当日"即 `[当日00:00, 当前时刻]`（实时口径，历史日期=整天）。
2. **前端展示**：
   - 首页 Today.vue 投诉专项：三源 KPI 卡改为每源两值（`登记 X / 处理 Y`，小字）；分类柱状图可按"登记/处理"做并列双柱（或保留分类单柱+新增登记/处理迷你双柱）；明细表标题改为 `今日登记 X · 今日处理 Y · 明细共 Z`；明细可加"登记时间∈今日 / 完成时间∈今日"筛选。
   - 运营看板同款处理。
   - 投诉分析 ComplaintAnalysis：管理摘要 KPI 卡片在 total 下加"新登记/已处理"；`water` 已是双柱+净水位，可保留（其口径是窗口内登记 vs 窗口内登记且完成，与"当日处理=finish 落当日"不同——需要**注明两个口径**，或把 water 的 out 也补一个"窗口内完成"视图。用户 Q3 选 finish 落当日即算，故建议把 trend/water 的出水统一为"finish 落窗口"口径，同时说明净水位语义需改为"窗口内新增 − 窗口内办结(任意登记日)"）。
   - ⚠️ **口径冲突要澄清**：现有 `water.out`（出水）刻意限定"窗口内登记且完成"以自洽积压（净水位≈积压）。若按 Q3 改成"finish 落窗口即算"，出水将包含历史单今日办结 → `净水位 = 当日新增 − 当日办结` 不再等于积压增量，**需与用户明确是否保留 v2 自洽口径作为"水位"、另增"当日处理"口径作 KPI**。建议：water 图保留原 v2（新增/消化对称，净水位=积压），三源 KPI 卡与明细计数用 Q3 的"当日处理(finish落当日)"。两者并存、文案写清。
3. **明细扩充（问题 2 尾 + 问题 4）**：
   - `/complaints/detail` 扩展响应：返回 `{ registered_count, handled_count, items }`（registered=register∈窗口；handled=finish∈窗口且真实完成）或前端对 items 计算（量大不建议前端全量）。
   - 明细增加列/筛选：已可支持 按登记日、按完成日；`ComplaintAnalysis` 的外部/商户号明细表已显示 登记时间、处理/跟进、主体等列。

## 问题 5：外部 token 应关联用户？——评估

### 现状
- 表 `external_access_tokens`（已 LOCKED 架构 A-20260902-021 v1.0 + migration 落地）：字段 `name`(调用方标识) / `scopes` / `rate_limit_per_min` / `enabled` / `expires_at` / `last_used_at` / **`created_by`(String, 创建人账号)** / `revoked_by`(String) / 时间戳。**无 user_id/person 外键**。
- 管理接口 `/external/tokens` CRUD + 前端 `system/ExternalAccess.vue`（列表有"调用方/前缀/权限/限频/状态/过期/最后使用/创建人/操作"）。
- 使用方：workbuddy 等服务账号，**不是个人登录用户**。token 是"调用方"凭证，非"用户"凭证。

### 评估（用户问题：外部接入 token 似乎应该关联到用户）
分两层看：
1. **创建/责任人归属（推荐）**：当前 `created_by` 只存账号字符串。若需"谁能创建、责任到人"，可：
   - 轻量：把 `created_by` 归一为 username（已是），并在管理界面展示账号 → 人员 display_name（查询 User/Person）。无需改表。
   - 或新增 `owner_user_id`(FK users.id) nullable + `owner_person_id`(FK persons.id) nullable（可选，服务账号一般无 Person）。
   - 价值：审计、责任追溯、离职清理。
2. **把 token 绑定到"登录用户会话"（不推荐）**：外部只读 token 是**长期服务凭证**（机器拉取），与"用户在浏览器登录态的 JWT"是两套体系（架构明确隔离）。让 token 关联一个 User 去替代登录态，或让用户个人持 token 调接口，都会削弱 scope/吊销/限频设计、并造成"个人凭证可批量拉全量经营数据"的越权面。不建议把外部 token 当用户凭据。

### 建议
- 保持 token=调用方凭证模型不变；若要"责任到人"，做**轻量归属增强**：管理界面创建/列表关联展示创建人（username→display_name）、按创建人筛选，并可登记"责任人/用途备注"（如加 `owner_note` 或沿用 name）。
- 若要更严谨，加 `owner_user_id` FK（可空），吊销/审计时追到人。
- 不改 scope/鉴权/隔离设计（LOCKED 架构）。

## 问题 6：本地 27B 模型做日报/只读接口分析助手？——评估

### 现状
- 本项目**无任何 LLM 集成**（前后端均无 chat/LLM 调用）。
- workbuddy 目前在外部：拉取只读数据 → 在其内部做大模型分析排版（用户展示的退款/投诉日报即其输出）。
- 本系统已具备 **`/api/v1/external/brief?period=daily|weekly|monthly`**（LOCKED A-20260902-021 实现）：返回 `reception.by_specialty`（专项名单+会话/设备）、`complaint.total/by_source`（**registered/handled/backlog × 三源**）、`refund.total_amount/count/routes/actual_cashflow_e/a_route.litigation`、`_spec` 口径说明。这正是"分析助手"最需要的数据底座，且**与内部权限隔离、token 限频、纯只读**。

### 本地 27B 模型方案评估（仅评估，未动代码）
**A. 部署形态**
- 27B 模型（如 Qwen2.5-27B/DeepSeek 蒸馏 27B 等）量化后（INT4/INT8）约需 **16~24GB 显存**；FP16 全精度需 ~54GB+。需评估部署机显存：
  - 若宿主机有 ≥24GB 显存（如 RTX 4090/3090×1 或 A10/A100 20~24G）：INT4/INT8 量化可跑，速度约 10~20 tok/s，**足够"日报分析/摘要"这类非实时任务**。
  - 若仅 CPU：27B 太慢（不可用），建议改用 7B~14B 或直接接云端 API。
- 推理服务：推荐 **Ollama / vLLM** 提供 `OpenAI 兼容 /v1/chat/completions`；本项目后端用 httpx 调用即可，不引入重框架。
- 部署位置：与 csctalon 同机 or 内网独立机。若放公网须内网/网关代理（本仓库已有 FRP/OpenResty 经验可参考）。

**B. 数据接入（关键设计）**
- 建议**不让模型直接连数据库/调内部 API**，而是：
  1. 后端提供"分析素材聚合接口"（如复用 external brief 或新增 internal `/reports/analysis-feed`，按当前用户角色鉴权），把选定日期/范围的结构化指标（today KPI、refund 四路、complaint 三源登记/处理/积压、reception 专项、环比）一次性拉成 JSON。
  2. 后端按**固定 Prompt 模板**（附 `_spec` 口径 + 用户问句）发给本地模型，流式返回。
  3. 前端以**右侧抽屉/右上角工具按钮**（MainLayout `header-right .quick-tools` 现成图标位，或页面级浮动按钮）唤出对话，逐条提问"今日退款怎么样/投诉积压/接待专项"。
- 安全：模型只拿到"聚合脱敏指标"，不接触 PII/明细；接口走后端鉴权（不能用 external token 给内部 UI 用）；限制并发/长度、输出仅作参考。
- 后续扩展：新增一个只读/内部维度 = 加一个 feed 段 + prompt 提示，无需改模型。

**C. 关于"界面询问分析输出"**
- 用户期望：右/右上角"辅助助手"，可问"昨日退款分析"并得类似 workbuddy 的结构化输出。技术上：选 `brief`/feed 拉当日/昨日数据 → 本地模型按模板生成 Markdown（emoji 分节、环比、要点）→ 前端渲染（可用简单 markdown 渲染或分段输出）。
- 成本评估：27B 本地推理 单次日报 2~5 千 token 输出，约几十秒；适合"点按钮生成"，不适合"逐字流式长聊"。备选小模型（7B~14B）可更快，若主要做固定日报模板，甚至可"模板+规则"离线拼装（不一定要 LLM）。
- 结论倾向：**架构上可行且与现有 external/brief 契合**；落地建议分两期：一期"固定结构日报/周报生成器"（用模板+规则，可选小模型润色）；二期"自由问答助手"（27B，需确认推理硬件）。是否上 27B 取决于宿主机显存与推理时延容忍度。
