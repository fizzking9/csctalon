### ⭐ 设备流量关键发现（HTTP JSON API，非页面导出）
考察时捕获到设备流量页的后端 API 契约，**已用真实设备验证非空**：

```
GET https://wifi.cloud-cat.cn/bms-portal/deviceFlow/sn/pageList?page=1&rows=20&sn=<SN>&timeType=2&flowDate=
→ 200 {"code":"0","msg":"操作成功","data":{"total":N,"totalFlow":X.X,"items":[{...}]}}
```

- `timeType`：1=按日 / 2=按月（实测 `timeType=2` 走通）。
- **`flowDate` 留空 = 返回该 SN 所有有流量月份**（每行一月，倒序，可多月）；`flowDate=YYYY-MM` 只查指定月。
- item 字段（实测非空样本 `68772550194237`）：`sn` / `businessId`(商户ID) / `businessName`(商户名) / `flowDate`("2026-08") / `flowValue`(GB) / `deviceTypeName` / `deviceGroupName` / `deviceComboName`(当前套餐)。
- **实测样本**：SN `68772550194237` → 3 行（2026-08:7.57GB 不完整月 / 07:14.82 / 06:141.15），totalFlow=163.55；SN `69212627276896` → 仅 2026-08:19.9GB。
- **设备流量"导出"按钮点击后 45s 无标准 download 事件** → 该页不走浏览器下载，**必须用 HTTP API 采集**（比 Playwright 点导出稳定）。
- 优点：无需 Playwright 点导出下载，纯 HTTP + 登录态 cookie 即可稳定分页拉取 → 与 `ai_acc_fetcher`（`fetch_mode="http"`）同一套路。

## 二、业务归类与对账闭环（核心洞察）

结合既有"商户号现金流视图修正方案（v4）"五大路线口径（A 线上直退 / B 钱包取现 / C 闪猫 / D 手动退款 / E 商户号现金流=对账基准），5 项新数据可归为 **2 大能力 + 3 个业务角色**：

### 能力 A：退款/订单对账数据扩充（#1 退款记录报表 为主，#2 订单 / #3 退货 辅助）

| 新数据 | 对应现有路线 | 对账价值 |
|---|---|---|
| **退款记录报表** | **≈ E 路**（商户号真实退款水单，refund_status=退款成功/退款中 等全状态） | 现 E 路 `merchant_refunds` 是 Excel 手工导入快照（截至 7/20，且 wx_refund_no 损坏、无精确退款时间）；退款记录报表提供**线上实时水单**：精确退款时间 + 商户号 + 设备号 + 平台订单号 → 可对 E 路"补全 + 更新 + 精确对账" |
| 退款记录报表 | **D 路**（manual_refunds 手动退款） | D 路登记台账 `order_no/device_sn/refund_amount/op_time`；退款记录报表含同维度 + 精确退款时间 → 可**把 D 路缺漏的实际退款时间回填**（用户点名"手动登记的退款还可以把时间匹配回填"） |
| 退款记录报表 | A/B/C 路 | 平台订单号/微信订单号可反向匹配 refunds(退费单号RF) / wallet / shanmao 的单据，形成"经营登记 vs 商户实扣"逐笔勾稽 |
| **订单管理** | 辅助（订单级水位） | 含 订单状态/支付状态/退款状态/激活时间/商户Id → 补全设备-商户-订单上下文，佐证 A 路退费单来源订单 |
| **退货跟踪** | 独立售后域（非现金流） | 设备退货/换货全流程（含"已激活退货/未签收"状态），SN 维度，补设备生命周期 |

### 能力 B：设备审计数据（#4 设备流量 + #5 设备管理）

| 新数据 | 现状 | 规划用途 |
|---|---|---|
| **设备流量（按月）** | `device_combos`(设备套餐) 仅存"当前快照可用/已用/剩余"；**无按月流量历史表** | 新增**独立的"设备月流量使用表"**，用于设备审计：单 SN 按月汇聚（每月一行/或逐日明细），"当月未完整时需重取更新" → 天然支持"审计时点拉取 + 后续回刷" |
| **设备管理** | `devices.sn` 主表已有，但 active_time/merchant_name/device_type/status 等信息不全（多为采集时 `_sync_devices` 建的空壳） | 用**激活时间窗口**全量导出 → 回填 `devices` 主表（active_time/设备类型/商户/状态/ICCID 等）→ 让设备档案完整 |

### 结论：不是 5 个孤立抓取，而是"一个对账体系（A-E 勾稽）+ 一个设备审计体系"的数据底座扩充

## 三、采集方式分类（哪些进采集计划、哪些是接口调用）

按用户提示"有些需纳入统一数据采集计划、有些用于接口调用"，结合架构约束与页面/API 特性：

| 新源 | 建议采集方式 | 理由 | 是否纳入定时 default_sync |
|---|---|---|---|
| #1 退款记录报表 | **Playwright 导出**（复用 BmsFetcher，wifi 域共享登录态） | 与现有 refund/wallet 完全同构；先按需手动跑通，验证后评估纳入日更 | ❌ 先手动（D3），验证后评估 default_sync |
| #2 订单管理 | **Playwright 导出**（同构） | 订单量较大，但与 ticket/refund 同套路 | ❌ 先手动（D3），验证后评估 |
| #3 退货跟踪 | **Playwright 导出**（同构） | 售后域，变动频率低于订单 | ❌ 先手动（D3），验证后评估 |
| #4 设备流量 | ⭐ **HTTP JSON API**（`fetch_mode="http"`，仿 ai_acc_fetcher 登录态复用） | 页面本身走 JSON API；**单 SN × 按月** 查询天然适合"按需/审计触发"，不适合整表定时全量 | ❌ 否 → **做成"设备审计工具"的按需接口调用**（手动/自动触发单 SN 汇聚入库） |
| #5 设备管理 | **Playwright 导出**（同构，激活时间窗） | 设备主数据，低频变动 | ❌ 默认否，定期/手动全量刷新（设备档案） |

### 关于"同一个 URL 账号密码不需频繁配置"
**确认：无需重复配置。** 5 个页面与 refund/ticket/wallet 同属 `wifi.cloud-cat.cn` 域 → 新源 `base_url="https://wifi.cloud-cat.cn/bms"` 会在 `source_group_service` 自动归入 **`bms-wifi` 组**，共享组级凭证（当前本地 `.env` 已配 `BMS_USERNAME=YKM-TZK`，运行时写入 sync_source_configs 组凭证），**单源无需再填账号密码**。已在本地 .env 检测到凭证，可复用登录态直接测试抓取。

#### 数据源分组凭证机制（现状 + D6 增强，2026-09-05 核实源码）
- **归组按域名/登录态，不按 data_type**：`_group_key_for_base_url` 把 wifi/support.cloud-cat.cn 同归 `bms-wifi`（同一浏览器登录 cookie，共享账号）。同一 data_type 全局唯一，不会跨组。
- **自动归组**：`ensure_source_groups_registered` 启动时为 group_key 为空的源自动归组；手动改过的不覆盖。
- **凭证解析**：`resolve_credentials` = 单源凭证 > 组凭证 > None → 新增源默认自动继承组凭证（=默认复用），单源填了凭证则覆盖（=显式不同）。
- **前端现状**：SyncSettings.vue 组卡片"统一配置凭证"（改组级）+ 单源独立编辑。
- **D6 增强（待实现，纳入 P5）**：
  1. 新建/编辑同步源弹窗：若该源已归组且有组凭证 → 明确提示"已归组 {组名}，将复用组凭证，可留空不填"。
  2. 单源填写账号密码时：追加选项"同时设为组凭证（作用于同组所有源）/ 仅本源"，避免误以为需逐源配置，也支持"把某源凭证一键提升为组凭证"。
  3. 组内源"复制到同组"批量操作当前不建议单独做（默认复用已覆盖主诉求），如确有需要二期加。

## 五、对账回填机制设计（#1 的核心增值）

用户原话拆解：
> "退款记录报表 = 商户号现金流筛选退款部分，这些退款与其他 ABCD 路一一对应……增加数据采集补充对账；ABCD 是运营明细记账，E 路是对账水单；D 路手动登记退款还可把时间匹配回填；商户号 ID + 设备编号 ID 都有，对账回填很有用"

### 5.1 E 路水单升级路径（推荐增量，非推翻）
现状 E=merchant_refunds（Excel 快照 7/20 截止，wx_refund_no 损坏）。退款记录报表能持续补充"线上实时退款水单"，建议：
- **新增 `refund_record_reports` 作为"线上退款水单明细"**，与 merchant_refunds 并存；两者按 (商户号, 退款时间, 金额, 平台订单号) 归并标识同一笔。
- 对账算法以 `refund_record_reports`（含精确时间）为"准水单"，反向把 merchant_refunds 缺失/损坏的字段（如 merchant_refund_no、精确 refund_time）按可信键**更新补全**（A-20260902-010 已留 merchant_refund_no 作对接键）。
- 对账口径扩展：现有 `(A+B+C+D) − E`，可加"水单级逐笔勾稽"视图：每笔退款记录报表行 → 尝试匹配 A/B/C/D 路单据 → 标记 matched/未登记；未登记 = 商户实扣但经营未记账（对账差异下钻）。

### 5.2 D 路时间回填（用户点名）
manual_refunds 的 `op_time`（实际退款时间）在人工台账里常缺失/不准。用退款记录报表（含设备号+商户号+金额+精确时间）做**可信匹配**：
- 匹配键：`(device_sn 或 order_no, refund_amount, 时间窗口)` → 命中则将 `refund_record_reports.refund_time` 回填到 `manual_refunds.op_time`（带 `quality_status=auto_filled` + 溯源 id）。
- 需质量护栏：仅回填当前为空/明显倒挂的 op_time；金额±容忍；唯一命中才回填，多候选挂 pending 人工。

### 5.3 商户号维度对账
退款记录报表含商户号+商户名 → 可映射到 `merchants.merchant_id`（现有 merchants 表有 merchant_id 字段，device/refund 侧用文本名未打通）→ 为"按商户对账"（现有 `/analytics/cash/merchant`）补全真实商户号关联。

## 六、设备流量审计工具设计（#4）

用户原话：
> "一次只能一个 sn；默认按月；页面选按日/按月 + 填 SN 查询 → 获取流量使用列表；用来设备审计时手动/自动点击查询该设备月流量汇聚，记录到单独流量使用表；当月未完整时后续需更新（9/5 查到 9 月 9G，10 月可能更新）"

### 6.1 接口调用形态（非定时全量）
- 新增后端模块 `device_flow_sync`：持有 BMS 登录态（复用 `bms-wifi` 组凭证登录拿 cookie），封装调用 `/bms-portal/deviceFlow/sn/pageList?sn=&flowDate=YYYY-MM&timeType=2`。
- 每次拉取 = 单 SN × 指定月 → 逐日明细 upsert `device_flow_daily` + 月汇总 upsert `device_flow_usage`（幂等，重复取=更新）。
- 触发方式：
  1. **手动**：设备审计页面（单 SN + 选月）→ 点击查询 → 拉取并入库 → 展示本地历史；
  2. **自动(可选)**：对"本月完整但上游有更新迹象"的设备，按周期重取最近 N 月回刷（补偿"当月未完整时统计会变"）。

### 6.2 与现有 RechargeTraffic 的关系
现 `/recharges/traffic/upstream` 为占位空实现（注释"需提供真实 BMS 接口后填充"）→ 本次正好把它接上（或新增独立端点），避免重复。
