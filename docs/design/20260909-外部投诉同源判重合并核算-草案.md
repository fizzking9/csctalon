## 1. 业务诉求（用户原话要点）

> 1. 外部投诉**实际都能匹配上 SN**。
> 2. 同一投诉可能被**登记多次**（客户通过多种渠道投诉，到达我方时间不同 → 多处登记）。
> 3. 这类多渠道投诉，**除渠道不同外，内容/手机号/姓名/描述基本一致，相差日期也不久**。
> 4. 外部投诉**一般及时处理**；但登记内容及时、工单可能不及时（已处理但工单没更新）。
> 5. 通过 API 获取的统计数量与状态**没及时更新**统计口径。

## 2. 现状数据验证（本地真实主批次 id<300000，已剔除疑似脏副本）

| 现象 | 数据 | 结论 |
|---|---|---|
| 315 登记有 SN | 2624 行中 1487 个 SN | "能匹配 SN"基本成立 |
| 匹配到工单 | 仅 897 行 / 824 工单 | **约 2/3 的 315 登记没有落工单** |
| 有 SN 但无工单 | 737 行 | 工单侧统计看不见 |
| 同手机号跨 ≥2 渠道 | 62 人 / 148 行 | 存在同源多渠道登记，量级约百行 |
| 同 SN 多行（同内容成对） | 大量 | 部分是真同源，部分是历史脏副本(乱年份) |
| handle_time 早于登记日 | 228/494 (46%) | handle_time 是"动作时间"，**非最终处理日** |
| result 空但有处理痕迹 | 31+18 条 | 已处理但 result 未标办结 → 统计漏 |
| 近30天 registered/handled | 217 登记 / 171 办结 / 12 非办结 | 当前 handled 口径基本贴近 |

**核心矛盾**：当前 `dedup_hash = md5(日期|手机|SN|问题签名)` 粒度太细（全表唯一），只防"完全相同的行重复推送"，**防不住"同一投诉多渠道、措辞略变、日期略差"的重复登记**。而现有 registered/handled/backlog 都按"行"算，不做同源合并 → 同源 N 行会被算成 N 个登记、N 个积压。

**渠道簇（2026-09-09 用户补充）**：市监局可能通过多个渠道主体/不同监管所登记（航城监所/宝安/南沙/天河市监局…），判重时**同一市监局的不同监所应视为同一渠道簇**（即同簇不算"跨渠道"，簇内重复反而是同源证据）。建议渠道簇映射：`{航城监所,宝安市监局,南沙市监局,天河市监局,...} → 市监局簇`; `{全国12315平台,全国消协智慧315平台,全国消协315} → 12315/消协簇`; 公共服务平台/消委会 各自成簇。

**判重关键结论(第一轮)**:
1. **手机号是最强关联键**（同一人多次投诉几乎都同手机号）。
2. **内容相似度是区分"同源跟进"与"新投诉"的核心** —— 同源内容围绕同一诉求（涨价的"假信息/虚标/答非所问"），不同源则诉求/时间明显不同。
3. **SN 不可靠**：同源行 SN 可能不同（`186****7267` 两设备），脏副本 SN 重复但内容不同。
4. **渠道**是辅助维度：同源常横跨 12315+航城监所；但同渠道(12315 内)也能同源（多次跟进）。
5. **时间窗**重要：同源登记集中在几天~两周内；间隔数月多为新投诉。

### 3.2 客服姓名括弧标注(N)信号 (2026-09-09 补充)

**现象**：客服登记时在 complainant 姓名后加括弧数字，如 `王杰（2）`、`胡康玲（3）`。真实批次 143 行(涉及 104 手机号, 142 行有手机号, 139 行有 SN)。

**语义澄清(关键, 防误用)**：实测 (N) 是「同投诉人(同手机号)第 N 次投诉/来电」的**总序号**, 而非"同一投诉第几次登记"——
```
胡阳(187****6503) 9行 跨 2025-03 ~ 2026-07, 多SN(6803********05/6877********71/6749********43),
多事件(预存/烁盟旗舰/虚假宣传/天猫/流量虚标), 标 2/3/4/5/6/8  → 同人多次投诉≠同源合并
```
→ **不能简单把 (N) 当"同源重复登记"直接合并**, 否则会把同一人一年内多起不同事件误并成 1 个案件。

**真正对口的同源(可合并)**：同 SN + 同关联工单 + 相邻几天 + 跨渠道，如
```
胡康玲(186****8556, SN58482343088704, 同工单GD845132894099030016):
  胡康玲 8-19航城 → (2) 8-20消协 → (3) 8-20全国12315   全部撤销结案 → 同源真重复
赵梓颐(198****8553, SN68772604272834, 同工单GD846178622409883648):
  8-23 12315 → (2) 8-26 航城 → (3) 8-28 航城           全部撤销结案 → 同源真重复
王杰(182****3354) 9-1 航城 同工单两行(有SN/无SN配对) → 同日重复登记
```

**补充的显式"重复投诉"强信号**（真实批次）：
- `result='重复投诉'`：**28 行**（上游直接定性, 最强信号）
- problem/明细 含 `重复投诉|再次投诉|重新投诉|重复`：**143 行**（较强）
- 注意："再次来电/市民再次来电补充" 多为**同一事件处理过程追加**(公共服务平台风格), 非新投诉也非重复 → 需与"再次投诉"区分

**纯内容相似度召回率实测仅 37%**(38/102 客服标注同源对) → **判重主信号不能靠内容字符相似**,
应为: 同手机号(142/143覆盖) + 归一化姓名 + 同SN + 同关联工单 + result=重复投诉 + 内容含重复词,
内容相似仅作辅助加分。

## 4. 目标口径（合并后核算）

> 对 external_complaints（**不含 card_complaints**，卡商群单列，统计时单独成桶）做一层"同源案件"归并，在归并后的案件级核算。

- **案件 = 一组同源投诉行**（同一消费者、同一核心诉求、时间相近、渠道可不同）。
- **案件登记日 = 组内最早 complaint_date**（多渠道到达，以首次为准）。
- **案件处理状态 = 组内"最新有效状态"**：任一/最新渠道行已办结（result∈办结类 且 无更新的未办结行）→ 案件已处理；否则未处理。
- **registered（新增案件）** = 窗口内**新增同源案件**数（组内最早登记日∈窗口）。
- **handled（处理案件）** = 窗口内**案件完成**数（以组内办结行为准）。
- **backlog / 积压 = 未闭环案件**数（组内无办结），而非行数。
- **效果**：同一投诉多渠道不再算 N 个积压；"已处理但 result 滞后某一行"只要同源另一行办结即可判定已处理。

## 5. 判重规则（✅ 已定稿 FINAL v5, 2026-09-09 用户全部拍板）

> 经 v1(同手机号+内容相似) → v2(+客服标注/重复词/同工单) → v3(同SN主键) → v4
> (+内嵌前文降人工) → v5(**去掉无SN退化**)。详见 `docs/reports/20260909-同源判重原型验证.md`。

### 5.1 最终判定规则
```
同源(重复登记/可同时关闭) ⇔ 同 device_sn(设备) AND 内容相似≥0.7 AND 日期差≤30天
                          AND NOT (任一行为"公共服务平台再次来电/投诉N次"内嵌前文 → 人工)
⚠️ 无SN行一律不参与自动判重(缺设备主键, 无法区分同源/重复登记)
```
- **渠道不同** = "重复投诉"特征（12315↔市监局 等），须叠加 同SN+内容+时间；单凭不够
- **手机号/姓名仅参考**（张帆↔刘佳奇 同SN同内容 sim1.00 但姓名不同 = 同源 ✅用户确认）
- **不同 SN 即便同人 = 不同投诉**（胡阳例 不合并）
- **同 SN 但不同诉求/跨久 = 不同投诉**（徐良例：1940 后台账单 vs 1992 iccid；梁先生例：流量扣费清单 vs 设备红灯全额退 均不合并）
- **⚠️ 公共服务平台"再次来电/再次来电补充/投诉N次"会把前次原文内嵌在 problem**
  （`<br/>` 分隔或整段复制，508 行中 65 行含 `<br/>`）→ 相似度被历史原文虚高 → 降 NEED_REVIEW 人工

### 5.2 重复导入脏数据（与同源判重分开，质量治理范畴）
- 用户发现"无SN内容不同却合并很多" → 根因：**同手机号 + problem 逐字相同 = 重复导入**
  （dedup_hash 因日期缺失/批次差异未拦住 → 物理重复行），全库真实批次 **48 组 / 97 行**，无SN 13 组
- 例："退款不及时和退费金额少"×3、"流量虚标"×2、"余额丢失"×2；含 SN 损坏(尾数截断/填0) case
- 处理：单独质量治理（保留最优行、其余标 dup_residual），**不归入同源判重**
  → `data/外部投诉重复导入治理清单_20260909.xlsx`（脚本 `complaint_dup_import_check.py`）
