## 一、背景与目标

### 1.1 观测数据（生产，2026-09-18 ~ 09-24）

| 指标 | 实测 |
|---|---|
| 预生成报告 | 7 天 **512 份**（≈73/天；客服时段 8:00~24:00 为 490 份，≈4.4 份/小时） |
| 用户实际拿到命中 | **90 次**（`is_public=FALSE AND hit_mode IN ('full','section')`） |
| 有命中的报告数 | 71 份（`matched_count>0`，含修复 L2 记账前口径）→ **约 88% 的报告从未被读到** |
| 单次 LLM 耗时 | 29 ~ 47.5s（本地 27b / APU，与实时问答、治理扫描共用同一队列） |
| 30 分钟窗口**零新增**占比 | 退费单 **39.2%**（144/367 桶）、投诉登记 **38.7%**（142/367 桶） |

> ⚠️ 口径修正（#193 审计，2026-09-24）：原先用"正文文本是否变化"判断刷新价值，
> 但正文是"窗口截止到 now"的**累计值**，数据毫无新增也会因窗口变长而变（实测相邻快照
> 原文完全相同占比 **0.0%**）→ 该指标无效，已换用**源表 30 分钟桶零新增占比**。

### 1.2 目标

1. **不牺牲有效新鲜度**：凡"自上次快照以来有新的退款/投诉/接待事件"的窗口，必须照常刷新。
2. **砍掉无效算力**：约四成"零新增"窗口不再重算同一批数字。
3. **一切可观测、可回滚**：跳过必须留痕、可统计；开关可关；先影子模式验证再执行。

### 1.3 非目标（明确不做）

- 不改 `refresh_on_sync` 的语义与触发点（同步完成即评估，仍由 #129/#130 决定候选）。
- 不动 `llm_scheduler` 优先级门闸（#127）。
- 不改报告内容口径与提示词（#189/#192 已闭合）。
- 不做"按命中量动态提升频率"（无证据表明热点模板需要更频繁刷新）。

## 二、现状机制（实施前必须理解的三层）

```
BMS 高频同步(8:00~24:00, 每 30min) / 投诉推送(约 20min)
        └─ 完成回调 → ai_report_worker.warm_on_sync_complete()
               ├─ 候选 = ai_report_templates WHERE is_active AND refresh_on_sync=TRUE  (当前 3 个: #1/#7/#8)
               ├─ 节流 = _window_generated_recently(template_id, period, snapshot_date, 20min)
               └─ generate_for_template(level=0)   → build_messages → llm_scheduler.acquire(L0)
```

- 当前"是否刷新"只看**时间**（同步来了一轮 + 距上次 ≥20min），不看**数据是否真的变了**。
- 报告窗口是"当日 00:00 ~ now"，因此零新增时重算得到的业务数值与上一份**完全一致**，
  只有窗口末尾时刻不同。

## 三、方案总览

在 `warm_on_sync_complete` 的候选循环里，插入**一步"新鲜度判定"**，三档模式控制行为：

| 模式 | 行为 | 用途 |
|---|---|---|
| `off` | 不判定，维持现状 | 回滚位 |
| `dry_run` | 判定但**照常生成**，把"本可跳过"写事件留痕 | 影子期验证（默认初始值） |
| `enforce` | 判定为"无新事件"则**跳过**（不调 LLM），写事件留痕 | 正式生效 |

判定输入 = `(模板 scope, 上次生成时刻)`；输出 = `has_new_events: bool` + 证据明细。

```
候选模板
  ├─ 20min 窗口节流已挡住？ → 跳过(现状不变)
  ├─ 当日尚无该模板快照？     → **必生成**(保底, 不受本机制约束)
  ├─ 距上次快照 > MAX_STALE_MINUTES(默认 120)？ → **必生成**(保窗口时刻不大幅落后)
  └─ 新鲜度判定:
        has_new_events=True  → 生成(现状行为)
        has_new_events=False → dry_run: 生成+留痕 / enforce: 跳过+留痕
```

## 四、详细设计

### 4.1 新鲜度判定（"上次生成以来是否有新事件"）

**判据**：在 `(last_gen_at, now]` 区间内，按模板 `scope` 对应的**业务时间列**统计新增行数，
全部为 0 → 无新事件。

| 模板 scope | 事件源（业务时间列） | 说明 |
|---|---|---|
| `overview`（#1 经营总览） | 退费单 + 钱包提现 + 投诉工单登记 + 接待记录 | 任一 >0 即算有新事件 |
| `refund`（#7 退款简报） | `refunds.created_at` / `wallet_withdrawals.op_time` / `shanmao_refunds.refund_time` / `manual_refunds.register_time` | 四路任一 |
| `complaint`（#8 投诉简报） | `service_tickets.register_time`（投诉登记）+ 315/卡商补充表 | 登记口径即可 |

SQL 骨架（参数化，禁拼接）：

```sql
SELECT count(*) FROM refunds WHERE created_at > :last_gen AND created_at <= now();
```

判定结果连同证据一起留痕：`{"template": "...", "scope": "...", "window": [last_gen, now],
"counts": {"refunds": 0, "wallet": 0, "tickets": 3, "cs_records": 41}, "has_new": true}`。

### 4.2 保底与例外（防"该刷不刷"）

| 场景 | 行为 | 理由 |
|---|---|---|
| 当日该模板无任何快照（首次 / 跨日） | **必生成** | 否则"我的待办/AI 报告历史"里当天没有底稿，#135/#151 命中链无候选 |
| 距上次快照 > `MAX_STALE_MINUTES` | **必生成** | 报告首行"统计窗口 …至 now"不能长期停在数小时前（可核对性） |
| admin 手动触发（`level=1`） | **必生成** | 人在盯，跳过会显得"点了没反应" |
| 判定查询异常（表/字段/DB 报错） | **必生成**（fail-open） | 宁可多算一次，也不能因监控故障停掉刷新 |
| 上一份快照生成失败（无 report_id） | **必生成** | 不能把失败当"刚生成过" |

### 4.3 开关与参数

**v1 用全局 settings（不加列、不加迁移）**：

| 参数 | 默认 | 说明 |
|---|---|---|
| `AI_PREGEN_SKIP_MODE` | `dry_run` | `off` / `dry_run` / `enforce` |
| `AI_PREGEN_MAX_STALE_MINUTES` | `120` | 保底重算上限 |
| `AI_PREGEN_FRESHNESS_ENABLED_SCOPES` | `refund,complaint,overview` | 灰度：先只对部分 scope 生效 |

**取舍（为什么不加 `ai_report_templates` 列）**：加列要走 Alembic 迁移 + 前端表单 + 校验，
而本策略初版是**全局策略**（3 个日报模板同一处理），无逐模板差异需求；全局开关已足够灰度与回滚。
待出现"某模板需单独放宽"的真实诉求，再加列（届时按 `alembic-migration管理规范.md` 走迁移）。

### 4.4 记账与可观测

**（a）跳过留痕**：写 `system_events`（`category="ai"`, `action="pregen_skipped"`,
`status="info"`, `level="info"`），`detail` 带 4.1 的证据 JSON。
> 取舍：不新建表（避免迁移），`system_events` 已有分页/按 category+action 查询能力；
> 预估新增量 ≈ 3 模板 × 每天十几轮 × 40% ≈ 20 条/天，与现有 `bms_sync` 事件量级同阶。
> 若 07 天后观测到噪音，再改计数器表（届时另开单）。

**（b）管理端可观测（条件 4）**：`web/src/views/system/AiTemplates.vue` 增加 4 列
（数据取自 `admin_ai.py` 模板列表接口新增字段，纯只读聚合）：

| 列 | 口径 |
|---|---|
| 最近生成时间 | `max(ai_reports.created_at)`（template_id + is_public） |
| 近 7 天命中次数 | `count(*) ai_reports(is_public=FALSE, hit_mode IN ('full','section'))` 中命中到该模板快照的次数 |
| 近 7 天跳过次数 | `system_events(action='pregen_skipped', detail->>'template'=code)` |
| 最近判定 | 最近一次 `has_new` 与 counts（来自同一事件 detail） |

> **界面五要素（按 `界面设计说明规范.md`，实施时必须三层落地）**
> 1. **目的**：替**运营/管理员**回答"这份报告为什么此刻是这版内容、值不值得继续按这个频率刷"
>    —— 支撑"调参/关停某模板刷新"的决定。
> 2. **逻辑**：4 列按"时间（最近生成）→ 价值（命中次数）→ 成本（跳过次数）→ 证据（最近判定）"
>    排列，一眼看出"刷了没人看 / 该刷被跳过"两类异常。
> 3. **口径**：命中次数以 `hit_mode` 为准（#193 审计修正，含 L2）；跳过次数来自
>    `system_events.pregen_skipped`；"最近判定"是采集水位证据，不是业务结论。
> 4. **取舍**：**不做**独立的"刷新成本看板"（与 AI 模板页重复展示，违反"同一指标唯一真身"）；
>    **不做**逐模板频率编辑器（v1 全局开关，避免过早暴露调参面）。
> 5. **工单**：**#193**；设计文档即本文。
> 三层落地：页面文件头 `设计说明（Design Rationale）` 注释块 + 页面可见 ⓘ（含取舍段）+
> `review-checklist.md` 对应项。

### 4.5 与既有机制的边界

- 与 #166 的"快照窗口节流"**叠加不冲突**：节流是"时间下限"，本机制是"数据下限"，
  两者都是"跳过"，但留痕与判定依据不同（`pregen_skipped` 需带 `reason` 区分
  `no_new_events` / `throttled_20min`）。
- 与 #181 专项分桶**无冲突**：判定按 `scope` 选事件源，分桶只影响 feed 切片。
- **不改变**命中链（#135/#151/#192）：跳过后快照仍是"当日最新可得"，命中链路照常。

## 五、前置核实项（编码前必须先确认，避免猜字段）

| # | 待核实 | 为什么 |
|---|---|---|
| 1 | 各事件源的**业务时间列**与统计口径是否一致：`refunds`（口径"按创建时间"）= `created_at` 还是 `created_at_raw`？`cs_records` = `operation_time` / `consult_time`？ | 判定必须与统计口径同源，否则"有新事件"与"报告数字变了"不一致 |
| 2 | 上述时间列的**索引**：实测仅 `service_tickets.register_time`、`refunds.created_at_raw` 有索引；`refunds.created_at` 等无索引 | 判定每 30 分钟 × 3 模板执行，无索引会全表扫（`refunds` ≈ 18.8 万行） |
| 3 | 315/卡商补充表（外部投诉）的业务时间列与去重键 | `complaint` scope 的完整事件源，参照 `docs/standards/数据采集合并去重机制说明.md` |
| 4 | 判定查询耗时实测（<200ms 目标），必要时改为"宽表/缓存水位" | 不能把省下的 LLM 时间换成 DB 压力 |

> 若索引不足：优先用**已有索引的列**（如 `refunds.created_at_raw`，需与口径核对）；
> 仍不足则加索引（走 Alembic 迁移，评估写入放大）。

## 六、验收标准（与工单 #193 一致）

1. **影子期（dry_run，≥3 天）**：`pregen_skipped` 事件的 `has_new=false` 占比落在
   30% ~ 50%（与源表 30 分钟空桶率 38.7%~39.2% 同阶）；同窗口**未发生**"应刷而跳过"
   （抽检：被标记可跳过的窗口，其源表计数确实全为 0，SQL 可复现）。
2. **执行期（enforce）**：单日 `pregen_success` 次数较基线（≈73 份/天）下降且
   `hit_mode` 命中次数**不下降**（下降需给出解释）；保底规则生效（当日首份、>120min、
   手动触发均有生成记录）。
3. **可观测**：管理端 4 列可见且与 SQL 对账一致（贴查询结果）；
   `pregen_skipped` 可按模板/日期统计。
4. **测试**：新增单测覆盖 ①有/无新事件两分支 ②五种保底场景 ③判定异常 fail-open
   ④dry_run 不改变生成行为；`ruff` + `pytest` 全绿。
5. **可回滚**：`AI_PREGEN_SKIP_MODE=off` 后行为与改造前一致（贴一次开关切换前后对比）。
6. **10-01 定参**：以 09-24~10-01 观测表为输入，确定 `AI_PREGEN_SKIP_MODE` 终值与
   `MAX_STALE_MINUTES`，并把取舍写回工单。

## 七、风险与回滚

| 风险 | 处置 |
|---|---|
| 判定口径与统计口径不一致 → 该刷刷不了 | 影子期比对"判定 has_new=false"与"相邻快照业务数值是否真的相同"，不一致即修口径（不执行 enforce） |
| 长期零新增导致窗口时刻落后 | `MAX_STALE_MINUTES=120` 保底；报告首行窗口说明照实展示 |
| 事件表过大导致判定慢 | 前置核实项 4；必要时加索引或缓存水位 |
| 留痕噪音 | 7 天后评估；必要时改计数器表（另开单） |

**回滚**：`AI_PREGEN_SKIP_MODE=off`（无需回滚代码）；留痕与列展示可保留（只读、无副作用）。
