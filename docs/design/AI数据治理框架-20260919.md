## 〇、一句话概括

**数据治理不应每次都走「人发现坏数据 → 写脚本 → 人工判断 → 改数据」的开发流程。**
本框架让系统自己完成这条链路：**确定性探测器算出可疑证据 → AI 研判哪些是真问题、给治理建议 → 按风险分级执行（只读/可逆自动，不可逆必须人工确认）**。

## 一、背景与目标

### 1.1 现状痛点（真实案例：C-P1-7）

`wallet_withdrawals` 的 device_sn 为 NULL 的行因 PostgreSQL「唯一约束对 NULL 不去重」，
被高频同步反复插入，**累积 40603 行重复**（全表虚胖 2.4 倍），而无人察觉。

发现它靠的是：人工读索引定义 → 手写 SQL 扫描 → 人工判断。**成本高、不可持续**：

| 环节 | 现状 | 问题 |
|---|---|---|
| 发现 | 靠人偶然看到 / 审计登记 | 漏检是常态 |
| 诊断 | 人写一次性 SQL 脚本 | 每次都要开发；脚本用完即弃 |
| 判断 | 人凭经验区分「真问题 vs 业务允许」 | **易误判**（本次 5 个候选中 4 个是误报，把「业务允许多个 NULL」当成重复） |
| 处置 | 人写清理脚本 + 人工确认 | 无回滚凭证、无留痕 |

### 1.2 目标

1. **发现自动化**：结构性可疑由确定性扫描器周期性算出，不依赖人偶然发现。
2. **判断 AI 化**：区分「真问题 / 业务允许」需要理解业务语义（如「实时问答的 task_id 本就为空」），
   这是 AI 擅长的，且**只需一次判断即可沉淀为规则**。
3. **执行分级化**：只读与可逆动作自动执行；不可逆动作（删/改数据）**必须人工确认**（红线）。
4. **产出配置化**：AI 判断结论沉淀为**治理规则**（DB 表），下次同类问题直接命中，不必重复问 AI。
5. **全链路留痕**：每次探测/建议/执行都记 `system_events`，可审计、可回滚。

### 1.3 非目标（取舍，评审重点）

- **不做**「AI 自动改数据」—— 不可逆动作永远需要人工确认（与 AI 数据接入助手同一红线）。
- **不做**全库全表无差别扫描 —— 只扫「有明确判据的结构性风险」，避免噪声淹没真问题。
- **不做**实时逐行校验 —— 探测器是周期性批量扫描（每日），不是写入路径上的钩子
  （写入路径的性能敏感，且已有 `quality_check` L2 校验）。
- **不做**新的解析器/清洗器代码 —— 治理结论落 DB 规则，执行复用现有处置动作。

## 二、总体设计：三层 + 一闭环

```
┌─ 探测层（确定性，无 AI）─────────────────────────────────────────┐
│  数据体检扫描器：算「结构性可疑」，**不下结论**                     │
│  · 唯一约束/索引重复（复现索引真实表达式，含部分条件/函数/COALESCE） │
│  · 表级：行数突变 / 外键孤儿 / 宽表关联覆盖率下降                    │
│  产出 findings[]：{表, 列/索引, 判据, 命中行数, 样本行, 复现 SQL}    │
└────────────────────▲────────────────────────────────────────────────┘
                     │ findings（结构化证据，不含「这是不是问题」的结论）
┌─ 研判层（AI，只出建议）──────────────────────────────────────────┐
│  AI 治理分析师：读 findings + 业务上下文（规范文档/表说明/口径）     │
│  → 区分「真问题 vs 业务允许」                                       │
│  → 产出建议：{severity, 判据引用, 建议动作, 影响面, 风险, confidence}│
│  复用：llm_scheduler L1（默认实时链 27b）+ 提示词配置化落 DB        │
└────────────────────▲────────────────────────────────────────────────┘
                     │ 建议（带 confidence + requires_human_confirm）
┌─ 执行层（分级，红线人工确认）────────────────────────────────────┐
│  · L0 只读：生成报告（永不改数据）                                  │
│  · L1 可逆：标 quality_status（如 ignored/dup_residual，可 restore）│
│  · L2 不可逆：删/改数据 → **必须人工确认**（红线）                   │
│  留痕：system_events(category=ai_governance) + 回滚凭证             │
└──────────────────────────────────────────────────────────────────────┘
```

**关键原则：**

1. **探测层确定性、无 AI** —— 算证据不下结论。避免「AI 算错数」这类不可控错误。
2. **AI 只出建议，永不自决** —— 每条建议带 `requires_human_confirm`（L2 恒为 true）。
3. **判断沉淀为规则** —— AI 结论 → `governance_rules` 表 → 下次同类问题规则直接命中，省 LLM 调用。
   这是「框架而非硬编码」的落点：**规则是数据，不是代码**。
4. **执行分级** —— 与现有 `quality_status` 机制天然契合（可逆标记已有 ignore/restore）。

## 三、数据模型

### 3.1 `governance_findings` 表（新增）—— 探测结果

```python
class GovernanceFinding(IDMixin, TimestampMixin, Base):
    """一次探测发现的结构性可疑（证据，不含结论）"""

    __tablename__ = "governance_findings"

    detector: str        # 探测器标识: unique_index_dup / row_count_jump / fk_orphan ...
    table_name: str      # 目标表
    target: str          # 目标列/索引名（如 uq_wallet_withdrawals_business）
    severity_raw: str    # 探测器给的原始严重度: info/warn/high（仅参考）
    metrics: JSONB       # 量化证据: {dup_groups, redundant_rows, total_rows, ratio, ...}
    samples: JSONB       # 样本行（脱敏，≤10 条，供 AI 研判）
    repro_sql: str       # 复现 SQL（可审计、可人工复核）
    detected_at: datetime
    status: str          # open / judged / resolved / ignored / auto_closed(重扫不再命中, 自动收敛)
    # ── AI 研判产物（研判后回填）──
    verdict: str | None          # real_issue / allowed_by_business / uncertain
    verdict_reason: str | None   # AI 判据（引用规范条款）
    suggestion: JSONB | None     # {action, params, impact, risk, requires_human_confirm}
    confidence: float | None
    judged_at: datetime | None
    rule_id: int | None          # 命中的治理规则（若规则直接判定，跳过 AI）
```

### 3.2 `governance_rules` 表（新增）—— 沉淀的判断规则

```python
class GovernanceRule(IDMixin, TimestampMixin, Base):
    """治理规则：把 AI 的判断结论沉淀为可复用规则（下次直接命中，省 LLM）"""

    __tablename__ = "governance_rules"

    detector: str        # 适用探测器
    table_name: str      # 适用表（支持通配如 "*"）
    target_pattern: str  # 目标匹配（正则/精确）
    match_metrics: JSONB # 额外匹配条件（如 ratio > 0.5）
    verdict: str         # real_issue / allowed_by_business
    reason: str          # 判据说明（人读 + 引用规范）
    disposition: str     # 建议动作: report_only / mark_ignored / delete_dups / ...
    disposition_params: JSONB
    auto_level: str      # L0_readonly / L1_reversible / L2_irreversible
    hit_count: int       # 命中计数（学习信号）
    last_hit_at: datetime | None
    source_finding_id: int | None   # 来自哪次 AI 研判（可追溯）
    created_by: str | None
    enabled: bool
```

> **与现有 `quality_disposition_rules` 的关系**：后者是**行级**处置规则（针对具体行标质量状态），
> 本表是**结构性**治理规则（针对表/索引级问题）。二者互补，执行动作复用后者的处置能力。

### 3.3 留痕

- 每次探测：`system_events(category=ai_governance, action=governance_scan)`
- 每次 AI 研判：`... action=governance_judge`（含 provider/耗时/token）
- 每次执行：`... action=governance_execute`（含动作/影响行数/是否人工确认）

## 四、探测层（确定性，v1 范围）

### 4.1 v1 探测器清单（第一期）

| # | 探测器 | 判据 | 产出证据 |
|---|---|---|---|
| D1 | **唯一索引重复** | 复现索引**真实表达式**（含 `WHERE` 部分条件、函数、`COALESCE`）后 `GROUP BY ... HAVING count(*)>1` | 重复组数、冗余行数、占总行数比、样本行、复现 SQL |
| D2 | **表级行数突变** | 与上期（同比窗口）对比，行数增幅/跳水超阈值 | 本期/上期行数、增幅、按日曲线 |
| D3 | **外键孤儿 / 约束未生效** | 引用列非空但主表无对应主键；或 FK `NOT VALID`（约束不拦新增） | 孤儿行数、涉及引用列、样本、`fk_validated` |

> **D1 的关键教训（#161 实证）**：`pg_indexes.indexdef` 里的表达式**必须原样复现**
> ——本次人工扫描时忽略了 `date(register_time)` 截断与 `COALESCE`，导致 `manual_refunds`
> 的 3062 行「重复」是误报。D1 必须解析索引定义生成等价 SQL，而非用 `indkey` 裸列名。
>
> **D1 的第二个关键教训（2026-09-20 全库排查实证）**：**「有重复组」≠「有保护缺口」**，
> 且「含 NULL」的组**还要再分两种**（此处曾判错，务必看清）：
> - PG 普通唯一索引用 `=` 比较 → 含 NULL 的行**永不冲突**（NULL≠NULL）；
>   而 `GROUP BY` 把 NULL 归为同一组 → 报出的正是**索引拦不住**的那些行
> - **整组所有列都 NULL**（`ai_reports.task_id` 176 行全 NULL、`dashboards.code` 2 行全 NULL）
>   → **设计如此**（该行在索引语义下无信息）→ 报告但**排除**
> - **部分列有值、仅某列 NULL**（`wallet_withdrawals`：仅 `device_sn` NULL，其余 5 列有值）
>   → ⚠️ **真缺口**（非 NULL 列足以判定「同一笔」，索引却拦不住）—— 这正是 C-P1-7 本质
> - 生产实测：59 个唯一索引（含可空列 19 个），报出 4 处重复经甄别**全为「整组全 NULL」**
>   → 排除；wallet 治理后归零 → **生产无缺口**
>
> **D1 实现（工单 #162 已落地）**：权威实现在 `app/services/governance_detector.py`
> （`scan_unique_index_dups` 纯探测 / `run_d1_scan` 探测+落 `governance_findings`）：
> 取 `pg_get_indexdef` 括号内原文作 GROUP BY 列、带 `WHERE indpred`、标注 NND/部分索引、
> 排除整组全 NULL 后报缺口；每条 finding 产出 `metrics` + **脱敏** `samples` + `repro_sql` 三件套。
> `scripts/governance_scan_unique_dup.py` 已改为**薄封装**（只调服务，不再自含判据 —— 两套逻辑必然漂移）。
> 单测 `backend/tests/test_governance_detector.py` 覆盖：表达式部分索引不误报（#161 回归）、
> NULL 列重复能检出（#160 回归）、整组全 NULL 排除、落库幂等。
> ⚠️ 判据首版曾把「组内全为 NULL」一律当豁免 → 会在未治理环境把 wallet 真重复静默跳过；
> 已修正并用本地库（未治理）反证：修正后本地库精确报出 wallet 为唯一缺口、生产库归零。

**D2/D3 实现要点（工单 #163）**

- **D2 时间列权威来源 = `data_sources.time_field`**（数据源注册表已声明，避免另建一份
  「哪张表用哪个时间列」的映射；缺失时回退该表第一个 timestamp 列）。
  口径：本期 = 最近 N 天（默认 7，含今天）、上期 = 其前的 N 天，按 `AT TIME ZONE 'Asia/Shanghai'`
  取日；`growth_ratio = cur/prev`。
  **增长（≥1.5）与跳水（≤0.5）都报** —— 只盯增长会漏掉「整批数据丢失」（D-P1-2 审计缺口）。
  产出 `metrics.curve` 按日曲线，便于下钻「到底哪一天突变」。

- **D3 的真正靶子是 `NOT VALID` 外键，不只是孤儿**（2026-09-20 生产实证）：
  PG **强制**校验已生效的 FK，`convalidated=true` 的约束上孤儿**恒为 0**
  （`DEFERRABLE` 也只把校验延到 commit，仍会拦）。生产 100 个 FK 全是 validated
  → 若只查孤儿，本探测器永远报 0（有检测等于没检测）。
  真正的风险是 `NOT VALID`（建约束时不校验存量数据，典型于给脏数据补约束）：
  约束**看似存在、实际不拦新增**、存量孤儿也留着 —— 与 D1 的「保护缺口」同一类。
  故判据为：**有孤儿 → 报**；**无孤儿但 NOT VALID → 也报**（`gap_kind=unvalidated_constraint`），
  `metrics.fk_validated` 一并留证。
  用 `NOT EXISTS` 而非 `LEFT JOIN`：避开「多列 FK + NULL 参与」的等值 NULL 比较坑。

### 4.2 第二期探测器（本期不做）

- 字段级：NULL 率异常 / 数值越界 / 时间倒挂（完成早于创建）/ 枚举值漂移
- 关联级：宽表关联覆盖率下降
- 采集语义：CSV 换行截断、明显错误日期、语义字段补全（见 §七）

## 五、研判层（AI 治理分析师）

### 5.1 输入

`findings[]`（批量，避免逐条调 LLM）+ 业务上下文：
- 表说明（`data_sources.description`）
- 相关规范原文（去重规范 / 时间规范 / 命名规范，按 finding 类型注入）
- 已知规则（`governance_rules` 命中则**短路，不调 LLM**）

### 5.2 输出（强制结构化 JSON，schema 校验，非法整体重试 1 次）

```json
{
  "verdict": "real_issue | allowed_by_business | uncertain",
  "reason": "判据（须引用规范条款或表说明）",
  "suggestion": {
    "action": "report_only | mark_ignored | delete_dups | fix_time | ...",
    "params": {},
    "impact": "影响面（涉及多少行/哪些统计）",
    "risk": "low | medium | high",
    "requires_human_confirm": true
  },
  "confidence": 0.0
}
```

### 5.3 提示词要点（v1，存 DB 可迭代）

- **角色**：你是数据治理分析师，判断「结构性可疑」中哪些是真问题。
- **铁律**：
  1. **区分「业务允许」与「数据错误」**：可空列上多个 NULL 通常是业务允许（如实时问答无 task_id），
     不要把「多个 NULL」当重复。
  2. **不可逆动作必须 `requires_human_confirm: true`**（删/改数据是红线）。
  3. 判据必须引用规范条款或表说明，**禁止编造业务结论**。
  4. 拿不准给 `uncertain` + 低 confidence，**不要硬判**。
- **调度**：复用 `llm_scheduler` L1（默认实时链 27b），超时 60s，失败重试 1 次。

### 5.4 规则沉淀（省 LLM 的关键）

AI 研判结论经**人工确认后**写入 `governance_rules`；下次同 `(detector, table, target_pattern)`
直接命中规则 → **跳过 AI 调用**，直接给建议。规则命中计数用于识别「高频问题」。

## 六、执行层（分级 + 红线）

| 级别 | 动作 | 是否自动 | 依据 |
|---|---|---|---|
| **L0 只读** | 生成治理报告、落 `system_events`、管理页展示 | ✅ 自动 | 无副作用 |
| **L1 可逆** | 标 `quality_status`（`ignored`/`dup_residual`），可用现有 `quality_restore` 回滚 | ✅ 自动（规则命中时） | 可逆，且不影响经营口径 |
| **L2 不可逆** | 删行 / 改值 / 建索引 / 改表结构 | ❌ **必须人工确认** | 红线：不可回滚或影响统计 |

**L2 执行前置**：
1. 人工在管理页确认（或接口显式确认）
2. **强制备份**（复用 #160 的备份模式：备份表 + pg_dump）
3. 执行后写凭证（影响行数、前后对比 SQL）
4. 重建受影响的物化表 + 失效缓存（数据源接入与缓存加速规范）

## 七、采集语义增强（同一框架，第二期）

> 用户明确要求纳入：**「导入的 CSV 出现的换行问题、截断问题，AI 表现会更好；
> 对于手动录入文件的采集，通过语义分析可以完善更多信息；对于明显错误的时间日期也能很好地解析」**

这三类与「治理已有数据」共享**同一套机制**（探测 → AI → 分级执行），只是探测器与动作不同：

| 场景 | 探测 | AI 研判/建议 | 执行级别 |
|---|---|---|---|
| CSV 换行截断 | 检测单元格内含 `\n`、字段长度贴近列宽上限、行内列数异常 | 判断是否应合并/恢复（如备注被换行截断） | L1 可逆（标待核）→ 人工确认修正 |
| 明显错误日期 | 检测不可能日期（如 `2026-13-45`、年份 1900/2099、未来日期） | 结合上下文推断正确值（如 `2026/9/19` → `2026-09-19`） | L2 人工确认 |
| 语义补全 | 检测可推断字段为空（如已知 SN 可补设备型号） | 给出补全建议 + 依据 | L1 可逆（标记）→ 人工确认 |

**取舍**：第二期做，因第一期需先跑通框架主链路（探测→AI→执行→留痕），
且语义增强的判据更依赖业务上下文（需更多规范注入），单独设计更稳妥。

## 八、接口契约

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/governance/scans` | 手动触发一次体检（202 + scan_id，异步经 llm_scheduler L1） |
| GET | `/api/v1/governance/scans/{id}` | 轮询扫描状态 + 本批 findings 概要 |
| GET | `/api/v1/governance/findings` | 体检发现列表（detector/table/status/severity 筛选 + 分页） |
| GET | `/api/v1/governance/findings/{id}` | 单条详情（证据 + AI 研判 + 建议 + 复现 SQL） |
| POST | `/api/v1/governance/findings/{id}/confirm` | 人工确认 AI 建议（L2 必须；确认后可执行） |
| POST | `/api/v1/governance/findings/{id}/execute` | 执行建议动作（按级别校验：L2 未确认则 400） |
| POST | `/api/v1/governance/findings/{id}/dismiss` | 判定「业务允许」并**沉淀为规则**（下次直接命中） |
| GET/POST/PATCH | `/api/v1/governance/rules` | 治理规则 CRUD（人工可增删改，AI 沉淀的也在其中） |
| POST | `/api/v1/governance/judge` | 手动触发一次研判（202 + judge_id，异步经 L1；★#165 补，设计原表只列体检入口，但 finding 无研判入口会只增不减） |
| GET | `/api/v1/governance/judges/{id}` | 轮询研判状态（占位事件 running→终态） |
| GET | `/api/v1/governance/summary` | 治理概览（open findings / 按 detector 分布 / 近期执行） |

响应遵循 [error-code.md](../standards/error-code.md)；权限：查看 = admin，执行 = admin（confirm 同）。

**前端**：admin 管理页（体检入口 + findings 列表 + 详情确认 + 规则管理），走界面设计说明规范三层落地。

## 九、调度（定时 + 手动）

- **定时**：每日凌晨（避开同步高峰，参考 `bms_scheduler` 空闲期机制）自动体检一次；
  与 `cache_warmer` 空闲期机制一致，不占同步窗口。
- **定时·研判**（工单 #167 补）：体检后自动研判一次（同日语义，低峰 0-5 点）。
  原因：体检会持续把同一复发问题报成新的 `open` finding，若研判只能人工触发则 `open` 只增不减；
  规则命中时研判是**零 LLM 成本**的（先跑规则短路），故低峰自动跑一次是安全的兜底。
- **重扫收敛**（工单 #167 补）：体检落库后，把「本次未再命中」的 `open`/`judged` finding
  置 `auto_closed`（只限本次**跑通**的探测器，防探测失败误关历史 finding）。
  `auto_closed ≠ resolved`：前者只表示「不再命中」，**未执行任何治理动作**。
- **手动**：管理页按钮触发（202 + 轮询，同 AI 数据接入助手模式）。
- **同步后触发**：**不做**（每次同步都扫会浪费；且数据问题不要求分钟级发现）。

## 十、验收标准 / 关闭条件（供工单用）

1. `governance_findings` / `governance_rules` 表迁移 + 模型落地，现有表不受影响。
2. D1（唯一索引重复）探测器：**复现索引真实表达式**（含部分条件/函数/COALESCE），
   对 `manual_refunds` 不误报（#161 误报场景回归）、对 `wallet_withdrawals` 能检出（#160 场景回归）。
3. D2/D3 探测器：行数突变、外键孤儿各含正反用例。
4. AI 研判：mock LLM 下产出结构化建议；非法输出重试 1 次；规则命中时**跳过 LLM**（断言未调用）。
5. 分级执行：L0/L1 自动；**L2 未人工确认时执行接口返回 400**（测试断言）。
6. 全链路留痕：`system_events(category=ai_governance)` 含探测/研判/执行三类动作。
7. 规则沉淀：`dismiss` 后写入 `governance_rules`，下次同 finding 命中规则不调 LLM。
8. 端到端（真实 LLM）：对一份含真实问题的数据跑通「探测 → AI 研判 → 人工确认 → 执行 → 留痕」。
9. 界面设计说明三层落地 + review-checklist 无 CRITICAL。

## 十二、边界与风险

| 风险 | 缓解 |
|---|---|
| 探测器误报（把业务允许当问题） | ①D1 复现索引真实表达式（#161 教训）；②AI 研判区分「业务允许」；③规则沉淀后不再重复误报 |
| AI 误判导致误删数据 | **L2 恒需人工确认**（红线）；执行前强制备份；执行后写凭证 |
| 扫描拖垮 DB | 只扫「有明确判据」的目标；批量 SQL 而非逐行；凌晨低峰执行；单表 LIMIT |
| 规则漂移（规则与业务脱节） | 规则命中计数 + 定期 review；规则可人工禁用/修改 |
| 与现有质量处置重复 | 明确分工：`quality_disposition_rules` 管**行级**，`governance_rules` 管**结构性**；执行动作复用不重写 |
| LLM 成本 | 规则命中短路（省调用）；批量研判（一次多 findings）；仅 L1 级别（不占用户问答） |
