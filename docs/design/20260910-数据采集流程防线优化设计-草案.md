# 数据采集流程防线优化设计（草案）

> 版本: v0.1（草稿，未锁定）· 2026-09-10
> 触发：用户指出「数据本身不重要，处理流程更重要，要能规避后续出错的可能性；采集流程需优化，确保数据拿回来就是干净的，或少量问题留到数据治理阶段处理」
> 关联：A-20260908-003（外部数据统一质量治理框架 LOCKED）、A-20260909-001（质量问题治理闭环 LOCKED）、docs/standards/数据采集合并去重机制说明.md、docs/standards/投诉数据接入说明.md

## 一、现状：采集全链路五层

```
┌ 入口层(7类) ──────────────────────────────────────────────────────────┐
│ ① BMS 网页采集 ② 共享文档(腾讯/金山) ③ 老腾讯文档 API                  │
│ ④ workbuddy 投诉推送 ⑤ workbuddy 手动退款推送 ⑥ 文件上传 ⑦ SCRM        │
└──────────────────────────┬────────────────────────────────────────────┘
                           ▼
┌ ② 读取/映射层  data_parser ───────────────────────────────────────────┐
│   read_csv_auto_encoding(编码识别/断行修复) + calamine 读 xlsx        │
│   COLUMN_TEMPLATES: 中文列名 → 模型字段(每 data_type 一套候选列名)    │
└──────────────────────────┬────────────────────────────────────────────┘
                           ▼
┌ ③ 清洗层 ─────────────────────────────────────────────────────────────┐
│   ⚠️ 双份实现：                                                        │
│   - 推送路径: complaint_sync._clean_external_row / _clean_card_row    │
│   - 上传/共享文档: upsert.upsert_external_complaints / _clean_*       │
│   公共工具: upsert._to_datetime / _sanitize_date / _truncate_str /     │
│             _sanitize_name_field / _clean_sn                          │
└──────────────────────────┬────────────────────────────────────────────┘
                           ▼
┌ ④ 去重/入库层 ────────────────────────────────────────────────────────┐
│   各 data_type 去重键 upsert(on_conflict_do_update)                   │
│   投诉: dedup_hash = md5(投诉日期|手机号|SN|问题签名)                 │
│   手动退款: (登记日期|订单号|设备号|登记人)                            │
└──────────────────────────┬────────────────────────────────────────────┘
                           ▼
┌ ⑤ 质量层(L1检测/L2治理/L3规则) ──────────────────────────────────────┐
│   L1 quality_check → quality_status(pending/auto_fixed)               │
│      未入库行 → ingest_rejected_rows(按行+人工判定)                  │
│   L2 治理闭环: ok / ignored / dup_residual / auto_filled              │
│   L3 规则复用: 治一次 → 沉淀规则 → 后续 auto/suggest                  │
└───────────────────────────────────────────────────────────────────────┘
```

## 二、缺口清单（本次实证，按严重度）

| # | 缺口 | 实锤证据 | 根因 | 影响 |
|---|---|---|---|---|
| **G1** | **类型防线缺失**：解析未做「数值↔文本」归一 | 库中 **229 行 handle_time = 1969-12-31 16:00:00.000046**；228 行早于登记日 | `_to_datetime` 序列号分支`只判 str`（`isinstance(val,str) and s.isdigit()`），数值 `46187` 落入 `pd.to_datetime(46187)`→按纳秒解释 | 时效/及时性统计**完全失真**；投诉"状态不及时"直接原因 |
| **G2** | **清洗双份实现、口径易漂移** | 推送走 `complaint_sync._clean_*`，上传/共享文档走 `upsert.upsert_*`，各自维护字段清单 | 两个入口历史独立演进 | 同一份数据不同入口结果可能不同；修一处漏一处 |
| **G3** | **投诉表无 L2 质量字段** | `QualityMixin` 仅 refund/shanmao_refund/ticket/wallet(+manual_refund 内联)；**external_complaints / card_complaints 无** | 治理框架先覆盖退款四路，投诉表未纳入 | 投诉脏数据（重复导入/坏时间）**无法在质量页打标治理** |
| **G4** | **去重指纹含易变字段** | 48 组/97 行"同手机号+同问题逐字相同"重复；方立国 2027(date 2025-04-11) vs 7005(date 空) | 指纹含 `complaint_date`，日期缺失/被改写即生成新行 | 重复登记累积；统计虚高 |
| **G5** | **静默降级**：解析失败/字段非法时置空而非拒收 | 姓名污染 `_sanitize_name_field` 置空；时间解析失败返回 None | "能入库就行"的宽松策略 | 坏值静默进入，事后才发现 |
| **G6** | **缺字段格式规范**：无"同列多格式"的显式处理约定 | 处理时间列 ≤8/7 为 Excel 序列号、≥8/8 为日期串（上游中途改格式） | 无"上游格式变更"的兼容/告警机制 | 上游一变，静默出错 |

## 三、优化设计：统一入库接口 + 四道防线

> 核心思想：**先归一 → 再校验 → 后入库；不合法不静默**。数据质量由"事后治理"前移到"事前拦截"。
> ⭐ 用户要求（2026-09-10）：**所有入口走同一个统一入库接口，便于维护、不易出错，且统一返回值**。

### D0 ⭐ 统一入库接口（唯一通道，收口全部入口）

**现状问题**：7 类入口各写各的（推送走 `complaint_sync.sync_complaints_from_payload`、上传/BMS 走 `run_upsert`、共享文档走 `doc_sync_service`、SCRM 走 `sync_scrm_service`），清洗逻辑**双份实现**（G2），返回值各不相同（`ImportResult` / `SyncRowResult` / dict）。

**设计**：单入口 + 注册表，所有入口只能调它。

```python
# services/ingest_service.py（新，唯一入库通道）
def ingest(
    db: Session,
    data_type: str,                      # 目标业务类型（注册表 key）
    *,
    df: pd.DataFrame | None = None,      # 表格入口（上传/BMS/共享文档）
    rows: list[dict] | None = None,      # 逐行入口（push/API）
    mapping: dict[str, str] | None = None,
    source: str,                         # 入口标识: bms/shared_doc/tencent_doc/workbuddy/upload/scrm
    source_ref: str | None = None,       # 溯源: upload_record_id / sync_log_id / doc_source_id
    options: dict | None = None,         # 如 full_sync=False
) -> IngestResult:                       # 统一返回值（见下）
```

内部固定流水线（每阶段可复用、可测试）：
```
① normalize(归一)   → ② validate(校验) → ③ dedup(去重键) → ④ upsert(入库)
                                                              ↓
                                         ⑤ 打标(quality) / 拒收(ingest_rejected_rows)
                                                              ↓
                                                    ⑥ 统一 IngestResult
```

**注册表（单一事实源）**——每 data_type 一行声明，新增数据源只加一行：

```python
# services/ingest_registry.py（新）
DATA_TYPE_REGISTRY = {
  "external_complaint": DataTypeSpec(
      model=ExternalComplaint,
      dedup_key="dedup_hash",            # 去重键字段
      identity_fn=complaint_identity_hash,  # 指纹算法（唯一实现，替换现有两份）
      normalizer=normalize_external_row,    # 字段归一（唯一实现）
      validator=validate_external_row,      # 校验规则
      column_template=COLUMN_TEMPLATES["external_complaint"],
      upsert_fn=upsert_external_complaints,
      quality_enabled=True,              # 是否 L2 打标
  ),
  # ... 其余 18 个 data_type
}
```

**统一返回值 `IngestResult`**（所有入口、所有 data_type 同一结构）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `data_type` | str | 目标业务类型 |
| `source` | str | 入口标识 |
| `run_id` | str | 本次入库批次号（可溯源 `ingest_rejected_rows.source_ref`）|
| `total` | int | 收到行数 |
| `inserted` / `updated` | int | 新增 / 更新（去重命中）|
| `skipped` | int | 空行/模板行跳过 |
| `rejected` | int | 未采纳（落拒收表，待人工判定）|
| `warnings` | list | 软告警（字段被清洗等，行保留）|
| `errors` | list | 硬失败（行被丢弃）|
| `status` | str | `success` / `partial` / `failed` |
| `quality_flagged` | int | 打标 `pending` 行数（L2）|

**对外 HTTP 统一包装**（遵循 `docs/standards/error-code.md`）：
```json
{ "code": 0, "message": "ok", "data": { ...IngestResult 字段... } }
```
错误仍走 `HTTPException(status_code, detail)`（**不套成功外壳**）。

**收益**：
- 入口新增/变更**只改注册表一行**，杜绝"修一处漏一处"（G2）
- 归一/校验规则**单一实现**，两条推送路径自动一致
- 返回值统一 → 前端/日志/告警**统一消费**，不再各写各的解析
- 与既有 `UPSERT_DISPATCH` 兼容：`run_upsert` 更名为内部阶段，保留向后兼容薄封装

### D1 解析归一（读取层，消除"同值多形态"）
**目标**：进入业务对象前，所有字段已完成类型化与格式化。

- **类型归一**（解决 G1）：统一 `_to_datetime` / `_to_numeric` / `_to_text` 三个归一器
  - 日期：**先判类型再判范围**——`int/float/str` 只要是 20000~80000 的纯数字 → 按 Excel 序列号；此后才走 `pd.to_datetime`
  - 数值：剥离货币/千分位/单位（已有 `_normalize_numeric_string`，推广到所有金额）
  - 文本：统一去 `\t`/全角/首尾空白/Excel 强制文本前导 `` ` ``
- **格式归一**：日期多格式（`YYYY/M/D`、`YYYY-MM-DD HH:MM`、序列号）统一；空值占位符（`NaN/null/none/-//`）统一 → None
- **列归一**：`COLUMN_TEMPLATES` 保持（已有）
- ⭐ **原则**：归一器必须**类型无关**（同一语义值无论来自字符串还是数字，结果一致）

### D2 校验拦截（入库前，非法即拒收）
**目标**：不合法行**不进业务表**，落 `ingest_rejected_rows` 待人工判定（不静默置空）。

- 校验四类（复现 `quality_check` 规则，**前移到入库前**）：
  - R-时间：缺失/未来/远古/倒挂（finish<register 等）
  - R-枚举：状态/类型不在预期集合
  - R-金额：≤0 或缺失（必填金额）
  - R-必填：关键关联键缺失（如必须有 SN 或订单号之一）
- 处置：`validate_fail` → 拒收行；`polluted`（如姓名填了手机号）→ 拒收行 + 原值留痕
- ⭐ **原则**：**拒收而非置空**——"未采纳行按行可见、人工判定、默认不纳入"（对齐 A-20260908-003 用户拍板原则）

### D3 入库打标（L2 覆盖到全业务表）
- `external_complaints` / `card_complaints` **补齐 QualityMixin**（`quality_status`/`quality_note`）
- 可疑但可入库（如 SN 长度异常、日期与入库时间差过长）→ 标 `pending`
- 统计口径统一走 `_quality_include_cond`（排除 `dup_residual`/`ignored`），替换散落手写排除

### D4 去重与治理兜底（防累积 + 闭环）
- **去重指纹重设计**（解决 G4）——三选一（待用户决策，见 §五）：
  - A 现状：`日期|手机|SN|问题` → 日期变即新行（累积）
  - B 去日期：`手机|SN|问题` → 防重复但可能误合同人同期多次投诉
  - C **折中（推荐）**：`手机|SN|问题` + **时间窗去重**（如 30 天内同键视为同一投诉，更新不新增；超窗才新行）
- **清洗实现收敛为单一来源**（解决 G2）：抽 `services/ingest_normalize.py` 统一归一+校验，两条入口共用
- **上游格式变更告警**（解决 G6）：记录"某列命中序列号/日期串的比例"，突变时在采集日志告警
- **治理闭环复用**（已有 A-20260909-001 L3）：拒收行判定沉淀规则，同类自动/半自动处理

## 四、改造清单（按优先级）

> 策略：**先立统一通道（D0），再把归一/校验挂到通道上**——避免在旧的散落实现里逐个打补丁。

| 优先级 | 改造项 | 涉及 | 解决 |
|---|---|---|---|
| **P0** | 新建 `ingest_service.ingest()` 统一入口 + `ingest_registry` 注册表 + `IngestResult` 统一返回 | 新模块 | D0 收口 |
| **P0** | `_to_datetime` 类型无关化（数值序列号） | `upsert.py` | G1 |
| **P0** | 回填库中 229 行 `1969-12-31` 坏值 | 脚本 | G1 |
| **P0** | `external_complaints`/`card_complaints` 加 QualityMixin（Alembic） | models + migration | G3 |
| **P1** | 归一+校验抽为注册表引用的函数，两条清洗路径改调统一实现 | `ingest_registry` | G2/G5 |
| **P1** | 7 类入口全部改调 `ingest()`（push/上传/BMS/共享文档/SCRM） | 各入口 | D0 |
| **P1** | 入库前校验拦截 → 拒收行（时间/枚举/金额/必填） | `ingest_service` | G5 |
| **P2** | 去重指纹重设计（方案待定） | 注册表 `identity_fn` | G4 |
| **P2** | 上游格式变更检测告警 | 采集日志/ingest health | G6 |
| **P2** | 补采 315 新增 8 字段（投诉关键词/内部分析/套餐金额 4 列等） | 注册表 + 迁移 | 分析能力 |

### 改造前后对比

| 维度 | 改造前（现状） | 改造后 |
|---|---|---|
| 入库入口 | 7 类入口各调各的函数 | **1 个 `ingest()`** |
| 新增数据源 | 改 5~6 处（模板/清洗/upsert/dispatch/入口） | **注册表加 1 行** |
| 清洗实现 | 2 份（push / upload） | **1 份**（注册表引用） |
| 返回值 | `ImportResult` / `SyncRowResult` / dict 混用 | **统一 `IngestResult`** |
| 坏值处理 | 静默置空或误入库 | **校验拦截 → 拒收行** |
| 时间类型 | 字符串对、数值错 | **类型无关** |
