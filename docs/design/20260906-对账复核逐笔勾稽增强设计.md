# 对账复核逐笔勾稽增强设计（2026-09-06）

**日期**：2026-09-06
**性质**：架构/增量设计（供评审后并入 A-20260906-002 或独立锁定；**先评审后实现**）
**关联**：A-20260906-002（五路对账复核，LOCKED，本设计是其"明细级闭环"增强）、A-20260902-011（口径）、工单 #22
**用户澄清（2026-09-06）**：
- 对账流程期望：① 区间总数核对 → ② 明细一一对应 → ③ 不符可逐笔处理 → ④ 复核留痕闭环。
- 粒度：**以 E 水单为基准逐笔核对**（E 每笔 → 候选匹配 ABCD 经营单 → 人工确认对应/无对应）。
- 深度：**仅打标不改源**（对勾稽关系打状态 + 原因，不碰任何源表；改数据仍走治理流程）。
- 存储：**新增逐笔勾稽结果表**（持久化、可追溯、可统计）。

> ⚠️ 本设计**叠加不推翻** A-20260906-002 已锁定核算语义：复核/勾稽标识只留痕，不参与任何统计；源表不变。

## 一、目标与差距

### 1.1 期望流程（用户）
```
① 区间总数 → preview_check 已有（五路 vs E + 差）
② 明细一一对应 → 缺：要能逐笔看到 E 水单 → 匹配到 ABCD 哪一笔，人工确认
③ 不符逐笔修订 → 缺：对单笔打"已确认/差异已确认/存疑/已排除重复"状态 + 原因（不改源数据）
④ 复核留痕闭环 → 批次级已有，缺单笔级痕迹
```

### 1.2 现状差距
- 后端已有 `water-statement`（E 水单逐笔自动归类 A/B/C/D/unmatched + 分页）与 `_build_route_maps`/`_classify_report`（匹配逻辑），**可复用**。
- 复核 Tab（ReconcileCheck.vue）只显示汇总归属（by_route_of_e），未展示逐笔列表，也无人工确认交互。
- `reconcile_checks` 只有批次快照，无单笔核对结果。

## 三、数据模型（ER 增量）

新表 **`reconcile_matches`**（E 水单逐笔勾稽结果；仅留痕，不参与统计，不改源表）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | IDMixin |
| check_id | bigint FK → reconcile_checks.id | 关联复核批次（可空 = 未成批的草稿核对） |
| report_id | bigint FK → refund_record_reports.id | E 水单 id（勾稽基准，唯一随批次） |
| platform_order_no | varchar(128) | 冗余快照（便于直接查/列表展示） |
| refund_amount | numeric(12,2) | E 笔金额快照 |
| refund_time | timestamptz | E 笔时间快照 |
| auto_route | varchar(16) | 自动归类 A/B/C/D/unmatched（_classify_report 结果） |
| matched_ref | jsonb | 候选匹配经营单引用：[{route, source_table, source_id, order_no/refund_no, amount}]（自动匹配的候选，供人工确认） |
| confirm_status | varchar(16) | 人工确认状态：`已核对一致`/`差异已确认`/`存疑待查`/`已排除重复`/`待核对` |
| confirm_note | text | 人工备注（差异原因/处理说明） |
| confirmed_by / confirmed_name | int / varchar | 确认人 |
| confirmed_at | timestamptz | 确认时间 |
| created_at / updated_at | timestamptz | TimestampMixin |

> 唯一约束：`(check_id, report_id)`（同批次同一 E 笔只一条勾稽记录）。check_id 可空时用 `report_id` 作草稿（约束用部分唯一索引或应用层保障）。

## 四、接口契约（挂 /reconcile/check/ 下，权限同现 check 端点）

| 端点 | 方法 | 权限 | 说明 |
|---|---|---|---|
| `GET /reconcile/check/{id}/lines?route=&status=&page=&page_size=` | GET | CurrentUser | 批次逐笔勾稽列表：E 笔 + auto_route + 人工状态（可过滤） |
| `GET /reconcile/check/line-candidates?report_id=` | GET | CurrentUser | 某 E 笔的候选匹配经营单明细（A 退费单/D 手动/WB 等，含金额/单号/SN，供人工选） |
| `POST /reconcile/check/line-confirm` | POST | Admin/Supervisor | 对单笔打确认状态 + 备注（body: check_id|report_id, confirm_status, confirm_note, matched_ref 可选） |
| `GET /reconcile/check/{id}/summary` | GET | CurrentUser | 批次内单笔确认进度：{total, confirmed, by_status:{...}, by_route:{...}}（区分子区"明细已核对 n/N"） |

参数：北京时间（复用 `_parse_win`/`_to_utc_aware`）。金额元。
**不改源**：line-confirm 只写 `reconcile_matches`，绝不 UPDATE refunds/manual_refunds/refund_record_reports。

## 五、前端（ReconcileCheck.vue 增强）

在现"历史复核批次"上方的"批次详情/当前预览"增加**逐笔核对区**：
1. 顶部：当前窗口 E 笔总数 + 已核对 n/N + 按 auto_route/confirm_status 过滤 tab。
2. 表格每行：E 笔（订单号/时间/金额）+ auto_route tag + 候选匹配（可展开看候选经营单）+ 人工状态下拉（已核对一致/差异已确认/存疑待查/已排除重复）+ 备注。
3. 点"确认"保存到 `reconcile_matches`（Admin/Supervisor 才可写；读全员）。
4. 对应关系：展开显示自动匹配的 ABCD 候选（金额/单号/SN），人工可选"就是它/换一个/无对应"。

> 交互对齐用户"一笔笔对应"：每笔 E 默认带出自动候选，人工核对后打状态，直到 n/N 全核对或有明确差异结论。

## 七、风险清单

1. **候选匹配可能错配**（同设备同额多笔/多批次）→ 展示多个候选 + 人工确认；L2/L3 匹配规则与治理/回填一致，仅提示不自动写。
2. **逐笔量大**（E 一笔对多候选或一候选对多 E）→ 分页 + 按 route/status 过滤；`line-candidates` 单笔查候选不批量。
3. **仅打标与"修订"期望落差**：用户可能期望复核页能直接改源数据（如标 dup_residual）。本期只打标（安全），改源仍走 #21 治理脚本/口径评审；若后续要"复核页直接治理"需另评审（涉及回滚/权限/统计口径）。
4. **草稿 vs 成批**：未落 reconcile_checks 的核对（check_id 空）与已确认批次的关系需明确——建议先建批次（confirm 落 check）再逐笔，避免游离草稿。
5. **确认状态口径**：`已核对一致` 不应被当作"数据一定正确"，仅代表"该笔已人工核对过对应关系"；UI 文案与 #22 一致的"非正确性保证"提示对齐。
