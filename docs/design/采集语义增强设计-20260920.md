## 〇、一句话概括

**采集进来的数据，可能在入库那一刻就已经被悄悄改坏了** —— 超长文本被静默截断、
换行被吞或原样塞进单行、日期解析成功但落在 1900 年。
本方案让这些坏值**在入库前留痕可见**、**在入库后可扫描可核对**，并把修正动作纳入
治理框架的**分级执行红线**（改值恒为 L2，必须人工确认 + 备份 + 凭证）。

## 一、背景与目标

### 1.1 现状痛点（三条，均带代码证据）

**P1 静默截断（数据被改坏而无人知晓）**

[upsert.py](../../backend/app/services/upsert.py) 的 `_truncate_str(val, max_len)` 对超长值直接
`s[:max_len]`，**无告警、无留痕**；`max_len` 靠人工与 DB 列宽对齐（同文件注释「迁移后列宽 64,
与 DB 对齐」即此维护方式）。后果：一份备注被砍掉后半段，使用者以为入库成功，
而库里那条记录与源文件已经不一致 —— 与 C-P1-7（钱包重复）同类：**坏在静默**。

**P2 换行处理两态不一致（同一份数据两种结果）**

| 路径 | 现状 | 位置 |
|---|---|---|
| CSV | 字段数不足时与下一行**用空格拼接** → 换行被「吞」 | [data_parser.py](../../backend/app/services/data_parser.py) `read_csv_auto_encoding` |
| XLSX | `_fix_xlsx_line_breaks` 把续行合并回上一行，**用 `"\n"` 拼接** → 换行原样入库 | 同文件 |

同一份业务数据，经 CSV 与 XLSX 两条路径导入会得到**不同内容**，且无人察觉。
个别列有手工清理（`complaint_no` 去 `\n`、卡商投诉 `device_sn` 取首个换行前片段），
但**没有统一判据**。

**P3 错日期只治理了「解析失败」，没治「语义错误」**

`upsert._to_datetime` 已经把「无法解析」的值判 `None` + 告警（注释明确「即本函数要根除的坏值类型」），
这条路径**已治理**。但**解析成功却语义错误**的没人管：

- 「合法但不可能」的日期：`1900-01-01`、`2099-12-31`（PG 本身拒绝 `2026-13-45`，能入库的都是这类）
- 未来日期（源系统填错年份）
- 时间倒挂：完成时间 < 创建时间

### 1.2 目标

1. **入库前可见**：截断 / 换行 / 可疑日期**留痕**（复用 #40 已有的拒收行机制与人工判定入口，**不新起一套**）
2. **入库后可查**：三个确定性探测器产出**可核对证据**（metrics + 脱敏样本 + 复现 SQL，沿用框架三件套）
3. **判断 AI 化**：区分「真问题 vs 业务允许」（备注里的换行可能是业务真需要）→ 结论沉淀为规则
4. **执行分级**：**改值类动作恒 L2**（人工确认 + 备份 + 凭证）；标记类（待核）L1

### 1.3 非目标（取舍，评审重点）

- **不做**导入期自动修复 —— 自动改值等于绕过「不可逆动作必须人工确认」红线（与框架 §六 同一红线）。
- **不做**全字段语义推断 —— 只做「**有权威来源可推**」的空缺（§3.3 三类），不做「猜」。
- **不做**实时逐行校验钩子 —— 沿用框架的「周期扫描 + 导入期留痕」，不在写入路径上加逐行校验（性能敏感）。
- **不新增**采集解析器 —— 复用 `data_parser` / `upsert`，只在既有落点加检测。
- **不新增**界面页面 —— 复用 #165 的 AI 数据治理页（按 detector 加筛选与证据渲染）。
- **不改动**任何去重键 —— 去重键是 META 权威定义（见关联文档），本期只加检测与留痕。

## 二、总体设计：双时点 + 判据同源

```
┌─ 导入期（治新增：不让新的继续坏）──────────────┐   ┌─ 事后扫描（治存量：把已坏的找出来）──────────┐
│ data_parser.clean_cell   → 检出换行            │   │ D4 text_anomaly    换行 / 贴近列宽上限      │
│ upsert._truncate_str     → 检出截断            │   │ D5 impossible_date 越界 / 未来 / 倒挂 / 聚集 │
│ upsert._to_datetime      → 检出越界日期        │   │ D6 fillable_gap    有权威来源可推的空缺      │
│        ↓ 只留痕，**不改入库数据**              │   │        ↓ 证据三件套（metrics/samples/sql）   │
│ IngestRejectedRow（复用 #40 表 + 判定入口）    │   │ 研判（规则短路 → AI，按 detector 注入判据）  │
│  category=truncate_suspect / newline_suspect /  │   │        ↓ 分级执行                            │
│           date_impossible                       │   │ L0 report_only / L1 mark_pending /          │
│        ↓ 人工判定 open/keep/discard（已有）    │   │ L2 fix_time（人工确认 + 备份 + 凭证）        │
└─────────────────────────────────────────────────┘   └──────────────────────────────────────────────┘
                     └──────────── 同一份判据函数（单一来源）────────────┘
```

**为什么两头都要做**（本方案最关键的取舍）：

- 只做事后扫描 → 每天新增继续污染，**永远追不上**（存量治理的收益被新增吃掉）；
- 只做导入期拦截 → 库里已有的坏值**无人知晓**（存量不追溯的反面：这里必须追溯）；
- 两条路径的判据**必须同源**（同一函数，导入期与扫描期共用），否则「拦截口径 ≠ 扫描口径」
  又是一次口径漂移（同 A-20260910-004 菜单漂移的教训）。

## 三、三个场景详细设计

> 三者的产出形态统一为框架既有的 finding 五元组：
> `detector / table_name / target / severity_raw / metrics / samples / repro_sql`。
> 新增探测器需改动的 5 处落点见 §六。

### 3.1 D4 `text_anomaly` —— 换行 / 截断

**判据 A（单元格含换行）**

```sql
SELECT count(*) FROM "<表>" WHERE "<文本列>" LIKE '%' || chr(10) || '%'
```

- 覆盖范围：`data_sources` 登记的 active 业务表 + 其中的 String/Text 列。
- **白名单**：`_TEXT_ALLOW_NEWLINE`（列名或 `表.列`）—— 业务确实要多行的列
  （AI 报告正文、政策正文、KB 正文等），**必须在常量里逐条写明理由**，
  否则「白名单」会变成「误报开关」。
- 一条 finding 一个 `(表, 列)`（`target` = 列名），便于按列 dismiss 沉淀规则。

**判据 B（长度贴近列宽上限 = 截断嫌疑）**

```sql
-- 列宽来自 information_schema（String(n) 有值，Text 为 NULL → 天然跳过）
SELECT count(*) FROM "<表>"
WHERE length("<列>") >= :col_max_len * 0.95
```

- 阈值 `0.95`：截断后长度恰等于 `col_max_len`，留 5% 容差覆盖「截断后又被 strip」的情形。
- ⚠️ 这是**嫌疑不是证据**：合法长文本也会命中 → **这正是要交 AI 研判的地方**
  （结合样本形态判断：是否切在词中、是否与前一行同源）。

**metrics**：`{hit_rows, total_rows, ratio, kinds:["newline","near_limit"], columns:[...], col_limits:{列:列宽}}`
**samples**：脱敏行 + `_sample_ids`（沿用 D1 的 `mask_value` / `collect_samples` 手法）
**severity_raw**：命中行数 / 占比分档（沿用 D1 的阈值风格：≥100 行或 ≥5% → high）

**导入期对应（治本，见 §四）**：`_truncate_str` 发生截断时、`clean_cell` 检出 `\n` 时，
各写一条 `IngestRejectedRow`（`truncate_suspect` / `newline_suspect`），**不改入库数据**。

**AI 判据段（注入）**：
- 备注/说明类列出现换行 → 可能业务需要（多行备注）；编号/SN/单号类列出现换行 → 几乎必是坏值（截断或串行）
- 截断嫌疑：看样本是否切在词中（中文突然终止、英文字母半截、数字位数不整）

**执行分级**：
- 默认 **L0 `report_only`**（源文件已不在库里，无法自动恢复原值 → 报告 + 按 `repro_sql` 人工处置）
- 若该列确认「不该含换行」→ 人工 **dismiss 沉淀规则**，下次同类不再报（框架已有能力）
- 若表已纳入行级质量处置（`QUALITY_TABLES`：`refund`/`ticket`/`wallet`/`shanmao`/`manual_refund`）
  → 可 **L1 `mark_pending`** 标待核（新增动作，见 §六）

### 3.2 D5 `impossible_date` —— 明显错误日期

**判据（四类，逐 `(表, 时间列)` 产 finding）**

| 类 | 判据 | 说明 |
|---|---|---|
| A 年份越界 | `extract(year from col) NOT BETWEEN :min_year AND :max_year` | `min_year=2015`（项目数据起点）、`max_year=当前年+1`，常量可调 |
| B 未来日期 | `col > now() + interval '1 day'` | 留 1 天容差覆盖时区/同步延迟，避免误报 |
| C 时间倒挂 | `"<完成列>" < "<创建列>"` | 列对按**阶段序**推断（创建→处理→完成，同阶段不配对），推断不出则跳过；比较用**北京日期**（跨天倒挂才是矛盾，同日内分钟级时差多为上游批量覆盖噪音）。**列对比例上限 30%**：倒挂占比 ≥ 30% → 判为**列对语义推断错误**（不是数据矛盾）→ 跳过该列对，原因记入 `metrics.skipped_pairs`（生产实证：`service_tickets.dispatch_time`/`active_time` vs `register_time` 倒挂占比 90.7%/67.5%，该表 `register_time` 语义是「服务登记时间」而非创建时间） |
| D 兜底值聚集 | 单一日期占该列非空行数 ≥ `:ratio`（默认 0.30）**且**行数 ≥ 3 **且**该日期形如兜底值（月日 01-01/12-31） | 典型「解析失败兜底 / 默认值填充」。**三道门缺一不可**：只看占比会把大促/月初结算这类**真实集中日期**一并报出（那是业务事实，报出来只能靠人工反复驳回）—— 工单 #169 验收 1 明确要求「真实集中日期（大促）不误报」。**已知漏报**：非 01-01/12-31 形态的默认值抓不到（宁可漏报，不可天天误报） |

- 时间列以 `data_sources.time_field` 为权威（框架 D2 已确立此口径，`metrics.is_time_field` 标出），时区一律按 `Asia/Shanghai`。
- **计划类列不判 A/B**（`PLANNED_DATE_COLUMNS`：`start_date`/`end_date`/`end_time`/`expired_at`/`service_valid_until` 等，本就应在未来；`start_date` 是生产实证后补入的 —— 39938 行在未来且**全部** `end_date` 也在未来且 end>start，属预购/长期服务）；**系统审计列不扫**（`created_at`/`updated_at`/`synced_at`/`fetched_at`/`matched_at`，是本系统写入时刻不是业务事实）；**物化宽表不扫**（`refund_wide`/`cash_flow_wide`，派生表改了会被重建覆盖 = 处置无效）。
- **一条 finding 一个 `(表, 列)`**（`target` = `表.列`），`metrics.kinds` 标明命中的类别。

**metrics**：`{hit_rows, total_rows, ratio, nonnull_rows, kinds:[...], counts:{类:行数}, col, is_time_field, min_date, max_date, top_dates:[{date,count,ratio}×5], year_range, cluster_ratio, reversed_pairs, skipped_pairs}`
> `skipped_pairs` = 被列对比例上限挡下的列对（含占比与原因，可审计「为什么这条没按倒挂报」）。
> `hit_rows` = 四类**并集**（去重），不等于 `counts` 之和 —— 一条记录可能同时命中多类（`2099-12-31` 既越界又未来；`finish_time` 既早于 `register_time` 又早于 `op_time`）。相加会虚高且与 repro_sql 对不上（D1 铁律）。
**repro_sql**：四类各一段可执行 SQL（数字必须与 `metrics.counts` / `hit_rows` 对得上，沿用 D1 铁律），另附 `top_dates` 与倒挂逐列对明细。

**导入期对应**：`_to_datetime` 解析成功但落在越界区间 → 写 `IngestRejectedRow(date_impossible)`，
**保留原值到 `raw_row`**（人工核对要用），不阻断入库。

**AI 判据段（注入）**：
- 结合上下文**推断正确值**并给出依据（如 `2026/9/19` 缺前导零、Excel 序列号误用、
  位数异常），`suggestion.params.updates = [{pk, col, old, new}]`
- 依据不足 → `uncertain` + 低 confidence，**禁止编造**

**执行分级：L2 `fix_time`**（动作位已在框架预留 `DISPOSITION_FIX_TIME`，当前被显式拒绝，本期实现）：
1. 人工确认（红线，框架已实现 400 拦截）→ 可在确认时**修改 AI 给的 `updates`**（§六 第 4 条）
2. 强制备份（复用 `_backup_rows`：`CREATE TABLE AS SELECT` 整行备份，行数必须相等）
3. 逐行 `UPDATE`（列名走 `_assert_ident` 白名单 + 值走绑定参数）
4. 凭证（old/new 对照）+ `_post_execute`（重建受影响宽表 + 失效缓存）
5. 重扫不再命中 → 自动收敛（框架 #167 已实现）

### 3.3 D6 `fillable_gap` —— 可推断空缺（语义补全）

**判据（只做「有权威来源可推」三类，不做「猜」）**

> ⚠️ **来源清单已按 2026-09-20 生产只读探测校正**（原表是设计期举例，与库中实际可用的来源不符）：
> `device_combos` **没有设备类型列**、`device_profile` 是**导入通道**（落库目标就是 `devices`
> 自身，推不出自己）；`refunds.device_sn` **无一为空**（无空缺可补）。
> 校正后的清单（顺序即优先级）见 `backend/app/services/governance_detector.py` 的 D6 段注释。

| 类 | 判据 | 权威来源（实测可用） | 生产可补规模 |
|---|---|---|---|
| A SN→设备属性 | `devices.device_type` 为空，且同 SN 在别处有设备类型 | `bms_orders.device_type_name` / `device_flow_usage.device_type_name` | 98863 / 57 个 SN |
| B 订单→SN | 退费类表 `device_sn` 为空，但同订单号在其它通道能关联到 SN | `refund_record_reports` / `refunds` / `device_combos` / `bms_orders`（均按订单号） | 2875 / 1136 / 558 / 1 行 |
| C 别名→标准人 | 人员文本列的值在 `person_aliases` 能命中**已归并**的 `person_id` | `person_aliases`；字段清单取 `person_extractor.PERSON_FIELD_SOURCES`（13 个字段中**只有 2 张表同时有 `person_id` 列**） | 现网 0（SCRM 未同步） |

C 类「只有 2 张表有 `person_id` 列」= 其余表的姓名列**没有可补的列**（补了没地方放），
不是漏做；且 `person_aliases` 里 `person_id` 为空的别名属**尚未归并**，不算权威来源（推不出就不报）。

**metrics**：`{fillable_rows, total_null_rows, ratio, rule:"sn_to_device_type"|"order_to_sn"|"alias_to_person", sources:{表:命中数}}`
**samples**：**必须含「推断来源」**（哪张表哪一行推出的值）—— 否则人工无法核对，
等于要求人盲信 AI（框架 §3.1「拒绝黑盒结论」的同一纪律）。

**AI 判据段（注入）**：给补全建议 + 依据 + confidence；**源里查不到就不许推**（禁止编造）。

**执行分级：L1 `mark_pending`**（标待核，可逆）+ 人工确认；
**本期不自动写值** —— 写值属 L2 改数据，且补全的收益（省手工）远小于改错的风险。

## 四、导入期留痕（复用 #40，不建新表）

| 项 | 决策 |
|---|---|
| 存储 | 复用 `ingest_rejected_rows`（模型 `IngestRejectedRow`，字段齐备：`data_type/source/source_ref/source_row_no/reject_category/reject_reason/raw_row/business_key/status/reviewed_by`） |
| 新增类目 | `truncate_suspect` / `newline_suspect` / `date_impossible` 三个 `reject_category` 值 |
| 是否要迁移 | **不需要** —— 已核实 `reject_category` 是 `String`，**无 CHECK 约束**；只改模型注释 |
| 是否静默 | **不静默** —— 这三类必须出现在人工判定列表里（`SILENT_CATEGORIES` 不含它们） |
| 写入点 | `data_parser.clean_cell`（换行）、`upsert._truncate_str`（截断）、`upsert._to_datetime`（越界日期） |
| 人工判定 | 复用现有 `/api/v1/data-quality/rejected/*`（列表 / stats / 单行 review / batch-review），**不新增接口** |
| 节流 | 沿用既有「每批上限 200 条」（`upsert.py` 里已有该上限），避免一次导入刷爆留痕 |

**改动纪律（这三处都在采集主路径上）**：
1. **不改变入库数据**（只多写留痕行）；
2. **不改变任何去重键**（META 红线）；
3. 单测必须覆盖「不留痕时行为完全一致」的回归（避免检测逻辑反噬采集）；
4. 留痕写入失败**不得阻断采集**（同 `record_system_event` 的容错策略：失败仅告警）。

## 五、提示词与判据注入

## 八、验收标准 / 关闭条件（供工单用）

1. **三个探测器各有正/反用例**，含**不误报**断言：业务确需换行的列、真实集中日期（大促）、
   无权威来源的空缺 —— 均不得报出。
2. **导入期留痕**：截断 / 换行 / 越界日期各写一条 `IngestRejectedRow`，且
   **入库数据与留痕前逐字节一致**（断言：加检测前后同一份文件的入库结果相同）。
3. **判据同源**：导入期与扫描期共用同一判据函数；对同一构造数据两边结论一致（断言）。
4. **`fix_time` L2**：未确认执行 → 400；确认后 → 备份表存在且行数相等、值已改、
   凭证含 old/new 对照；重扫不再命中（自动收敛）。
5. **`mark_pending` L1**：仅 `QUALITY_TABLES` 覆盖表可用；未覆盖表 → 明确报错（不静默）。
6. 全量回归通过 + **生产实测凭证**（三个场景各一条真实 finding，贴 metrics/样本/复现 SQL 与执行凭证）。

## 十、风险与边界

| 风险 | 缓解 |
|---|---|
| **误报**（业务确需换行 / 真实集中日期） | 白名单常量（逐条写理由）+ 阈值可调 + AI 研判 + dismiss 沉淀规则后不再重复报 |
| **改动采集主路径**（截断/解析三处都在热路径） | 只留痕不改数据 + 每批 200 上限 + 留痕失败不阻断采集 + 单测断言「不留痕行为一致」 |
| **自动修日期改错** | 恒 L2 + 人工确认（可覆盖 AI 的 updates）+ 强制备份 + old/new 凭证 + 重扫收敛 |
| **语义补全编造** | 只做「有权威来源可推」三类 + 样本必带推断来源 + 人工核对 + 不自动写值 |
| **与 #40 重叠** | 分工写死：#40 管「**已拒收行**的判定」，本期管「**已入库行**的可疑检测」；留痕共用一张表与同一个判定入口 |
| **判据漂移**（导入期与扫描期两套口径） | 判据函数单一来源 + §八 第 3 条一致性断言 |
| **历史坏值规模未知** | 探测器先跑全库统计（只读），按 metrics 规模决定处置批次；不追求一次清完 |
