# #217 金额单位「元 → 分」迁移评估（决策门 · 只评估不实施）

**性质**：需求（REQ）—— 一项具体改造（金额单位迁移）的**前置决策评估**，不是跨项目规范。
**工单**：#217（B1〔决〕，台账 R-P1-8；依据 R 报告 §3.3 W4）
**状态**：⏳ 待人工拍板（**拍板前不实施任何金额字段/计算改动**）
**日期**：2026-10-07
**一句话结论**：现状是「**全链路自洽地用「元」**（DB 定点 Numeric + Python float + 前端按元展示），并非半迁移混乱；它违反铁律字面（金额以分/整数、禁浮点），但因 DB 侧定点无损 + 出参前系统性 `round(x,2)` 兜底 + 金额量级有限，**生产未出现可观测精度事故**。因此这是一次「**合规性 / 风险洁癖**」驱动、而非「线上爆雷」驱动的改造，方案选择本质是「**要字面合规（分/整数）**」还是「**只要消除浮点风险（Decimal 化）**」——二者工作量相差数倍，须人工裁定。

---

## 1. 现状单位流（全链路 = 元）

```
外部数据源（微信支付/商户号/手动Excel/315共享文档/BMS）
  原始金额单位就是「元」，2 位小数
   │  data_parser.COLUMN_TEMPLATES（中文列「退费金额/订单金额/套餐价格…」）
   ▼
_to_float()（upsert/_core.py:154）  —— 字符串/数字 → Python float（元）
   │
   ▼
SQLAlchemy 模型  Mapped[float]  +  Numeric(12,2)   —— 37 列 / 16 模型（元）
   │  （PostgreSQL NUMERIC 定点存储，落库本身无精度损失）
   ▼
读取：ORM 给 Decimal，服务层普遍 float(r.amt) 累加 / abs(float-float) 比较
   │  出参前 round(x, 2) 系统性兜底（≥10 处）
   ▼
API：dict/ORM 透传 float（analytics schema 显式 float 5 处）+ 对外 external.py
   ▼
前端：formatMoney（utils/format.js，按元千分位/万元）+ 各页 Number(x).toFixed(2)
```

**关键事实**：全链路**没有任何元↔分换算**；单位「元」从数据源一路贯穿到 UI。这意味着迁移动到「分」不是改某一层，而是要在**两个边界**（数据进入、数据展示/对外）都插入换算，中间层全部改类型。

### 2.2 ORM 注解：37 处 `Mapped[float | None]`
列类型改整数后，Python 注解须同步改 `Mapped[int | None]`（或 `Decimal`），否则类型层面仍诱导 float。

### 2.3 写入通道：`_to_float()` 与逐通道字段映射（≥30 处）
- 总闸：`app/services/upsert/_core.py:154 _to_float()`（所有金额字段入 float 的唯一入口）。
- 逐通道映射（`app/services/upsert/`）：`_masters.py`（actual_amount/refund_amount/combo/price/paid 等 9 处）、`_refunds.py`（退费/钱包/商户/闪猫，含 fee/rate，约 20 处）、`_tickets.py`（2 处）；另有 `manual_refund_sync.py:266`。
- 迁移影响：单位改分后，**入口必须把「元」源数据换算为分**（且换算本身不能再用 float，见 §5）。

### 2.4 读取/聚合/比较：float 化与 round 兜底
- 聚合 SQL：`app/services/analytics/refund.py` 5+ 处 `sum(...)`（线上直退/钱包提现/闪猫/手动/E 路现金流），结果 `float(r.amt)` 累加；`cash.py` A~E 五路金额。
- 对账/质检：`reconcile.py:485-487`、`reconcile_check.py:101/156/158`、`quality_check.py:230/249`（负数检测）、`quality_disposition_service.py`（多处 `float(...)` 及 `abs(float(a)-float(b))` 差异比较 :1007）。
- **`round(x, 2)` 兜底点 ≥10**（cash.py:425-428、reconcile.py:485-487、reconcile_check.py:101/156/158、quality_disposition_service.py:576 等）——现状正是靠它压住 float 累加尾差。

### 2.5 API / Schema / 对外契约
- `app/schemas/analytics.py`：refund_amount / audit_amount / cash_out_total / wallet_balance_total 等显式 `float`（5 处）；大量接口直接透传 ORM/dict 的 float，无显式 schema 拦截。
- **对外只读开放平台** `app/api/v1/external.py`：金额字段（refund/order 等）当前以「元」对外。**这是面向第三方的契约**，单位变更属破坏性变更，需版本化或边界换算，不能直接改口径。

### 2.6 前端（web/）：统一按「元」展示，无换算
- 统一函数 `web/src/utils/format.js:12 formatMoney()`（元→千分位/万元，`1234.5 → "1,234.50"`、`12345.67 → "1.23 万"`），有单测（`utils/__tests__/format.spec.js`）。
- 但另有**大量就地 `Number(x).toFixed(2)`**（AuditView/AuditTimeline/QualityAudit/ReconcileCheck/ReconcileLines/KpiCard/RouteSplit/useToday 等 ≥10 处自带 fmtMoney）。
- 迁移影响：后端若出「分」，前端必须统一在 formatMoney 一处做分→元，**且要先收敛那些绕过 formatMoney 的就地 toFixed**，否则必然出现「放大 100 倍」事故。

### 2.7 数据源模板（单位由外部决定，不可改）
`data_parser.py` 的 `COLUMN_TEMPLATES`：退费金额/实退金额/套餐价格/操作金额/应结订单金额/代金券金额/订单金额… 全部来自外部「元」口径。**入口永远收到元**——即使内部改分，边界换算无法消除。

## 3. 现状到底有没有真实精度风险？

- **存储层无风险**：PostgreSQL `NUMERIC(12,2)` 定点；写入的 float 落库时被四舍五入到 2 位，误差不会跨请求累积持久化。
- **计算层有理论隐患、实际未爆**：Python float64 有 15~16 位有效数字；单笔金额万元~百万元、累加条数有限时，尾差远小于 1 分，且出参统一 `round(2)`，对「展示/对账（容忍 1 分级）」无可见影响。严格 `abs(float-float)==0)` 式比较（quality_disposition:1007）在「同源应相等」判断上理论上可能误判，但金额本就是 2 位小数、量级内碰撞概率极低，**当前未见相关缺陷工单**。
- **真正的问题是合规与脆弱性**：① 违反 AGENTS 铁律（金额分/整数、禁浮点存储/计算）；② 精度安全依赖「人记得 round(2)」这一纪律而非类型，新增聚合一旦漏 round 即可能裸露尾差（如 0.1+0.2）；③ 对账类「严格相等」埋雷。

**定性**：低紧迫、高「埋雷面」的合规债；不属于需紧急止损的生产事故。这也是 R 报告将其列为 W4（而非 P0/P1 必修代码项）、本单只出评估的原因。

## 4. 三个方案

### 方案 A：全量迁移「元 → 分（整数）」——字面完全合规
- **做法**：37 列 `Numeric(12,2)` → 整数类型（`BIGINT`，分）；Alembic 数据回填 `ROUND(元*100)`（**用 SQL 定点 `ROUND(x*100)` 在库内完成，不用 Python float**）；ORM 改 `Mapped[int]`；`_to_float` 入口元→分（字符串先 Decimal 再 `*100` 取整，禁用浮点）；聚合去掉 float/round 改整数求和；对外 API 与前端边界做分→元。
- **收益**：完全满足铁律字面；整数运算无尾差，可删掉全部 `round(2)` 兜底；对账严格相等安全。
- **成本/工作量（粗估，待实施单细化）**：16 表 37 列迁移 + 数据回填核对；约 5 个 upsert 通道、20+ 服务聚合/对账点、API（含对外版本化）、前端 formatMoney + ≥10 处就地 toFixed 收敛、全量退款/对账/看板回归。**量级约 8~15 人日 + 一轮完整回归与发布窗口**（宽表/投影重建、历史 SCD 表是否一并改需另判）。
- **风险**：面广、跨前后端与对外契约；边界换算写错（尤其入口 `*100` 用 float）会系统性放大/缩小 100 倍或产生零星错分；历史数据回填须可回滚。
- **回滚**：迁移自带 down（分→元 `/100.00`），执行前备份；回填后用「新旧值金额一致」批量校验（见 §5）。

### 方案 B：双字段/双类型过渡（新旧并存）
- **做法**：新增 `*_fen` 整数列与旧元列双写，读双轨校验，稳定后切读、再下线旧列。
- **收益**：可灰度、可随时回退；对外契约不动。
- **成本/风险**：37 列翻倍、双写一致性负担、周期长（多次发布）；与仓库「禁止同指标重复真身」的治理取向相悖；最终仍要付方案 A 的全部成本。**仅当要求零停机/灰度强保障时才值得**，本项目单机 PG + 发布窗口可停维护，**一般不推荐**。

### 方案 C′：维持「元」单位，但 Python 侧全面 Decimal 化 + 登记铁律豁免（推荐备选）
- **做法**：DB 保持 `NUMERIC(12,2)`（本就定点无损）；ORM 注解 `Mapped[Decimal]`；`_to_float→_to_decimal`；聚合用 `Decimal` 求和、比较用 Decimal；删除 `float()` 与 `round(2)` 兜底（Decimal 精确）；前端/对外契约/导入模板**全部不动**（仍是元）。同时按文档性质纪律，**把「本仓金额口径=元 Decimal（定点）」作为铁律第 4 条金额条款的显式豁免登记**（META 变更，需人工审核）。
- **收益**：直击真实风险源（Python float），精度安全由类型保证；**不动单位 → 不动前端、不动外部契约、不回填 37 列历史数据**；工作量与回归面显著小于 A（量级约 3~6 人日，主要在后端 upsert/聚合/对账）。
- **成本**：**不满足铁律「以分为单位（整数）」的字面要求**，需走 META 人工修订（把口径改为「金额用定点数，分整数 或 元 Decimal 二一并全仓统一，禁止二进制浮点」之类）；Pydantic/JSON 对 Decimal 需统一序列化为字符串或定点数，避免前端又拿到二进制浮点文本。
- **风险**：Decimal↔JSON 序列化若处理不当，前端可能收到 `0.30000000000000004` 文本，需在响应层统一 quantize(0.01) 后格式化。

> 说明：工单原列第三选项为「登记豁免维持现状」。**纯维持现状（什么都不改、只登记）不建议**——浮点风险源仍在。C′ 在其基础上加「Decimal 化」，才真正消除风险；若只求登记豁免而不 Decimal 化，等于把已知脆弱性正式背书，不采纳。

## 5. 若选 A，必须遵守的硬约束（实施单再展开，本单不写）

1. 入口元→分**禁用 float**：字符串经 `Decimal` 解析后 `int((d*100).quantize(1))`，或库内 `ROUND(元*100)`。
2. Alembic 单一 head；回填迁移过 `db_guard.assert_safe_to_destroy()`，生产显式 `--allow-real-db`，执行前备份，迁移自带 down。
3. 回填后批量核对：`新分 = ROUND(旧元*100)`，全 37 列零差异方可切读。
4. 对外 `external.py` 做版本化或边界分→元，避免破坏第三方契约。
5. 前端先**收敛所有绕过 formatMoney 的就地 toFixed/fmtMoney**，再把唯一 formatMoney 改为分→元，杜绝放大 100 倍。
6. `fee Numeric(12,4)`（4 位小数）与费率 `rate Numeric(8,4)` 需单独定口径（分只能表示 2 位小数；4 位小数金额无法用「分」整数表达，可能要「厘」或保留 Decimal）——**这是方案 A 的一个硬障碍**，反而是 C′ 的天然优势。

## 6. 建议（供决策，不代替拍板）

- 若立项动机是**审计/规范硬性要求「金额=分整数」** → 选 **A**，按「源表→宽表/投影→服务聚合→API/对外→前端」切片，进 B2/B5 排期，本批不实施。注意 §5.6 的 4 位小数问题需先解。
- 若动机是**消除浮点精度这一真实风险**（与 W4「埋雷面」定性一致）→ 推荐 **C′（Decimal 化 + META 豁免登记）**：以约 1/3 成本从类型层面根除浮点、不动外部契约与历史数据，且天然容纳 fee(12,4)。
- **B 不推荐**（本项目有发布窗口、无需零停机灰度，双写负担不划算）。
