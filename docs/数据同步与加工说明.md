## 一、数据同步链路总览

### 1.1 数据源与抓取方式

系统当前支持 5 个数据源，按 `fetch_mode` 分流到两条抓取链路：

| data_type | 名称 | base_url | fetch_mode | 抓取器 | 备注 |
|-----------|------|----------|-----------|--------|------|
| refund | 退费单管理 | https://wifi.cloud-cat.cn/bms | playwright | BmsFetcher | 浏览器自动化 |
| ticket | 服务请求管理 | https://support.cloud-cat.cn/bms | playwright | BmsFetcher | 浏览器自动化 |
| wallet | 提现操作记录 | https://support.cloud-cat.cn/bms | playwright | BmsFetcher | 浏览器自动化 |
| device_combo | 设备套餐 | https://support.cloud-cat.cn/bms | playwright | BmsFetcher | default_sync=False |
| cs_record | 智能助手处理记录 | http://ai-acc.cloud-cat.cn | **http** | ai_acc_fetcher | REST API，非浏览器 |

> `fetch_mode` 不在 `sync_source_configs` DB 表里，由 `BMS_DATA_SOURCES` 种子在配置读取时（`_row_to_config`）合并进来，用于 `bms_sync.sync_all` 分流。

### 1.2 抓取链路分流

`bms_sync.sync_all` 把任务按 `fetch_mode` 分两组：

- `fetch_mode == "http"` → `ai_acc_fetcher.fetch_one`（httpx，无浏览器）
- 其他（默认 `playwright`）→ `BmsFetcher.fetch_all`（共享一个 Playwright 浏览器实例）

两条链路最终都产出一个本地 xlsx 文件，统一走 `_auto_import`（`parse_file` → `load_dataframe` → `run_upsert`）入库。因此**所有数据源共用一套解析与加工口径**（列映射、类型转换、时区加工、去重策略），抓取方式的差异不渗透到导入层。

### 1.3 时间范围计算（v0.3.2 重构后）

| 触发方式 | 时间范围 | 实现 |
|---------|---------|------|
| 定时同步 | 当天 00:00 ~ now（东八区） | `bms_scheduler._do_scheduled_sync` 硬性限定 `today_start ~ now_cn` |
| 手动同步（未指定 range, 默认增量）| `上次成功同步 end_time` ~ 当前时间；若从未成功过或比今日 0 点早，则从**今日 0 点**起算 | `SyncTaskManager.compute_incremental_ranges` (查 `bms_sync_logs` 最近 SUCCESS 记录的 `time_end`) |
| 手动同步（用户指定自定义区间）| 调用方传入的精确区间 | 前端按 today/yesterday/本周/自定义等 UI 传 `time_ranges` + `force=true` 跳过冷却 |
| `/task/preflight` 返回值 | 三种组合字段：`busy` (有运行中任务)/`cooldown_remaining`(距上次成功剩余秒数)/`incremental_ranges`(`data_type→[start,end]`) | 供前端展示给用户，用户可确认后再调 `/task/submit` |

> **硬性约束**：
> 1. 定时同步必须显式限定到当天数据，不允许同步过多历史数据。每次定时覆盖当天 0 点至今，upsert 幂等不产生重复，反而能补回上次失败漏掉的数据。
> 2. 手动同步有 5 分钟冷却期 (`DEFAULT_COOLDOWN_SECONDS = 300`) — 上次成功结束到本次开始不足 5 分钟的，非 `force=true` 一律拒绝，避免无意义地频繁拉取服务器。
> 3. 任何时刻**最多一个同步任务在执行** — 由 `SyncTaskManager._lock`（全局 asyncio 互斥锁）保证：手动/定时无论谁先拿到锁，另一路都会抛 `RuntimeError("当前有同步任务正在执行…请等待其完成")`。

## 二、ai-acc 智能助手处理记录接入（cs_record）

### 2.1 为何走 HTTP 而非 Playwright

ai-acc 平台提供标准 REST API（登录 + 导出），无需浏览器自动化即可完成抓取，相比 Playwright：

- 无浏览器进程开销，启动快、资源占用低
- 无 1 分钟操作间隔限制（BMS 系统有此限制）
- 无页面 DOM 变更脆弱性
- 适合服务器无人值守定时同步

### 2.2 接口契约

**登录**：`POST {base_url}/ai-acc/portal/v1/auth/login`
- body: `{"username":"...","password":"..."}`
- response: `{"token":"...","userId":"...","username":"..."}`
- ⚠️ **token 在 JSON 顶层**，不在 `data` 字段下——与 BMS 风格 `{data:{token}}` 不同。`_login` 同时检查 `data.token` 与顶层 `token` 兼容两种风格。
- 登录同时下发 session cookie，httpx 共享 client 自动保持。

**导出**：`GET {base_url}/ai-acc/cs/v1/assistant/handleRecord/export`
- params: `createDateStart=YYYY-MM-DD HH:mm:ss & createDateEnd=YYYY-MM-DD HH:mm:ss`
- auth: `Authorization: Bearer {token}` + session cookie
- response: xlsx 文件流（`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`）
- ⚠️ 用户提供的 URL `/admin/assistant/handle-record-export` 是前端路由，不是 API 端点。

### 2.3 非文件流识别

导出接口在业务异常时返回 JSON 而非文件流，典型场景：

```json
{"code":"500","message":"操作时间范围不能超过7天","timestamp":1785459901135}
```

`_export_chunk` 检查 `Content-Type`，含 `json` 则抛异常（带响应体前 300 字符），避免把错误 JSON 当 xlsx 解析。

## 三、7 天时间范围分片

### 3.1 限制规则

ai-acc 导出接口限制单次时间范围**不得超过 7 天**：

- 正好 7 天：允许（HTTP 200）
- 超过 7 天：拒绝（返回上述 JSON 错误）

### 3.2 分片实现

`ai_acc_fetcher._chunk_time_range` 把 `[start, end]` 切成若干 ≤7 天的连续子区间：

```python
def _chunk_time_range(start, end, max_days=7):
    chunks = []
    cur = start
    step = timedelta(days=max_days)
    while cur < end:
        chunk_end = min(cur + step, end)
        chunks.append((cur, chunk_end))
        cur = chunk_end
    return chunks
```

- 子区间**边界相接**（`chunk_i.end == chunk_{i+1}.start`）
- API 端点 `inclusive`，边界秒的记录可能在两片中都出现 → 合并时 `drop_duplicates()` 去重

### 3.3 合并实现

逐片 GET → `pd.read_excel(BytesIO(content), dtype=str, engine="openpyxl")` 读为 DataFrame → `pd.concat` 合并 → `drop_duplicates()`：

```python
frames = []
for cs, ce in chunks:
    content = await _export_chunk(...)
    df = pd.read_excel(BytesIO(content), dtype=str, engine="openpyxl")
    frames.append(df)
merged = pd.concat(frames, ignore_index=True).drop_duplicates()
```

- **`dtype=str`**：与 `data_parser` 解析口径一致（全文本读入，由 upsert 层做类型转换），避免数值/日期列在合并时被 pandas 推断错类型。
- 合并后写入单个 xlsx（`openpyxl`，单行表头 + 全文本），文件名 `ai_acc_{data_type}_{ts}.xlsx`，落 `uploads/{YYYY-MM}/`。

### 3.4 验证

14 天范围（2 片）E2E 测试：合并文件 69015 行，内部 0 重复，边界 0 重复。已清理测试数据。

## 四、时区加工（关键 bug 修复）

### 4.1 问题

运营平台（BMS CSV / ai-acc xlsx）导出的时间字段为 **naive 北京时间字符串**（无时区标识）。原 `upsert._to_datetime` 用 `pd.to_datetime` 返回 naive datetime，存入 `DateTime(timezone=True)` 列时，因 DB 时区为 `Etc/UTC`，naive 值被当 UTC 解释，导致按北京显示时**偏后 8 小时**。

**复现**：CSV 原始 `2026-07-30 22:32:00` 存为 `22:32+00` UTC，前端按北京显示为 `2026-07-31 06:32:00`（次日）。

### 4.2 修复

`upsert._to_datetime` 把 naive 视为北京时间（UTC+8）→ `tz_localize(_TZ_CN).tz_convert(utc)` 后再存；aware datetime 原样返回：

```python
_TZ_CN = timezone(timedelta(hours=8))

def _to_datetime(val):
    if isinstance(val, datetime):
        if val.tzinfo is None:
            return val.replace(tzinfo=_TZ_CN).astimezone(timezone.utc)
        return val
    result = pd.to_datetime(val)
    if result.tzinfo is None:
        result = result.tz_localize(_TZ_CN).tz_convert(timezone.utc)
    return result.to_pydatetime()
```

- 影响所有 BMS/ai-acc 导入路径（手动上传、一键同步、定时同步、Playwright/HTTP 两条链路），因为统一走 `upsert` 层。
- 纯日期字段（如 `complaint_date`）迁移后按北京显示 `00:00`（日期不变）。
- 系统内部表（`incidents`/`measures`/`reports` 等服务器生成 UTC 时间）未动。

### 4.3 存量数据迁移

修复代码只影响**新写入**数据，存量 naive-当-UTC 的数据需一次性 SQL 迁移。对 7 张有数据的业务表执行 `col - INTERVAL '8 hours'`：

| 表 | 迁移行数 |
|----|---------|
| wallet_withdrawals | 9653 |
| service_tickets | 18706 |
| refunds | 42944 |
| cs_records | 70227 |
| device_combos | 44672 |
| external_complaints | 1312 |
| card_complaints | 720 |
| merchant_refunds | 0（空表，跳过） |

**验证**：wallet 记录迁移后显示 `2026-07-30 22:32:00` 北京 = CSV 原始值；wallet 小时分布回归业务时段（不再凌晨聚集）。

### 4.4 后续保障

代码已编译部署，**未来所有同步路径**（手动上传 / 一键同步 / 定时同步 8·12·16·20·24 点 / BMS / ai-acc）自动按北京时间 → UTC 转换，无需额外操作。

## 五、去重策略（pk_strategy）

### 5.1 三种策略

各业务表按是否有天然唯一键采用不同入库策略，由 `upsert_*.py` 内部分流：

| 策略 | 实现 | 适用表 |
|------|------|--------|
| **upsert**（主键去重更新） | `pg_insert.on_conflict_do_update`，已存在则更新非主键字段 | refunds(refund_no)、tickets(ticket_no)、merchant_refunds(wx_refund_no)、merchants(sub_name)、device_combos(recharge_order_no)、external_complaints(有 complaint_no 的部分) |
| **none**（无主键插入） | `pg_insert.on_conflict_do_nothing` 兜底，不去重 | wallet、cs_record、card_complaint、external_complaints(无 complaint_no 的部分) |
| **fallback 主键** | 无天然主键时构造稳定合成主键，再走 upsert | device_combos 初始套餐 |

### 5.2 cs_record 为何不去重

`cs_record`（智能助手处理记录）**无天然唯一键**：

- 同设备同时间可多次接待（业务上合法）
- 导出表无单号/ID 列
- 即使用 (device_sn, operation_time) 组合也无法保证唯一（同秒多次接待）

因此 `upsert_cs_records` 走 `on_conflict_do_nothing`，**不去重**。带来的影响：

- ✅ 正常增量同步（定时用 `last_end_time` 非重叠区间）：无重复
- ⚠️ 手动重同步**重叠范围**：会产生重复行（需人工避免重叠，或后续提供去重工具）

### 5.3 device_combo fallback 主键

初始套餐（免费赠送/体验套餐）在 BMS 导出时无充值订单号，此前被主键非空校验跳过导致缺失。现生成稳定 fallback 主键：

```
INIT::{device_sn}::{package_name}::{start_date}
```

- `INIT::` 前缀与真实订单号（BR/WX/SP 开头）隔离，绝不冲突
- `(device_sn, package_name, start_date)` 组合唯一，保证多次增量同步幂等（命中 `on_conflict_do_update`）
- `device_sn` 缺失时无法构造稳定唯一键，才报错跳过（安全网，正常初始套餐不触发）

### 5.4 external_complaints 混合策略

投诉编号有则走 upsert（96%），无编号的行（~3%）走 `on_conflict_do_nothing` 插入（与 cs_record 一致，重复导入会累计）。投诉编号单元格含 `\n` 前缀，导入时剥离。

### 5.5 通用 upsert 执行器

`_execute_upsert` 先查已存在主键数量再执行 `on_conflict_do_update`，以精确区分 insert/update 计数。同批次内重复主键会被去重（保留最后一条，符合"后到覆盖"语义），避免 `ON CONFLICT affect row a second time` 错误。

## 六、凭证管理

### 6.1 加密存储

各数据源账号密码独立配置，存于 `sync_source_configs` 表，用 Fernet 加密（`app/core/crypto.py`）：

- 启动时 `ensure_sync_sources_registered` 幂等 seed：缺失的源用 `.env` 的 `BMS_USERNAME`/`BMS_PASSWORD` 加密灌入；已存在的源不覆盖（保留用户在 UI 的编辑）
- 运行时 `get_sync_source_config` 解密返回给 fetcher
- API `list_sync_source_configs` 返回掩码（`has_credentials` 布尔），不泄露明文

### 6.2 ⚠️ 加密密钥变更影响

**修改 `.env` 的 `CONFIG_ENCRYPTION_KEY` 或 `JWT_SECRET_KEY` 会使现有 `sync_source_configs` 凭证解密失败**：

- 现象：解密失败后系统把密文当作用户名发送给 BMS，BMS 返回"用户密码错误"
- 修复：在「系统管理 - 同步设置」页重新填写各源账号密码（PUT `/api/v1/system/sync-sources/{data_type}`），重新加密入库
- 预防：变更加密密钥后，**所有数据源凭证必须重新写一次**

### 6.3 凭证来源优先级

1. DB `sync_source_configs` 表（解密后）—— 运行时主用
2. `.env` `BMS_USERNAME`/`BMS_PASSWORD` —— 仅 seed 初始值 / DB 缺失时回退

## 七、定时同步调度

### 7.1 调度规则

- 定时时刻（东八区）：`00:00, 08:00, 12:00, 16:00, 20:00` 每天 5 次
- 触发窗口：每分钟检查，只在定时小时的前 5 分钟内触发（防止错过）
- 同一小时去重：`_last_run_hour` 字典防止同一小时重复执行
- 仅同步 `default_sync=True` 的源（`DEFAULT_SYNC_TYPES`）

### 7.2 启动前置检查

`_default_sources_have_credentials` 检查默认同步的源是否都已配置凭证，未配置则跳过本次定时并告警（无人值守必须预设）。

### 7.3 时间范围硬约束

定时同步强制 `time_ranges = {dt: (today_start, now_cn)}`，**不允许同步历史数据**。理由：

- upsert 幂等不会产生重复
- 覆盖当天 0 点至今能补回上次失败漏掉的数据
- 防止无人值守时误同步过多历史数据拖垮系统

### 7.4 与 SyncTaskManager 共享全局互斥锁 (v0.3.2)

调度器现在不直接跑 `sync_all_data`，而是把任务提交给 `SyncTaskManager.submit(trigger_type='scheduled'…)`：

- **效果**：若此时用户正手动同步，调度器拿不到锁会立即抛错跳过本小时（日志记录 `scheduler task skipped: 有 xxx 触发的任务在执行`），不会阻塞。
- **反方向也保护**：若定时正在执行，用户点「开始同步」也会被后端拒绝并提示"当前有定时任务在执行"。
- 冷却对 `scheduled` 触发无效（定时本就按 4h+ 间隔运行，无需再叠冷却）。

## 八、同步任务管理：SyncTaskManager（v0.3.2 新增）

### 8.1 设计背景与目标

单后端单实例部署 + 长耗时抓取（BMS playwright 登录+导出 4~5 张表通常 3~8 分钟，下载到本地与导入到 DB 合计又数分钟）下，原实现存在几类典型问题：

| 问题 | 用户表现 | 解决方式 |
|------|---------|---------|
| 重复发起 | 用户点击「同步」后 UI 无进度反馈，超时后再点，会在后台同时开两个浏览器，BMS 同账号多 session 被踢下线 | 全局 `asyncio.Lock` 互斥锁 + 前端提交后**不再阻塞**（`taskSubmit` 返回 task_id → 前端轮询进度） |
| 冷却不足 | 用户 30 秒内点两次，其实服务器数据一分钟内并无差异 → 白白浪费抓取配额 | 上次成功结束后 5 分钟内，非 `force=true` 一律拒绝 |
| 无增量语义 | 每次「一键同步」都默认拉今日 0 点，重复抓取白天相同记录 → 浪费服务器流量与配额 | `compute_incremental_ranges` 查 `bms_sync_logs` 最近 SUCCESS 记录的 `time_end`，下次就从那个时间起 |
| 无进度可见 | 点按钮后前端长时间转圈 / 超时，后端日志只能看 shell，无法在 UI 内反馈进度 | 每个任务一个 `SyncTaskProgress`，实时记录阶段 + 子步骤进度，`taskStatus` 接口可轮询 |

### 8.2 核心数据结构

`SyncTask` (一个任务对象，内存常驻直到被覆盖) + `SyncTaskProgress`：
```python
@dataclass
class SyncTaskProgress:
    stage: str                          # preflight / fetching / importing / done
    message: str = ""                   # 中文文案, 直接展示
    current_step: int = 0
    total_steps: int = 0
    sub_progress: float = 0.0           # 0.0 ~ 1.0, 用于当前步骤内细分进度
    sub_message: str = ""
    results: list = field(default_factory=list)  # 每个 data_type 完成后立即写入
    started_at: datetime = field(default_factory=lambda: datetime.now(timezone.utc))
    finished_at: Optional[datetime] = None
    status: str = "running"             # running / success / failed
    error: Optional[str] = None
```

进度回调签名：`on_progress(stage, message, *, cur, total, sub=0.0, sub_msg="")` — 所有 fetcher/sync 代码都已接入这个回调，下载一个文件 / 导入一张表后立刻推进前端可见进度。

### 8.3 新增异步 API（`/api/v1/fetch/*`）

| 路由 | 方法 | 用途 |
|------|------|------|
| `/task/preflight` | POST | 提交前检查：返回 `{ busy, current_task, cooldown_remaining, cooldown_total, incremental_ranges }`。前端可据此显示"当前有任务执行/距离上次仅过 41 秒/本次增量范围 14:23 起"等提示。 |
| `/task/submit` | POST | **异步提交**，校验锁+冷却后立即返回 `{task_id, message}`，然后在后台 `asyncio.create_task` 里执行真正的同步（不阻塞 HTTP 响应, 避免超时）。 |
| `/task/status` | GET `?task_id=sync_xxx` | 轮询进度（每秒一次即可），返回完整 `SyncTaskProgress`。前端据此渲染进度条 + 各步骤卡片。 |
| `/sync-all` | POST | 兼容旧前端，内部调用 submit。若 submit 失败则回落到 legacy 阻塞式同步，保证行为一致。 |

> **前端调用推荐流程**：先点「开始同步」→ 前端调用 `/task/preflight` → UI 提示用户本次将做什么 → 确认后调用 `/task/submit` → 拿到 task_id 后按 1s 间隔轮询 `/task/status` → finished 后 toast 成功 + 刷新当前页图表；中途可任意关闭页面不影响后台执行（除非重启后端进程）。

## 九、BMS 同 base_url 复用浏览器 Context（v0.3.2 优化）

### 9.1 问题来源

5 张 BMS 表里，`refund` 的 base_url 是 `wifi.cloud-cat.cn`，其余 `ticket`/`wallet`/`device_combo`/`cs_record_bms` 都在 `support.cloud-cat.cn`。若每抓一张表都**新 Context + 新登录**，就会发生：

- BMS 登录滑块偶尔触发，人工 1 分钟限制也在"每次登录"上叠加 → 总耗时成倍增加
- 同一 IP 反复登录触发风控 → 导出接口变慢

### 9.2 优化：按 base_url 分组共享登录后的 Context

`BmsFetcher.fetch_all()` 内部先按 `base_url` 对 tasks 分组，组内**共用一个 Playwright `BrowserContext`**：

1. 组首任务第一次去该 URL 时走完整登录（含滑块 → 等待登录成功 Cookie）
2. 登录成功后 `already_logged_in = True`
3. 组内后续任务访问时，带上已有 Cookie / 会话 → BMS 后台直接放行，**不再重登**
4. 组内两个任务之间仍遵守 BMS 官方 1 分钟「两次下载间隔」限制（同一 web 间隔超过 1 分钟即可，登录复用后下载等待语义不变）
5. 整组结束后 `finally: context.close()` 保证会话释放

实测效果（4 张 support 域 + 1 张 wifi 域 = 两组）：**登录次数从 5 次降为 2 次**，端到端耗时平均缩短 40%~60%。

## 十、抓取与导入**并行化**（v0.3.2 优化）

### 10.1 关键点：下载等待 1 分钟 vs DB 导入可并发

BMS/ai-acc 对「两次导出请求的间隔」有 1 分钟下限（同一 Web），但这个 1 分钟等待发生在**抓取器**（BmsFetcher）内部，跟本地的 DB 写入是无关的。以前链路是串行：

```
抓 refund → 等待间隔 60s → 抓 ticket → 等待 60s → 抓 wallet → 等待 → …
全部抓完后 → 导入 refund → 导入 ticket → 导入 wallet → …
```

等待间隔期间 CPU/DB 都是空转。

### 10.2 优化后：每个 `FetchResult` 就绪立刻启动独立导入线程

```python
# bms_sync._sync_all_async_runner 的 progress 包装回调
async def on_progress_with_import(stage, message, **kw):
    if stage == "fetch_done":
        # 单个 data_type 刚下载到本地 xlsx, 立刻扔线程池开始导入, 不阻塞下一次抓取
        asyncio.create_task(asyncio.to_thread(_do_import, fr))
    await orig_progress(...)  # 继续调用上层回调推进整体进度条

# 所有抓取跑完后, gather 等待所有导入线程结束
await asyncio.gather(*import_pending_tasks, return_exceptions=True)
```

如此**抓取与导入重叠**，总体端到端耗时可以进一步压缩 30%~40%（尤其表数多、单表体积大时效果更显著）。

> 不破坏原有的 1 分钟访问约束：互斥只在"抓取请求之间"，导入是本地写库，跟抓取互不阻塞。
