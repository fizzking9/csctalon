## 二、角色与权限体系（5 级）

### 2.1 五级角色定义
| 角色 | 数据范围 | 可见分析/看板 | 核心可操作 |
|------|---------|--------------|-----------|
| 系统管理员 | 全量 | 全部 | 系统配置、用户/角色、数据源/同步、全模块读写、删除 |
| 主管 | 全部组 + 全部专项 | 全部决策看板/报告/周报/措施/绩效 | 审核（发票报销、政策发布）、登记异常、排班管理 |
| 专项组长 | 本专项（含跨组该专项人员） | 本专项的退款挽回/投诉/人员成功率 | 本专项标签、本专项政策、登记异常、本组排班 |
| 专员 | 本人 + 被指派专项 | 本人接待/退款挽回/投诉数据 | 登记异常/发票、执行被指派事项、提交报销 |
| 普通客服 | 仅本人 | 本人工作台、本人接待、待读政策 | 只读（政策/规范），提交发票报销 |

### 2.2 角色 × 模块权限矩阵
| 模块 | 系统管理员 | 主管 | 专项组长 | 专员 | 普通客服 |
|------|-----------|------|---------|------|---------|
| 排班 | 读写删 | 读写（全员） | 写本组+读本专项 | 读本人 | 读本人 |
| 异常事故 | 读写删+复盘 | 登记/跟进/复盘 | 登记/跟进（本专项相关） | 登记/跟进（本人） | 只读（知情） |
| 设备专项标签 | 读写删+批量导入 | 读写+批量导入 | 读写（本专项标签） | 读 | 读（接待提示） |
| 政策措施 | 发布/废止/删 | 发布/审核 | 起草（本专项） | 读 | 读（必读） |
| 知识库/话术 | 读写删 | 读写 | 写本专项+读 | 读 | 读（检索） |
| 发票登记 | 全量+审核 | 审核/导出 | 提交本人 | 提交本人 | 提交本人 |
| 投诉分析（统计） | 全量 | 全部 | 本专项 | 本人 | 无 |
| 投诉审计 | 全量+审计结论 | 审计+结论 | 本专项审计 | 只读 | 无 |
| 退款挽回 | 全量 | 全部 | 本专项 | 本人 | 无 |
| 统一待办中心 | 全量 | 本部门 | 本专项+本人 | 本人 | 本人 |
| 系统配置/数据源 | 读写 | 无 | 无 | 无 | 无 |

### 2.3 与现有模型的重构映射
- 现有 `users.isAdmin` / `users.isManager` → 重构为 `users.role` 枚举（admin / supervisor / specialty_lead / specialist / cs）。
- **专项组长** = 业务专项负责人，走 `specialty_leadership_history`（SCD Type 2）判定「本专项」。
- **专员** = `person_specialty_assignments` 被指派专项成员；**普通客服** = 无专项指派的一线客服。
- 数据范围过滤统一走「person_id → 专项/分组归属（SCD 按时间切面）」+「本人」两级，在服务层统一拦截，避免各接口各写一套。
- 过渡期 `isManager` 双写，兼容现有决策看板可见性。

## 四、逐项设计（7 个功能模块）

### 4.1 排班管理（全新 · 企业微信对接 · 优先级 P0）

> 关键决策（§十三 D7/D7a/D7b）：排班已在企业微信做，**以企微为源头对接同步，系统不重复手工排班**；系统内保留「顶班/请假/调班」微调标记；对接方式**先探测企微排班/考勤 API，有则同步，无则导出导入**。

**4.1.1 数据源头与同步**
- 复用现有 SCRM 同步设施（§19），注册新数据源类型 `wecom_schedule`（排班/班次）、`wecom_attendance`（考勤打卡）。
- 先探测企业微信「考勤打卡」API 是否开放排班计划/打卡记录查询；有则 API 增量同步，无则企微后台导出 Excel 导入（复用 xlsx_import）。
- 同步策略与 SCRM 一致：增量同步 + 全局互斥锁 + 冷却期 + 凭证 Fernet 加密。

**4.1.2 班次模板 `shift_templates`**
- 预设两班：`早班 08:00–16:00`、`晚班 16:00–24:00`；管理员可增删改（未来加午班/跨天）。
- 字段：班次名、起止时间、是否跨天、颜色、排序、是否启用。若企微排班规则可拉取则对齐映射。

**4.1.3 排班事实表 `schedules`**
- 粒度 `人 × 日`，唯一约束 `(person_id, schedule_date)`。
- 字段：person_id、schedule_date、shift_template_id、start_time/end_time（冗余）、status（正常/顶班/请假/调班）、note、source（wecom_api/wecom_export/manual）、created_by。
- **微调**：`status` + `note` 轻量标记（不引入审批流）。

**4.1.4 考勤打卡表 `attendance`（新增）**
- 从企微同步打卡记录：person_id、attendance_date、check_in_at、check_out_at、source、raw。
- 用于「实际在班」判定。

**4.1.5 排班 × 实际接待关联展示（四源对照）**
| 数据 | 回答的问题 |
|------|-----------|
| 排班（企微） | 计划谁该上班 |
| 考勤打卡（企微） | 实际谁来了 |
| 接待记录（cs_records/scrm_sessions） | 实际谁在干活、干多少 |
| 工单（service_tickets） | 实际处理了什么 |

- 输出对照：排班人数 vs 实际在班人数、每班接待量/人均、无排班但有接待（顶班/漏排）、有排班但无接待（请假/脱岗）。
- 周/月视图日历展示 + 按组批量查看；时间口径复用 [数据时间字段使用规范.md](standards/数据时间字段使用规范.md)。

### 4.2 异常事故登记（增强 · P0）

**4.2.1 增强字段（incidents 增列）**
| 字段 | 说明 |
|------|------|
| `category` | 来源/类型：生产/运营/商务部/店铺/系统平台开发/其他服务商（可配置字典，两级：部门+子类） |
| `department` | 涉及部门（首版单选，JSONB 预留多选） |
| `severity` | 严重程度：高/中/低 |
| `resolved_at` / `closed_at` | 解决/闭环时间 |
| `is_closed` | 是否闭环（与状态解耦） |

**4.2.2 跟进时间线 `incident_followups`**：id、incident_id、author_id、content、status_change、created_at（复用跟进交互）。

**4.2.3 极简录入**：必填仅 3 项（事项名+涉及部门+影响），其余折叠；快捷模板/快捷词；一键转待办/转措施。

### 4.3 设备专项标签（增强 · P0）

- 批量 SN 导入：`device_tag_batches` 批次表，粘贴清单/Excel/CSV，回执成功/已存在/无效。
- 标签生命周期：`device_tag_rel` +status/expired_at，支持撤销/失效，统计按时间切面看「当时标签」。
- 接待关联展示：设备详情/审计时序/工单详情高亮标签 + 处理建议。
- 统计分析：各标签 SN 数、趋势、与退款/投诉交叉（复用分析视图引擎或扩展 refund_wide）。

### 4.4 政策措施登记（增强+收敛 · P1）

**边界收敛**：政策措施主载体 = `policies`；`strategy_docs` 保留已读回执逐步并入；`measures` 保持管理措施+到期回看。

**新增能力（policies 增列）**：
| 能力 | 字段 |
|------|------|
| 替代关系 | `replaces_policy_id`（self-FK）+ `replaced_by_policy_id`（冗余） |
| 主题/关联 | `topic_tags JSONB`（首版 JSONB，量大再字典化） |
| 示意图 | `diagram_urls JSONB`（复用贴图存储） |
| 便捷查询 | 关键词/主题/启用/废止/状态多维筛选 + 时间轴 + 替代链可视化 |

首版纯文字 + 附件/示意图。

### 4.5 发票登记（全新 · P1）

**识别链路**：上传（二维码图/PDF/图片）→ 二维码本地解码（全电发票标准结构化数据）→ PDF/图片本地 OCR 兜底 → 写入 expense_invoices → 人工核对 → 归入报销单 → 导出。

**数据模型**：`expense_invoices`（ocr_result JSONB + confidence + status 待识别/已识别/待核对/已入账/已报销）、`reimbursements`（审核状态机）、`reimbursement_items`。**不关联业务对象**（纯报销流水）。

**导出**：报销清单 + 发票清单 Excel（复用 utils/excel.py）。报销流程：提交→主管审核→报销。

### 4.6 投诉分析（增强 · P0）

**单个投诉审计**：设备 SN（复用 audit_timeline 全时序）+ 涉及人员 + 接待过程 + 聊天记录（截图附件+按需拉取）+ 归因（归因字典）+ 审计结论（复用 audit_notes，新增「投诉审计」来源）。

**三源统一统计**：专项页三 Tab（内部/商户号/外部），每源含趋势/归因类型/接待人员排行/结案率（编排已有视图）。

> **三源归类口径(2026-09-01 确认)**：内部=工单商品/服务投诉；商户号=工单微信投诉（仅工单）；外部=工单平台类（12315/工信部/消协/监督局等）+ 315外部投诉 + 卡商群投诉。

**扩展**：归因类型可配置；挂载自定义视图。

### 4.7 退款挽回（已基本完成 · P2）

- 口径确认：分类 = 现有 4 类 problem_type（不想用了/充值错误/设备故障/服务原因）。
- 小增强：补「4 类 × 成功率」交叉视图；其余不动。

## 五、统一工作流设计

> 核心：部门软件第一屏应「**推着人走**」，而非「人到处找事」。

### 5.1 统一待办中心（Phase A 第一优先）
- 汇聚：待办事项、待跟进异常、待回看措施、待审发票/报销、待读政策、被指派工单。
- 每条带来源 + 优先级 + 截止 + 一键跳转；按角色过滤（§2.2）。

### 5.2 通知/提醒中心
- 站内信 + 角标（局域网内），内容：到期提醒、异常登记通知、政策发布通知、审计指派。
- 新增 `notifications` 表：recipient_id、type、title、content、ref_type/ref_id、is_read、created_at。

### 5.3 状态机统一
- 各模块状态流转统一语义 + 颜色（§六 色板），流转落时间线，不各写一套。

## 六、界面操作逻辑与交互规范（横切硬规范）

> 定位：所有新页面照模板拼装、老页面渐进对齐，目标是「不培训就会用」。

### 6.1 四大交互范式
| 范式 | 标准结构 | 适用 |
|------|---------|------|
| 列表页 | FilterBar 筛选 + 批量操作 + 表格 + 分页 + 导出 + 右上角主操作按钮 | 异常/标签/发票/政策/排班 |
| 详情页 | 面包屑 + 元信息头 + 主体 + 侧栏（时间线/批注） | 异常/投诉审计/发票/政策 |
| 表单页 | 必填 ≤3 项置顶 + 其余折叠「更多」+ 保存草稿/提交 + 未保存离开提醒 | 所有登记 |
| 导入页 | 模板下载 + 上传 + 预览复核 + 确认（回执明细） | 标签批量/排班/发票 |

### 6.2 状态语义色板（全局统一）
| 状态族 | 颜色 | 语义 |
|--------|------|------|
| 待处理/待审/待回看 | 黄 | 需要动作 |
| 进行中/执行中 | 蓝 | 已启动 |
| 已完成/生效/闭环 | 绿 | 结束 |
| 异常/失效/超期 | 红 | 需关注 |
| 归档/废止 | 灰 | 只读留存 |

### 6.3 角色化工作台（五角色差异化首页）
| 角色 | 工作台第一屏 |
|------|-------------|
| 系统管理员 | 全局 KPI + 系统告警 + 待审队列 |
| 主管 | 全局 KPI + 例外清单（异常/超期/待回看）+ 待审（发票/政策） |
| 专项组长 | 本专项 KPI + 本专项待办 + 本组排班 |
| 专员 | 本人待办 + 本人数据 + 被指派专项 |
| 普通客服 | 待读政策 + 本人接待 + 提交发票入口 |

### 6.4 防错与恢复
删除二次确认、关键操作落日志、导入预览、未保存离开提醒。组件复用遵循 §16 看板组件化（KpiCard/FilterBar/ChartCard）。

## 七、知识库 / 话术库（全新 · P1）

> 决策（§十三 D1/D2）：做，与政策登记打通；包含纯文字标准话术（客服接待时复制）。

### 7.1 定位
- 「政策」= 管理发布（面向全员/客服的规范），落 `policies`。
- 「话术/知识」= 一线检索（问题→标准处理流程/标准话术），落 `kb_articles`。
- 两者通过 `kb_articles.related_policy_id` 打通，前端「知识库」统一检索两个视图。

### 7.2 数据模型 `kb_articles`
| 字段 | 说明 |
|------|------|
| id PK | |
| title | 条目标题（如「退款不想用了怎么回复」） |
| category | 分类（退款/投诉/套餐/网络/通用…可配置） |
| question | 常见问题/触发场景 |
| answer | 标准处理流程 / 标准话术（首版纯文本 Markdown） |
| tags | 标签 JSONB |
| related_policy_id | 关联政策（可空） |
| status | 草稿/已发布/已归档 |
| view_count | 检索次数 |
| created_by / created_at | |

### 7.3 能力
- 面向一线：关键词/分类检索 + 高亮 + 复制话术。
- 与政策打通：话术条目挂政策，政策更新时提示关联话术同步更新。
- 首版纯文字；流程图/富媒体后续加（§十三 D2）。

## 八、预警中心 + 运营补充模块

> 决策（§十三 D3/D4/D5/D6）：预警中心 Phase B 起；周报一键生成；跨部门协作落地 Phase C；数据质量先占位。

### 8.1 预警中心（P1 · Phase B 起）
- **异常自动识别**（§12.1 占位落地）：某时段工单/投诉量超基线 N 倍 → 自动标记疑似异常 → 触发登记（人从"登记员"变"确认员"）。
- **工单积压预警**：待处理工单超阈值。
- **退款激增预警**：退款量/金额环比异常。
- 数据模型：`alert_rules`（规则：name/type/condition JSONB/threshold/enabled）+ `alerts`（记录：rule_id/title/level/detail/occurred_at/status 待确认/已确认/已忽略）。
- 预警进通知中心 + 待办中心。

### 8.2 周报一键生成（P1）
- 复用 `weekly_reports` + 10 项框架数据源映射（§12.4），自动填充各项数据快照，人只补结论。
- 砍掉周例会前的手工汇总。

### 8.3 跨部门协作 UpstreamTicket（P2 · Phase C）
- 落地 §12.5 设计：`upstream_tickets`（issue/upstream_dept/dispatched_at/responded_at/resolved_at/status/score）。
- 客服给上游打分（响应/解决率），推动上游改进。

### 8.4 数据质量看板（P2 · 先占位）
- 数据真实性识别规则（§11.6 占位）：异常数据模式识别，先留字段后扩充。

## 九、管理哲学：不过度管理原则（横切硬约束）

> 站在一线管理者角度：**系统是解决问题的，不是制造麻烦的**。以下 9 条为硬约束，违反即返工。

1. **能自动绝不手动**：数据从 BMS/SCRM/企微同步，标签批量导入，发票自动识别——人只做判断，不做搬运。
2. **录入 ≤30 秒**：任何登记动作超过 30 秒就没人做，数据必失真。
3. **把"写"变成"选"**：默认值 + 模板 + 快捷词 + 级联字典，减少自由文本。
4. **例外管理**：主管只看异常/超期/待办，正常数据不打扰（看板默认只突出例外）。
5. **自动提醒代替人工盯**：到期自动进队列，不靠人记、不靠人催。
6. **归因不归责**：数据真实的前提是不惩罚诚实（绩效只做汇总，不做扣分依据）。
7. **砍掉没人看的报表**：每张报表必须回答「谁看、看完做什么决策」，答不上就不上线。
8. **字段克制**：每个字段问一句「会不会被用起来」，不加"以后可能有用"的字段。
9. **闭环分级**：小事一句跟进，大事才走复盘→措施；不搞一刀切的流程。

## 十一、遗漏点与风险提示

1. **【企微排班/考勤 API 可用性】** 需先探测企业微信「考勤打卡」是否开放排班计划/打卡记录查询接口；若仅有打卡记录、无排班计划 API，则排班用导出导入、考勤用打卡记录反推实际在班。参照 §14.2「用户提供前端路由非 API 端点，接入前先 curl 探测」的经验。
2. **【聊天记录】** 投诉审计用截图附件 + 按需拉取（Phase D 增强单会话拉取接口），不阻塞首版。
3. **【发票 OCR 合规】** 本地二维码解码为主，PDF/图片 OCR 准确率有限，靠人工核对兜底，「待核对」状态要在 UI 醒目呈现。
4. **【政策措施三表重叠】** 扩展 policies；strategy_docs 并入需评估已读回执迁移成本（Phase C）。
5. **【设备专项标签生命周期/SCD】** 统计历史须按「当时标签」时间切面过滤。
6. **【排班与实际接待口径】** 实际在班 ≠ 有排班；容忍顶班/请假，展示区分而非一律判异常。
7. **【角色数据范围】** 专项组长/专员数据范围是横切改造重点，服务层统一拦截，避免各接口各写一套。
8. **【isManager 兼容】** 5 级角色重构过渡期双写 isManager，避免破坏现有决策看板。
9. **【组件复用】** 新页面遵循 §16 看板组件化，禁止重复内联样式。
10. **【菜单命名】** 「设备专项标签」与「专项任务」「业务专项」区分。
11. **【数据迁移幂等】** 新增表/增列幂等（_table_exists/_column_exists）。
12. **【知识库维护】** 话术/知识会过期，需「已发布/已归档」状态 + 定期清理，避免变成垃圾堆。
13. **【在线文档同步漂移】** 腾讯/WPS 在线文档列名/格式会被随手改漂移、多人编辑可能读到半成品、无历史版本；同步须做列结构校验 + 异常行提示 + 可降级（API→导出→复制粘贴），且只读不写回，避免双向同步冲突。

## 十三、数据源策略与在线文档对接（横切 · 已确认）

> 决策（§十四 ADR E1/E2/E3）：分场景混合策略 + 探测在线文档 API + 现状盘点（多数数据在腾讯/WPS 在线文档）。

### 13.1 核心原则
- **数据在哪儿产生、大家习惯在哪儿维护，系统就去适配，不逼人改习惯**（延伸 §九 原则 1「能自动绝不手动」）。
- 判断标准一句话：**需要结构化/版本化/闭环/审计的进系统；纯清单搬运的对接同步；写草稿的留在线文档、定稿进系统**。

### 13.2 分场景映射（结合现状盘点 E3）
| 数据 | 现状（在线文档） | 建议策略 |
|------|----------------|---------|
| SN 专项清单（清退/降速/异常） | 腾讯/WPS | **对接同步**（三层降级，见 13.3） |
| 异常事故记录 | 在线文档临时记 | **系统极简录入（≤30秒）** + 历史一次性批量导入 |
| 发票/报销清单 | 在线文档 | **系统上传识别**（二维码/PDF/图片）+ 历史清单 Excel 导入 |
| 周报/报告草稿 | 在线文档 | **系统一键生成 + 归档**；草稿可在线写、定稿进系统 |
| 政策/话术文档 | 在线文档草稿 | **在线写草稿 + 系统正式发布**（版本/审批/已读） |
| 措施跟进 | 在线文档 | **系统措施模块 + 跟进时间线**（已有）+ 历史批量导入 |

### 13.3 在线文档对接技术方案
- **三层降级**：① 腾讯/WPS 开放 API 同步（需企业版/开放平台账号 + 管理员授权）→ ② 定期导出 Excel 导入（复用 xlsx_import）→ ③ 复制粘贴。
- **先探测**（参照 §14.2「接入前先 curl 探测」经验）：确认腾讯文档/WPS 是否开放读表格 API、鉴权方式、个人版 vs 企业版限制。
- **同步前校验**：列结构校验 + 异常行提示 + 去重，防止在线文档「列名/格式被改漂移」「多人编辑半成品」污染系统。
- **历史数据迁移**：一次性批量导入（复用 xlsx_import + 预览复核工作流），不在线文档做长期双写。

### 13.4 落地约束
- 在线文档同步只做「读」不做「写回」；系统是分析的权威源，在线文档是录入入口之一。
- 若某类数据同步后仍需在在线文档维护（如 SN 清单），则在系统做「同步入口」页一键拉取，不做双向同步（避免冲突）。

- 流程：`wx.login()` 取 code → `POST /wechat/auth/code-login` → 已绑定直接签发 JWT；未绑定创建 pending 申请；`POST /wechat/auth/register` 补填资料；管理员在「用户管理 → 注册审批」Tab 审批（`GET /wechat/registrations/pending` + `POST /wechat/registrations/{id}/approve`），通过后自动创建 User、分配角色/分组并绑定 WechatAccount。
- 本地开发未配置 `WECHAT_APPID/WECHAT_SECRET` 时，`code` 退化为 `mock-` 前缀 openid。
- 迁移：`alembic` 版本 `w1x2y3z4a5b6`（幂等，`down_revision=c0d1e2f3a4b5`）。

### 16.2 移动端 H5 访问 + 采集触发

- **方案**：移动端用 H5 响应式（复用现有 Vue 前端，屏幕 <768px 走移动布局 + 精简菜单），手机浏览器打开域名即可，免 ICP 备案审核、免独立工程。**不采用微信小程序**。
- **移动端 MVP 仅开放 3 项**，其余菜单/功能隐藏，后续深挖再放开：

| 移动端功能 | 前端路由 | 权限 |
|---|---|---|
| 今日看板 | `/dashboards/today` | 按现有角色 |
| 运营看板 | `/dashboards/operation` | 按现有角色 |
| 数据采集（启动同步 + 进度/日志） | `/data/ingest` | 仅 admin |

- 数据采集在手机端可**完整操作**：触发 `incremental`/`today`、查看进度条与实时日志、查看失败源。
- 超级管理员在移动端同样可启动采集（与 Web 同源，非独立小程序入口）。
- 预留后端 `/miniapp/*`（summary/status/trigger）保留，供未来若切换微信生态时复用，不删除、不接入 H5 主路径。
- **实现状态（已落地）**：`MainLayout.vue` 增加 `isMobile` 检测（`matchMedia('(max-width:768px)')`），移动端隐藏侧边栏、改抽屉菜单（仅今日看板/运营看板/数据采集[admin] + 退出登录），并附带紧凑型 header/main 响应式样式。

### 16.3 菜单结构收敛：数据中心拆入「系统管理」

- 原「数据中心」主菜单下 6 项按性质拆分：
  - **系统管理（仅 admin）**：数据采集、视图构建器、视图清单（分析视图）、看板配置。
  - **业务功能**：设备审计、人员审计 —— 作为退款看板人员/设备分析的「时序」钻取页（隐藏入口），不再进入任何主菜单。
- 路由层已对应收紧：`data/ingest`、`analytics/builder`、`analytics/views`、`dashboards/designer` 增加 `admin` 守卫（前端 `meta.admin=true`），非 admin 访问重定向回首页。

### 16.4 数据采集并发优化（冷却期穿插其他数据源）

- `sync_task_manager` 新增 `submit_multi`：一次任务内通过 `asyncio.gather` 并发执行多个独立 runner，使 BMS 抓取冷却（服务端 1 分钟下载间隔）期间穿插 SCRM 抓取，缩短整轮同步耗时。
- `bms_scheduler` 定时同步由「BMS → SCRM 串行」改为「BMS/SCRM 并发 runner」，共用同一全局互斥锁与 progress 事件。
- 同步完成后统一失效 `today:*`/`analytics:*` 缓存，保证 Web 与移动端（H5）看板数据一致。
