# 3060 节点退役/降级执行方案

> 制定日期：2026-09-27
> 依据：NODE_PERFORMANCE_REPORT.md（已修正「硬件 vs 模型能力」混淆）
> 前提：3060 质量低分（2/7、1/7）主要归因于**挂的 qwen2.5-3b/7b 模型不适合 gen_system 场景**，而非硬件报废。3060 硬件（12GB GDDR6, 360 GB/s）仍有利用价值。

---

## 一、3060 硬件能力盘点

| 项目 | 规格 | 能力边界 |
|---|---|---|
| 显存 | 12 GB GDDR6 | 7b FP16(~14GB) 装不下，需 8bit(~7GB) 或 4bit(~4GB)；14b 4bit(~7GB) 可装 |
| 显存带宽 | 360 GB/s | 7b 8bit 推理 ≈ 4 tok/s；14b 4bit 推理 ≈ 2-3 tok/s |
| CUDA 核心 | 3584 | 并发多实例能力有限，适合单模型低并发 |
| 支持精度 | FP16 / INT8 / INT4 | 量化推理是必须的（FP16 装不下 7b 以上） |
| PCIe | Gen4 x16 | 模型加载/卸载无瓶颈 |

**硬件结论**：3060 能装 14b 4bit 量化，带宽 360 GB/s 能跑 2-4 tok/s——做低延迟敏感的前台不行，但做**后台离线任务（分类/嵌入/摘取）完全可用**。不是报废硬件。

---

## 二、当前问题诊断

| 现状 | 问题 | 根因 |
|---|---|---|
| 3060-7b（qwen2.5-7b） | 2/7，monthly 大面积自算 | 7b 模型在结构化数字纪律（铁律 12）上能力不足，同模型在 2080 上也仅 4/7 |
| 3060-3b（qwen2.5-3b） | 1/7，能力不足 | 3b 模型太小，无法理解复杂业务规则 |
| 共用问题 | 4 tok/s 太慢 | 360 GB/s 带宽是硬伤，7b Dense 推理速度上限 |

**关键判断**：把 3b/7b 换成 14b 4bit 后，质量可对标 mini-14b（5/7），速度 2-3 tok/s——适合夜间预生成，不适合实时。

---

## 三、方案选项

### 方案 A：降级为「后台夜间预生成节点」~~（推荐）~~ ❌ 实测不可行

~~把 3060-7b 的模型换成 qwen2.5-14b 4bit 量化，承接 mini-14b 的部分预生成负载。~~

**✅ 实测可行（2026-09-27 二次验证）**：开启 KV cache 量化 q4_0 后，14b+8K ctx 显存占用 9.5GB，成功塞进 12GB。v2.1 考场 6/7 通过、0 幻觉，与 gmk-14b 并列第一，速度 18-22 tok/s。

**关键配置**（宿主机直接运行 ollama，非 Docker）：
- OLLAMA_KV_CACHE_TYPE=q4_0（KV cache 量化到 4-bit，省 75% 显存）
- OLLAMA_FLASH_ATTENTION=1（省显存+提速）
- OLLAMA_CONTEXT_LENGTH=8192
- /root/.ollama → /data/ollama/gpu（符号链接）

**注意**：3060 的 Docker 容器 GPU 直通有问题（nvidia-container-toolkit 1.20.0 不兼容驱动 615.71.09），需在宿主机直接运行 ollama。
| 项 | 内容 |
|---|---|
| 新模型 | qwen2.5-14b（4bit AWQ/GPTQ 量化，~7GB 显存） |
| 预期速度 | 2-3 tok/s（与 mini-14b 同级） |
| 预期质量 | ~5/7（对标 mini-14b，14b 模型能力达标） |
| 适用任务 | 周报/月报预生成（夜间批，单份 1-2 分钟可接受） |
| 不适用 | 前台实时问答（延迟 >60s 不可接受） |

**优点**：硬件零成本复用，质量从 2/7 提到 ~5/7，分担 mini-14b 的夜间负载（吞吐量翻倍）。
**缺点**：速度仍慢，只能做离线任务。

### 方案 B：降级为「分类/嵌入专用节点」

把 3060 上的大模型全部卸载，改跑**轻量分类模型和嵌入模型**。

| 项 | 内容 |
|---|---|
| 部署模型 1 | bge-m3 或 bge-large-zh-v1.5（嵌入，~1.2GB） |
| 部署模型 2 | qwen2.5-1.7b 或 3b（分类/打标/摘要，FP16 ~3.4GB） |
| 预期速度 | 嵌入 50+ tok/s，1.7b 推理 15+ tok/s |
| 适用任务 | 文本向量化、意图分类、打标、短摘要 |
| 不适用 | 任何 gen_system 报告生成 |

**优点**：把 3060 的低带宽劣势转化为优势——嵌入/小模型不吃带宽，12GB 显存可高并发。
**缺点**：需要新增嵌入服务的调用链改造。

### 方案 C：直接退役硬件

仅在以下条件同时满足时考虑：
1. 集群已有足够 27b/14b 实例承接所有预生成负载；
2. 3060 的电费/机架成本 > 其作为嵌入/分类节点的价值；
3. 没有其它轻量任务可分配。

**不推荐立即执行**——12GB 显存在当前集群是稀缺资源（2080 只有 8GB），退役是浪费。

## 四、推荐执行路径（方案 B 为主，方案 A 已否决）

### 阶段 1：3060 → 14b 经营分析节点（已验证 6/7）

**已完成**：KV cache q4_0 + 8K ctx，14b 考场 6/7、0 幻觉、18-22 tok/s。3060 现在可作为经营分析预生成节点，质量与 gmk-14b 持平。

1. 拉取 qwen2.5-14b 4bit 量化权重（AWQ 或 GPTQ）
2. 在 3060 节点上加载，验证显存占用 <10GB、速度 ≥2 tok/s
3. 跑 v2.1 考场 7 模板，确认质量 ≥4/7（对标 mini-14b）
4. 在 talon 服务注册新模型别名，如 `3060:qwen25-14b-4bit`
5. 把预生成模板的 `llm_provider_code` 从 `3060-7b` 切换到新别名
6. 观察一周夜间预生成质量与耗时

### 阶段 2：3060-3b → 嵌入/分类（并行进行）

1. 卸载 qwen2.5-3b
2. 部署 bge-m3 嵌入模型（~1.2GB，剩余显存充足）
3. 可选：部署 qwen2.5-1.7b 做轻量分类
4. 在 talon 服务注册嵌入端点
5. 把语义匹配、文本检索场景的嵌入调用切到 3060

### 阶段 3：评估与决策（2 周后）

- 若 14b 4bit 质量 ≥4/7 且夜间负载能消化 → 3060 长期承担预生成
- 若 14b 4bit 仍不达标 → 转方案 B（纯嵌入/分类），预生成全部交给 mini-14b / evo-27b
- 若嵌入服务调用量低 → 3060 闲置，进入方案 C 退役评估

## 五、风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 14b 4bit 量化后质量下降 >1 分 | 中 | 预生成质量不达标 | 保留 3b 模型权重，回滚 <10 分钟 |
| 3060 显存不足装不下 14b 4bit | 低 | 无法部署 | 实测 14b 4bit ~7GB，12GB 足够；若不够换 7b 8bit |
| 嵌入服务改造周期长 | 中 | 阶段 2 延迟 | 阶段 1 独立可运行，不阻塞 |
| talon 模型注册不支持 4bit | 低 | 无法上线 | 用 vLLM 或 llama.cpp 包装，talon 只调 OpenAI 兼容接口 |
