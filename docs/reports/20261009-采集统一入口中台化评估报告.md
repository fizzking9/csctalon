## 一、现状盘点（代码实证）

### 1. ingest_service 中台雏形（`app/services/ingest_service.py`）

- `DATA_TYPE_REGISTRY`（L117-157）注册 18 类表格型数据源 + 投诉专用通道 + 手动退款专用通道；新增表格型数据源只需注册一行。
- `ingest_table()`（L163-201）为表格型统一入库：文件上传 / BMS 网页 / 共享文档 / 设备流量全走这里 → `upsert.run_upsert`（含去重键、拒绝行留痕 `ingest_rejected_rows`）。
- `ingest_complaints()`（L204-265）为投诉类专用入口（315/卡商两 sheet），去重走 `fingerprint.py` 单源指纹（#277 已收口）。

### 2. BMS 链路 —— 已实质中台化

`bms_sync.sync_all`（bms_sync.py L32-38）按 `fetch_mode` 分流 Playwright / HTTP 抓取，**最终统一汇入 `_auto_import()`（L224-299）→ `ingest_table()`**。抓取差异在「取数层」，入库层已统一。**BMS 侧无需再改。**

### 3. SCRM 链路 —— 平行体系，未入中台

- `scrm_sync_service.py`：OpenAPI / Playwright / Dual 三种抓取模式；操作员全量 upsert、会话增量拉取、转接明细拆分、质量指标计算（模块头 L1-20）。
- 任务调度**已共享**：`SyncTaskManager.submit()/submit_multi()`（sync_task_manager.py L254-357）全局互斥 + 冷却，BMS 与 SCRM 同锁（fetch.py L670-751）。
- 入库**未共享**：SCRM 直连自有 upsert，不经过 `ingest_table()`，因此去重键、拒绝行留痕、`DATA_TYPE_REGISTRY` 注册均不在中台口径内。
- ⚠️ 生产实证（#274 C6）：`scrm_sessions`/`scrm_operators`/`scrm_session_transfers`/`scrm_staff_profiles` 四表全空，`scrm_sync_logs` 末次记录 **2026-08-09**——SCRM 采集已停摆两个月。

### 4. 注册表三处双写（#223 遗留）

新增 `data_type` 需人工同步三处：`data_source_registry.py`（展示树 SEEDS）、`ingest_service.py`（DATA_TYPE_REGISTRY）、`upsert/_runner.py`（DISPATCH）（依据：20261007 深研报告 L197-199）。漂移风险同 A-20260910-004 菜单漂移。

### 5. 水位/缺口现状

`gap_records` + `gap_queue_service` 已有缺口台账，但仅覆盖 BMS 类数据源；各通道同步日志分散（`bms_sync_logs` / `complaint_sync_logs` / `manual_refund_sync_logs` / `scrm_sync_logs`），无统一水位视图。

## 二、方案对比

| 方案 | 内容 | 收益 | 代价/风险 |
|---|---|---|---|
| A. 完全收口 | SCRM 入库改走 ingest_table；三注册表合一；统一水位 | 口径单源 | SCRM 是「会话流 + 操作员 + 转拆 + 质量计算」复合管线，硬塞进按行 upsert 的表格型模型需抽象重构，改动面大；且 SCRM 已停摆两月，若 #283 判弃用则全部白做 |
| B. 维持现状 | 不动 | 零成本 | 注册表双写漂移风险仍在；SCRM 口径游离中台外 |
| C. **部分收口（建议）** | ① SCRM 去留并入 #283 拍板：若保留→把 SCRM 去重键/拒绝行/水位纳入中台口径（注册进 REGISTRY + gap_records），入库管线保持独立；② 三注册表去双写按 #223 单源化；③ Provider 工厂**不形式化**（fetch_mode 分流已是事实工厂） | 用最小改动拿到口径统一的实质收益；不赌 SCRM 存废 | 去双写需动三处注册入口，需回归测试（#223 已立） |

## 三、建议（与 O-13 对齐）

1. **采「部分收口」**。表格型通道已完成中台化，剩余差异集中在 SCRM——而 SCRM 的存废本身是 #283 的决策对象，收口动作不应先于存废决策。
2. **对 #283 的输入**：本报告建议 #283 按如下判据拍板——若 SCRM 业务仍需要（客服会话分析依赖），则「保留 + 口径入中台（去重键/水位/拒绝行三件套），管线不动」；若已弃用（停摆两月无人感知即为强信号），则「下线 scrm 采集 + 四表处置 + 注册表摘除」，一并释放 #274 C6。
3. **Provider 工厂模式不做**：现有 `fetch_mode` 分流 + `SyncTaskManager` 共享互斥已达成工厂的实质（统一调度、统一互斥、统一冷却）；再抽象一层基类/接口只增复杂度不产生新能力。
4. **统一水位台账做轻量补齐**：把 SCRM/投诉/手动退款通道的最近水位并入 `gap_records` 同一视图（只读聚合，不改各通道写路径），归入 #223 或随 #283 一并实施，不单独立大项。
