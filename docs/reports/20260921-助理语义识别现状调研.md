# csctalon 助理「语义识别」现状调研

> 调研日期: 2026-09-21 ｜ 性质: **只读调研，未改任何代码**
> 起因: 用户提出「助理对语义的识别还是个问题」，并列出 4 个应区分的维度

---

## 结论速览

**用户的直觉是对的 —— 确实缺一个统一的意图识别层**，但具体形态与用户设想有差异：

| 用户的维度 | 我的初步判断 | **核实后的实际情况** |
|---|---|---|
| 1. 时间窗口 | 已实现 | ✅ **确认**，且相当完善 |
| 2. 内容域 | 未做真正的识别 | ⚠️ **我说错了** —— 已有 `_KEYWORD_TO_SCOPE`，覆盖 4 域 |
| 3. 明细 vs 简报 | 缺失 | ❌ **确认缺失** —— 但另有 `detail_level`/`format` 字段未参与问句判定 |
| 4. 可裁剪 vs 需实时 | 只有事后补救 | ✅ **确认**，且这是**最严重的缺口** |

**核心问题不是"没有识别"，而是"识别散落在 5 处、各自用关键词匹配、互不协调"。**

## 一、现有分流链路（实测梳理）

`POST /ai/analyze` 的完整分支：

```
问句
 ├─ force_llm=True（前端"直接生成"按钮）→ 跳过全部命中链 → 实时 LLM
 └─ force_llm=False
     ├─ _has_deep_req_intent()  ← 12 个后悔式词（太简单/再详细/重新分析…）
     │   └─ 命中 → deep_req 模式：跳过命中链，直接实时重算
     └─ 未命中
         ├─ match_template_report()  ← L1 关键词窗口匹配
         │   ├─ 命中 → classify_question() 分级
         │   │   ├─ brief    → extract_section 摘取（秒回）
         │   │   ├─ standard → 完整性校验 → 缺维度则补算
         │   │   └─ deep     → 转实时重算
         │   └─ 未命中
         │       ├─ semantic_match()  ← L2 27b 语义匹配（候选前 5 条）
         │       │   ├─ 命中 → 同上按 mode 分级
         │       │   └─ 未命中
         │       │       ├─ 有候选 → L3 clarify（返回 H2 标题让用户选）
         │       │       └─ 无候选 → 实时 LLM
```

### 识别散落在 5 处

| # | 位置 | 识别什么 | 方式 | 输出 |
|---|---|---|---|---|
| 1 | `ai_time_parser` | 时间窗口 | 正则 + LLM 兜底 | start/end/label |
| 2 | `ai_focus_service._KEYWORD_TO_SCOPE` | 内容域 | 字面包含 | refund/complaint/reception |
| 3 | `ai_report_matcher._question_matches_keywords` | 模板命中 | 字面包含 | template |
| 4 | `ai_mode_service.classify_question` | 粒度意图 | 字面包含 | brief/standard/deep |
| 5 | `_has_deep_req_intent` | 事后补救 | 字面包含 | bool |

**它们互不知晓**：`classify_question` 判 deep 时，不知道 `_has_deep_req_intent` 已经在前面拦过一次；`_KEYWORD_TO_SCOPE` 的域信息也没有传给 `classify_question`。

## 二、逐维度核实

### 维度 1：时间窗口 ✅ 已实现且完善

`ai.py` 的 `_Window.resolve()`：

- 显式参数**永远优先**（避免"智能"覆盖用户意图）
- 正则 `parse_time_intent` → 未命中再调 LLM `llm_parse_time_intent`
- 已处理"单日区间回退为 date 语义"（#151，防窗口标签与内容错位）
- 闲聊时跳过 LLM 时间解析（省一次慢调用）

**判定**：无需改动。这是三个维度里唯一做扎实的。

### 维度 2：内容域 ⚠️ 已存在，但覆盖面窄

`_KEYWORD_TO_SCOPE`（16 个词）：

```python
"退款": "refund", "提现": "refund", "涉诉": "refund", "退费": "refund",
"投诉": "complaint", "积压": "complaint", "登记": "complaint", "处理": "complaint",
"商户号": "complaint", "外部投诉": "complaint", "内部投诉": "complaint",
"接待": "reception", "会话": "reception", "咨询": "reception", "专项": "reception",
```

**问题**：
1. **无「全量经营」域** —— 只有 refund/complaint/reception 三域，问"整体经营"时域集合为空
2. **无「个人绩效」域** —— 用户提到的这个维度完全不存在
3. **「处理」这个词太宽** —— 任何含"处理"的问句都会被判为 complaint 域

### 维度 3：明细 vs 简报 ❌ 缺失（但字段已存在）

**关键发现**：`ai_report_templates` 表**已有** `detail_level`（standard/deep）与 `format`（brief/detail）字段：

| 模板 | detail_level | format |
|---|---|---|
| daily_general_morning | standard | brief |
| weekly_compare_last | deep | detail |
| monthly_overview | deep | detail |
| daily_refund_brief | standard | brief |
| daily_complaint_brief | standard | brief |

而 `ai_report_matcher` 里**已有** `_question_format_intent()` 函数 —— 但它只在**多候选排序**时用，**不参与意图识别**。

`classify_question` 用的是**另一套词表**（`_DEEP_WORDS`/`_STANDARD_WORDS`），与 `detail_level`/`format` **语义重叠但不一致**。

**问题**：同一个概念（粒度）有两套定义，且互不引用。

### 维度 4：可裁剪 vs 需实时 ✅ 确认是最大缺口

**现状**：

| 路径 | 何时触发 | 用户体验 |
|---|---|---|
| 命中快照 | 模板关键词命中 | 秒回（可能裁剪） |
| clarify | 未命中但有候选 | 返回标题列表，用户要再选一次 |
| 实时 LLM | 未命中且无候选 | **30~50 秒** |

**关键问题**：**是否走实时，取决于"命中与否"，而不取决于"问句是否需要实时"**。

即：用户问"今天退款四路明细"，若恰好命中 `daily_refund_brief` 快照 → 秒回；
但若问句措辞稍有差异没命中 → **直接掉进 30-50 秒实时**，中间没有"这可否用快照回答"的判断。

**唯一的事前干预**是 `_has_deep_req_intent()`，但它匹配的是**后悔式表达**（"太简单"/"再详细"）——
即**用户看到结果不满意后才触发**，属事后补救，不是事前识别。

## 三、预生成覆盖范围（决定"命中率"上限）

生产仅 **5 个模板**（全部 `visibility_scope=public`）：

| code | 名称 | period | scope | 粒度 |
|---|---|---|---|---|
| `daily_general_morning` | 每日晨会·整体经营 | daily | overview | standard/brief |
| `daily_refund_brief` | 日报·退款专项(含涉诉) | daily | refund | standard/brief |
| `daily_complaint_brief` | 日报·投诉专项(三源) | daily | complaint | standard/brief |
| `weekly_compare_last` | 周报·本周与上周对比 | weekly | overview | deep/detail |
| `monthly_overview` | 月报·本月总览 | monthly | overview | deep/detail |

**覆盖空白**（用户问到就会掉进实时路径）：

- ❌ **接待/会话专项**（有 `reception` 域关键词，但**无对应模板**）
- ❌ **个人绩效**（完全无）
- ❌ `weekly` × refund/complaint（周期有、域无）
- ❌ `monthly` × refund/complaint
- ❌ 任意自定义时间区间（如"9月1日到9月15日"）

## 四、根因归纳

### 问题 A：识别层缺失，而非识别错误

用户的表述是"语义识别还是个问题"，准确说是：
**没有一个环节回答"这个问句整体要什么"** —— 5 个模块各答一小块，且互不通信。

### 问题 B：粒度概念双重定义

`ai_report_templates.detail_level/format`（数据侧）
vs `ai_mode_service._DEEP_WORDS/_STANDARD_WORDS`（问句侧）

两套词表各自演化，语义重叠但不一致 → 改一处不会影响另一处。

### 问题 C：实时性判定倒置

```
现状:  命中失败 → 实时（不论问句类型）
      ↓
问题:  "今天退款明细" 若没命中模板 → 30-50 秒
      而它其实是可以在快照基础上补算的
```

**正确方向应是**：问句类型决定处理方式，命中失败只影响"能否复用快照"。

### 问题 D：关键词匹配的固有脆弱性

全部 5 处都用字面包含（`if kw in question`）。实测反例：

| 用户实际可能说的 | 现有词表 | 结果 |
|---|---|---|
| "客诉" | 有"投诉"，无"客诉" | ❌ 未命中 |
| "退费情况" | 有"退费" | ✅ 命中 |
| "退款咋样了" | 有"退款" | ✅ 命中 |
| "整体经营" | **无该域** | ❌ 域为空 |
| "张三的成绩" | 无个人绩效域 | ❌ |
| "9月1号到15号" | 时间解析可处理 | ✅ |

## 五、建议方向（待决策，本次未实施）

### 短期（低成本、立即见效）

1. **补 `_KEYWORD_TO_SCOPE` 的同义词**：客诉→complaint、退单→refund、来电→reception
2. **统一粒度词表**：让 `classify_question` 直接读 `detail_level`/`format`，消除双重定义
3. **补 `reception` 模板**（域关键词已有、模板缺失，是最容易补的空白）

### 中期（需设计）

4. **抽出统一意图识别层**，一次输出全部维度：

```
Intent {
  window:    {start, end, label}      ← 复用现有 ai_time_parser
  domain:    {overview|refund|complaint|reception|personal}
  granularity: {brief|standard|deep}
  freshness: {snapshot_ok | needs_live}   ← 新增：事前判定
  confidence: float                        ← 规则未命中时的自评
}
```

关键设计点：**`freshness` 应由问句类型推导，而非由命中结果决定**。

5. **实时性判定规则**（示意）：

| 问句特征 | freshness |
|---|---|
| 命中快照 + 维度齐全 | `snapshot_ok` |
| 命中快照 + 缺维度 | `snapshot_ok`（走补算） |
| 昨天及更早 | `snapshot_ok`（数据已定） |
| **今天 + 未命中** | `needs_live` |
| 明确要求"最新的/现在的" | `needs_live` |
