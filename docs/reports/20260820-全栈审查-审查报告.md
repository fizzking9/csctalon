## 一、可用性审查（代码质量 · dsh-code-review）

### ✅ 通过项
- 后端导入正常（74 模型 / 43 路由），前端构建通过，4 容器健康（backend/db/redis/web）。
- 冒烟测试 18/18，深测 10/10（发票识别/报销审核/投诉审计/跨部门/Excel 导出）。
- **SQL 注入风险低**：3 处 f-string SQL 均用于内部表名/固定结构（ANALYZE、固定聚合），无用户输入拼接。
- **无硬编码密钥**：scrm client_secret 为空默认值，凭证走 Fernet 加密。
- 新代码（微信扫码注册/审批流、pyzbar 发票解码、调度器预警扫描）均有优雅降级与错误隔离。

## 七、结论

- **能用 ✅**：代码质量合格（无注入/无密钥泄露/构建运行通过），功能完备。
- **有用 ⚠️**：业务价值高，但统一待办中心有两处缺口（发票待审/微信注册），补上即闭环。
- **好用 ❌**：最大短板在界面——617 处硬编码颜色 + 5 页内联 KPI 卡违反设计规范；token 化 + 组件化是"好看好用"的关键一步。
- **文档 ❌**：严重落后于代码（56→75 表），需立即对齐，否则误导后续开发。

> 建议实施顺序：P0（文档对齐 + 待办闭环）→ P1（颜色 token 化 + KPI 组件化 + 权限收紧 + 入口治理）→ P2（菜单归组 + helper 抽取 + 报表审计）。
