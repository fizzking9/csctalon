### 3.5 AI：训练链路 / 批处理 / 编排 —— LlamaFactory + Qwen-fine-tune + dify（R5/R6）

**LlamaFactory 微调全链路（每步有证据，可直接排 Phase 2）**

1. 样本组装 → JSONL（alpaca 三字段）+ `dataset_info.json` 注册（异构样本零改码接入，`data/README_zh.md:3-5`）；
2. 训练：`llamafactory-cli train qwen3_lora_sft.yaml`（8B LoRA 16G 卡可跑；27B 须 QLoRA 4bit）；
3. 合并导出：`llamafactory-cli export merge_lora.yaml`（**merge 与量化互斥，必须两步**，`train/tuner.py:182`）；
4. 可选 GPTQ 量化（需校准集）；
5. 部署：vLLM 加载 + `llamafactory-cli api`（OpenAI 兼容 `/v1/chat/completions`）；

> 本节为**用户在本报告撰写期补充的业务口径**（第一轮 5 条 + 第二轮 3 条），目的：校准 §四 深审结论与 §七 行动项的优先级——**同一处技术缺口，在业务口径下可能重排**；同时为「客户域建模」「夜间预警」「排班」三个方向提供事实基线。

### 5.1 八条业务事实（用户原述归纳）

1. **设备 = 流量设备**：卖出后**持续充值**（收入持续发生在存量设备上）；**客户识别主轴 = 设备 SN**。
2. **分析深化方向**：现状是浅层分析，后续要下沉到 **设备类型 → 店铺 → 商户号 → 企业**；组织形态 = **1 个企业管理很多店铺**；**设备绑定到商户号**；**商户号与店铺无必然关系**（两条独立通路）。
3. **套餐会不时调整**，且**套餐名不同可能是同一个**（销售策略差异）→ 口径上需要「套餐字典/归一」。
4. **设备会被不定时打标签**，**客服操作依赖标签** → 标签是业务操作的事实基础，须进分析。
5. **大量数据手工登记或经共享表格同步** → 手工/共享通道是**常态化**的（不是例外），其可观测与入库质量必须与自动采集同标准。
6. **〔第二轮〕客服绩效与管理太粗糙**（用户评价）——期望绩效口径与管理动作（风险预判、改进闭环）成体系。
7. **〔第二轮〕夜间风险预警（功能愿望，具体定义）**：每天晚上分析**当天所有接待过的客户**，把**「优质但可能要投诉」**的客户**提交给投诉专员优先处理**。好客户判据 = **充钱多、流量少、愿意沟通**；风险信号 = **同样的问题多次沟通**（可能升级为投诉）。
8. **〔第二轮〕排班空缺**：排班功能目前偏空缺，**现行执行是在企微中排班**。

### 5.3 对功能规划的含义（与 §4.2 合并看）

- **「客户 360°」的正确形态 = 设备 360° 为主轴**（客户 = 设备 SN），商户号 / 店铺 / 企业是**聚合上卷**层级——§4.2 的「客户 360 缺口」按此重述为：「**设备 360 + 四层上卷主数据**」。
- 深化分析推进顺序（成本递增）：**设备类型维度**（字段已在，最小成本）→ **商户号主数据 + 建链** → **企业/店铺主数据与上卷**（1 企业多店铺）→ **店铺-商户号交叉分析**（两通路不必然相关，是分析机会点）。
- 套餐归一与标签分析是**横切依赖**：凡涉及「按套餐 / 按标签」的看板口径，都需这两个字典先行。
- **夜间预警是「AI 二阶段」首个高价值落地场景**：判据（充值/流量/沟通/重复问题）明确 → **v1 确定性评分**（规则引擎，即可产出专员清单）→ **v2 弱监督模型**（标签 = 历史投诉结局，接 S-P1-8 管线）。输出物 = 投诉专员的**优先处理清单**，与投诉域天然打通。
- **绩效 / 排班 / 接待三件事是一个闭环**：排班（企微源）→ 接待流水（`cs_records`）→ 绩效口径（人均效率算法）；建议先决策排班目标形态（S-P1-15），再谈三者联动（与 S-P1-10 合并推进）。
