## 二、警告（WARNING）——建议修复，非阻塞

- [ ] **W1（external.py list_tokens 清空 owner_note 无效 / ExternalAccess.vue:246）**：前端 `submitEdit` 用 `if (editForm.owner_note) payload.owner_note = ...` —— 用户**清空"责任人"输入后保存，空串不发送** → 后端 payload 无 owner_note（None）→ `update_token` 不更新 → **旧值残留，无法清空**。后端已支持"空串清空"（`if payload.owner_note is not None`，传 `""` 即清），但前端被 `if` 挡住。**建议**：`submitEdit` 改为始终发送 `payload.owner_note = editForm.owner_note`（创建 `submitCreate` 可保留 `if`，空串→null 等价）。测试已覆盖后端空串清空，但缺前端链路验证。

- [ ] **W2（complaints.py /detail subject 过滤可能漏外部工单行, 6f86657 L~898）**：subject 过滤在 Python 侧对 `records` 按其 `entity` 归一比较。`entity` 对**外部投诉工单主行**仅当 `include_supplementary=True` 且命中补充表 `company_entity` 回填才非空；`include_supplementary=False` 或未匹配到补充表的**外部工单主行 entity=None** → 该主体的外部工单会从下钻结果**消失**（前端 openSubjectDetail 用 include_supplementary=true 可回填大部分，但未匹配补充表的外部工单仍漏）。**建议**：subject 过滤移到数据库层（对 registrant 归一 in 匹配商户号行 + 补充表 company_entity/SN 关联），或文档注明"主体下钻含补充表关联到的工单；未关联补充的外部工单不入主体"。当前实现满足 subject_ranking 生成口径的主体（其外部计数来自补充表 entity），与 Top 榜点击一致性可接受，但建议补测"外部补充未关联工单 + subject"场景。

- [ ] **W3（complaints.py /detail 无 subject 时的 registered/handled 与明细集合口径差, 6a3defb L~896）**：`/detail` 返回的 `registered/handled` 取自 `_sources_reg_handled`（窗口内全量按 source_type 桶），与 items 集合（register **或** finish 在窗口）**不同口径**——明细标题"登记 X/处理 Y"可能略偏离该明细实际构成；对 `source_type` 过滤时 registered/handled 是该源全窗口数（非该窗口下 items 的 register/finish 拆分）。**建议**：标题口径注明"窗口内登记/处理计数（全窗口，非当前筛选子集）"或改为对 items 计数（参考 subject 分支做法），避免误导。

- [ ] **W4（list_tokens 对 pydantic 实例直接赋值 created_by_display, external.py L~495）**：`d = ExternalTokenOut.model_validate(t); d.created_by_display = ...` 依赖 pydantic v2 默认非冻结可赋值。能运行但属隐式写法；**建议**用 `d.model_copy(update={"created_by_display": ...})` 或构造 dict，避免未来冻结模型/校验开启时隐性破坏。
