## 五、结论

### 已确证的 3 点（你原本的判断成立）

1. **存在重复计算**：315/卡商补充表与工单侧在同一时间窗内有重叠
2. **状态不同步**：315 已办结但工单非完成态 **224 行（24.9%）**；
   且 **80% 的 315 记录没有处理日期** → **无法通过同步解决**
3. **一个投诉多渠道、不同日期**：已证实（54 个 SN 跨两张补充表）

### 我的新发现（此前未知）

4. **无时间窗的 SN 关联会跨年错配**（>180 天占 4.7%）
   → 现有 `_sn_to_ticket_map` 取"最早一张工单"的做法**存在错配**
5. **补充表 80% 无处理时间** —— 这是状态无法同步的**结构性原因**

### 我的错误（已自查纠正）

6. 前一版"兜底桶 42,253 / 175,723 行" **均为我的 SQL 臆造条件所致**，
   **真实值 5 行**。生产代码无此问题。
