## 三、根因分析

### 根因 1：`conftest.py` 用 `setdefault` 无法纠正污染

```python
# 事故前
os.environ.setdefault("POSTGRES_DB", os.environ.get("TEST_POSTGRES_DB", "csctalon_test"))
```

`setdefault` 语义是「**变量已存在时不覆盖**」。因此当会话里残留
`POSTGRES_DB=csctalon` 时，测试库名设定**完全不生效**，测试直连开发库。

### 根因 2：测试清理的「无条件整表删除」

```python
# 典型写法（事故前，多处）
for cls in (RefundRecordReport, Refund):
    session.execute(cls.__table__.delete())   # ← 无 where，全表删除
```

在一次性测试库上这是合理设计；一旦库名错配，即成为破坏性操作。

> **放大器效应**：根因 1 让「连错库」静默发生，根因 2 让「连错库」的后果为
> 不可逆的整表清空。二者叠加才构成事故。

## 五、防再发加固（双层防御）

### 第一层：`backend/tests/conftest.py`
- **强制覆盖**库名（弃用 `setdefault`）：
  ```python
  os.environ["ENV"] = "test"
  os.environ["POSTGRES_DB"] = _EXPECTED_TEST_DB   # 强制，不用 setdefault
  ```
- **库名守卫** `_assert_test_database(url)`：在 engine 建立前断言实际库名，否则 `RuntimeError` 中止。

### 第二层：`backend/tests/_db_guard.py`
每次破坏性清理**执行前**再校验一次 session 实际连接的库：

```python
from tests._db_guard import safe_wipe

safe_wipe(session, Model)                                  # 全表清空（仅测试库允许）
safe_wipe(session, Device, where=Device.sn.like("SN-D-%"))  # 带条件（推荐）
```

> **设计权衡**：保留「全表清空」能力而非硬性禁止 —— 部分用例需断言
> 「导入前该表为空」。策略是「**限定库 + 强制显式**」，而非「禁止」。
>
> 为何不「自动改写库名」而是「报错中止」：静默改写会造成「以为连 A 实际连 B」的
> 隐性错配，宁可显式失败。

**改造范围**：9 个测试文件、**47 处**裸删除 → `safe_wipe`。

### 回归锁（3 道）
| 测试 | 作用 |
|---|---|
| `test_conftest_forces_db_name_not_setdefault` | AST 判定库名必须强制赋值 |
| `test_no_bare_table_delete_in_tests` | AST 全量扫描，禁止再出现裸 `__table__.delete()` |
| `test_guard_rejects_non_test_db` | 守卫必须拒绝非测试库 |

## 六、操作规范补充（写入团队约定）

1. **禁止**在持久终端执行 `set -a && . ./.env` 后再跑 `pytest`。
   需要加载配置跑脚本时，使用**一次性子 shell**：
   ```bash
   (set -a && . ./.env && python script.py)
   ```
2. 涉及数据库的只读分析脚本，也应在**独立进程**中加载配置。
3. 跑测试前可用 `env | grep POSTGRES` 自检，确认无残留。
