## 一、背景与触发

#338 落地「业务层零读 ods」时，10 张无采纳子集语义的表统一用**零存储 `std_*_all` 视图**（`SELECT * FROM ods.*`）承接。当时的判断是「点查走 ods 原有索引，性能够用」。

实际运行后暴露两类瓶颈：

| 瓶颈 | 实证 |
|---|---|
| 宽表列多导致 I/O 与规划开销大 | `bms_orders` 31 列（含 `raw_extra` JSONB / `synced_at`），`cs_records` 16 列，视图透传后单次宽扫描读页数翻倍 |
| 时间窗口放大后走全表扫描 | 90 天窗口已覆盖全表 92%，`device_sn` 维度 TOPN 无法走窄索引，退化为 Seq Scan |

工单 #339 的触发条件（三条中命中两条）：
1. `EXPLAIN ANALYZE` 确认视图走 ods 宽扫描且无有效索引路径 ✅
2. 新增业务分析接口涉及全表排序/分组（`analytics/refund.py` 24 处消费 `cs_record_clean`） ✅
3. 看板 TOPN > 3s —— 未命中，故不按"降阈值 50%"作为本次主目标，改以**索引路径提速 + I/O 削减**为主指标

## 二、列审计（核心依据）

审计方法：**生产 `information_schema` 实测列集** × **全仓 `grep` 消费点交叉验证**（不是只看命名猜用途）。

### 2.1 `cs_records` → `std_cs_record`

| 项 | 值 |
|---|---|
| ods 列数 | 16 |
| 保留列数 | 12 |
| 削减率 | **-25%**（12/16 = 75%） |

**剔除 4 列及判定依据**

| 列 | 判定 | 依据 |
|---|---|---|
| `send_content` | 零业务消费 | 仅采集解析（`data_parser`）/ 采集写入（`upsert/_tickets`）/ 元数据注册（`data_source_registry`）引用，均作用于 ods 源表 |
| `problem_create_time` | 零消费 | 同上，无 analytics/api 读取点 |
| `last_consult_time` | 零消费 | 同上 |
| `updated_at` | 零消费 | 采集系统导入戳，业务侧不读 |

**保留 12 列**：`id, problem_category, problem_type, device_sn, solution, operation_time, operator, description, execution_result, user_accepted, consult_time, created_at`

### 2.2 `bms_orders` → `std_bms_order`

| 项 | 值 |
|---|---|
| ods 列数 | 31 |
| 保留列数 | 19 |
| 削减率 | **-39%**（19/31 = 61.3%） |

**剔除 12 列**：`raw_extra`（JSONB 内部溯源）、`synced_at`、`payable_price`、`wx_order_no`、`order_result`、`order_status_raw`、`last_stored_time`、`mch_id`、`business_id`、`before_serve_valid_date`、`after_serve_valid_date`、`days`

**保留 19 列**：`order_no, order_type, device_sn, combo_name, combo_price, actual_pay_price, balance_pay_price, pay_date, pay_type, order_status, refund_status, create_user, create_date, business_name, merchant_name, active_date, device_type_name, created_at, updated_at`

### 2.3 审计中纠正的一次误判（值得复用）

初版审计把 `order_type` / `combo_price` / `balance_pay_price` / `pay_type` / `pay_date` 判为零消费，准备删除。复核 `audit_timeline._build_bms_items` 的 UI 详情渲染逻辑后发现**实际被读取**，已加回保留列集。

> 教训：**"字段名不出现"不等于"不消费"**——UI 渲染层常通过 `row.xxx` 动态取值或用字典批量构造，grep 单列名会漏。审计必须落到「渲染函数实际读取哪些键」这一层。

## 三、方案设计（三阶段）

| 阶段 | 内容 | 关键决策与理由 |
|---|---|---|
| **① 建物化表** | migration `d9e1f0c2b4a6` 建 `std_cs_record`(12 列) / `std_bms_order`(19 列)，`CREATE TABLE AS SELECT` 初始灌数 + 6 索引 + 主键 | **不**把 `std_*_all` 镜像视图改成物化——保留其 `SELECT * FROM ods` 实时语义，二者分工明确：`std_*` 精简物化供分析，`std_*_all` 全量镜像供对账 |
| **② 消费切换** | `table()` 路径 9 处改指精简表；`rebuild_std_big` 挂 03:40 定时 | 零业务代码改动（迁移时已按消费列对齐，列集是超集） |
| **③ 视图重定向** | migration `0dce885e5a06` 把 `cs_record_clean` / `bms_order_clean` 从「over ods 宽表」改为「over std 精简表」 | 让 analytics 24 处 `refund.py` 消费**无需改一行代码**即吃到红利；`down` 恢复原列集，双向可跑 |

### 3.1 索引设计（按实际查询模式，不按列名堆砌）

| 表 | 索引 | 服务的查询 |
|---|---|---|
| `std_cs_record` | `ix_std_cs_record_op_time (operation_time)` | 时间窗口过滤（主时间字段） |
| | `ix_std_cs_record_sn (device_sn)` | 设备点查 / 按 SN 聚合 |
| | `ix_std_cs_record_cat_op (problem_category, operation_time DESC)` | **90 天 TOPN GROUP BY** —— 复合索引直接覆盖，免回表 |
| `std_bms_order` | `ix_std_bms_order_sn (device_sn)` | 设备点查 |
| | `ix_std_bms_order_create_date (create_date)` | 同步锚点窗口 |
| | `ix_std_bms_order_active_date (active_date)` | 激活日期窗口 |

> `DESC` 修饰符无法通过 `op.create_index` 表达（会被当成字面列名），改用原生 DDL `op.execute`。

### 3.2 重建作业设计

`app/services/governance/std_big_rebuild.py`：

- **幂等**：`TRUNCATE + INSERT…SELECT` 同事务，原子换装，读侧 MVCC 无感知中间态
- **防并发**：`pg_advisory_lock(1101/1102)`（cs / bms 各自独立锁）
- **破坏性操作合规**：`TRUNCATE` 前过 `db_guard.assert_safe_to_destroy()`（AGENTS 铁律 3），显式 `allow_real_db=True`
- **调度**：`batch_runner.BATCH_JOBS["rebuild_std_big"] @ 03:40`，错峰 `02:00 purge → 02:30 cash_flow_wide → 03:10 refund_wide → 03:40 std_big`，早于 `05:00 BMS 补跑` 窗口

## 五、实测性能数据（生产 `EXPLAIN ANALYZE`）

### 5.1 索引路径（30/90 天 `problem_category` TOPN）—— 主收益

| 查询对象 | 耗时 | Buffer | 计划 |
|---|---|---|---|
| `std_cs_record`（物化） | **44 ms** | read -83% | `ix_std_cs_record_cat_op` 索引扫描 |
| `std_cs_record_all`（视图 = ods 宽扫描） | 83 ms | 基准 | 并行索引扫描 |

**提速 1.87x**，且随窗口收紧进一步放大（30 天窗口实测 17 ms / shared hit 8107）。

### 5.2 全表扫描路径（90 天 `device_sn` TOPN）—— 收益形态不同

| 查询对象 | 耗时 | buffers read | 规划时间 |
|---|---|---|---|
| `cs_record_clean`（Phase③ 后挂 std） | 221 ms | 8,547 | **0.3 ms** |
| `ods.cs_records`（原路径） | 226 ms | 14,896 | 72.9 ms |

> **诚实解读**：90 天窗口覆盖全表 92%，两边的**最优计划都是 Seq Scan**，所以耗时差异很小（221 vs 226 ms）。真正省下的是：**I/O -43%**（8547 vs 14896 页）+ **规划时间 0.3ms vs 72.9ms**（宽表 31 列让 planner 统计成本高一个量级）。
>
> 结论要分开说：**窄窗/索引路径 = 1.87x 提速；宽窗/全扫路径 = I/O 与规划开销削减，而非墙钟时间**。不要把后者宣传成"提速数倍"。

### 5.3 `bms_orders` 同比

| 查询对象 | 耗时 | Buffer |
|---|---|---|
| `std_bms_order` | 401 ms | -28% |
| `std_bms_order_all`（视图） | 423 ms | 基准 |

提速 1.06x —— 该表 TOPN 主要 cost 在 67 万行排序本身，列宽削减无法改变排序复杂度。**预期内，不是缺陷**。

## 七、过程中踩到的坑与解决（4 类）

| 问题 | 根因 | 解决 |
|---|---|---|
| migration revision ID 连续两次撞车 | 手写 12 位 hex ID，与仓库既有 `add_external_token_owner_note` / `add_urge_dispatch_fields` 冲突 | 改用 `alembic revision` 自动生成（`d9e1f0c2b4a6`）；**不要在已有 190+ 迁移的仓库手写 revision ID** |
| `op.create_index` 建复合 DESC 索引失败 | 该 API 把 `"problem_category", "operation_time DESC"` 中的 `DESC` 当字面列名 | 改 `op.execute("CREATE INDEX ... (col, col2 DESC)")` 原生 DDL |
| 测试库用例全零（`score.contact=0`） | conftest 建的是**物理表** `CREATE TABLE AS SELECT FROM ods`（建表时 ods 为空）→ fixture 后续往 ods 插数据，物理表**无感知** | 测试库改建成**视图**（`SELECT 精简列 FROM ods.*`），fixture 插 ods 后自动可见，与 `STD_ALL_VIEWS` 同范式。**线上是物理表、测试是视图 = 有意为之的测试适配，非口径偏差** |
| `DROP TABLE` 对视图报 `WrongObjectType` | 上一轮残留对象类型不确定 | 先查 `pg_class.relkind` 判型再选 `DROP VIEW` / `DROP TABLE`（#322 同款） |
| `bms_orders` 列审计漏项 | grep 单列名漏掉 UI 动态取值 | 复核 `audit_timeline._build_bms_items` 渲染键，加回 5 列（见 §2.3） |
| 误提交 `audit_cols.sql` | 审计中途生成的临时 SQL 落入工作树 | `git rm --cached` + 单独清理提交（`60e8f02`） |

## 八、风险与限制（必须知悉）

1. **数据新鲜度滞后（设计内，实测已量化）**
   `std_cs_record` / `std_bms_order` 是**日更物化**。两轮实测印证：
   - cs：手工重建时 541,790 行 → 数小时后 ods 542,242（+452），std 未跟
   - bms：**滞后可达约 26h** —— 03:40 重建快照 667,788，05:00 BMS 补跑后 ods 已 680,054（+12,266），需等次日 03:40 才同步
   → 消费端语义：**看板/analytics 看到的是 T-1 数据，bms 域最坏接近 T-2**；需要实时全量的场景（对账、状态分布、导出明细）应读 `std_*_all` 镜像视图（实时透传 ods）。这是两者的分工边界。

2. **`cs_records` 列数 75% 未达工单 70% 目标 → 降级验收**
   零消费列已删尽，其余 12 列均在用。继续削减会破坏在用口径，故按工单纪律在关闭凭证中显式声明降级，而非静默凑数。

3. **首轮定时执行已复核通过（2026-10-22 补记）**
   `last_run_at=2026-10-21 19:40:55Z`（北京 10-22 03:40:55）、`last_status=success`、`consecutive_failures=0`、`next_run_at` 已顺延至 10-23 03:40。定时链路（`batch_runner` → advisory lock → `db_guard` → TRUNCATE+INSERT 同事务）**端到端跑通**。
   ⚠️ 但由此暴露的 **bms 26h 滞后**（§6.1）需产品侧确认可接受；若不可接受，才需评估把窗口移到 05:00 补跑之后（属 §10 增量刷新范畴，当前无实证必要）。

4. **既有异常（非本次引入，未越界修复）**
   `rebuild_refund_wide` 的 `next_run_at = 2026-10-08`（已过期）、`last_status = skipped`，属存量调度异常，建议另开单处理。

5. **`std_*_all` 与 `std_*` 双轨并存**
   同一业务表存在两个读入口（实时镜像 vs 日更精简），**必须靠文档与命名区分**，否则新同学容易误读滞后数据做实时判断。已在 `ods_clean.py` 与 `std_big_rebuild.py` 注释中声明。
