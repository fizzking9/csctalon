## 三、性能与正确性提升

### 3.1 金额计算正确性（#217 方案 C′ / #222）

- **Decimal 定点化**：16 模型 37 列金额从 `float` → `Numeric(12,2)/(12,4)` + `Mapped[Decimal]`，计算路径用 `D()` 定点化（`app/services/analytics/_core.py:68`）
- **根除二进制浮点进入金额存储与计算**导致的累计误差
- 出参边界统一 `float(round(...))` 一次性转换，JSON 契约保持 number（元）不变
- **回归修复**（`6cd5f45`）：#222 落地后 3 个接口 500 —— 累加器仍初始化为 `0.0`/`0`，与 `D(...)` 做 `+=` 抛 `TypeError`；8 处全部改 `D(0)` 修复

**为什么不是"元→分"方案**：#217 评估了"元→分"全量迁移，成本高、回归面大；方案 C′（元 Decimal，禁浮点入计算）在不动 DB 列类型的前提下达成正确性目标，风险更低。

### 3.2 事件循环阻塞治理（#213 / `5fef31e`）

- **9 个"假 async"路由修复**：函数声明 `async` 但体内无 `await`，实际同步阻塞事件循环
- AST 盘点 `app/api` 全量：9 个假 async + 22 个真 async，全部修复
- 单 worker（保证互斥锁有效）下，并发吞吐显著改善

### 3.3 部署一致性（#212 / `a984cb9`）

- **Gunicorn `-w 4`/`-w 1` 矛盾消除**：应急补丁镜像（`Dockerfile.patch`）内嵌 `-w 4`，与主 `Dockerfile` / `docker-compose.yml` 的 `-w 1` 冲突
- 多 worker 导致**互斥锁失效**（多进程并发写同一资源）
- 三处统一单 worker 后，互斥锁重新有效

### 3.4 库名安全（#214 / `727d327`）

- compose 默认库名从 `csctalon`（真实库）改为 `${POSTGRES_DB:-csctalon_dev}`
- 启动期**硬校验**模式与库名自洽：`APP_MODE=dev` → 库名以 `_dev` 结尾；`test` → `_test`；`prod` → 不含 `_dev`/`_test`
- 不一致即拒绝启动，杜绝开发环境误连生产库

## 七、结语

这轮升级的本质不是"加功能"，而是把一个能跑但治理松散的系统，通过 **Decimal 化、async 治理、互斥锁修复、看板双强制、规范挂铁律**，改成了一个**金额算得准、并发不互踩、数字可下钻、改动可审计**的生产级系统。

三个判断：

1. **治理优先于堆功能是对的** —— fix(205) > feat(193) 不是"没做新功能"，而是"先把地基夯稳"。一个金额算不准、互斥锁失效的系统，功能再多也不能上生产。
2. **规范挂铁律比规范写文档重要** —— 22 篇 standards 如果不挂进 AGENTS 引用链，就只是标签，不构成约束。第 14 条铁律（入库规范）挂入后，gitleaks + CI 兜底才真正闭环。
3. **开源对照的价值在"机制级可移植"而非"整体引入"** —— 参照了 Chatwoot/LLaMA-Factory/DataEase 的机制，但没有整体引入任何一个，因为业务事实不同（多源异构投诉 / 单 worker 互斥 / 五路退款对账）。机制借鉴 + 业务适配，比"拿来主义"更耐用。
