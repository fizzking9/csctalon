## 三、审查过程中**发现并修复**的缺陷

### D1（HIGH 级隐患，已修复）：migration revision ID 冲突

| 项 | 内容 |
|---|---|
| 现象 | `alembic heads` 报 `Multiple head revisions`，且警告 `Revision a1b2c3d4e5f6 is present more than once` |
| 根因 | 我新写的 migration 用了 `a1b2c3d4e5f6`，**与 8 月既有的 `a1b2c3d4e5f6_add_shanmao_phone_paid_amount.py` 撞车**，把 revision 图劈成两个 head |
| 影响 | 若未发现就部署，`alembic upgrade head` 会直接报错失败 → **部署阻塞** |
| 修复 | 改名 `b2c3d4e5f6a7`，`down_revision` 指向真实 head `f0a1b2c3d4e5`；`alembic heads` 恢复单一 head |
| 防复发 | 已在提交流程中固定执行 `alembic heads` 校验（本次即靠该步骤发现） |

### D2（MEDIUM，已修复）：配置变更回调调用不存在的方法

| 项 | 内容 |
|---|---|
| 现象 | 端到端实测时日志出现 `[调度器] 变更后重算槽位失败(下次 tick 自愈): 'BmsScheduler' object has no attribute '_reload_today_completed_slots'` |
| 根因 | 我在 `on_settings_changed()` 里写了 `_reload_today_completed_slots`，而实际方法名是 `_reload_today_completed_hours`（改造时漏改名） |
| 危害 | 异常被 `except` 吞掉 → **配置写入成功但调度器当日槽位登记未重算** → 管理员改小间隔后，部分槽位可能被跳过（例如 10:17 把 60 改成 30，旧的 "10:00" 登记仍占位） |
| 为何单测没抓到 | 测试直接调 `update_settings`，而回调内部异常被吞（静默降级），断言仍通过 |
| 修复 | 改为正确方法名；**补 `test_update_settings_notify_scheduler_does_not_raise`** 断言回调路径不产生 warning 级失败日志 |
| 教训 | "静默降级 + 日志 warning" 的代码路径，必须用日志断言锁住，否则单测全绿也挡不住 |

## 四、MEDIUM / LOW

### M1（MEDIUM，部署注意）：缓存预热仍按小时节奏

`services/cache_warmer.py` 仍用 `DAYTIME_HOURS = range(8, 24)` 判断"是否白天"，
其 `warm_idle` 由调度器主循环每分钟调用、内部按 TTL 节流，**因此功能上不受影响**
（只是判断口径仍写死小时）。

不改的理由：该判断仅用于"夜间不预热"这一粗粒度门控，与 30/60 分钟节拍无强关联；
按"最小改动面"原则不在本单扩大范围。**若后续要统一，建议随缓存模块重构一并处理。**

### L1：`SyncDashboard.vue` 体积
该文件已 1000+ 行，本次仅做最小插入（配置面板抽成独立组件）。建议后续按"统一入口 8 个 tab"拆分。

### L2：槽位预览为本地预演
`ScheduleConfigPanel.previewCount` 在前端本地按同语义计算（避免每次调参都请求后端）。
逻辑已与后端 `compute_slots` 对齐，但存在**双份实现**风险。当前用途仅是"改前预估"，
保存后以后端返回值（`slot_count`）为准，风险可控。
