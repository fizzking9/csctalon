## 〇、业务澄清（用户口径，权威）

1. **工单「投诉」的判定 = `service_category` 为空白**
   —— 工单里 `换货/其他/设备故障/套餐疑问/退款/(空白)` 这几种，
   **只有"空白"那个才是投诉**。BMS 平台修复后可能会正式显示"投诉"。

2. **内部投诉（商品投诉/服务投诉）与商户号投诉（微信投诉）不参与外部匹配**
   —— 它们本来就从工单统计，不涉及跨表去重。

3. **只有以下两类需要与工单匹配**：
   - **外部投诉**：工单侧平台类 + `external_complaints`（315 补充表）
   - **(外)卡商**：`card_complaints`（卡商补充表）

4. **一个投诉分多渠道、不同日期**：同一个投诉可能从不同渠道在不同日期进来，
   处理一个就全部处理了 → **统计上算 1 笔，保留渠道明细**。

## 六、建议方案

### 6.1 分类（四桶 + 卡商独立）

```
内部投诉      工单: service_category 空白 AND item ∈ {商品投诉, 服务投诉}
商户号投诉    工单: service_category 空白 AND item = 微信投诉
外部投诉      工单: service_category 空白 AND item ∈ {工信部,12315,公共服务平台,消费者协会}
              + external_complaints（按实体+时间窗去重后）
(外)卡商      card_complaints（独立成桶，不并入外部）
其他(待定)    空白 item(81) + 套餐扣费申诉(14)
```

### 6.2 去重（实体级，统计时去重，两侧数据都保留）

```python
# 优先级：SN → 手机 → 姓名（多维度联合）
# 时间窗：30 天（覆盖 87% 的关联对，且避免跨年错配）
key = (sn, phone[-4:], name_hash)  # 任一命中即视为同一笔
```

- **同一笔多渠道 → 算 1 笔**（用户拍板），但**保留渠道明细**（标注 `dedup_of`）
- 两侧数据**不物理删除**

### 6.3 状态展示（不追求同步）

- 因 80% 无处理日期，**不试图与工单状态对齐**
- 展示时**并列两侧状态**：`工单状态 / 渠道登记状态`，由人工判断
- 或定义**合并状态**：任一为完成态 → 视为已处理（但需标注来源）

### 6.4 被投诉主体

| 来源 | 字段 |
|---|---|
| 315 | `company_entity`（云客猫 1069 / 赤霄 / 小皮丘 / 青晋…） |
| 卡商 | `complaint_group`（需过滤内部群：`投诉处理内部群`、`航城投诉处理内部群`） |
| 工单 | `registrant`（商户号投诉的被投诉商户） |

**建议**：建统一映射（只读解析，不加表列），
卡商侧 `complaint_group` 过滤规则：排除含「内部群/投诉处理」的群名。
