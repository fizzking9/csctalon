## 3. 数据质量问题

### 3.1 处理时间 81.2% 为空（2170/2673）——严重
- 有值的 503 行里**两种格式并存**，分界线 = **2026-08-08**：
  - ≤2026-08-07：**Excel 序列号**（`46187`=2026-06-14），229 条
  - ≥2026-08-08：**标准日期字符串**（`2026-08-08 00:00:00`），274 条
- **推断**：上游 8/8 改了填写格式；系统同步 `_to_datetime` 对纯数字序列号可能解析异常 → 处理时间丢失/不准。**需核实系统库中该字段的落地情况**（与"外部投诉统计状态不及时"直接相关）

#### 🔴 已实锤：系统库 handle_time 序列号解析 BUG（229 行）
核实系统库：`external_complaints`(id<300000) **handle_time 非空 497/2624 = 18.9%**（与表格 18.8% 一致，**同步未额外丢失**），但：
- **229 行 handle_time = `1969-12-31 16:00:00.000046+00`**（Excel 序列号纪元起点，**小数点后 `000046` = 原序列号 `46` 被当成"天数"解析**）
- 这 229 行 **正好等于表格里"序列号格式"的 229 条**（≤2026-08-07 区间）
- 结果：**228 行 handle_time < complaint_date**（处理时间早于登记日，物理不可能）

**结论**：上游 ≤8/7 把处理时间写成 Excel 序列号（如 46187），系统 `_to_datetime` 未识别序列号 → 解析成 1969-12-31 → **时效/及时性统计完全失真**（这正是"外部投诉统计状态不及时"的技术根因之一）。
**修复**：`_to_datetime` 对 **40000~60000 范围的纯数字**按 Excel 日期序列号解析（1899-12-30 起算）；并对已落库的 229 行做一次回填/重算。

## 6. 结论与建议

### 结论
1. 本表**比系统库多 8 个高价值字段**，尤其"投诉关键词(结构化原因)+套餐金额(4列)"可直接支撑投诉核算分析。
2. **处理时间 81% 缺失 + 格式变异(8/8分界)** 是最大数据质量隐患，需核实系统侧是否同样丢失。
3. 重复登记(33组/69行)、异常日期(2行)属治理范畴，量不大。

### 建议（待用户决定）
1. **补采集新字段**：把 8 个新列纳入 `external_complaints`(Alembic 迁移) + `complaint_sync` 清洗映射 + `data_parser` 列模板；否则每次导出都看不到这些信息。
2. **🔴 修处理时间序列号解析(高优先)**：`_to_datetime` 兼容 Excel 序列号（40000~60000 纯数字按 1899-12-30 起算）；核实 8/8 后续格式；对已落库的 **229 行 1969-12-31** 回填真实处理时间。
3. **用新字段做投诉核算**：可按 投诉关键词/套餐名称/协商退款金额 做"投诉原因×金额"分析报表——比现有 problem 关键词归类准确得多。
4. **重复登记治理**：33组/69行 标 dup_residual（与库内 48 组统一治理）。
