## 一、结论（先行）

**维持全量重建，不做增量、不做分区。** 依据：当前生产数据量（宽表 6.9 万行）下，全量重建预估分钟级以内，而增量方案的"删除探测 + 全量集合预载"两个硬约束使复杂度收益比极差（§三）。重评触发条件见 §五。

## 二、现状与量级实测

### 2.1 现行机制

`build_cash_flow_wide(db)`（builder L50-239）：

1. `DELETE FROM cash_flow_wide` 全表清空（纯派生表，重建安全）；
2. A/B/C/D 四路各一条 SELECT 全量扫描 → Python 侧过滤（排除集/失败关键词）→ 批 5000 行 `pg_insert`；
3. 两个**全量内存集合**预载：E 对账键集（`refund_record_reports.platform_order_no`，38,112 行）+ 外部投诉 SN 集（`external_complaints`），用于逐行打 `e_matched` / `has_external_complaint` 标记；
4. 夜批 02:30 由 batch_runner 调度（#258，生产未部署前无 batch_job_runs 实测时长）。

### 2.2 生产量级实测（2026-10-08，只读查询生产节点 db 容器）

| 表 | 行数 | 角色 |
|---|---:|---|
| cash_flow_wide | 68,917 | 物化目标 |
| refunds | 197,613 | A 路源（过滤后仅"线上+已退款"子集） |

### 2.3 全量重建成本估算

- 扫描：4 条 SELECT 合计扫描 ≤24 万行（过滤前），PG 索引/顺序扫描均为秒级；
- 写入：DELETE 68,917 行（秒级）+ 约 14 批 INSERT 共 6.9 万行（批插 5~15 秒）；
- **合计预估 < 2 分钟**，夜批 02:30 低谷期无感；timeout_minutes=120 有 60 倍余量。
- 校准计划：#258 部署后 batch_job_runs 会记录 started_at/finished_at，首周回看一次实测值替换本估算。

## 三、增量方案评估（方案 A：水位线 + upsert + 删除探测）

### 3.1 有利条件

`src_id` 每路天然唯一（A/C=refund_no，B=`W{id}`，D=`M{id}`），加 `(route, src_id)` 唯一索引后 `ON CONFLICT DO UPDATE` 即可幂等 upsert——**写入侧增量改造是可行的**。

### 3.2 两个硬约束（增量不划算的根因）

**约束①：四路都存在"移除条件"，删除探测无法只看新增。**
宽表行的存续是**谓词的函数**，源行状态迁移会导致昨日已物化行今日必须**消失**：

| 路 | 纳入谓词 | 移除场景（真实存在） |
|---|---|---|
| A | 线上+已退款 + quality_status 不在排除集 | 退款状态流转；治理标记 dup_residual/ignored（A-20260909-001 日常治理动作） |
| B | 用户提现 + 备注无失败/冻结关键词 + 排除集 | 备注补录失败关键词；治理标记 |
| C | status='已退款' + 排除集 | 同上 |
| D | is_refunded='是' + 排除集 | 是否退款回改；dup_residual 治理（O-3/O-5/O-6 一键治理即批量改 quality_status） |

这意味着水位线增量必须配"**变更行反查 + 删除对账**"（或双写软删标记），等于为每路维护一张影子变更表——复杂度与维护成本远超每晚 2 分钟的全量重建。

**约束②：标记列依赖全量集合，扫描省不掉。**
`e_matched` 依赖 E 全量键集（38K）、`has_external_complaint` 依赖 EC 全量 SN 集。即便只增量写入当日行，这两个集合仍需全量预载 + 当日行逐行重算；历史行的标记（如 E 补录后历史单 e_matched 翻转）在纯增量下**不会自动修正**，需另设周期性回刷——又回到全量语义。

### 3.3 结论

增量把"简单可重入的全量函数"换成"水位线 + 删除对账 + 标记回刷"三件套，节省的只是 <2 分钟的重建时间。**不采用。**

## 四、分区方案评估（按 pay_time RANGE 月分区）

- 收益前提：单表千万级以上（分区裁剪 / 维护窗口按分区交换）。当前 6.9 万行，年增长估 3~4 万行/月量级，**3~5 年内不达收益线**；
- 分区还会打断现有 `route+src_id` 语义（分区键须为 pay_time），重建脚本的 DELETE 全表 → 分区下变为 DROP 分区 + 批插，改造本身不大但纯属提前投资；
- **不采用**，与 A-20261008-003 §四"分区设计先行、不执行"的口径一致。
