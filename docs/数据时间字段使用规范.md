# 数据时间字段使用规范

**生效日期**: 2026-08-01
**适用范围**: 全系统统计分析(预设视图、自助分析、自定义 SQL、周报/审计输出)
**关联文档**: [数据时间审核报告.md](数据时间审核报告.md)(一次性审计快照)、[规划设计.md](规划设计.md)、[数据同步与加工说明.md](数据同步与加工说明.md)

> 本规范基于 2026-08-01 的全系统时间审核结论制定,目的是确保所有统计分析的时间标签合理、可比、可信。

## 一、客服上班时段与统计合规原则

- **客服上班时间**:全年无休 `08:00 ~ 23:59`(北京时间)
- **客户自操作**:提现等可发生在任意时段(含 0~7 点)
- **合规原则**:
  - 凡**客服操作记录**(`cs_records.operation_time`、`refunds.created_at_raw` 真实客服、`service_tickets.register_time`、`external_complaints.handle_time` 等)按理应落在 08:00~23:59
  - 凡**系统自动操作**(SYS/system/Wallet/WeChat 自动退费转入、套餐激活、自动赠送工单)可落在凌晨,合规
  - **数据库时区** = `Etc/UTC`,所有业务时间已存为 `timestamptz`(aware)。统计/显示时统一 `AT TIME ZONE 'Asia/Shanghai'` 转北京时间

## 二、SYS/system 系统操作人排除标准(强制)

### 2.1 标准排除清单

```python
["sys", "system", "SYS", "System"]  # 必须 4 种写法全列
```

### 2.2 为什么必须 4 种全写

- **PostgreSQL `NOT IN` 大小写敏感**(`varchar` 默认按字节比较)
- `refunds.operator` 实际并存 `system`(8132 条)和 `SYS`(5577 条)两种写法
- 只写 `["sys", "system"]` 会**漏排 5577 条 SYS 系统退款**(退到会员钱包,非真实现金流出),导致金额虚高、人员工作量虚增
- **唯一例外**:`wallet_withdrawals` 用 `op_type` 区分(`用户提现` vs `订单退费转入`),不依赖 operator

### 2.3 引擎层过滤写法

```python
# preset_views_seed.py 中的标准写法
{"field": "operator", "op": "notin", "value": ["sys", "system", "SYS", "System"]}
```

或 SQL 层:
```sql
WHERE operator NOT IN ('sys', 'system', 'SYS', 'System')
```

### 2.4 真实现金流出定义(沿用规划设计.md)

```
真实现金流出 = 直接退款(refund_method='线上' AND operator NOT IN ('sys','system','SYS','System'))
            + 用户提现(wallet.op_type='用户提现')
```

## 三、时间字段优先级表

> 选字段时**优先用「推荐」列**,「不推荐」列因不可靠或语义不符,仅在明确知晓风险时使用。

| 分析场景 | 推荐字段 | 不推荐 | 原因 |
|---|---|---|---|
| 客服接待时段/工作量 | `cs_records.operation_time` | — | 已验证干净(0.004% 异常) |
| 退费单产生时间 | `refunds.created_at_raw` | ~~`updated_at_raw`~~ | updated_at_raw 被 SYS 03:15 批量覆盖 |
| 工单产生时段 | `service_tickets.register_time` | ~~`finish_time`~~ | finish_time 89% 不可靠(见第四节) |
| 工单完成时间 | `handle_duration` + `register_time` 推算 | ~~`finish_time`~~ | 同上 |
| 用户提现时间 | `wallet.op_time`(`op_type='用户提现'`) | — | 注意排除 `订单退费转入`(SYS 自动) |
| 设备套餐生效 | `device_combos.start_date` / `end_date` | ~~`created_at_raw`~~ | created_at_raw 含 02:05 Wallet 批量激活时间 |
| 外部/卡商投诉日期 | `complaint_date` | — | 日期型(00:00:00),无小时维度 |
| 商户号退款时间 | `merchant_refunds.trade_time` | — | 微信侧自动时间 |

## 四、不可靠时间字段清单(已在 UI 隐藏)

以下字段因数据质量问题,在数据源注册里已设 `is_filterable=False`,**不再出现在自助分析的筛选器/维度选择 UI**。字段数据保留,直接 SQL 仍可查(但需知晓风险)。

| 字段 | 不可靠原因 | 替代方案 |
|---|---|---|
| `ticket.finish_time` | 89% 非真实完成时间:50% 被 BMS 批量覆盖(finish>register+12h)、23% finish==register(同步填充)、17% 同瞬填充;仅 10.7% 是真实完成 | `register_time`(产生时段)+ `handle_duration`(处理时长) |
| `refund_wide.ticket_finish_time` | 同上(来自 ticket 表关联) | 同上 |
| `refund.updated_at_raw` | 被 SYS 03:15 批量任务覆盖(841 条/27 天),反映"最后触碰时间"非真实业务变更时间 | `created_at_raw`(创建时间,稳定) |

### 4.1 finish_time 不可靠的证据(2026-08-01 审计)

对「已完成且 handler 非空」工单核对 `register_time` vs `finish_time`:

| 时序类型 | 数量 | 占比 |
|---|---|---|
| finish 晚于 register > 12h(被批量覆盖) | 5967 | 49.6% |
| finish == register(同步填充) | 2773 | 23.0% |
| finish == register 同瞬(自动填充) | 2002 | 16.7% |
| **真实完成(稍晚于 register)** | **1282** | **10.7%** |

典型证据:`企微-叶珍凤` 工单 register=2026-07-28 14:52,finish=2026-07-30 07:09(批量覆盖);`企微-吴晓龙` 工单 register=2026-07-26 07:55,finish=2026-08-01 06:11(6 天后批量覆盖)。

### 4.2 若必须统计工单完成时间

```sql
-- 仅保留真实完成记录(10.7% 样本,慎用,样本量小)
WHERE status = '已完成'
  AND handler IS NOT NULL AND handler <> ''
  AND handler NOT IN ('SYS', '客户')
  AND finish_time BETWEEN register_time AND register_time + INTERVAL '12 hours';
```
