# CSCTalon 规划设计审查报告 v0.6（管理/工作安排视角）

> 日期：2026-08-18 · 审查对象：[规划设计.md](规划设计.md)（v0.4）+ [规划设计-v0.5.md](规划设计-v0.5.md）
> 审查技能：pmbok8-project-management / requirements-definition / product-manager-toolkit / writing-plans / csctalon-workflow-design / csctalon-management-effectiveness
> 结论：**设计层合理且完整度较高（数据模型/模块/角色/交互/闭环均覆盖）；但"项目治理层"缺失——无验收标准、无成功度量、无里程碑/工作量/RACI、无变更管理流程、无迁移与上线执行计划。规划停留在"系统设计文档"，未达到"可交付的项目规划"。**

---

## 一、合理性评估（是否合理）

### ✅ 合理之处
1. **理念正确**：管理哲学（不过度管理/归因不归责/例外管理/闭环分级）与 management-effectiveness 技能完全一致——"系统解决问题不制造麻烦"。
2. **范围贴合定位**：7 大模块 + 5 级角色 + 交互规范，符合"客服中心工作台 + 数据分析平台"定位；数据源策略（在线文档分场景混合）务实。
3. **决策机制好**：30 项 ADR 已确认（角色/聊天记录/OCR/发票/排班/政策等），避免反复摇摆。
4. **分层路线合理**：Phase 0（横切）→ A（高价值低依赖）→ B（全新模块）→ C（增强收敛）→ D（占位）顺序正确。

### ⚠️ 不合理/需补强处
| # | 问题 | 技能依据 | 说明 |
|---|------|---------|------|
| R1 | **缺成功度量指标** | product-manager-toolkit「每功能必须有成功度量」 | 规划说"砍掉没人看的报表"，但没定义"如何知道有人看"（报表使用率/点击率）；待办闭环率、审批时效、挽回成功率提升均无目标值 |
| R2 | **优先级缺量化** | product-manager-toolkit「RICE/MoSCoW」 | 路线图只标 P0/P1/P2，无 RICE 得分或 Must/Should/Could/Won't 清单；如"发票登记(P1)"与"投诉统计(P0)"的真实优先级缺乏数据支撑 |
| R3 | **需求缺验收标准** | requirements-definition「每条需求必须有验收标准」 | 7 模块只有设计描述，无"FR-XXX + 验收标准 + 测试场景"，无法判断"完成" |
| R4 | **非功能需求缺失** | requirements-definition「NFR 可度量」 | 性能（接口 P95 响应/并发）、安全（审计/权限/数据）、可用性（容错/降级）无量化要求 |

## 二、完整性评估（是否完整）

### ✅ 已有（设计层覆盖充分）
数据模型（15 新表+5 变更）、7 模块逐项设计、5 级角色权限矩阵、交互规范（四范式/色板）、统一工作流（待办/通知/状态机）、知识库/预警/跨部门、管理哲学、12 条风险、5 期路线图、30 项 ADR、数据源策略。

### ❌ 缺失（项目治理层，按 PMBOK 8 七大绩效域逐项对照）
| 绩效域 | 缺失内容 | 影响 |
|--------|---------|------|
| **干系人** | 无干系人登记：谁是项目发起人/验收人（总主管张蕾？）/最终用户代表/跨部门对接人 | 验收无主、需求无确认人 |
| **治理** | 无项目章程：目标/边界/成功标准/审批链；无变更管理流程（新需求如何进入→评估→排期） | 范围蔓延、ADR 被绕过 |
| **范围** | 需求无 FR 编号与验收标准（同 R3）；无"明确不做"清单（Won't Have） | 边界模糊 |
| **进度** | 路线图有 Phase 无里程碑日期、无工作量估算（人日）、无依赖关系图 | 排期不可控 |
| **资源** | 无 RACI（谁负责/批准/咨询/知会）；无开发/测试人力规划 | 责任不清 |
| **风险** | 12 条风险缺责任人/触发条件/应对措施/缓解跟踪 | 风险无人跟进 |
| **财务** | 无成本/工作量估算（内部项目可简化为"人日"级） | 无法排资源 |

**另缺（流程与上线层）**：
- **验收与测试计划**：无端到端测试策略/回归清单/上线验收流程。
- **数据迁移执行计划**：E1-E3 定了策略，但无"在线文档/企微→系统"的历史数据导入步骤、双跑期、校验规则。
- **运维与支持**：备份恢复（ADR 里"暂缓"未排期）、系统监控（现有预警是业务预警非系统级）、培训（用户手册/角色化培训）、初始权限配置清单。
- **效果度量与复盘节奏**：上线后如何按成功度量验收、复盘周期（周会/月度 postmortem）、迭代节奏。

## 三、更好的需求功能规划方案（v0.7 规划升级建议）

### 3.1 规划文档应补的 5 层结构（按技能产出）

| 层 | 技能 | 产出物 | 示例 |
|----|------|--------|------|
| **需求层** | requirements-definition | 每模块 FR 编号 + 验收标准 + 测试场景 + NFR | FR-01 排班：管理员可对人员×日期排班，验收=批量排班 50 人 1 分钟完成；NFR：列表接口 P95<300ms |
| **优先级层** | product-manager-toolkit | RICE 评分表 + MoSCoW 清单 + 每功能成功度量 | 待办中心：Reach=全部角色, Impact=高, 成功度量=审批时效 P95<24h |
| **治理层** | pmbok8 | 项目章程 + 干系人登记 + WBS + 里程碑(带日期) + RACI + 工作量估算 + 风险登记册(责任人/触发/应对) | 里程碑 M1(8/31)=角色重构+待办闭环上线；RACI：排班模块 负责=张蕾 批准=管理员 |
| **执行层** | writing-plans | 每 Phase 出实施计划 docs/plans/YYYY-MM-DD-*.md（bite-size 任务/TDD/频繁提交） | 待办闭环计划：改 agenda.py → 加测试 → 跑通 → 提交 |
| **度量层** | management-effectiveness + postmortem | 上线验收按成功度量；周会/月度复盘；报表使用率季度审计 | 季度审计报表"谁看/做什么决策"，下线僵尸页 |

### 3.2 具体补丁建议（改哪些章节）

1. **§十二 路线图 → 升级为里程碑计划**：给 Phase 0/A/B/C 加目标日期 + 人日估算 + 依赖 + 验收标准（对照 A-P0/B-P0 行动项）。
2. **新增「成功度量」章节**：7 模块各 1~2 个可度量指标（闭环率/时效/使用率/成功率），上线即埋点。
3. **新增「验收与测试」章节**：每模块验收标准 + 端到端场景 + 回归清单。
4. **新增「项目治理」章节**：章程（目标/干系人/验收人）+ RACI 表 + 变更管理流程（新需求→评估→ADR→排期）。
5. **风险 §十一 → 风险登记册**：12 条风险补责任人/触发条件/应对措施/跟踪频率。
6. **数据迁移 §十三 → 加执行计划**：导入步骤、双跑期、校验规则、回滚。
7. **新增「上线与运维」章节**：备份恢复排期、系统监控、培训计划、初始权限配置清单。

### 3.3 优先级重排建议（RICE 视角）

| 功能 | Reach | Impact | Conf | Effort | RICE | 建议 |
|------|-------|--------|------|--------|------|------|
| 统一待办中心补全（发票/微信审批） | 高 | 高 | 高 | 小 | **最高** | P0（已列） |
| 投诉审计 | 中 | 高 | 中 | 中 | 高 | 保持 P0 |
| 排班（企微对接） | 中 | 高 | 中 | 大 | 中 | P1（对接依赖探测） |
| 发票登记 | 高 | 中 | 中 | 中 | 中高 | 保持 P1 |
| 政策措施增强 | 中 | 中 | 高 | 中 | 中 | P1 |
| 数据质量看板 | 低 | 低 | 中 | 小 | 低 | 可后置 P2（先占位） |

> 说明：上表为示例口径，真实 RICE 需按"每季度影响人数/影响程度/置信度/人月"填入后决定。

## 四、结论

- **合理性**：设计理念与分层路线合理 ✅；缺**成功度量**与**量化优先级** ⚠️。
- **完整性**：设计层完整（数据/模块/角色/交互/闭环）✅；**项目治理层缺失**（无验收/里程碑/RACI/变更管理/迁移执行/上线运维）❌。
- **更好方案**：按 §3.1 的五层结构（需求层/优先级层/治理层/执行层/度量层）升级规划，即可从"系统设计文档"变为"可交付的项目规划"。
- **行动项**：已登记 B-P0-1（验收+度量）、B-P1-1~3（治理/风险/变更）、B-P2-1~2（迁移/运维），见 [审查行动项登记.md](审查行动项登记.md)。

> 建议：先补 B-P0（验收标准 + 成功度量）——它同时解决 R1/R3，是"规划可验收"的前提；再补 B-P1 治理工件（里程碑/RACI/风险登记册），让 Phase 路线图可执行、可跟踪。
