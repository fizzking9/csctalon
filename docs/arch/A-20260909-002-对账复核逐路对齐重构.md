## 〇、顶层口径：E 是财务基准，用 E 调校 ABCD(用户 2026-09-09 明确)

> "现金流 E 路最准确; 运营操作 ABC 路准确(需剔除不相干记录); D 路手动登记会有误操作;
> ABCD 登记内容主要是便于分析, 财务上以 E 为准。我们是通过 E 来调校 ABCD, 然后进行经营分析和干预经营行为。"

**本方案的一切展示/交互均以此单向关系为纲**:

```
E(商户号真实退款流水) = 财务权威基准
   │  用 E 调校(校验 + 纠偏)
   ▼
ABCD(运营登记台账) = 便于经营分析/干预经营行为的登记
   ├ A 线上直退 / B 钱包(用户提现)/ C 闪猫   → 运营操作较准, 需剔除不相干记录
   └ D 手动登记                              → 人工台账, 会有误操作(可信度最低, 最需治理)

差异的两类方向(含义不同, 治理动作不同):
  ① E 有, ABCD 无登记      → "漏记/空悬": 真实发生了退款但运营没登记 → 建议补录到对应路
  ② ABCD 有, E 无对应      → "疑似误记/多记": 登记了但财务流水无 → 建议核对/忽略/标残留
                            (E 延迟 1~2 天除外: 待复查)
最终产出: 调校后的 ABCD → 经营分析可信 + 干预经营行为有据
```

**对页面语义的推论**:
- "已对齐" = 该路登记与 E 一致(E 有该单、该单也在 E) → 可信, 可放心用于经营分析
- "差异" 永远以 E 为裁判: 该路多记的(E 无)→ 治理(疑误操作/残留); 该路漏记的(E 有路无)→ 空悬/补录
- 不做"A 与 E 平等互相找差异"的双向平等展示, 而是"E 调校 ABCD"的单向审视

## 一、问题诊断(用户不满的根因)

### 1.1 现有页面(ReconcileCheck.vue)的展示模型缺陷

现有页面把**两套不同语义的数字混在一起显示**,造成"林林洒洒没意义":

| 区块 | 语义 | 问题 |
|---|---|---|
| 五路 KPI(A/B/C/D/经营合计/E/偏差) | ABCD **总量** vs E **总量** | 总量对比无法定位是哪路的问题; 偏差是各路差异**互相抵消后的净值**(如 A 多 D 少可能偏差为 0 却两路都有问题) |
| E 勾稽归属表 | E 每笔 → 归 A/B/C/D/unmatched | 只给汇总, 不能下钻单条; 且 "E 归到 A" ≠ "A 与 E 对齐" |
| D 重复/残留提示 | D 路内部重复/脏数据 | 只警告, 不接治理 |
| 逐笔核对 | 建批次后 E→ABCD 打标 | 仅留痕不改源, 非治理闭环 |

**核心缺陷**:展示的是**"总账对比"而非"逐路对账"**。用户真正要的是**每一路单独跟 E 核对**:
- 该路经营单有多少能在 E 找到(路→E 覆盖率)→ 找不到的是**该路差异**
- 该路应承接的 E 单是否齐全(E→路)→ 少了的是**E 空悬/待承接**
- 剩下的(差异/空悬/存疑)**单列、下钻、给治理建议**

### 2.2 "逐路对齐"的口径定义(以 E 为基准单向调校, 路 × 退款方式)

依据顶层口径(§〇): **E 是裁判, 调校 ABCD**。对每一路 R ∈ {A线上, B提现, C, D},
只审视两类差异:
- **误记/多记**(R 有, E 无)→ 该路登记了财务上不存在的退款 → 疑误操作/残留 → 治理
- **漏记**(E 有, R 应承接却无)→ 真实退款未登记 → 空悬/补录

差异方向 + 治理动作(在 2.3 细化为下钻):

**A 线上直退(仅 refund_method='线上' 且已退款)**
- 已对齐: A线上单 → platform_order_no 在 E(同窗退款成功) → 近段应 ~99%
- 误记(差异): 近段(E 覆盖起点后)仍未在 E 找到 = 疑多记/漏采/状态不同步 → 下钻核对
- (A 转入提现账户/线下 不在此路对账 —— 见 §一·5 矩阵)

**B 用户提现(链路对账, 非直接比对)**
- 链路: B提现 remark 解析 RF → A 路 refund_no(refund_method='转入提现账户')
  → 该 A 单 platform_order_no → E 水单
- 已对齐: 链路通(B→A→E 三段都有, 近30天 96%)
- 差异(链路断): ①RF 在 A 找不到 ②A 单不在 E → 分别下钻(疑 B 误操作或 A/E 未记)
- B 订单退费转入/系统扣费: 钱包内部资金, 不参与 E 对账

**C 闪猫(已退款)**
- 已对齐: C order_no(WXALR) → E platform_order_no(WXALR)
- 误记(差异): C 有 E 无(闪猫登记退了但 E 无流水 → 疑状态不符/误操作)
- 漏记: E 有 C 无(E 退了但 C 未记已退款/状态不符 → 补录/状态修正)

**D 手动(已退款, 剔 dup_residual/ignored + 剔 A线上 已承接歧义)**
- 已对齐: D order_no → E(非 A 线上重复部分)
- 误记(差异, D 可信度最低最需治理): D 有 E 无, 须区分
  = E 延迟(近2天, 待复查) / 乱年份残留(待治理 dup_residual/ignore) / 线下手动(不对E)
- A∩D 歧义单列: 同单在 A 线上 与 D 都记 → 按 A 优先建议标 D dup_residual(见 M-3 25行候选)

### 2.3 差异/空悬/存疑的"单列下钻 + 治理建议"

用户核心诉求: 剩下的都单列下钻给建议。每一类差异都提供:

| 类别 | 下钻内容 | 治理建议(接 A-20260909-001) |
|---|---|---|
| 误记/多记(该路有, E 无) | 该路经营单列表(order_no/金额/时间/质量状态) | 若 E 延迟→"待 E 补录复查"; 若疑残留/误操作→"彻底忽略/标 dup_residual"; 若线下→标记"非 E 范围" |
| 漏记/空悬(E 有, 路无) | E 水单列表(单号/金额/时间/SN) | 建议: 补录到对应路 / 确认为 B 钱包链路 / 忽略 |
| A∩D 归属歧义 | 同单在 A 与 D 的双边行 | 按用户裁定 A 优先: D 侧该行建议"标 dup_residual"(A 已计) |
| 已对齐 | (可选)该路对齐行明细 | — |

每条差异行 → 复用质量页处置(确认/忽略/回填/标重复), 由 A-20260909-001 的服务/API 支撑, 前端可跳转或内嵌操作。

## 三、技术落点

### 3.1 后端: 新增逐路对齐查询(替代/补充现有 preview_check)

新增 `reconcile_check.per_route_alignment(db, start, end)` 返回:

```jsonc

  "e_data_until": "2026-09-07",
  "e_coverage_from": "2026-06-01",        // E 采集起点(之前单不在E, 不做对齐误报)
  "routes": {
    "A": { "method": "线上", "total": 8412, "matched_in_e": 8330,
           "unmatched": 82, "unmatched_amt": 12345.6 },   // 仅线上直退
    "B": { "method": "用户提现", "total": 2153,
           "chain_ok": 2068, "chain_break": 85,            // 链路 RF→A转入→E
           "break_no_a": 36, "break_a_no_e": 49 },
    "C": { "total": 61, "matched_in_e": 57,
           "c_no_e": 4, "e_no_c": 3 },
    "D": { "total": 2371, "matched_in_e": 2290,
           "excl_a_overlap": 1006, "unmatched": 81 }       // 剔除A线上歧义
  },
  "issues": {                                                // "剩下单列"
    "e_orphan":  { "count": 64, "amount": 6396.17 },        // E无路承接
    "a_d_overlap": { "count": 1006, "amount": 179655.2 },   // A∩D歧义
    "a_transfer_not_e": { "count": 3500, "amount": 0 }      // A转入未在E(参考, 非主对账)
  }
}
```

- 差异明细单独端点(分页): `GET /reconcile/alignment/{route}/unmatched?start&end&page`
  → 返回该路"E 找不到"的经营单列表(带建议)
- B 链路断明细: `GET /reconcile/alignment/b-chain-break?start&end&page&break_type=no_a|a_no_e`
- 空悬明细: `GET /reconcile/alignment/e-orphan?...` → E 无路承接的水单
- 歧义明细: `GET /reconcile/alignment/ad-overlap?...` → A/D 同单对(可跳治理)
- 复用 M-3 的 `scan_ad_overlap_dup` 已识别的 25 行 A/D 候选逻辑(放大到全窗)

## 五、风险与注意

1. **"已对齐"的判定要防口径误导**: A 路 83.5% 在 E 找到 ≠ A 全对齐——A 的"线上直退"若含
   未真正走线上退款的部分(如已退款但实际线下), 会误报差异 → 对齐判定需明确 E 的覆盖边界
   (E=商户号线上退款水单, 仅覆盖线上; A 中 refund_method=线上 才应要求 E 对齐)
2. **D 路差异的"合理原因"占大头**: E 延迟 2 天 + 线下手动, 若不区分会大量误报 →
   差异列表需带原因分类(E 延迟待复查/疑似残留/线下), 减少噪音
3. **歧义 A∩D 的 1006 笔**: 不能自动剔 D(A 优先是人工裁定的治理规则, 需逐条确认),
   方案只"单列+建议", 处置走人工
4. 性能: 全窗差异明细需分页, 避免一次拉全量
