## 一、目标与背景

BMS「退款记录报表」（已入库 `refund_record_reports`，含平台订单号/商户号/设备号/精确退款时间/金额/状态）是**线上退款水单**。对账价值：
1. **E 路水单补充**：`merchant_refunds`（Excel 快照，7/20 截止、wx_refund_no 损坏）之外，`refund_record_reports` 提供持续、精确的线上退款流水 → 作 E 路的实时水单来源之一。
2. **D 路时间回填**：`manual_refunds.op_time`（实际退款时间）在人工台账里常缺失/不准 → 用退款记录报表的精确退款时间按可信匹配回填（带质量标记）。
3. **逐笔勾稽**：每笔退款记录报表行 → 尝试匹配 A/B/C/D 路单据 → 标 matched/未登记，下钻"商户实扣但经营未记账"的对账差异。

## 二、核心不变式（不破坏 v4 LOCKED）
- 现有核算口径（`_cash_routes_total` 等）：经营四路 A+B+C+D 合计、E=merchant_refunds SUCCESS 对账基准、偏差=(A+B+C+D)−E——**全部不动**。
- `refund_record_reports` 是**新增独立表**，不与 merchant_refunds 合并、不改变 E 的取数来源。
- D 路回填只**补 op_time 空值/倒挂值**，不改变 is_refunded/refund_amount 等已确认字段；每次回填写 `quality_status=auto_filled` + `quality_note` 溯源，可审计可回滚。

## 三、D 路 op_time 时间回填设计

### 3.1 匹配目标
`manual_refunds` 中 `is_refunded='是'` 且 `op_time IS NULL`（或明显倒挂：op_time < register_time - 1天）的行。

### 3.2 匹配源
`refund_record_reports`（已入库，含 device_sn/merchant_id/refund_time/refund_amount/platform_order_no）。

### 3.3 匹配规则（多级，命中即停）
| 优先级 | 匹配键 | 条件 | 说明 |
|---|---|---|---|
| L1 | order_no ↔ platform_order_no | manual.order_no == report.platform_order_no | 最强键（若 D 台账有真实订单号） |
| L2 | device_sn + refund_amount | 相等 | 设备+金额锁定（容忍金额 ±0.01） |
| L3 | device_sn + 时间窗 | report.refund_time ∈ [register_time−7d, register_time+7d] | 宽匹配，仅当唯一候选 |
| 兜底 | 唯一命中才回填；多候选 → pending 人工 | | |

### 3.4 质量护栏
- 仅回填 `op_time IS NULL` 或 `op_time` 倒挂的行；
- 金额匹配允许 ±0.01（元）；多候选命中同一 manual 行 → 不自动写，标 `quality_status=pending`；
- 回填值 = `report.refund_time`（naive-北京已在入库时转 UTC aware）；
- 回填后：`manual_refunds.op_time` 更新 + `quality_status='auto_filled'` + `quality_note='由退款记录报表 refund_time 回填,来源 refund_record_reports.id=N'`；
- `refund_record_reports.backfill_manual_refund_id` 记录回填到的 manual id（溯源反向）。

### 3.5 幂等/重复执行
同一 report 行只回填一次（backfill_manual_refund_id 已置位则跳过）；manual 行已有 auto_filled 的 op_time 且来源 report 未变 → 跳过。重复执行安全。

## 四、E 路水单勾稽视图（逐笔勾稽）

### 4.1 勾稽方向
以 `refund_record_reports` 每行为基准，尝试匹配经营四路 A/B/C/D 的对应单据：

| report 行特征 | 匹配目标 | 匹配键 | 结果标记 |
|---|---|---|---|
| 平台订单号 WX/WS/WN 前缀 | A 路 refunds（退费单线上直退） | refunds.platform_order_no == report.platform_order_no（或 refund_no） | A-matched |
| 设备号+金额 | B 路 wallet / C 路 shanmao / D 路 manual | wallet/shanmao/manual 的 device_sn+refund_amount | B/C/D-matched |
| 无任何匹配 | - | - | **未登记**（= 商户实扣但经营侧未记账，对账差异下钻） |

### 4.2 输出（新接口，不改现有）
`GET /analytics/reconcile/water-statement`（或独立 reconcile router），返回：
```
{
  date_start, date_end,
  total_report,               // 退款记录报表总笔数/金额
  matched_count / matched_amount,
  unmatched_count / unmatched_amount,   // 未登记 = 对账差异明细
  by_route: {A: n, B: n, C: n, D: n},   // 命中各经营路的分布
  unmatched_samples: [...],              // 未登记明细(下钻, 分页)
}
```
- 金额单位元（与退款报表一致），不做分/元换算（外部口径是元）。
- 时间窗口：report.refund_time 落在窗口内。

### 4.3 与现有 /analytics/cash/merchant 的关系
现有"商户号对账"是聚合口径（按 E vs A+B+C+D 偏差）；勾稽视图是**明细逐笔级**，是它的下钻补充，不重复不替代。前端展示位二期定（可在决策概览加 Tab 或独立页）。

## 五、接口契约
| 端点 | 方法 | 说明 | 权限 |
|---|---|---|---|
| `POST /reconcile/backfill-d-op-time` | POST | 触发 D 路 op_time 回填（幂等），返回 {matched, skipped_pending, manual_rows_updated} | Admin/Supervisor |

## 六、风险清单
1. **误匹配风险**：同设备同金额多笔退款可能张冠李戴 → L2/L3 要求唯一候选，多候选进 pending；金额仅作佐证不作唯一锚。
2. **D 路 op_time 语义**：D 台账 op_time 是"客服操作退款时间"，退款报表 refund_time 是"微信实际扣款时间"——两者理论上接近但不绝对相等；回填仅当缺失/倒挂，且留 auto_filled 标记供人工复核。
3. **勾稽口径边界**：退款记录报表含"退款成功"与可能其他状态；只勾稽 refund_status='退款成功' 的行，避免把失败/处理中计入。
4. **不影响 v4**：不修改 `_cash_routes_total`/`merchant_cash_summary` 等；新增独立 service/API。需回归测试保证 0 影响。
