## 〇、结论摘要（TL;DR）

1. **原设计判断正确，落地时漏了一环**。`A-20260910-001 §四` 已明确
   「生产 Docker 需 Xvfb；`xvfb-run` 包裹 或 常驻 `Xvfb :99` + `DISPLAY=:99`」，
   并写明「探测显示环境可用性，不可用则返回 **501**」。**方向是对的。**
2. **实际落地只做了「装包」**：`backend/Dockerfile` 加了 `xvfb xauth`，但
   `docker-compose.yml` 的启动命令、容器 PID1 均**没有任何进程启动 Xvfb**，
   `$DISPLAY` 为空 → 有头浏览器必然失败。
3. **更隐蔽的问题：探测判据把「装了没」当成「跑着没」**。原
   `check_display_available()` 判据为 `$DISPLAY 存在 or which(xvfb-run)`。
   容器装了包 → `xvfb-run` 必定在 PATH → 判据返回 **True** → **501 降级从未触发过**，
   用户实际收到 **502 + Playwright 原始日志**（`Missing X server or $DISPLAY`）。
4. **修正方向**：把判据从「安装态」改为「运行态」（X socket），并在真正启动浏览器前
   **按需拉起 Xvfb**；确实拉不起来才走 501。

## 一、偏差明细（对比 LOCKED 设计）

| # | LOCKED 设计要求（§四） | 实际落地 | 偏差性质 |
|---|---|---|---|
| 1 | 生产容器需 Xvfb 提供 DISPLAY（`xvfb-run` 包裹 或常驻 `Xvfb :99` + `DISPLAY=:99`） | Dockerfile 装了包；**没有任何进程启动 Xvfb**，`$DISPLAY` 为空 | 🔴 **未落地** |
| 2 | 探测方式：`os.environ.get("DISPLAY")` 存在 → 认为有显示服务；否则尝试探测 `xvfb-run` 是否在 PATH | 未区分「包已装」与「服务在跑」→ 容器内返回 True（误判） | 🟠 **判据不足** |
| 3 | 降级：不可用时返回 **501** + 可执行的一键命令 | 501 分支**从未被触发**（因 #2 误判），用户见 502 + 原始日志 | 🟠 **降级失效** |
| 4 | 降级命令：`cd /path/to/backend && ./.venv/bin/python ../scripts/xxx_login.py` | 该路径在**生产容器内不存在**（容器无 `scripts/`、无 `.venv`） | 🟠 **假降级路径** |

**根因一句话**：**「包装了」≠「服务在跑」**。设计文档写的是「需 Xvfb（服务）」，
落地时被简化成了「装 xvfb（包）」，而探测函数又恰好用「包装了没」当判据，
两者叠加导致**功能静默不可用，且降级保护也一起失效**。

**实测证据**（2026-09-13 生产容器，只读）：

```
$ docker exec csctalon-backend sh -c 'command -v Xvfb; command -v xvfb-run; echo DISPLAY=[$DISPLAY]'
/usr/bin/Xvfb
/usr/bin/xvfb-run
DISPLAY=[]
$ docker exec csctalon-backend python -c "from app.services.shared_doc_login_service import SharedDocLoginManager as M; print(M.check_display_available())"
True                      ← 误判（实际 $DISPLAY 为空）
$ docker inspect csctalon-backend --format '{{.Path}} {{.Args}}'
gunicorn [app.main:app -w 1 ...]        ← PID1 是 gunicorn，无 Xvfb
```

反证（临时拉起 Xvfb 后立即验证并清理）：

```
$ docker exec csctalon-backend sh -c 'Xvfb :99 & export DISPLAY=:99; python - <<PY
  from playwright.sync_api import sync_playwright
  with sync_playwright() as p:
      b = p.chromium.launch(headless=False)   # 有头
      pg = b.new_page(); pg.goto("https://docs.qq.com/sheet/...")
      print("HEADED_LAUNCH_OK", pg.url)
  PY'
HEADED_LAUNCH_OK https://docs.qq.com/sheet/...
```

→ **Xvfb 缺失是唯一根因**；装包本身没问题。

## 二、修正方案（本次已实现）

### 2.1 判据：安装态 → 运行态

| | 旧 | 新 |
|---|---|---|
| `check_display_available()`（只读，供 `/states` 提示） | `$DISPLAY` 有值 **or** `which(xvfb-run)` 有值 | `$DISPLAY` 指向的 **X socket 真存在**（或远程 DISPLAY）**or** `xvfb-run` 在 PATH |
| `ensure_display_available()`（可自愈，launch 前调用） | 不存在 | 运行态判定 → 不满足则**按需拉起 Xvfb** 并注入 `DISPLAY` → 仍不行返回 False |

**为什么保留两个函数**：`check_*` 用于 GET 接口回显状态，**不应有起后台进程的副作用**；
`ensure_*` 是写操作，只在真正要 `launch(headless=False)` 前调用。

**远程 DISPLAY 例外**：`DISPLAY="host:0"` 走 TCP，本地无 socket 可探 → 信任之（避免误判 501）。

### 2.2 按需拉起（替代「常驻 Xvfb」）

```
$DISPLAY 有效？ ──是──> 直接用
        │
        否
        ▼
镜像有 xvfb-run？ ──否──> 501 降级（+ 两段式命令）
        │是
        ▼
拉起 `xvfb-run -n 99 -s "-screen 0 1280x800x24" sleep infinity`
（幂等：socket 已存在则复用；上限 2s 等待 socket 就绪）
        │
        成功 ──> 注入 os.environ["DISPLAY"]=":99" → launch(headless=False)
        失败 ──> 501 降级
```

**取舍（为什么不选常驻 `Xvfb :99`）**：

| 维度 | 常驻 | 按需（本次采用） |
|---|---|---|
| 内存 | 多一个 ~20MB 常驻进程 | **零常驻开销** |
| 首次点击延迟 | 无 | +约 1s |
| 部署改动 | 需改 `docker-compose.yml` command（每次升级重建都依赖该配置） | **纯应用层，无需动编排** |
| 单 worker 风险 | 无 | Xvfb 拉不起来时最多占用 worker 约 2s（有硬上限） |

选按需的另一理由：**不改编排即可对旧版本镜像生效**（回到 2026-09-11 镜像也能自愈），
降低本次修复的部署耦合。

**为什么不改用 `headless: true` 绕开 Xvfb**：本链路的前提是**人来扫码**，
无头模式拿不到可供人工扫描的二维码渲染，且腾讯/金山对无头浏览器有识别风险。**不采纳。**

### 2.3 降级命令：改为两段式（修正假路径）

```
# ① 本地(macOS 有 GUI)生成登录态; 脚本会弹浏览器, 扫码后回车保存
cd backend && ./.venv/bin/python ../scripts/tencent_doc_login.py --url "<文档地址>"
# ② 上传到生产宿主机(挂载点 → 容器内 /app/data/browser_states)
scp backend/data/browser_states/tencent_doc.json tanzk@<服务器IP>:/tmp/ && \
  ssh tanzk@<服务器IP> "sudo mv /tmp/tencent_doc.json /opt/csctalon/browser_states/"
```

**单一事实来源**：命令文本由后端 `GET /api/v1/sync/shared-docs/cli-fallback` 下发，
前端「命令行」按钮只负责复制。修正前前端**另写了一份**同样的假路径 → 后端改了前端还是旧的。

**501 detail 不再塞长命令**：多行命令在 Element Plus 消息条里无法阅读/复制 →
501 改为指向「命令行」按钮，命令由上述接口提供。

## 四、风险清单

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | 按需拉起的 Xvfb 生命周期跟随后端进程（`sleep infinity`）；后端崩溃重启会残留旧 Xvfb | 低 | 容器重启即整体回收；socket 存在时复用不重复拉起（幂等）；可用 `XVFB_DISPLAY` 环境变量改显示号 |
| 2 | Xvfb 拉起期间占用**单 worker**（上限约 2s） | 中 | 硬上限 2s；失败即 501，不无限等；沿用现有单 worker 假设（与项目部署一致） |
| 3 | `check_*` 与 `ensure_*` 语义不同，易被误用 | 中 | 函数名区分（check 只读 / ensure 可自愈）；`start()` 内只用 `ensure_*`；测试锁定该契约 |
| 4 | 腾讯/金山改版导致登录页判定漂移 | 低 | 沿用原设计：以「离开登录域名」为稳定信号 + confirm 人工兜底 |
| 5 | 截图在 1280×800 下二维码不可扫 | 低 | Xvfb 屏幕设为 `1280x800x24`，与浏览器 viewport 一致；实测截图非空 |
