**状态**：LOCKED（v1.0）
**锁定日期**：2026-09-08
**锁定脚本**：scripts/lock-arch-docs.sh（人工审核通过）
**关联**：A-20260902-002（refund_wide 原设计，本文件为其 v1.1 精简变更）、A-20260902-011（商户号现金流 v4 口径）、A-20260905-002（E 路切换 refund_record_reports）
**触发**：用户提出"宽表构建逻辑应精简——A 路只需线上退款成功；宽表大体与 E 表一一对应；E 表有 T+2 延迟故保留宽表作即时版"（2026-09-08 多轮澄清后拍板方案 B）

## 一、背景与现状问题

### 1.1 refund_wide 现状（实测 2026-09-08，本地+生产一致）

| 指标 | 值 |
|---|---|
| refund_wide 行数 | 177,116 |
| refunds 全表 | 177,115 |
| 其中「线上 + 已退款」（A 路经营口径） | 41,997（金额 ¥590 万） |
| 其中「申请中 / 无需退款 / 驳回」等非成功 | ~135,000（占 76%） |

宽表当前**全量物化所有退费单**（含申请中/无需退款/线下/转入提现账户），是 LOCKED `A-20260902-002` 阶段 2 的原始设计（"为 refunds 所有退费单构建宽表行"）。

### 1.2 用户判断（本变更依据，已多轮确认）

1. A 路（refunds 线上直退）原始表只需「**线上 + 已退款**」进宽表，其余状态无统计意义。
2. **钱包水位**应从 `wallet_withdrawals` 单表解决（已核实：`wallet_balance` 每行=该账户操作后即时余额，单表自足，与 refunds/宽表无关）。
3. 宽表**大体与 E 表（refund_record_reports）一一对应**（已实测：E 覆盖窗口内命中率 99.7%），但因 **E 表 T+2 延迟**（平台当天不产生、只能次日抓前一天），不能当日实时 → **保留宽表作为 E 的"即时版"**，而非取消。
4. 宽表不能直接取消：仍有 2 个预设视图 + 1 条分类规则依赖其免 JOIN 物化。

### 1.3 决定性实测证据

**线上+已退款 ↔ E 表对应率**（用户判断的验证）：
- E 表覆盖期 2026-05-31 ~ 09-06（29,493 行）；refunds 覆盖自 2025-03。
- 同窗口（E 覆盖期内）命中率 = **99.7%**（16,060 订单中 16,012 在 E）。
- 全量 40% 命中率是窗口差（E 只从 5/31 采，2025-03 起老数据无 E 对账），非逻辑问题。

**mr_\* 商户退款字段 = 零消费死字段**（全库 `analysis_views` 含自建逐字段核实）：
- refund_wide 关联字段全部消费点仅 5 处：视图3 用 `service_item`；视图5 用 `wallet_op_time/wallet_id/wallet_op_amount/ticket_no`。
- `wx_refund_no / mr_trade_time / mr_refund_amount / mr_refund_status / mr_fee / merchant_id`（宽表版）**无任何视图/规则/接口消费**，仅存在于定义与构建填充处 + 1 句诊断手工 SQL（`uploads/run_match.py`）。

## 二、核心决策

### 2.1 宽表新定位

> **refund_wide = 「最终会进入 E 表（微信真实扣款水单）的线上退款」的当日即时物化层**，叠加少量审计/客诉辅助行。

主体口径与 A 路（线上+已退款）一致；E 表到账后可用于对账核验（对账本身走既有 E 路视图，不重复建设）。

### 2.2 行范围：方案 B（用户拍板）

```
行范围 = 线上+已退款                       （主体，≈41,997 行）
       ∪ 带 wallet 关联的退款单           （视图5 提现时序审计，≈22,097 行）
       ∪ 设备 SN 有外部投诉的退款单       （分类规则1 客诉覆盖，≈1,476 行）
```

实测合并后 ≈ **64,365 行**（较现状 177,116 缩 ~64%）。

- **线上+已退款**：经营统计口径（视图3 / 与 E 对账基准）。
- **带 wallet / 有外部投诉**：审计辅助行，不参与"经营≈E"统计口径，仅保证视图5/客诉分类不被收窄破坏。

### 2.3 字段精简（删死字段）

| 动作 | 字段 | 依据 |
|---|---|---|
| **删除** | `wx_refund_no / mr_trade_time / mr_refund_amount / mr_refund_status / mr_fee / merchant_id` | 全库零消费死字段，构建端纯负担 |
| **删除** | `ticket_finish_time` | 89% 被 BMS 批量覆盖不可靠（见 A-20260902-005，已在 UI 隐藏）；且**全库零消费**（无视图/规则引用）；保留它仅增加误解风险。删除方向与"已隐藏防误用"一致（物理删除是彻底化）。若审核希望保留列只删索引，可降级为"列保留、仅从 data_source_registry 移除注册" |
| **保留** | refund 主表冗余、`ticket_no/service_item/service_category/ticket_handler`、wallet 四字段、external_complaint 三字段、`matched_at` | 视图3/视图5/规则1 实际消费 |
| **待议** | `ticket_handle_duration` | 无直接消费，保留作审计（成本低）；如需可一并删 |

> ⚠️ 删除 mr_\* 是**删 refund_wide 的物化字段**，**不删** matcher 的 merchant_refund 关联匹配、不删 `merchant_refunds` 表（仍被 match.py 人工补关联 UI / E 路旧快照引用）。二者解耦。

## 四、数据库变更（ER 增量）

### 4.1 建表后变更（Alembic migration，单一 head）

`refund_wide` 表结构变更：
- **删列**：`wx_refund_no / mr_trade_time / mr_refund_amount / mr_refund_status / mr_fee / merchant_id / ticket_finish_time`
- 同时**删除** `ix_refund_wide_wx_refund_no` 索引（唯一消费它的诊断 SQL 同步移除）
- `ticket_handle_duration` 默认保留（见 §2.3 待议；若用户确认删则一并列入）

> Alembic 规范：新 migration 一个 head，`down_revision` 指向当前 head；删除列前确认无视图/规则引用（已核实）。存量数据列删即可，无需回填。

### 4.2 数据清理

- 存量 refund_wide 中不属新行范围的行：全量重建时**物理删除**（现有 upsert 逻辑只增改不删，残留行会滞留）。
- **实现方式（Developer 无歧义）**：全量重建完成后执行一条
  `DELETE FROM refund_wide WHERE refund_no NOT IN (<新行范围子查询>)`；
  增量重建不触发删除（增量只刷新 affected 行，残留删除由下一次全量承担）。
- **状态回退口径（见 §6 风险 5）**：行范围以物化时刻的「当前状态」判定。若某行曾满足范围、后被改回申请中/无需退款，则下一次全量重建时会因不在当前范围被清除——该场景罕见（已退款极少回退），且对账差异由 E 路视图兜底，宽表不做“历史保留”。
- 重建后应满足：`SELECT count(*) FROM refund_wide` ≈ 64,365。

## 六、风险清单

1. **删除 mr_\* 若未来要展示"该退款的微信侧事实"**：宽表失去该能力。缓解：E 表（refund_record_reports）已含真实扣款事实且对账视图已接 E；未来如需可在 E 视图侧补充，不必回宽表。
2. **视图5（提现时序）数据源语义需厘清**：视图5 消费的带 wallet 行主力是「转入提现账户/线下」（非线上）。本方案以"带 wallet 即保留"覆盖它，但需确认视图5 是否应改用 wallet 单表直查（那样更贴合其"提现"语义）——本变更不处理，另立评估。
3. **残留行清理**：当前宽表 upsert 全量重建不删已不存在 refund_no 的行（实测 177,116 vs 177,115 差 1）。本方案在全量重建时加清理，避免范围收窄后旧行滞留。
4. **触发链不一致**：`uploads.py` 上传后置任务每次全量重建宽表，而 bms_sync post-sync 已增量。范围收窄后全量重建成本下降（177k→64k），但仍建议 uploads 入口统一走 affected 增量（本变更不展开，标注后续）。
5. **范围判定口径漂移**：行范围依赖 `refunds.status='已退款'`，状态是**可变**的（申请中→已退款）。物化时以「当前状态」判定；已退款被改回申请中/无需退款的罕见回退场景，下一次全量重建会将其移出（见 §4.2），对账差异由 E 路视图兜底（E 路独立于宽表，不受影响）。设计取舍：不引入“曾满足即保留”的历史状态跟踪复杂度。
6. **LOCKED 文档变更**：A-20260902-002 为 LOCKED，本文件是对其阶段 2 的 v1.1 变更。需人工审核通过后：本文件标记 LOCKED + 打 tag；A-20260902-002 由人工增补 v1.1 变更注记（AI 不擅自改 LOCKED 文档）。
