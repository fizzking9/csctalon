5. **无"治一次复用"**:同类问题(如 WM 单 2031 年份 + E 无匹配)每次出现都要人工重新判断。

### 1.2 用户目标

1. 对账准确(核心不变式,不改动 LOCKED 权威口径的纳入/排除逻辑,只收敛实现)
2. 操作闭环(质量页处置 → 源头生效 → 下游同步排除/纳入 → 不再重复报警)
3. 足够多的修复手段(确认通过 / 编辑修正 / 彻底忽略 / 待 E 回填 / 恢复)
4. **治理学习**:治理一次 → 沉淀为规则 → 后续同类行自动(suggest)或半自动(auto)治理

### 1.3 治理落点决策(已与用户对齐)

**治理状态落在源头业务表**(manual_refunds 等),**不落在宽表**:
- `cash_flow_wide`/`refund_wide` 是 DELETE+重建的纯派生表,人工状态塞入会在每次重建丢失。
- 既有先例 `dup_residual` = 标在 manual_refunds 源头,下游现金流水/统计/导出同步排除,一致可追溯。
- 源头治理 → 所有消费方(宽表/统计/导出/对账)自动受益;宽表治理 → 源头仍脏,下一个报表又踩坑。
- 宽表只是重建/统计时**应用统一的源头排除规则**。

## 二、核心设计

### 2.1 三层治理架构

```
┌─ L1 检测(已有) ──────────────────────────────────────┐
│  quality_check + 各入口 → pending / 拒收行           │
└──────────────────────────────────────────────────────┘
                    ↓ 发现问题
┌─ L2 治理闭环(本次核心) ──────────────────────────────┐
│  质量页处置: confirm(ok) / fix(编辑修正) /            │
│             ignore(彻底忽略) / backfill_pending(待E回填) │
│  ⚡ 处置时"检测特征+处置动作+依据" 沉淀为治理规则     │
└──────────────────────────────────────────────────────┘
                    ↓ 规则命中
┌─ L3 学习复用(治一次,后续自动) ──────────────────────┐
│  新行 → 匹配已确认规则 → auto 自动应用 / suggest 建议 │
│  同类问题治一次,后续自动或一键半自动治理             │
└──────────────────────────────────────────────────────┘
```

### 2.2 L2 治理动作(源头打标,新增 2 个状态 + 复用 2 个)

质量状态机扩展(所有 QualityMixin 表 + manual_refunds 内联):

| quality_status | 含义 | 是否纳入经营统计 | 产生方式 |
|---|---|---|---|
| (空/None) | 正常 | ✅ 纳入 | 默认 |
| ok | 人工确认通过 | ✅ 纳入 | L2 confirm |
| auto_fixed | 已自动纠错 | ✅ 纳入 | L1 自动 |
| auto_filled | E 表回填 | ✅ 纳入 | backfill |
| pending | 待人工确认 | ⚠️ 见 2.3 | L1 检测 |
| **ignored** | 人工裁定彻底忽略 | ❌ 排除 | L2 ignore(新增) |
| dup_residual | 已治理重复 | ❌ 排除 | 既有(重复治理) |

> `ignored` 与 `dup_residual` 语义并列但用途不同:dup_residual 专治"重复";ignored 是通用"该笔不属经营/确证虚假/无需纳入"的人工裁定(如 2031 无佐证残留行)。两者在统计排除上等价,合并为一个排除集合 `('dup_residual','ignored')`。

### 2.3 pending 是否纳入?——按路区分,不改既有行为

**关键约束:wallet 的 pending(15,172 条)是"冻结/失败业务标记",不是数据异常**。B 路统计已用"op_type='用户提现' AND 备注非失败/冻结"业务过滤排除,不依赖 quality_status。若把"pending 一律排除"推广到 B 路会误伤(那些行本就没进 B 路经营)。

故:**pending 的"是否纳入"维持现状口径,不因本设计改变**:
- A/C: 按业务状态(status='已退款')纳入,pending 仅提示不排除(与现状一致)
- B: 按业务过滤(op_type+备注),pending 中的冻结行天然不计 B 路(现状)
- D: 按 `COALESCE(op_time, register_time)` 纳入,排除 `dup_residual`;**新增排除 `ignored`**;`pending` 维持现状(待确认但 COALESCE 可进桶)
- 时间异常(pending 乱年份)通过 **L2/L3 回填或忽略**解决,而非"pending 一律排除"一刀切。

**本设计不改变任何现状纳入/排除口径**,只新增 `ignored` 排除 + 回填/复用能力。

### 2.4 L3 治理规则(治一次复用)——新表 `quality_disposition_rules`

一次治理沉淀一条规则:

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| table_code | str | 作用表(refund/wallet/shanmao/manual_refund/ticket) |
| trigger_category | str | 触发问题分类(与 quality_note 分类对应: time_future / time_past / time_reversed / enum_dirty / amount_invalid / missing_field / e_mismatch / residual / dup...) |
| **match_pattern** | jsonb | 特征匹配条件(表字段级: 如 `{"order_no_prefix":"WM","reg_year_future":true,"e_match":"none"}`) |
| **disposition** | str | 处置动作: fix_field / ignore / backfill_from_e / confirm_ok |
| disposition_params | jsonb | 动作参数(如 fix_field 的 `{field:"register_time", mode:"copy_from_op_time"}`; backfill_from_e 的匹配键) |
| auto_level | str | **auto**(直接执行) / **suggest**(带建议待确认) |
| confidence | int | 置信度 0-100(自动积累) |
| hit_count / last_hit_at | | 命中计数/最后命中(学习信号) |
| source_rule_id | int 可空 | 由哪条人工处置沉淀而来(溯源) |
| created_by / updated_by | | 创建/更新人 |
| enabled | bool | 启用 |
| created_at / updated_at | | |

> **复用 DataQualityRule 还是新建?** 决策:新建 `quality_disposition_rules`。DataQualityRule 是"检测规则"(L1, 判定该不该标问题),本表是"处置规则"(L2/L3, 标了之后怎么治),职责不同,不宜混在一张占位表。前端质量规则 Tab 管检测规则,治理规则在 QualityAudit 内嵌管理。

### 2.5 处置动作 → 规则沉淀流程

**人工处置时**(质量页对 pending/问题行):
1. 用户点"确认通过/编辑修正/彻底忽略/待E回填"
2. 后端执行处置(改源头 quality_status/字段)
3. **可选**:弹窗询问"将本次处置沉淀为规则?"(可跳过)
   - 用户确认 → 系统提取该行检测特征(问题分类 + 匹配字段值如 order_no 前缀/年份特征/E匹配状态)→ 存 `quality_disposition_rules`
   - 默认 auto_level = suggest(涉及金额/排除)或 auto(补录/格式),用户可改

**规则应用时**(scan / 导入 / 定时):
1. 新行被标 pending 后,进入"规则匹配器"
2. 按 table_code + trigger_category + match_pattern 匹配已启用规则
3. auto → 直接应用处置(记审计 quality_note + 溯源 source_rule_id)
4. suggest → 不自动改,但在质量页该行显示"建议:按规则#N 忽略(命中 xx 次)"+ 一键应用按钮
5. 用户应用建议 → hit_count+1(规则越用越可信)

### 2.6 E 表回填队列(backfill_pending 语义)

- 对 D 路 pending 且 E 可匹配的行,现有 `backfill_d_op_time` 已自动回填(置 auto_filled)。
- 本次增强:质量页提供**"标记待回填"**动作 → 语义 = "这条我知道要修,但 E 表当前没匹配(可能延迟两天),保持 pending + 记 `backfill_pending` 意图,等 E 补录后复查自动回填"。
- 落地:不新增状态值,复用 `pending` + `quality_note` 前缀 `[待E回填]`,或 quality_note 结构化。**简化:不加列**,待回填意图记录在 note + 可选规则沉淀(规则 backfill_from_e 在 E 有匹配时自动应用)。E 表刷新后 backfill 扫描自动处理。
- 若 E 永远无匹配 → 人工"彻底忽略"或"编辑修正"(闭环)。

### 2.7 统计排除收敛(`_quality_include_cond`)

#### 2.8.2 A/D 重叠归属规则(用户裁定: A 优先)

**问题实证**:D 路已退款(排除 dup_residual)4021 行中,520 个 order_no(1017 行)同时出现在 A 路已退款。但深挖后**绝大多数是"同一订单多次退款各记各的"(金额不同),非同一笔重复登记**:
- 金额与 A 完全一致的行仅 **31 行/28 单/¥3,171.90**
- 其中 27 行年份正常、4 行乱年份、7 行无 SN(乱年份+无 SN 者即历史残留脏行特征)

**用户裁定**:A/D 归属优先 A(D 为手动数据可信度低),但**只剔"真同一笔重复"**(同 order_no + 金额一致 ±0.01),禁止按订单一刀切剔除(会误伤同单多次不同退款)。

**时间窗约束(2026-09-09 数据实证补充, 用户确认合理)**:
金额一致的全量候选行(含已治理 dup_residual)时间差分布存在**清晰自然断档**:

| D侧时间 vs A侧created 差 | 行数 | 金额 |
|---|---|---|
| ≤ 7 天 | 28 | ¥2,734.90 |
| 90-365 天 | 1 | ¥179 |
| > 365 天 | 2 | ¥258 |

→ **7 天 ~ 90 天之间为空档**,真重复集中在 7 天内;3 个跨期行(364/727/2185 天)为乱年份残留/同单跨年另次退款。取 **±30 天窗口**(兼容 D 台账批量补录滞后数周,又排除跨期误判),作为识别规则的**第二道护栏**,降低误操作。

**规则验证(2026-09-09 全量 SQL 实测, 规则可行)**:

| 指标 | 数值 |
|---|---|
| 金额一致候选(非 dup_residual) | 28 行 / ¥2,797.90 |
| **±30 天窗命中** | **25 行 / ¥2,360.90** |
| 被排除(>30 天) | 3 行 / ¥437.00 |

- 命中 25 行时间差均 ≤4.5 天, 每行找到**金额+时间唯一匹配**的 A 退费单 → 可靠
- 被排除 3 行(364/727/2185 天)**全部为 无SN + pending 乱年份残留行** → 本就不该判"当前重复", 走残留治理路径
- **验证结论: ±30 天窗口不误伤、不漏真重复, 规则可用**

**规则落点**(走治理闭环标记,非写死排除):
- 识别条件: `manual_refunds.is_refunded='是' AND order_no 在 refunds(已退款)存在 AND |refund_amount - a.refund_amount| ≤ 0.01 AND |D侧时间 - A侧created_at_raw| ≤ 30天` → 疑似重复
- 处置: 质量页展示建议 → 人工确认 → 标 `dup_residual`(复用现有治理标记, 从 D 路排除)
- 沉淀规则: `trigger_category='ad_overlap_dup'`, disposition=ignore, 后续 scan 自动提示

## 六、风险清单

1. **自动治理误伤**:auto 规则改错数据 → 用 auto_level 分级 + 全量审计(quality_note 溯源 + source_rule_id);默认 suggest,累计 hit 后再升 auto。
2. **排除口径回归**:收敛排除函数时误改现状 → 回归红线(见 2.7)+ 全量测试(现有 D 路 dup_residual 排除/对账测试)。
