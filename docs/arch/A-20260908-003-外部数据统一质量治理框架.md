## 一、背景与现状

### 1.1 现状盘点（2026-09-08 全库+代码核实）

**外部数据入口 7 类**（写业务表的入口）：

| 入口 | 落库表 |
|---|---|
| BMS 网页采集（refund/ticket/wallet/device_combo/cs_record/shanmao） | 对应业务表 |
| 共享文档采集（腾讯315/金山退款） | external/card_complaints、manual_refunds |
| 老腾讯文档 API 采集 | external/card_complaints |
| workbuddy 投诉推送 | external/card_complaints |
| workbuddy 手动退款推送 | manual_refunds |
| 文件上传（18 种 data_type） | UPSERT_DISPATCH 全表 |
| SCRM 采集 | scrm_operators/sessions |

**核心缺口**：
- **无统一"未采纳行按行可见+人工判定"机制**。
- 现状 3 类去向：①日志摘要级（add_error≤50 → log error → 收敛成"N 条"）②计数级无明细（filtered/批内去重/do_nothing 冲突，仅计数或 logger）③入库打标（pending/ok/auto_fixed，仅 5 主表有 L2）。
- 原始行仅**文件级保留**（upload_records.stored_path），无行级拒收表。
- 投诉两表/SCRM/BMS 五源**无 L2 质量**（QualityMixin 仅 5 表）。
- 共享文档读取层**静默过滤**全空行/业务空行（无计数无记录）。

### 1.2 治理原则（用户拍板）

1. 所有接受外部数据的入口都纳入数据质量。
2. 未采纳数据（未入库行）**按行显示**，人工判定处理。
3. 不处理（默认/未判定）则**不纳入统计**。

## 二、核心设计

### 2.1 统一"未采纳行"落点：泛化拒收表 `ingest_rejected_rows`

一张表承接所有入口"从未进业务表"的行：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| data_type | str | 目标业务表类型（refund/external_complaint/manual_refund/...） |
| source | str | 入口标识：bms/shared_doc/tencent_doc/workbuddy_pull/upload/scrm |
| source_ref | str | 溯源：upload_record_id / sync_log_id / doc_sync_source_id |
| source_row_no | int | 源文件/批次内行号 |
| reject_category | str | 拒因分类：parse_fail / validate_fail / dup_skip / polluted / empty_template / reconcile_away |
| reject_reason | str | 人读原因描述 |
| raw_row | jsonb | **原始整行**（列名→值） |
| business_key | str 可空 | 若能识别业务键（如 RF 单号/订单号/手机），用于与业务表关联 |
| status | str | 人工状态：**open**（未判定，默认）/ keep（采纳）/ discard（明确不纳入） |
| reviewed_by / reviewed_at | | 判定人/时间 |
| created_at / updated_at | | |

> ⚠️ **与"入库打标"分层**：现有 L2（pending/ok/auto_fixed/dup_residual）是"已入库但标记待审"（第二层）；拒收表专注"从未进业务表"的行。两者以 business_key + 行指纹关联，UI 可分两个 Tab 展示。

### 2.2 各入口改造（按最小成本排序）

| 入口 | 改造点 | 说明 |
|---|---|---|
| workbuddy 投诉/退款推送 | `SyncRowResult.dropped/filtered` 处 | complaint_sync.py / manual_refund_sync.py 集中插桩，dropped/filtered → 写拒收表 |
| 文件上传 / BMS upsert | `ImportResult.add_error` | errors 已带 data（raw），落拒收表 |
| 污染清洗置空 | `_sanitize_name_field` | 置空时同时记拒收行（含原污染值） |
| 共享文档读取层 | 空行过滤处 | 改为"计数 + 可选进拒收表"（**可配置默认静默**，见 2.4） |
| SCRM | `_upsert_*` failed 分支 | 逐条失败落拒收表 |
| 全量对账删除 | `_reconcile_full` | DELETE 前先落拒收表（reconcile_away），供复核 |

### 2.3 统计口径：统一行级过滤器

- 约定：**未判定 open / 人工 discard → 不纳入统计；keep → 纳入**。
- 现有"入库打标排除"（dup_residual/pending）与"拒收行不纳入"统一收敛到一个**行级过滤器函数**（如 `_quality_include_cond(table_alias)`），替换 analytics.py 各处散落的 `quality_status <> 'dup_residual'` 手写排除（当前治理回归风险点）。

### 2.4 噪音治理：按源可配置"默认静默/计数/全量显示"

- 共享文档/金山"预留空模板行"当前刻意静默滤掉——全量进拒收表会产生大量噪音。
- 框架支持 `reject_category × source` 级配置：`silent`（默认不显示，仅计数）/ `count`（计数+可查）/ `visible`（默认进拒收表待判定）。
- 默认值：`empty_template → silent`，`parse_fail/validate_fail/polluted/dup_skip → visible`，`reconcile_away → visible`。人工可改。

## 六、风险清单

1. **噪音堆积**：全空/模板行大量进拒收表 → 靠 2.4 可配置默认静默缓解；需明确各源默认分类。
2. **改造面广**（7 入口 + 前端 + analytics）→ 分期：一期先落 workbuddy push + 上传（改造点集中、价值高），二期 BMS/SCRM/共享文档。
3. **统计口径一致性**：行级过滤器替换散落排除逻辑，需回归测试防误改（现有 D 路 dup_residual 排除、#36 ok 保护语义不能破坏）。
4. **与现有 L2 双轨**：拒收表与 pending 表需清晰边界（入库前 vs 入库后），避免同一问题行两处都出现。
5. **业务键识别**：raw_row 无业务键时关联困难 → 用 source_ref + row_no 溯源，不强求业务键。

1. migration 应用成功；ingest_rejected_rows 可写可查。
2. 某入口（如上传含坏行文件）→ 坏行出现在拒收表，open 状态，raw_row 完整。

4. 统计过滤器：已知 dup_residual/pending 排除行为不变（回归）。
5. 前端拒收 Tab：按源/类筛选 + 批量判定。
6. 噪音源（空模板）默认 silent，不淹没可见拒收。
