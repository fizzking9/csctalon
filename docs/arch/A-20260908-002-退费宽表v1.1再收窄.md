### 1.2 用户质疑（本变更依据）

> "在退费宽表物化里为什么还有转入提现账户？按道理这个应该不纳入宽表吧。"

核实结论（2026-09-08）：
- 「转入提现账户」在 v4 口径（A-20260902-011）**属 B 路钱包入账侧，不是 A 路线上直退**。
- 宽表定位 = "E 表（refund_record_reports 线上退款水单）的即时版" → E 表对应**线上+已退款**。
- 「转入提现账户」是当初方案 B 的"∪ 带 wallet"条件为保视图5 拉入的**妥协产物**，与宽表定位不符。

### 1.3 决定性确认

**分类规则1（客诉-外部投诉）不受收窄影响**（关键安全确认）：
- 规则1/2/3 只被 `preset_refund_daily_detail_v2`（视图3）消费；
- 视图3 本身过滤"线上+已退款"，这些行**全部保留** → 收窄后规则判定不变。

**视图5（提现时序）可改 wallet 源表直查**：
- `wallet_withdrawals` 用户提现 26,431 行，10,079 行 remark 含 RF 退费单号、10,119 行有 device_sn；
- wallet 源已在分析引擎注册（视图1/视图4 已用），源表直查能力现成；
- 提现审计数据比宽表关联更全（含所有提现，不限线上退款关联）。

## 二、核心决策

### 2.1 宽表行范围：回归纯「线上+已退款」

```
新行范围 = refunds WHERE refund_method='线上' AND status='已退款'   （≈41,997 行）
```

- **剔除**：转入提现账户（13,119）/ 线下已退款带 wallet（4,198）/ 空 method（~3,500）等所有非线上已退款行。
- 实测合并后 ≈ **41,997 行**（较 v1.0 的 64,303 再缩 ~35%，较最初 177k 缩 76%）。
- 宽表彻底回归"A 路/E 表即时版"单一语义。

### 2.2 视图5（提现-退款时序）改源表直查

`preset_wallet_refund_timing_v2` 从 `source_code=refund_wide` 改为 `source_code=wallet`：
- 以 `wallet_withdrawals`（op_type=用户提现）为主表；
- 维度/度量用 wallet 原生列：`op_time`（提现日期）/ `op_amount`（提现金额）/ `device_sn` / `remark`（含 RF 退费单号可关联）；
- 若需展示关联工单/退款原因：分析引擎禁 JOIN，可改为展示 wallet 自身字段（remark/device_sn），或保留一张"wallet×refund 轻关联"（另立评估，本期不做 JOIN）。
- **视图5 退出 refund_wide 消费**。

### 2.3 分类规则1 不变

规则1（has_external_complaint）继续在宽表上判定——但**收窄后宽表只剩线上已退款**，外部投诉字段只对线上退款物化。因规则1 只服务视图3（线上已退款），覆盖不变。若未来需"线下退款也有客诉标记"，另在源表/独立物化处理（本期不做）。
