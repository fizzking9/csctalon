# A-20261008-003 统一变更审计与日志保留期设计

**性质**：需求（REQ）—— 落地 S-P1-11 的统一变更审计模型与保留期/分区设计
**工单**：#261（B4-5）
**日期**：2026-10-08
**关联**：[开源深研报告](../reports/20261007-开源源码深研与架构规划调整-分析报告.md) S-P1-11、AGENTS.md 铁律 3（破坏性操作守卫）、[数据时间字段使用规范](../standards/数据时间字段使用规范.md)

## 一、背景与缺口

1. **HTTP 层审计有了，字段级变更审计没有**：`operation_logs`（中间件自动落）只回答
   "谁在何时打了哪个接口"（method/path/action），不回答"**这个字段从什么改成了什么**"。
   人员归属、退款质量处置、别名归并等高价值人工变更，出争议时无法追溯改动前值。
2. **日志类表无限增长**：`operation_logs` 及本次新增的 `audit_changes` 无保留期；
   日志类表膨胀会拖慢查询与备份。
3. **分区未设计**：大数据量后的归档路径缺失。

参照范式（开源深研报告 §3.2/§3.7）：zammad `histories` / helpdesk `TicketChange`
—— **统一变更模型：实体 + 动作 + 字段级 before/after**。

## 二、统一变更审计模型（已落地）

### 2.1 表 `audit_changes`（迁移 b4_3_audit_changes）

| 字段 | 说明 |
|---|---|
| `entity_type` | 实体表名（persons / manual_refunds …），联合索引主路径 |
| `entity_id` | 实体主键（统一字符串，兼容 int/复合标识） |
| `action` | create / update / delete |
| `actor_id` / `actor_name` | 操作人（冗余账号名，用户删除后仍可审计） |
| `source` | api / night_batch / manual_import / system |
| `changes` | JSONB `{field: [before, after]}`；create 时 before=null，delete 时 after=null |
| `summary` | 人类可读摘要（缺省自动生成） |

### 2.2 服务层 `app/services/audit_change.py`

- `diff_model_changes(obj, data)`：对即将 `setattr` 的变更字段逐个比对新旧值，
  **只在 setattr 前调用**（commit 后旧值已丢）。
- `record_change(db, ...)`：独立事务落库，**审计失败绝不影响业务**
  （与 operation_log 中间件"任何异常都吞掉"同一纪律），但 `logger.error` 留痕。

### 2.3 接入纪律（谁改谁接）

新增/改造任何**人工改业务数据**的端点时，按 `update_person`（persons.py）模式接入：

```
data = payload.model_dump(exclude_unset=True)
diffs = diff_model_changes(obj, data)   # ① setattr 前
... setattr / 关联处理
db.commit()                             # ② 业务提交
if diffs:
    record_change(db, ...)              # ③ 审计独立提交(失败不影响业务)
```

**本单只接 1 个示范点**（PUT /persons/{id}）；其余实体按需扩，不做一次性全量埋点
（避免大范围 diff 代码铺开引入回归面）。

## 三、保留期（已落地：夜批 purge_expired_logs）

| 表 | 保留期（settings） | 依据 |
|---|---|---|
| `operation_logs` | `OPERATION_LOG_RETENTION_DAYS` = 180 天 | HTTP 层审计，追溯价值随时间快速衰减 |
| `audit_changes` | `AUDIT_CHANGE_RETENTION_DAYS` = 730 天 | 字段级变更审计价值更高，争议追溯窗口长 |

实现要点（`batch_runner._purge_expired_logs`，调度 02:00）：

1. **破坏性操作纪律**：`assert_safe_to_destroy(allow_real_db=True)` 显式声明 ——
   该删除是设计内常态运维而非脚本误触，reason 写明 #261 以便审计（铁律 3）。
2. **分批删除**：按 id `LIMIT 5000` 循环，避免长事务锁表与 WAL 尖峰。
3. **时区**：cutoff 用北京时间（`analytics.TZ`）计算，与既有调度口径一致。

## 四、分区方案（设计先行，本单不执行）

**触发条件**（满足其一才考虑）：`operation_logs` 单表 > 5000 万行，或保留期清理
批删耗时 > 10 分钟影响夜批窗口。

**推荐方案：原生按月范围分区（RANGE on created_at）**，理由：

- 分区键 = `created_at`（入库时刻）—— 审计日志的查询/归档/淘汰都以时间为轴，
  与业务数据"应按业务时间分桶"的纪律不同（日志无业务时间语义，入库时刻即正确键）。
- 保留期清理从 `DELETE` 降为 `DROP PARTITION`（瞬时、零 WAL）。

**迁移步骤（未来执行时）**：
1. 新表 `operation_logs_p`（分区母表 + 索引随分区），双写期 shadow 表；
2. 触发器或应用层双写 → 历史数据按月批量搬移（每批 commit）；
3. 切读 → 停旧表 → rename；
4. 分区创建由夜批预建下月分区（drop 超期分区替代 purge 任务）。

**不做**：pg_partman 扩展（引入外部依赖，人工预建逻辑简单）；哈希分区
（不能按时间淘汰，与保留期目标冲突）。

## 五、取舍（不做什么及原因）

1. **不归并 13 张既有 Log/History 表**：`*_sync_log` / `*_leadership_history` /
   `LlmCallLog` 等 schema 差异大、各有消费页面；全量归一是伤筋动骨的大改且无
   消费方。统一模型从本单起新增变更审计走 `audit_changes`，存量按需逐步接。
2. **不执行分区改造**：存量未到阈值（§四触发条件），先上保留期清理即可控增长。
3. **不做审计查询 API/页面**：当前无消费方（删掉无损判据）；数据先落库，
   查询入口待有真实追溯诉求再建（届时走 issue）。
