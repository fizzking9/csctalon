## 〇、结论摘要（TL;DR）

1. **客户主轴 = 设备 SN**，不另造 customer 账户主数据（ADR G5）。分析沿「**设备类型 → 商户号 → 店铺 → 企业**」上卷；**商户号与店铺是两条独立通路**（设备绑商户号；1 企业管多店铺；商户号与店铺无必然关系），交叉分析是机会点而非先验外键。
2. **代码已有三块雏形，本设计是"演进/补全"而非"从零新建"**（复核已纠偏报告口径）：
   - `merchants` 表**已存在**，但以 `sub_name` 名称唯一（仍是"名称即键"），且**设备未外键建链、无生效期**；
   - 设备标签**三表已完备**（`device_tags` / `device_tag_rel` / `device_tag_batches`），rel 已带批次/状态/失效期，**只缺业务事实来源（source_table/source_id）且 analytics 零消费**；
   - 设备 360 **已有后端雏形**（`GET /devices/{sn}` 生命周期 KPI + `GET /devices/{sn}/timeline` 跨表时序，21 张表带 `device_sn`）与前端画像抽屉（`DeviceAnalysis.vue`）。
3. **新建的只有两块**：**店铺 `shops` + 企业 `enterprises`** 主数据（B5）；以及若干**关系/字典/建链**结构（设备-商户号 SCD 建链、套餐字典、设备类型维度、标签事实来源列）。
4. 推进严格按成本递增：**设备类型维度 → 商户号建链 → 套餐字典 → 设备 360 MVP（只读）→ 标签分析化 → 店铺/企业上卷**（对齐 v0.7 B2/B5）。
5. 建链铁律：**先出匹配率报告 + 人工校对入口 + 低置信不建链 + 原始文本快照保留**；历史切面用生效期/SCD，**不覆盖旧值、打标不删、全程可回滚**。

## 一、目标与边界

### 1.1 要回答的问题（替谁/答何决策）
- **运营/主管**：从一台设备的 360 视图看清"这台设备是谁的、买过什么套餐、还剩多少流量、投诉/退款/接待经历"，并能沿 设备类型→商户号→店铺→企业 上卷，回答"哪类设备/哪个商户/哪家店铺在流失、在投诉"。
- **客服**：设备 360 直接消费标签（标签是客服操作事实基础），并能从任一标签卡片**下钻到设备明细**。
- **数据治理**：消除"名称即键""套餐改名即拆散口径""标签只存不用"三类统计脆弱性。

### 1.2 边界（不做项，立此存照）
- 不建客户独立账户/会员体系；**客户 = 设备 SN**。
- 不做多租户/多组织层（单企业内部系统，轻量工单家族教训：抄来即负担）。
- 不做 CRM 销售漏斗、营销自动化。
- 主数据**允许人工校对 + 共享表格/手工 Excel 通道录入**，不追求全自动建模。
- 本设计只到"结构 + 切片 + 回填策略"，**不在本单产出 DDL/迁移/接口代码**。

## 三、目标态领域模型

### 3.1 四层主数据 + 两条独立通路（ER 概要）

```
                         企业 enterprises (B5, 新建)
                          │ 1 企业 : N 店铺 (父子, SCD)
                          ▼
                         店铺 shops (B5, 新建)
                          │  ═══════════════════ 两条独立通路, 无必然外键 ═══════
   设备类型 dim_device_type │                                                  │
        ▲ (成维度)          │ (通路② 归属, B5)                                  │ (通路① 交易)
        │                  ▼                                                  ▼
                      设备 devices (sn 主键, 客户主轴) ──SCD 建链──▶ 商户号 merchants (演进)
                              │                                                  │  merchant_id=业务键
                              │  device_sn 贯穿 21 张业务表                       │  稳定代理键 merchant_pk
                              ▼
                        充值/投诉/退款/接待/标签/流量 (事实域, 已存在)
```

- **通路①（交易）**：设备 —SCD 建链→ 商户号（来自充值/退费/商户明细）。
- **通路②（归属）**：设备/门店 —归属→ 店铺 —父子→ 企业（来自组织/共享表格，人工维护为主）。
- **两通路不强制关联**：店铺与商户号之间不设先验外键；"某商户号的设备落在哪些店铺"这类**交叉分析作为派生视图**在 B5 做。

### 3.2 设备类型维度（最小成本先行，B2）
- 新增维度表 `dim_device_type(type_code PK, type_name, normalized_from[])`，把 `devices.device_type` 自由文本归一（保留原始 `device_type` 文本不删，新增 `devices.device_type_code` 可空外键）。
- 归一方式：先出"文本值分布 + 归并建议"，人工确认后回填；无法判定的留空（低置信不建链原则一致）。

### 3.3 商户号主数据演进 + 设备建链（B2）
- `merchants` 演进（**不新建同名表**）：引入稳定代理键 `merchant_pk`（沿用现有 `id` 即可，避免再造），把 `merchant_id`（商户号）作为**业务键**加唯一约束（空值允许，需部分索引）；`sub_name/main_name` 降级为**带生效期的名称属性**（名称会改）。
- **设备建链表 `device_merchant_links`（SCD Type2，新表）**：
  `device_sn · merchant_pk · effective_from · effective_to(null=至今) · is_current · confidence(机匹置信度) · match_source(manual/xlsx/auto) · raw_merchant_name(快照原始文本) · change_reason · created_by`。
  - 部分唯一索引：`(device_sn) WHERE is_current`（同一时刻一台设备仅一条当前归属）。
  - **devices 不直接放 merchant_pk 外键**（归属会变、要留历史）；当前归属由 is_current 链路解析，360 头取当前行。
- 建链门控（v0.7 风险 G）：机匹先出**匹配率报告**（名称→merchant_pk 候选 + 置信度）；**低置信不建链**；提供人工校对入口；`raw_merchant_name` 永久保留快照可回溯。

### 3.4 店铺 / 企业主数据（B5，新建）
- `enterprises(enterprise_pk, name, status, ...)`；`shops(shop_pk, shop_name, enterprise_pk→enterprises, status, raw_source, ...)`。
- 店铺父子（归属企业）用 SCD：`shop_enterprise_history(shop_pk, enterprise_pk, effective_from/to, is_current, source, change_reason)`（企业可能调整门店归属，不覆盖旧值）。
- 设备↔店铺归属：`device_shop_links`（同 3.3 SCD 结构，通路②）；**录入以共享表格/人工校对为主**，不做自动推断硬绑定。
- 首批种子来源：`return_tracking.shop`、`external_complaint.complaint_shop/company_entity` 文本去重候选 → 人工确认。

### 3.5 套餐字典（原始名→归一码 + SCD，B2，S-P1-12）
- `combo_dict(combo_code PK, canonical_name, package_type, traffic_type, status)`：归一套餐。
- `combo_name_alias(id, combo_code→combo_dict, raw_package_name, merchant_pk 可空, effective_from, effective_to, is_current, source)`：**原始名 → 归一码**映射，带生效期（套餐会变、异名同实；同名在不同商户/时期可能指向不同套餐，故别名键含商户与生效期，不做全局唯一硬归一）。
- 口径切换：`complaint.py:233-237` 等按套餐聚合处改 `join combo_name_alias + combo_dict` 取归一码；**历史报表用"事件发生时生效"的别名快照**（SCD 时点关联），不回改历史数字。看板卡片须给"归一口径 + 未命中原始名占比"的 ⓘ 说明（满足看板双强制）。

### 3.6 标签事实化（复用三表 + 补来源/约束，B2 末/B3，S-P1-13）
- 在 `device_tag_rel` **补可空来源列**：`source_table`、`source_id`（这条打标由哪个业务事实触发，如某次投诉/质检行）、`reason`（可空）。老批次数据来源为 `device_tag_batches`（经 batch_id 关联），两来源并存不冲突。
- 加**部分唯一约束**防重复打标（同 device_sn+tag_id 当前有效仅一条；对齐 cskefu 教训）。
- **下钻**：标签卡 → 设备明细（复用 360 设备选择与下钻框架，带时间窗 + 筛选，遵守看板下钻规范）；设备 360 标签区列出标签及来源/批次/有效期；投诉分析支持按标签组合维度。

## 四、设备 360 视图（在现有雏形上增强）

### 4.1 页面结构（B2 交付只读 MVP）
1. **设备头**：SN、设备类型（归一码）、当前商户号（merchant_id + 名称，来自当前 SCD 行）、店铺/企业（B5 上线后补）、当前套餐 + 剩余流量（device_combos 最近生效单 / devices.current_combo_name）、服务有效期、状态。
2. **标签区**：当前有效标签（色/名/来源/批次/有效期），标签可点下钻设备明细；B5 前先做"标签→设备列表"。
3. **充值生命周期**：device_combos 时间轴（套餐、金额、三档流量、有效期）。
4. **投诉/退款/接待时间线**：**复用 `build_device_timeline`**（合并 21 表中投诉/退款/接待/钱包/流量事件），不另起聚合。
5. **操作日志**：复用 operation-logs 同口径。
- MVP **只读**；编辑/建链校对入口放主数据管理页（B2 商户号校对），不塞进 360 头。

### 4.2 界面五要素（设计阶段先立，实施按规范三层落地：代码头注释 + 页面 ⓘ + 审查清单）
- **目的**：替客服/主管在一屏内回答"这设备是谁的、值多少、经历了什么、为何被打标"，支撑挽留与投诉处置决策。
- **逻辑**：按"身份（头）→ 人为分层（标签）→ 交易（充值）→ 经历（时间线）→ 审计（日志）"组织；时间线复用而非另建。
- **口径**：金额/流量/套餐单位与时点逐区标注；商户归属取 SCD 当前行（并可查看历史归属）；标签区分当前有效/已失效。**"空"必须写明含义**（无建链=未确认归属，不等于无商户）。
- **取舍（不做）**：MVP 只读、不做编辑、不做客户账户/联系人 CRM 信息、不做营销动作；不重复展示各看板已有指标，360 只做"单机聚合下钻"，指标真身仍在各看板（投影需声明真身）。
- **工单**：#219（本设计），实施单 B2 另开。
- **下钻双强制**：标签/充值/时间线每块可下钻且带时间窗与筛选；确不可下钻处页面显式声明理由。

## 五、与现有 86 表 / SCD 历史表的关系（影响面）
- **不改主键、不删列**：devices.sn 保持主键；所有 `*_name` 原始文本列保留作为快照与回溯依据。
- 新增：1 维度表（dim_device_type）、2 主数据表（shops/enterprises，B5）、5 张关系/字典表（device_merchant_links、device_shop_links、shop_enterprise_history、combo_dict、combo_name_alias）+ 标签 2 来源列。
- 复用 SCD 范式：与 `group_leadership_history/person_group_membership` 同构（effective_from/to/is_current/source/change_reason + 部分唯一索引）。
- 事实表（device_combos、各 refund/complaint/cs_record…21 表）**不加主数据外键、不回填历史**；上卷通过建链表在查询期完成，历史事实不可变。
- 所有变更走 Alembic 单一 head；新增表/列均向后兼容（可空列、不破坏现有采集与看板）。

## 六、新旧数据迁移与回填策略（策略层；执行在实施单）
1. **只增不改不删**：原始文本列全部保留；归一结果写新列/新表。
2. **门控式回填**：每类归一（设备类型/商户号/套餐/店铺）先生成**候选 + 匹配率报告**，人工确认阈值以上的才回填；低置信悬空待校对，不硬配。
3. **可回滚**：回填数据全部在新表/可空列，回滚 = 去外键/清新表，原始数据无损；建链/别名均带批次号便于整批撤销。
4. **不覆盖历史口径**：统计时点关联 SCD 生效期；历史已发布数字不因归一而改变（如需重算，另出"口径变更前后对照"，不静默改数）。
5. 生产数据写操作过 `db_guard.assert_safe_to_destroy()` + `--allow-real-db`；先备份；默认 dry-run。

## 七、分阶段实施切片（对齐 v0.7）

## 八、风险（摘）
- 名称→商户号错配污染全部上卷（v0.7 G5）→ 匹配率门控 + 人工校对 + 低置信不建链 + 文本快照。
- 套餐别名过度归一（同名异实在不同商户/时期）→ 别名键含商户 + 生效期，不做全局唯一硬归一。
- 360 变"又一个大而全看板"重复堆指标 → §4.2 取舍：只做单机聚合下钻，指标真身留看板。
- 交叉外键诱惑（强行把店铺-商户号绑死）→ 明确两通路独立，交叉只做派生视图。
