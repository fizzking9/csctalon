## 一、目标

提供 ABCD/E 五路按时间窗口的手动对账复核能力：
- 复用统一核算口径（`_cash_routes_total`）展示五路合计 + 差异；
- 逐笔勾稽 E 水单命中 A/B/C/D/unmatched 分布（复用 `water_statement` 分类）；
- 检出 D 路重复/脏数据规模（辅助复核）；
- 复核结论+时点快照落库留痕，可回看、可审计。

## 三、数据模型（ER 增量）

新表 **`reconcile_checks`**（对账复核批次，仅留痕不参与统计）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | IDMixin |
| check_no | varchar(32) unique | 复核单号 `RC+YYYYMMDD+序号` |
| window_start / window_end | timestamptz | 对账时间窗（北京时间 naive → UTC aware 存） |
| grain | varchar(8) | 粒度 day/week |
| route_snapshot | jsonb | 时点快照 {A/B/C/D:{count,amount}, operational, actual_cashflow, diff}（`_cash_routes_total` 输出） |
| by_route_of_e | jsonb | E 勾稽归属 {A, B, C, D, unmatched} 笔数金额（water_statement 分类） |
| dupe_detect | jsonb | D 路检出 {dup_order_groups, dup_amount, no_sn_weird_rows} |
| conclusion | varchar(16) | 结论：`一致`/`差异已确认`/`存疑待查` |
| note | text | 复核备注（差异原因等） |
| reviewed_by / reviewed_name | int / varchar | 复核人 |
| reviewed_at | timestamptz | 复核时间 |
| created_at / updated_at | timestamptz | TimestampMixin |

## 四、接口契约（挂现有 /reconcile router，prefix 不变）

| 端点 | 方法 | 权限 | 说明 |
|---|---|---|---|
| `GET /reconcile/check/run?start=&end=&grain=` | GET | CurrentUser | 生成对账预览（不落库）：快照+勾稽+D检出 |
| `POST /reconcile/check/confirm` | POST | Admin/Supervisor | 发起复核落库（check_no 自动生成） |
| `GET /reconcile/check/list?page=&page_size=&conclusion=` | GET | CurrentUser | 复核批次列表 |
| `GET /reconcile/check/detail?id=` | GET | CurrentUser | 批次详情（快照+勾稽明细+差异下钻） |
| `POST /reconcile/check/{id}/conclusion` | POST | Admin/Supervisor | 补/改结论与备注（留痕，更新 reviewed_*） |

参数：`start/end` 北京时间（`YYYY-MM-DD` 或 ISO），后端 `_to_utc_aware` 归一；`_to_cn` 返回。金额单位**元**（与退款报表一致）。

**统一包装**：`{code:0, data:{...}, message:"ok"}`（R），错误走 HTTPException（error-code.md）。

## 七、风险清单

# 十、v1.1 逐笔勾稽明细核对（2026-09-06 用户澄清）

## 目标
用户对账流程期望：① 区间总数核对（v1.0 已做）→ ② **明细一一对应**（本增量）→ ③ 不符可逐笔处理 → ④ 复核留痕闭环。澄清：E→ABCD 逐笔粒度 / **仅打标不改源** / 新勾稽结果表。

## 模块边界（增量）
```mermaid
graph LR
  UI[ReconcileCheck.vue 增"逐笔核对"子区] --> API[/api/v1/reconcile/check/.../]
  API --> SVC[reconcile_check 服务]
  SVC --> WS[reconcile.water_statement/_build_route_maps 复用]
  SVC --> CAND[候选匹配: E笔→ABCD候选经营单]
  SVC --> MATCH[(reconcile_matches 逐笔勾稽表)]
```

## 三B 数据模型（ER 增量）
新表 **`reconcile_matches`**（E 水单逐笔勾稽结果；仅留痕不改源）：
| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | IDMixin |
| check_id | bigint FK → reconcile_checks.id | 复核批次（可空=草稿） |
| report_id | bigint FK → refund_record_reports.id | E 水单 id |
| platform_order_no / refund_amount / refund_time | varchar/numeric/timestamptz | E 笔快照冗余 |
| auto_route | varchar(16) | 自动归类 A/B/C/D/unmatched（复用 `_classify_report`） |
| matched_ref | jsonb | 候选经营单 [{route, source, source_id, ref_no, amount}] |
| confirm_status | varchar(16) | `已核对一致`/`差异已确认`/`存疑待查`/`已排除重复`/`待核对` |
| confirm_note | text | 备注 |
| confirmed_by / confirmed_name / confirmed_at | int/varchar/timestamptz | 确认人/时间 |
| created_at / updated_at | timestamptz | TimestampMixin |

唯一约束 `(check_id, report_id)`。

## 四B 接口契约（挂 /reconcile/check/ 下）
| 端点 | 方法 | 权限 | 说明 |
|---|---|---|---|
| `GET /reconcile/check/{id}/lines?route=&status=&page=&page_size=` | GET | CurrentUser | 批次逐笔勾稽列表（E 笔+auto_route+人工状态） |
| `GET /reconcile/check/line-candidates?report_id=` | GET | CurrentUser | 某 E 笔候选匹配经营单明细（供人工选） |
| `POST /reconcile/check/line-confirm` | POST | Admin/Supervisor | 对单笔打确认状态+备注（只写 reconcile_matches，不改源） |
| `GET /reconcile/check/{id}/summary` | GET | CurrentUser | 批次内单笔确认进度 {total, confirmed, by_status, by_route} |

## 五B 前端
ReconcileCheck.vue 增"逐笔核对"子区：E 笔列表（订单号/时间/金额 + auto_route + 状态）+ 候选展开 + 人工状态下拉/备注 + n/N 进度。可写仅 Admin/Supervisor。

## 六B Alembic
新增 `reconcile_matches` 表（见三B），单一 head。

## 七B 风险补充
1. 候选匹配可能错配（同设备同额/多批次）→ 多候选展示+人工确认，仅提示不自动写。
2. 仅打标与"修订期望"落差 → 本期只打标（安全），改源走治理流程（#21）；若要复核页直接治理需另评审。
3. 草稿 vs 成批 → 建议先建批次（confirm 落 check）再逐笔。
4. `已核对一致` 不代表数据必然正确（对齐"非正确性保证"文案）。

## 八B 验收标准（增量）
- lines/line-candidates/line-confirm/summary 可用；不改任何源表（断言）；
- 逐笔确认后 reconcile_matches 可查、可追溯；
- 测试 `test_reconcile_check.py` 扩展逐笔确认用例。
