## 一、背景与目标

### 1.1 现状

- **refund_wide**（A-20260908-001 已收窄到 ~64k，生产 64,498）：服务 A 路视图3 + 客诉分类，PK=refund_no，结构绑死 A 路。
- **对账**：`_cash_routes_total`（analytics.py:559）**每请求实时对 4 表 count/sum** + Python 求和，无统一明细物化；`reconcile_matches` 是 **E→ABCD 逐笔勾稽**（E 视角，对账下钻）。
- **运营分析**：A 路有视图3（退款原因/操作人/分类），但 **B/C/D 无统一运营维度视图**。
- ABCD 有效行合计 **76,268**：A 41,997 / B 26,431 / C 1,934 / D 5,906。

### 1.2 用户目标（本次变更）

> 宽表不应只解决 A 路；应服务 ①对账（A+B+C+D vs E）②快速响应 ③运营分析（投诉/退款原因/退款人/商户号/套餐）。
> 每笔出款一行 + **路别列 A/B/C/D** 区分，形成一个高效的统一流水宽表。

### 1.3 核心设计原则（承接 v4 LOCKED）

- **A+B+C+D = 经营估算**（不累加 E）；**E = 实际现金流对账基准**；**对账偏差 = (A+B+C+D) − E**。
- `cash_flow_wide` = **经营四路每笔出款的统一明细物化**（经营视角）。
- E 不进入本表（E 是独立对账基准，另查 refund_record_reports / reconcile_matches）。
- 与 refund_wide 边界：refund_wide 服务 A 路视图3/客诉（保留现状）；cash_flow_wide 服务对账+运营多维分析（新建）。

## 二、表设计：cash_flow_wide

### 2.1 一行 = 一笔出款（ABCD 经营四路）

PK = 自增 id（无跨路自然唯一键，全量保序插入，同 merchant_refunds 的 IDMixin 策略）。

### 2.2 统一字段（跨路语义对齐）

| 统一列 | 类型 | A.refunds | B.wallet | C.shanmao | D.manual |
|---|---|---|---|---|---|
| **route** | str(1) | 'A' | 'B' | 'C' | 'D' |
| **业务单号 biz_no** | str | refund_no | remark 解析 RF（无则置空，回退 account_id） | refund_no/order_no | order_no |
| **来源表主键 src_id** | str | refund_no | wallet.id | shanmao.id | manual.id |
| **出款时间 pay_time** | timestamptz | created_at_raw | op_time | audit_time(回退 created_at) | op_time(回退 register_time) |
| **出款金额 pay_amount** | numeric(12,2) | refund_amount | op_amount | actual_amount | refund_amount |
| **设备 device_sn** | str | device_sn | device_sn | device_sn | device_sn |
| **操作人 operator** | str | operator | operator | operator/auditor | refund_operator/registrant |
| **对账键 e_key** | str | platform_order_no | (空/弱关联) | order_no | order_no |

> ⚠️ 时间口径遵守「数据时间字段使用规范」：A=created_at_raw、B=op_time、C=audit_time（回退）、D=COALESCE(op_time,register_time)。已退款判定：A=status='已退款'、B=op_type='用户提现'+排除失败备注、C=status='已退款'、D=is_refunded='是'。

### 2.3 运营维度（能填则填 + 归一）

| 统一列 | 来源 |
|---|---|
| **退款原因 reason** | A=refund_reason / C=refund_reason（B/D 通常无，置空，可按 biz_no 回查） |
| **服务项/工单关联 service_item** | 经 matcher ticket 关联（A 为主，B/C/D 按 SN/单号可有则填） |
| **商户号 merchant** | A=merchant_name / C=merchant_name（B/D 弱） |
| **套餐 package** | A=package_name / C=package_name |
| **外部投诉 has_external_complaint** | 按 device_sn 聚合（复用 external_complaints） |
| **审核人/登记人** | A=auditor / C=auditor / D=registrant |

> 归一：operator/auditor 人名走 PersonAlias 归一（同 analytics 现有 _norm_op）；reason/merchant/package 原样冗余，缺失置空，不强求每路都有。

### 2.4 对账支撑列（可选，支撑对账下钻）

| 列 | 说明 |
|---|---|
| e_matched bool | 该笔是否在 E（refund_record_reports）有匹配（A 按 platform_order_no 精确；B/C/D 按 device_sn+金额或 order_no 弱匹配，多候选置 NULL 待 reconcile） |
| reconcile_hint | 'matched'/'unmatched'/'ambiguous'(多候选) / NULL(不参与逐笔) |

> 逐笔人工勾稽仍走既有 reconcile_matches（E 视角）；本表 e_matched 仅作**经营侧快速标记/下钻**，不替代 reconcile。

## 三、构建逻辑

- `build_cash_flow_wide(db, only_*: None)` 全量物化 + 增量（同步后钩子）：
  1. A：refunds 线上+已退款 → 行 route='A'
  2. B：wallet 用户提现成功（排除失败备注）→ route='B'
  3. C：shanmao 已退款 → route='C'
  4. D：manual 已退款（排除 dup_residual/pending 治理标记？——按统计口径，经营估算排除 dup_residual，故 D 行跳过 dup_residual）→ route='D'
  5. 外部投诉按 SN 聚合补 has_external_complaint
  6. e_matched：A 精确对 E.platform_order_no；B/C/D 弱匹配
- 清理残留：全量重建后 DELETE 不在源范围的行（复用 NOT EXISTS 模式，W1 教训）。
- 触发：bms_sync post-sync / uploads 后置（同 refund_wide 模式）。

## 七、风险清单

1. **对账一致性**：cash_flow_wide 聚合必须与 `_cash_routes_total` 直查结果一致（D 路 dup_residual 排除、B 路失败备注排除、各路时间口径）——这是核心正确性风险，需回归测试锁定。
2. **B 路对 E 弱关联**：B（钱包提现）与 E（商户号扣款）不是逐笔对应关系（钱包钱从哪来、提走多少是另一记账视角），e_matched 对 B 仅弱参考，不能当作"B 未在 E = 差错"。
3. **C/D 量小但口径独立**：C（闪猫）/D（手动）有各自状态/时间/金额列，映射错误会污染对账——需逐路映射测试。
4. **与 refund_wide 职责重叠**：需明确"A 路分析走 refund_wide 还是 cash_flow_wide"？建议：refund_wide 保留给视图3/客诉（既有），新统一运营分析视图用 cash_flow_wide，避免双写混乱。
5. **物化规模增长**：76k 现可控；长期关注全量重建耗时，复用 NOT EXISTS 清理 + 增量 affected。
