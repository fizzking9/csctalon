## 一、问题（为什么需要这份规范）

### 1.1 现象

2026-09-22，AI 助手为探查数据执行了一条只读 `python -c`，**差点连到真实库并执行 `DROP DATABASE`**。
仅因真实库有活跃连接而失败 —— **纯属运气**。

同一模式在 **2026-09-10** 已造成真实损失：
`refunds 170960→2`、`refund_wide→64313`、`manual_refunds→0`
（见 [20260910-开发库数据事故与恢复.md](../reports/20260910-开发库数据事故与恢复.md)）。

**同因复发** → 说明前次修复（`tests/conftest.py` + `tests/_db_guard.py`）只堵了**一个入口**。

### 1.2 根因：模式机制不存在（而非"配置没分离"）

实测证据：

| 维度 | 现状 | 证据 |
|---|---|---|
| 模式变量 | 存在但几乎不用 | `settings.ENV` 全仓仅 **2 处**引用，均不涉及数据（`wechat.py:129` 微信 mock、`main.py:370` 错误措辞） |
| 配置分叉 | 不存在 | 只有一份 `.env`；`SettingsConfigDict(env_file=".env")` 按 **CWD** 解析 |
| 启动分流 | 不存在 | `Dockerfile` / `docker-compose.yml` 硬编码 `--log-level info` |
| 日志分级 | 不存在 | `main.py:30` 硬编码 `logging.basicConfig(level=logging.INFO)` |
| 数据目录 | 隐式 | 靠 compose 变量默认值 `${DB_DATA_DIR:-./data/postgres}` |
| 前端模式 | 概念混用 | `VITE_BUILD_MODE` 实际控制「显示哪些菜单」，与环境无关 |

### 1.3 三条失效链（必须同时修）

**① 库名同名 → 错误完全不可见**
```
本地 backend/.env : POSTGRES_DB=csctalon
生产 /opt/.env    : POSTGRES_DB=csctalon   ← 同名
```
连错库时，配置、日志、界面**没有任何异常信号**。

**② 默认值指向真实库 + `.env` 按 CWD 解析**
```python
POSTGRES_DB: str = "csctalon"    # 默认值 = 真实库名
```
且仓库根目录存在一份 `ENV=prod / POSTGRES_HOST=db` 的 `.env`
→ 从**根目录**执行 `python -c` 或 `python scripts/xxx.py` 会加载**生产配置**。

**③ 防线够不着脚本**
| 入口 | 是否有守卫 |
|---|---|
| pytest 内 | ✅ `conftest.py`（导入期强制覆盖）+ `tests/_db_guard.py`（操作前二次校验） |
| `python scripts/xxx.py` | ❌ 无 |
| `python -c` / REPL | ❌ 无 |

**结论**：危险不来自「不知道」，而来自「手上少打几个字符」。
故**纯文档（铁律）对此无效** —— 它拦不住不读文档的进程。必须有**运行时机制**。

## 二、设计

### 2.1 唯一入口：`APP_MODE`

```
APP_MODE ∈ {dev, test, prod}     # 唯一的环境真值来源
```

- 环境变量 `APP_MODE` 是**唯一**模式入口（兼容旧 `ENV`，但 `ENV` 降级为别名）
- 未设置时**默认 `dev`**（安全侧：dev 不连真实库）
- 由 `APP_MODE` 推导出一个 **Profile**，profile **硬决定**下列全部行为

### 2.2 Profile 决定什么

| 维度 | dev | test | prod |
|---|---|---|---|
| **库名** | `csctalon_dev` | `csctalon_test` | `csctalon` |
| **`.env` 文件** | `.env.dev` | （不用文件） | `.env.prod` |
| **日志级别** | `DEBUG` | `WARNING` | `INFO` |
| **日志格式** | 详细（含文件/行号） | 精简 | JSON 结构化 |
| **数据目录** | `./data/` | `/tmp/` | `/data/` |
| **SQL echo** | 可选开 | 关 | 强制关 |
| **危险操作** | 需 `--allow-real-db` 之外**全禁真实库** | 同 dev | 允许 |
| **API 文档** | 开 `/docs` | 关 | 按需 |

### 2.3 三道防线（自内向外）

```
① 默认值安全     POSTGRES_DB 默认 = 不可用占位符（不再是 csctalon）
② 模式一致性守卫  启动期断言「模式 ↔ 库名」匹配；不匹配拒绝启动
③ 危险操作守卫    破坏性操作前二次校验（scripts/ 与 tests/ 共用同一实现）
```

**②的具体判据**：
| 模式 | 允许的库名 | 违反时 |
|---|---|---|
| `prod` | 必须**不含** `_dev` / `_test` | 拒绝启动 |
| `dev` | 必须含 `_dev`（或显式声明豁免） | 拒绝启动 |
| `test` | 必须含 `_test` | 拒绝启动 |

→ 这样「prod 连到 dev 库」与「dev 连到生产库」**都会在启动期炸掉**，而不是静默运行。

### 2.4 库名分离（让错误可见）

本地开发库 `csctalon` → **改名 `csctalon_dev`**；生产保持 `csctalon`。

改名的价值：连错库时，库名会出现在
`SELECT current_database()`、日志、界面、告警里 → **肉眼可见**。

> 生产库名**不变**（用户 2026-09-22 决策）：改名会牵动 `deploy/backup.sh`、
> `restore.sh`、`sync-from-prod.sh` 与存量备份文件，需停机窗口，收益不抵成本。
> 本方案通过「prod 模式库名不得含 `_dev`/`_test`」达成同等防护。

### 2.5 向后兼容

`app/core/config.py` → 拆为 **包** `app/core/config/`（`__init__.py` 重新导出 `settings`）。
全仓 **175 个文件**、**62 处** `from app.core.config import settings` **无需改动**
（实测导入形式 100% 统一）。

## 三、实施

### 3.1 文件布局

```
backend/app/core/config/
  __init__.py       # 导出 settings（向后兼容唯一入口）
  base.py           # 公共设置 + profile 解析
  profiles.py       # dev/test/prod 的 profile 定义（单一真值来源）
  guard.py          # 模式一致性守卫（启动期）
backend/app/core/
  db_guard.py       # 危险操作守卫（scripts/ 与 tests/ 共用）
  logging_setup.py  # 按 profile 初始化日志
```

### 3.2 兼容层

`tests/_db_guard.py` 保持现有 API 不变（已有测试锁定），内部委托给
`app/core/db_guard.py` —— 避免出现「第二份守卫实现」（同 A-20260910-004 漂移教训）。

## 四·补、实施中发现并修正的三个问题（记录以防复发）

实施过程中，**"字段必须真的被读取"**这条自检抓出了三处问题。
它们比功能缺失更危险 —— 因为会让人**误信一个不成立的保证**：

| # | 问题 | 危害 | 修正 |
|---|---|---|---|
| 1 | `Profile.docs_enabled` **声明了但没人读** | 使用者以为"prod 关了 /docs"，实际一直开着 —— 空承诺 | 接线到 `main.create_app()`；并加测试扫描源码防再犯 |
| 2 | `Profile.data_dir` / `allow_destructive_on_real_db` **未接线** | 同上；`allow_db_mismatch` 更是与 `db_guard.allow_real_db` **语义重复** | `data_dir` 接线（派生 `BROWSER_STATE_DIR`）；`allow_destructive_on_real_db` 接线到 `_bootstrap`；**删除** `allow_db_mismatch`（避免两名一事） |
| 3 | `Profile.vite_app_mode` **未接线** | 前端环境传递实际走 compose 环境变量，后端字段是冗余声明 → 又一处"双份定义" | **删除**该字段，前端真值来源统一为 compose 的 `APP_MODE` |

**固化为测试**（`test_runtime_mode_framework.py::TestProfileFieldsAreWired`）：
- `test_docs_enabled_is_read_by_main` — 关键字段必须被读取
- `test_no_profile_field_is_obviously_unused` — 启发式扫描：Profile 的字段名
  必须在 `app/`、`tests/`、`scripts/` 的**别处**出现过，否则失败
  （正是这条抓出了上表三个问题）

### 另一条教训：接线时**不得顺手改变默认值**

把路径默认值改为由 profile 驱动时，`_PROD` 的 `data_dir` 一度被写成 `"/data"`
（改造前是 `"./data"`）—— 这是**非预期的行为变更**：
框架升级不该顺带改动生产的数据目录。

现 `_PROD` 的路径默认值**与改造前逐字一致**（`./uploads` / `./data/browser_states`），
容器部署时由 `docker-compose.yml` 显式覆盖为 `/app/uploads` 等绝对路径。

> 通用原则：**重构不得改变行为**。凡"接线"动作都会碰到默认值，
> 必须逐项比对改造前的字面值，差异即需显式论证。

## 五、取舍（不做什么及原因）

| 不做 | 原因 |
|---|---|
| **不**改生产库名 | 牵动备份/还原/部署与存量备份兼容，需停机窗口；用「prod 库名不得含 `_dev`」达成等价防护 |
| **不**引入 pydantic-settings 的多环境继承机制 | 会与现有 `Settings` 单类结构冲突、175 文件受影响；改用「profile 函数返回覆盖字典」零破坏 |
| **不**禁止 `python -c` | 无法禁止（语言能力）；改为**让误连必然失败**（默认值 + 启动守卫） |
| **不**把铁律当作主要手段 | 铁律是「读的约束」，拦不住不读文档的进程；仅作辅助（AI 写脚本时的意图提醒） |
| **不**给所有脚本加 `--apply` | 部分脚本本就是一次性运维操作；只在**破坏性操作前**要求显式声明 |
