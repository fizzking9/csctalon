## 一、重规划背景与触发

v0.5/v0.6 规划的模块约 9 成已落地（S 报告 C2 评估），系统从「功能从无到有」进入「**深化分析 + 管理闭环 + 扩展性还债**」阶段。2026-10-07 完成的两轮全仓审查暴露了规划旧版未覆盖的三类新输入：

1. **正确性/合规欠账（R 系列）**：7 项 P0 级发现——看板双强制大面积缺失、硬编码内网 IP、#193 逾期、LLM 同步路径绕过调度器、熔断事件未按 LOCKED 设计登记 Incident；另有 worker 数矛盾、async 阻塞、db_guard 缺口、CI 门禁弱化等 43 项。
2. **扩展性瓶颈（S 系列）**：口径与注册表多份定义、`today.py` 3570 行口径巨石、单 worker 内存任务模型、前端手写大页与三份导航重复——「加一个新东西要动 3~10 处、漏改静默失效」成为深化的第一阻力。
3. **业务方向跃迁（用户两轮 8 条事实）**：客户主轴 = 设备 SN；分析要沿「设备类型→店铺→商户号→企业」四层下沉；套餐异名同实需归一；标签是客服操作基础但 analytics 零消费；手工/共享表格是常态通道；**夜间「优质但可能投诉」客户预警**成为 AI 二阶段首个落地场景；排班实际在企微、系统内空缺；绩效/管理动作粗糙。

同时，对 17 个开源参考项的深研给出明确裁决：**无整体引入项**（AGPL/GPL/OSL/无 LICENSE 红线 + DataEase/Dify 运维成本否决），真正可移植的是**机制级模式**（指标事件表+rollup、注册表+工厂+启动自检、调度幂等锁、客户 360 聚合、坐席状态段、情绪分级等，逐条出处见 S 报告 §三）。

**本版要回答的问题**：在不带病扩展的前提下，如何把 68 项待办、3 项历史悬置、3 个新业务方向（设备 360 与四层主数据、夜间投诉风险预警、排班×绩效闭环）排成一条「合规清账与能力建设双线并行、每批可独立交付验收」的路径。

## 三、业务目标：三个闭环 + 一条深化主轴

> 承接 v0.5「管理哲学 9 条」（继续有效，本版不重复），把 8 条业务事实组织为可交付的目标结构。

**一条深化主轴**：以 **设备 SN** 为客户识别主键，沿「设备类型 → 店铺 → 商户号 → 企业」四层上卷；商户号与店铺是两条独立通路（设备绑商户号；1 企业管多店铺；商户号与店铺无必然关系），交叉分析是机会点而非先验关系。

1. **客户风险闭环（本版业务第一优先级）**：当天接待过的客户，夜间按「充钱多 / 流量少 / 愿意沟通 / 同题重复」四判据评分 → 产出投诉专员**次日优先处理清单** → 处理结果回流 → v2 用历史投诉结局弱监督迭代。输出是「推着专员走」的清单，不是又一张看板。
2. **排班→接待→绩效闭环**：先决策排班形态（企微镜像 vs 系统编排）→ 接待流水（cs_records，已有 operator/execution_result/user_accepted）→ 工时口径（借鉴坐席状态段/业务日历/工时规则）→ 人均效率算法出 debug_only 产品化 → 管理动作（风险预判、改进闭环，不做扣分式绩效，守管理哲学第 6 条）。
3. **经营分析深化闭环**：设备类型维度（最小成本先行）→ 商户号主数据建链（名称即键不可靠）→ 套餐异名归一（原始名→归一码+生效期）→ 标签从「只存不用」变为可下钻分析维度 → 店铺/企业主数据与上卷 → 设备 360 聚合页（活动/充值/套餐/标签/投诉/退款一屏）。

**手工/共享表格是常态通道，不是例外**：其批次台账、质量留痕、可观测性必须与自动采集同标准。

## 四、v0.7 工程原则（在 v0.5 管理哲学之外新增）

1. **口径单源**：任何统计判据（排除集合/渠道口径/系统人变体/指纹组装/指标公式）全仓只准一份字面量定义，其余导入引用；双实现必须有等价性测试锁定。
2. **注册即完备**：新增 data_type/数据源/指标/通道只改一个注册点；注册表启动期自检（各表分派齐全），漏配**启动即报错**，禁止静默失配。
3. **增量迁移、拒绝重写**：沿用用户偏好——巨石拆分按主题域逐块抽取+公共口径进 `_core`，旧入口保活转发，每步可回滚；禁止大面积推倒。
4. **机制借鉴不抄码**：AGPL/GPL/OSL/无 LICENSE 参考项只学设计；移植模式须在 A 文档注明来源与证据 file:line。
5. **每批可独立验收**：批次内工单带来源编号（R/S）、可复现验收凭证；每批结束向用户汇报，经审核再开下一批（沿用每 5 轮审核节奏，批次为审核节拍）。
6. **决策门先行**：#193、判重 v5、L-3、排班形态、金额单位 5 个悬而未决项，先做「决策」工单（选项+建议+影响面），禁止在决策缺位时直接实施。

## 五、架构专题概要（方向 + 边界 + 取舍；详细设计另起 A 文档）

### 专题 A：客户域建模 —— 设备 360 与四层主数据（S-P0-4 / S-P1-12 / S-P1-13）

- **目标态**：设备 SN 为分析主轴；主数据四层 = 设备类型（成维度）→ 商户号（`merchants` 主数据 + 设备建链，替代「名称即键」）→ 店铺（新主数据）→ 企业（店铺父子，1 企业 N 店铺）；套餐字典（原始名→归一码 + SCD 生效期，套餐会变、异名同实）；标签事实化（带来源 `source_table/source_id`、批次、有效期，可从任何标签卡片下钻到设备明细）。
- **设备 360 页**：借鉴 crm/crmeb 客户 360 聚合（MIT/思想借鉴，不抄码）——设备头（SN/类型/商户号/店铺/企业/当前套餐与剩余流量）+ 标签区 + 充值生命周期（device_combos 已含金额/三档流量/有效期）+ 投诉/退款/接待时间线（复用 audit_timeline）+ 操作日志。
- **边界/取舍**：① 推进顺序严格按成本递增——设备类型维度 → 商户号建链 → 套餐字典 → 设备 360 MVP（只读）→ 标签分析 → 店铺/企业上卷（B5）；② 主数据允许人工校对 + 共享表格通道录入，不追求全自动；③ 不做多租户/多组织层（轻量工单家族教训：单企业内部系统抄来即负担）；④ 历史切面用生效期/SCD，不覆盖旧值。
- **不做**：客户独立账户体系（客户 = 设备 SN，不另造 customer 主数据）；CRM 销售漏斗。
- **出口**：B1 末提交 `A-202610xx-客户域主数据与设备360设计.md` 走人工审核后，B2/B5 分批实施。

### 专题 B：统计口径与指标体系现代化（S-P0-1 / S-P0-3 / S-P1-1 / S-P2-1~3）

- **目标态（分两步，本版只走第一步大半）**：
  1. **口径单源化（B0/B4）**：排除集合（quality_status）、系统人排除变体、渠道口径、指纹组装各收敛为一份定义 + 导入引用；builder↔analytics 两条统计路径补等价性测试；先修 A 路/refund_wide 的 quality_status 敞口（S-P0-1，可能导致治理标记后经营统计不一致）。
  2. **指标字典 + 统计分层（B4 起）**：仿 chatwoot「指标事件表 + 夜间 rollup upsert」与 DataEase「字段语义 + 公式存储/执行分离」（均只取模式）——新增指标登记 `id/名称/口径文档指针/公式参数/聚合方式`，卡片引用指标 id 不内联 SQL；`today.py`（3570 行）按主题域（接待/投诉/退款/现金流/设备）逐块拆分，公共口径进 `analytics/_core`。
- **边界/取舍**：① 事件表化是**目标方向不是本版承诺的全量重写**——先在夜间预警等新场景试点事件+rollup，存量看板保持宽表路线、逐块迁移；② `cash_flow_wide` 增量重建（S-P2-2）仅做方案评估，不与拆分同批；③ 金额「元→分」（R-P1-8）在 B1 只出迁移评估与决策，**不在本版实施全量迁移**；④ 分桶时间一律业务时间戳（chatwoot 用入库时刻的反模式教训）。
- **不做**：不引入 DataEase/第二 BI 运行时（与口径单源、看板双强制冲突，R 报告 §五已裁决）；不引 Calcite/Java 栈。
- **出口**：B4 起逐域 A 文档（或单份「统计侧拆分与指标字典设计」总 A 文档 + 分域附录）。

### 专题 C：任务调度与韧性模型（S-P0-2 / S-P0-3 / S-P1-7 / R-P1-16/17）

- **目标态**：① 五处注册表（data_source seeds / data_type / table_types / upsert dispatch / metric defs）单一注册点 + 启动完备性断言（仿 osTicket 注册+工厂+DataEase Provider 枚举）；② 夜间批处理基建 = 调度表（cron/tz/next_run_at/last_status）+ 幂等锁（仿 zammad daily_event_lock）+ 每 tick 批量上限与熔断 + 节点级执行日志（仿 dify 定时触发三要点，**不引入 Dify**）；③ 同步任务忙时排队（取代 `RuntimeError` 忙拒），队列模型复用 `llm_scheduler` 的 L0-L2 范式。
- **边界/取舍**：① **多 worker 水平扩容本版立此存照、不做**——调度表/幂等锁设计成「未来可迁移到多实例」但不提前付成本；Gunicorn 保持 `-w 1`，B1 先消除 Dockerfile.patch 的 `-w 4` 矛盾（R-P1-9）；② 调度只承载夜间分析类作业，采集实时链路维持 SyncTaskManager；③ 失败水位与心跳分离（R-P1-16）、缺口台账闭环（R-P1-17）随调度基建同批修。
- **不做**：不引入 Airflow / Celery / Quartz；不做分布式锁（Redis 单机足够）。
- **出口**：B1 注册表收敛直接建工单实施（模式清晰无需大设计）；B2 夜间调度基建起 A 文档。

### 专题 D：AI 二阶段 —— 夜间风险预警与微调管线（S-P1-9 / S-P1-8；收口 R-P0-3/4、R-P1-1~4）

- **v1 确定性评分（B3，本版承诺）**：夜间作业扫描「当天有接待的设备 SN」，四判据全部确定性可算（充值额/剩余流量在 device_combos；沟通意愿与同题重复在 cs_records.problem_category/problem_type/user_accepted；投诉结局在 external/card_complaints）→ 规则引擎出分 + 分级 + **投诉专员次日优先处理清单**（页面：待办形态，带四判据证据与设备 360 跳转，处理结果可回填）。情绪/文本暂不取对话原文（守既定约束），只用话题类型与结构化字段。

## 八、开发交付计划：工单规则与节拍

1. **母单**：#199 跟踪本规划整体；各批次可建批次 Epic 单，行动项单挂 Epic 与母单。
2. **一单一行动项**（同源可合单：如 B0 R-P0-1+R-P1-5、B1 CI 三项、B2 采集四项）；每单正文含：来源编号、报告 file:line 依据、验收标准（可复现）、不做项、关联 A 文档。
3. **提交带 issue 号**；关闭前逐条凭证（测试名/commit/实测命令），降级接受须显式写结论（守工单纪律）。
4. **审核节拍**：每批结束向用户汇报（完成清单/凭证/偏差/下一批开工请求）；用户每 5 轮审核偏好以批次审核承载。
5. **LOCKED 边界**：本规划本身是 REQ；专题落地凡触架构锁定文档（菜单 A-20260910-004、采集 A-20260904-002、运行模式 A-20260922-001 等）一律先发起人工审核，不擅改。
6. **发布纪律**：所有上线走标准发布流程（git push + 节点 upgrade 入口 + 自动备份），禁止节点上手拼命令。
7. **数据纪律**：金额分/时区/去重键/db_guard/bootstrap 等铁律不因批次赶工豁免；夜间作业先 dry_run 后 enforce（#193 同款三档可复用）。
