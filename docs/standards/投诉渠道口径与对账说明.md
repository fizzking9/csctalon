## 〇、一句话概括

**BMS 工单是「经营登记」，文档采集是「接待过程」。二者是同一投诉的两条腿，侧重点不同、互为补充。**

- **BMS 工单侧**：**只读**（原始数据不可更新），登记"谁投诉了、流转到谁"
- **文档采集侧**：可回填、可重采 —— 承载"接待过程、分析、处理细节"

**对账的目标不是"数量相等"，而是找出双方的缺口。**

## 一、渠道口径（权威定义）

### 1.1 工单侧（BMS `service_tickets.service_item`）

| 服务项 | 归类 | 说明 |
|---|---|---|
| 商品投诉 / 服务投诉 | **内部投诉** | 工单直接登记，未走外部渠道 |
| 微信投诉 | **商户号投诉** | 微信侧受理 |
| **工信部投诉** | **(外)卡商** | ⚠️ 见 §2 |
| 全国12315平台 / 公共服务平台 / 消费者协会 | **外部投诉** | 与 315 文档对账 |

> **投诉判据**：`service_category` 为**空白** 或 `= '投诉'`（不看 `service_item` 内容）。
> BMS 导出时若客服未选类别，该字段即为空白 —— 这是**已知的 BMS 导出特性**，
> 空白即视为投诉。

### 1.2 文档侧（315 表 `platform`）

| 平台 | 归类 |
|---|---|
| 航城监所 / 南沙市监局 / 宝安市监局 / 天河市监局 / 武汉市监局 | **外部投诉**（市监局/监所类） |
| 全国12315平台 / 公共服务平台 / 消委会 / 全国消协智慧315平台 | **外部投诉** |
| （文档侧**无工信部**） | — |

### 1.3 卡商侧

| 来源 | 归类 |
|---|---|
| `card_complaints`（卡商群投诉表） | **(外)卡商** |
| 工单侧 `工信部投诉` | **(外)卡商** |

> ⚠️ **「航城监所」与「工信部」是两个完全不同的渠道**，不归一类。
> 航城监所属**外部投诉**；工信部属**卡商投诉**。

### 1.4 统计独立性

| 桶 | 是否计入"投诉总量" |
|---|---|
| 内部投诉 | ✅ |
| 商户号投诉 | ✅ |
| 外部投诉 | ✅ |
| **(外)卡商** | ❌ **完全独立统计，不纳入总量** |

## 二、已识别的渠道错位问题

### 2.1 现象：市监局/监所投诉被录入为「工信部投诉」

**实测数据（生产，2026 年）**：

| 项 | 数量 |
|---|---|
| 工信部工单总数 | 327 |
| └ 其中 SN 在 315 属**监所/市监局类** | **241（73.7%）** |
| └ 其中 SN 在两表中属**真卡商** | 80（24.5%） |
| └ **两边都无**（无法判断） | 6（1.8%） |

**月度趋势（误录数）**：

| 月份 | 01 | 02 | 03 | 04 | 05 | 06 | 07 | **08** | 09 |
|---|---|---|---|---|---|---|---|---|---|
| 条数 | 14 | 6 | 11 | 1 | 33 | 22 | 32 | **92** | 19 |

### 2.2 根因

**BMS 工单侧没有「监所 / 市监局」这个服务项类别**，客服收到监所转来的投诉时
**只能选一个现有类别** —— 实测多选「工信部投诉」。

**验证**：工单表 11 个字段搜索「监所 / 市监局 / 监督局」，命中 **0**（仅 2 条
`remark` 是客户话术里的"我要去举报"）。

### 2.3 应对（本项目已实现）

**因 BMS 侧原始数据不可更新**，本项目采取**对账侧软纠正**：

```
315 文档(platform='航城监所')  ← 权威事实来源（可回填、可重采）
        ↓ 按 SN 关联
工单侧 service_item='工信部投诉' → 统计/对账时**纠正为外部投诉**
```

| 要点 | 说明 |
|---|---|
| **不改 BMS 数据** | 仅统计/对账口径纠正；原 `service_item` 保持原样 |
| **覆盖率 98.2%** | 327 条中 321 条可判断（241 监所 + 80 卡商） |
| **6 条无法判断** | 文档侧确无记录 → **保持原样**，不猜测 |
| **可回滚** | 纠正逻辑在代码层，无数据变更 |
| **统计层 + 对账层同口径** | #65 起统一，见 §2.4 |

> **该软纠正为临时方案**。已提交 BMS 开发：**建议增加「监所/市监局」类服务项**，
> 从源头解决。BMS 补齐后，本软纠正可保留作兜底（不冲突）。

### 2.4 ⚠️ 口径落地层级（#65 修复，2026-09-11）

**踩过的坑**：软纠正最初（#58）**只落在对账模块** `external_reconcile.py`，
统计层 `analytics._complaint_source_type_case()` **没有接** → 出现两个后果：

| 后果 | 说明 |
|---|---|
| **统计层少 160 条** | 工信部桶在统计侧**两边都不算**：外部桶排除它（#57 判为卡商桶），而 `card_total` 又只查 `card_complaints` 表 → **真实监所投诉被静默丢弃** |
| **看板与对账对不上** | 外部投诉：看板 211 vs 对账 371 |

**#65 修复方式** —— 软纠正**下沉到分桶函数**：

```python
complaint_bucket_case(item_col, channel_col=None, sn_col=None)
#                                                     ↑ 传入即启用软纠正
# 规则: 原判为 (外)卡商(工信部) ∧ SN 在 315 属监所/市监局类 → 改判「外部投诉」
```

`analytics._complaint_source_type_case()` 已**默认传入** `ServiceTicket.device_sn`
→ 全部统计口（总览 / 明细 / 分析 / 积压 / 主体）**一处修复，全域对齐**。

**不传 `sn_col` 时保持历史行为**（纯 item/channel 判据），
兼容 `metric_registry_service` 等不便取 SN 的调用点。

**数学性质**（有单测守护，见 `tests/test_issue65_source_scope.py`）：

$$
\text{raw 外部} \cup \text{raw 卡商} \;=\; \text{effective 外部} \;\sqcup\; \text{effective 卡商}
$$

即软纠正是对原始分桶的**完备互斥拆分** —— 无遗漏、无重叠。

**修复后实测（近 3 个月）**：

| 侧 | 修复前 | 修复后 | 对账接口 |
|---|---|---|---|
| 外部投诉 | 211 | **371** | 371 ✅ |
| 卡商 | 78 | **111** | — |
| 工单侧四桶合计 | 13,521（缺口 188） | **13,616 = 总数** ✅ | — |

### 2.5 (外)卡商总量的并集去重（#65）

**踩过的坑**：#53 撤销卡商去重，理由是「工单表 `service_item`/`service_category`
含「卡商」均为 **0 行** → 工单侧无卡商分类」。

**该断言的检测方式有误** —— 卡商在工单侧**不以「卡商」字面存在**，
而是以 `service_item='工信部投诉'` 存在（#57 证实）。所以 #57 之后工单侧
**已有真卡商**，老结论失效。

**实测（近 3 个月）**：

| 项 | 值 |
|---|---|
| 工单侧真卡商 | 28 条 |
| `card_complaints` 行数 | 78 |
| **SN 重叠** | **16 条**（全部已 `matched`）→ 不去重会双计 |

**#65 修正为与外部侧平行的公式**：

$$\text{卡商总量} = \text{工单侧真卡商} + \text{card\_complaints} - \text{重叠}$$

> ⚠️ **卡商仍不参与投诉总量**（#53 的用户口径不变）——
> 仅「卡商自身的总数」改为并集口径。看板三源合计仍**不含卡商**。

## 三、采集特性与去重机制

### 3.1 特性：源文档「先建行、后补 SN」

源文档存在**先建一行、稍后再补 SN** 的登记习惯。由于去重指纹含 SN，
补 SN 后指纹变化 → 会**新增**而非更新，产生：

| 行 | 特征 | 入库时间 |
|---|---|---|
| **残影** | 缺 SN（字段不全） | **较早** |
| 完整行 | 有 SN（字段齐全） | 较晚 |

**实测规模**：85 条 = 37 组，冗余 48 条。

### 3.2 处理三层（已实现）

| 层 | 机制 | 作用 |
|---|---|---|
| **入库侧** | 双指纹（主指纹含 SN + 弱指纹不含 SN） | 完整行入库时**把残影标记为被取代**（不删） |
| **统计侧** | `quality_status='dup_sn_backfill'` 排除 | 残影**不计入总数**（避免虚高） |
| **事件侧** | 弱指纹归并 | 残影**归入对应事件**（避免重复计事件） |

> ★ **零删除**：残影行保留，仅打标；置空 `quality_status` 即可完整回滚。

### 3.3 对上游的建议

| 建议 | 收益 |
|---|---|
| **源文档一次填全 SN** | 从源头避免残影 |
| **源文档登记时不要先建空行** | 同上 |
| 若确实需分步登记，请**在同一行内补充**（而非新建行） | 减少重复 |
