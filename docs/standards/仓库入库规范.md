# 仓库入库规范（什么该进 git，什么不该）

**生效日期**：2026-09-26（30b 终审 approved · 已定稿）
**版本**：v1.0-rc（v0.1 草案 → R1-R3 模型扫描增补规则 1-7 → 30b 终审增补规则 8 及措辞锐化）
**适用范围**：本仓库全部新增/存量文件与目录；约束 commit、CI 检查与任务收尾流程
**性质**：**元需求（META）** —— 约束"所有文件该怎么处置"，不描述具体功能

## 〇、一句话铁律

> **入库决策按「内容性质」判，不按「文件名形态」判。**
> `.` 开头只是 Unix 隐藏文件约定，与是否入库无关：
> `.gitea/workflows`（协作配置）必须入库；`.env`（密钥）严禁入库。
> 判据只有一个核心问题：**别人 clone 之后，需要它才能跑起来/理解系统吗？**

## 一、六类分类（SSOT）

| # | 类别 | 一句话判据 | 处置 | 正例 | 反例（严禁入库） |
|---|---|---|---|---|---|
| C1 | **共享资产** | 别人 clone 后需要它才能跑/理解 | **入库** | `backend/` `web/` `deploy/` `docker-compose.yml`、CI/CD 流水线配置、`.env.example` 模板、文档模板 | — |
| C2 | **耐用工具** | 跨任务复用的运维/迁移脚本 | **入库**（`scripts/`） | `kdocs_export.py`、`migrate_*.py`、`install-gitleaks-hook.sh` | 一次性 debug 脚本（应落 C4） |
| C3 | **结论报告** | 任务收尾提炼的结论与决策依据 | **入库**（`docs/reports/`、`docs/incidents/`） | 审计结论、事故复盘、治理报告 | 报告所依据的原始数据（属 C5/C6） |
| C4 | **任务现场** | 一次性、可再生成、噪音大的中间产物 | **本地保留**（`workdata/`，gitignore） | meta-loop 脚本、模型 raw 输出、轮次 state/log、探针 dump | 冻结语料若含 PII 升级为 C6 |
| C5 | **密钥凭证** | 泄露即事故 | **禁入** + gitleaks 拦截 | — | `.env`、token 文件、`certs/` 私钥 |
| C6 | **PII/业务数据** | 含手机号/单号/SN 等，合规风险 | **禁入** | — | 冻结语料 xlsx/csv/pkl、核查导出 CSV、`01样本数据/` |
| C7 | **缓存运行时** | 工具自动产生、**人不维护其内容**，删掉后工具自动重建**且语义不变**（锁文件除外，见补充规则 5） | **忽略** | — | `__pycache__`、`.ruff_cache`、`logs/`、`data/`、`backups/`、`dist/`、`.DS_Store` |

## 二、入库决策树（新增文件/目录时自问）

```
一个文件要不要入库？
│
├─ 1. 含密钥/token/私钥/密码？ ── 是 ──→ C5 禁入（gitleaks 应拦住；拦住前绝不 add）
│
├─ 2. 含真实业务数据（手机号/订单号/SN/姓名）？ ── 是 ──→ C6 禁入
│   （例外：脱敏后的样例、且行数 ≤ 20，可作 C3 报告附录）
│
├─ 3. 机器生成、删掉可重建？（缓存/日志/DB数据/打包产物）── 是 ──→ C7 忽略
│
├─ 4. 是任务中间过程？（loop 脚本、raw 输出、state、探针、冻结语料）
│      ── 是 ──→ C4 留 workdata/（gitignore），任务结束后提炼结论进 C3
│
├─ 5. 别人 clone 后需要它才能跑/理解/协作？ ── 是 ──→ C1/C2 入库
│
└─ 以上都不是 ──→ 问一句「删了它，三个月后的我会不会骂自己」
                   会 → C3 入库；不会 → 删
```

**判不出来的默认动作**：先不入库。入库容易出库难（历史里删 PII 要 rewrite history）。

### 补充判定规则（Round 1 扫描实证增补）

1. **点号配置 vs 点号缓存**：`.gitignore`/`.gitattributes`/`.gitleaks.toml`/`.editorconfig` 等是**人维护的协作配置**（C1），只有工具自动写入且人不看内容的（`.DS_Store`/`.pytest_cache/`）才是 C7。判据：「这个文件的内容是人写的吗？」
2. **测试代码 = C1**：`tests/`、`conftest.py`、`pytest.ini` 是「别人 clone 后验证系统所需」，一律入库。
3. **本地环境覆盖文件**：`docker-compose.override.yml`、`.env.local` 等「只对本机有意义的覆盖**实例**」**不入库**（属本机状态）；其**模板**（compose 主文件、`.env.example`）入库。判据：「这个文件换台机器还有意义吗？」没有 → 不入库。注意 override 文件本身是实例不是模板。
4. **vendored 第三方产物**（如 `scripts/1panel-v2.1.7-linux-amd64/` 整个安装包）：能走包管理/下载的**不入库**；必须随库分发的，整体视为 C1 一个原子单元，**内部文件不单独分类**（其内部 dotfiles 是上游产物，不适用本规范）。
5. **锁文件必须入库**（C7 的重要例外）：`package-lock.json`/`pnpm-lock.yaml`/`poetry.lock`/`uv.lock`/`Cargo.lock` 是机器生成，但其价值恰恰是**锁定版本、不可随意重建**——删掉重建语义就变了。判据：「删掉重建后，协作者拿到的还是同一个世界吗？」不是 → 入库。
6. **工具链状态文件**（如 `.ds-manifest` 这类工具自动生成的基线/清单）：判据——**该文件内容是否影响其他协作者在不同环境下的行为一致性？** 影响 → C1（同 lock 文件逻辑，如 `.ds-manifest` 作为上游修复对比基线）；不影响（纯本机状态）→ C7。
7. **IDE 配置颗粒度**：`.vscode/extensions.json`（团队推荐插件）= C1 入库；`.vscode/settings.json` 看内容——团队统一工具链配置（pytest/linter 路径等）= C1，纯个人 UI 偏好（主题/字号/窗口状态）= 不入库。项目应在 `.gitignore` 注释中显式声明选择哪种约定。
8. **测试数据生成脚本**：脚本本身 = C2（耐用工具）入库；**生成的数据**按内容判——脱敏合成数据 = C1 可入库，含真实业务数据 = C6 禁入。

## 三、目录约定（物理落点）

```
csctalon/
├── backend/  web/  deploy/        # C1 代码与部署
├── docs/                          # C3 文档与结论
│   ├── standards/                 #   元需求（本文件所在）
│   ├── reports/YYYYMMDD-主题/     #   任务结论报告（治理/审计/核查）
│   └── incidents/                 #   事故复盘
├── scripts/                       # C2 耐用工具（入库前需过§四门槛）
├── workdata/                      # C4 任务现场（gitignore，本机工作区）
├── .gitea/ .github/               # C1 协作配置（点号 ≠ 不入库）
└── data/ logs/ backups/ dist/
    uploads/ certs/ 01样本数据/     # C5/C6/C7 运行时与敏感数据（gitignore）
```

**`workdata/` 的使用纪律**：
- 什么都能放：loop 脚本、冻结语料、raw 输出、diag dump —— 它是本机工作台，不洁癖
- 任务收尾时必须做一件事：**提炼结论 → `docs/reports/`，过程留本地**
- 提示词类资产（如 `complaint_date_judge_prompt.py`）属 C2，验证有效后移入 `scripts/`，不长期滞留现场

**`scripts/` 的入库门槛**（防泥沙俱下）：
1. 已被 ≥2 个任务/场景复用，或明确是运维链路一环（备份/迁移/导出）
2. 无硬编码本机路径/密钥
3. 一次性调试/原型脚本（`debug_*`、`*_proto`、`*_v2`）一律先落 `workdata/`，证明耐用再移入

## 五、任务收尾 Checklist（C4 → C3 的固化动作）

任务（工单）收尾时，对本次产生的 `workdata/` 内容问三个问题：

1. **有没有结论值得留？** → 有则写 `docs/reports/YYYYMMDD-主题.md`（结论 + 证据摘要 + commit 引用）
2. **有没有工具值得留？** → 有则按 §三门槛移入 `scripts/`
3. **剩下的？** → 留在本地 `workdata/`，不入库、不删除（磁盘便宜，历史现场可能还有用）

## 六、常见误判（FAQ）

| 问 | 答 |
|---|---|
| `.` 开头的是不是都不入库？ | **不是**。点号 = 隐藏文件，与入库无关。`.gitea/`、`.github/`、`.editorconfig` 是协作资产必须入库 |
| 冻结语料是证据，不入库怎么复核？ | 语料含 PII 属 C6；复核靠 C3 报告里的**工具可重算的计数锚点**（行数/哈希/关键计数），不靠语料本身入库 |
| 模型 raw 输出呢？ | C4。它是过程噪音；终审结论（approved/issues）提炼进 C3 报告 |
| 一次性的迁移脚本算 C2 吗？ | 跑完即弃的不算；但**数据迁移类**建议入库——三个月后查"这批数据怎么来的"时它就是 C3 证据 |
| 本地 `.env` 想备份怎么办？ | 不进 git。用密码管理器或加密备份渠道 |
| AI 工具目录（`.trae/`、`.workbuddy/`、`.dsh/`）怎么判？ | **按内容性质判，不按目录判**：<br>① 团队协作资产（`.dsh/skills/`、`.github/agents/`）= C1 入库<br>② 内容型产物（`.trae/documents/` 设计文档）= C3 入库，但建议逐步迁往 `docs/design/`，内容不该长期住在工具目录里<br>③ 状态型产物（`.workbuddy/memory/` 工具记忆、会话状态）= C7 机器生成，**不入库**（已跟踪的移除跟踪，gitignore 兜底） |

**AI 工具目录速判**：问「这是写给**人**看的，还是写给**工具自己**用的？」
写给人的（技能、文档、指令）→ 入库；写给工具自己的（记忆、缓存、会话）→ 不入库。
