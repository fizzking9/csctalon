## 〇、一句话概括

**树上每一项 = 一张可下钻的物理表；它的中文名必须让人一眼看出「这是哪一类/哪一路」，并且能与物理表名一一对上。**

---

## 一、为什么需要这份规范

在 #100 之前，数据查看树有三类结构性问题（都不是"某一行写错了"，而是**没有约束**）：

| # | 现象 | 实际后果 |
|---|---|---|
| 1 | A~E 经营口径在树上完全不可见 | `refunds` 就是 A 路、`refund_record_reports` 就是 E 路对账基准 —— 这些定义只存在于架构文档里，看数据的人不知道，**容易把 E 与经营四路相加** |
| 2 | 同一事实两处说法打架 | `merchant_refunds` 在 `Upload.vue` 已标「旧,作废」，在数据查看仍叫「商户号现金流」 |
| 3 | 投诉三源被打散 | 工单侧在「工单与客服」、外部/卡商在「投诉登记」，与口径文档的三源分桶对不上 |

这些问题的共性是：**改一处不影响另一处，于是漂移**。本规范的作用是把"应该怎样"变成断言（§五），让漂移在 CI 就被拦住。

## 二、分组规范

分组顺序的**唯一来源**是 `data_source_registry.py::CATEGORY_ORDER`。前端**不得**再定义一份顺序（历史教训：两份定义必然漂移，见 A-20260910-004 菜单漂移）。

| 顺序 | 分组 | 回答的问题 | 包含 |
|---|---|---|---|
| 1 | **经营与对账** | 钱从哪出、对不对得上 | A~E 五路 + 聚合/视图物化 + 已停用源 |
| 2 | **投诉** | 谁在抱怨 | 工单侧投影 + 外部315 + 卡商群（三源分桶） |
| 3 | **工单与客服** | 谁在处理 | 服务请求**真身** + AI 助手 + SCRM 接待 |
| 4 | **交易与售后** | 交易后链路 | 订单台账 + 退货跟踪 |
| 5 | **基础数据** | 设备底座 | 套餐 / 标签 / 打标 / 流量 |

### 2.1 归属判据（避免"看着像就放进去"）

- **经营与对账**：该表的数据**参与或校准资金口径**。仅"有金额字段"不算 —— 订单台账有金额但只是佐证，故不在本组。
- **投诉**：该表的数据**是投诉本身**（谁投诉了什么），不是投诉的处理过程。
- **工单与客服**：该表记录**谁接待/处理了**这次接触。
- **交易与售后**：**交易发生之后**的履约链路（发货、退货、换货）。
- **基础数据**：**设备/商户维度的底座**，不随业务事件产生。

> ⚠️ 归属有疑问时，**判据是"这张表回答上面哪个问题"**，不是"它和哪个分组的表很像"。

### 2.2 组内顺序

由种子的 `sort_order` 决定（未声明 = 999，排组末尾）。约定：

| 场景 | 顺序 |
|---|---|
| 经营五路 | A(10) → B(20) → C(30) → D(40) → E(50) |
| 派生表 | 排在**源路之后**（聚合 60 → 视图 70 → 已停用 80） |
| 投诉组 | 工单投影(10) → 外部(20) → 卡商(30) |
| 真身 vs 投影 | 顺序无关（不同分组），但投影在本组内应前置（它是该工作流的第一入口） |

**原则：先看原路，再看派生物；先看入口，再看明细。**

## 三、命名规范

### 3.1 格式

```
[⚠️]<域前缀>·<中文语义>
```

- **域前缀**：必填，取自下方白名单。
- **中文语义**：必填，用业务词汇，**禁止出现 code 原文**（`refund`/`wallet` 这种）。
- **⚠️**：仅在数据不可靠或已停用时加（见 §3.3）。

### 3.2 前缀白名单

| 前缀 | 用途 | 示例 |
|---|---|---|
| `A`~`E` | 经营五路（口径见 A-20260908-004） | `A·退费单(线上直退)` |
| `聚合` | 多路合并物化 | `聚合·经营四路出款(物化)` |
| `视图` | 关联预计算结果 | `视图·A路退费关联宽表(物化)` |
| `投诉` | 投诉三源 | `投诉·外部315/监督局` |
| `工单` | 工单记录 | `工单·服务请求(投诉+退款)` |
| `客服` | 接待/处理记录 | `客服·智能助手处理记录` |
| `SCRM` | SCRM 平台数据 | `SCRM·客服接待会话` |
| `订单` / `售后` | 交易与售后 | `订单·支付台账` / `售后·退货跟踪` |
| `设备` | 设备底座 | `设备·套餐` |
| `旧` | 已停用（必须与 ⚠️ 同用） | `⚠️旧·商户号款项(已停用)` |

新增前缀需同步更新：
1. 本表
2. `backend/tests/test_data_source_naming.py::_ALLOWED_PREFIXES`
3. `docs/README.md` §六 性质索引（若涉及新分组）

### 3.3 必须加 ⚠️ 的情形

| 情形 | 要求 | 例 |
|---|---|---|
| **已停用**（不再作统计取数） | 显示名必须含「停用」或「作废」+ `旧·` 前缀 | `⚠️旧·商户号款项(已停用)` |
| **口径易误用**（会被误加减/误当基准） | 必须在**显示名**中标注，不能只写 description | `E·退款记录报表(对账基准)` |

> ⚠️ **只写在 `description` 里不算**。树上看到名字的人不会点开描述 —— 显示名是唯一保证被看到的位置。
> 这条规则来自 #100 的实际教训：`merchant_refunds` 的名字与 `Upload.vue` 的说法曾是两套。

### 3.4 code / table_name / name_cn 三者关系

| 字段 | 约束 |
|---|---|
| `code` | 全局唯一；是 API 与前端路由的稳定标识，**改名属破坏性变更** |
| `table_name` | 必须等于 `model.__tablename__` |
| `name_cn` | 全树唯一（否则同一名字指向两张表，使用者无法判断） |

**唯一允许的例外**：`device_tag_binding` ↔ `device_tag_rel`
—— 该表与 ORM 多对多关联表 `device_tag_rel` 是**同表双映射**（`DeviceTagBinding` 用 `extend_existing=True`）。
此类例外必须在 §3.5 登记，并在测试中同步。

### 3.5 例外登记表

| code | 实际 table_name | 理由 |
|---|---|---|
| `device_tag_binding` | `device_tag_rel` | 同表双映射：`device_tag_rel` 供多对多 secondary 使用，`DeviceTagBinding` 供行级 upsert 与数据浏览使用 |

## 四、投影机制（同表别名）

### 4.1 问题

投诉工作流的使用者从「投诉」组进入，但 `service_tickets` 只能注册**一次** ——
双注册会让同一张表出现在两个 code 下，统计与去重口径立刻分裂（违反 [数据采集合并去重机制说明.md](数据采集合并去重机制说明.md)）。

### 4.2 方案

在 `DATA_SOURCE_PROJECTIONS` 声明**投影**：

```python
{
    "code": "complaint_ticket",
    "projection_of": "ticket",          # 必须指向已注册 code
    "name_cn": "投诉·服务请求工单",
    "category": "投诉",                 # 必须与真身不同分组（同组内重复才是冗余）
    "sort_order": 10,
    "true_body_category": "工单与客服",  # 必须声明真身分组
    "true_body_name": "工单·服务请求(投诉+退款)",  # 必须声明真身名称
}
```

### 4.3 硬性要求

| # | 要求 | 理由 |
|---|---|---|
| 1 | 投影**不落** `data_sources` 表 | 它无独立元数据，落库就会与真身漂移 |
| 2 | `projection_of` 必须指向已注册 code | 否则投影查不到字段/记录（"点了没反应"） |
| 3 | **必须**声明 `true_body_category` + `true_body_name` | AGENTS.md 界面纪律第 5 条：投影必须声明真身位置，否则属违规重复展示 |
| 4 | 必须与真身**不同分组** | 同组内重复仅是冗余 |
| 5 | 恒为 `readonly` | 写操作必须回到真身，否则使用者不知道改的是哪张表 |
| 6 | 后端所有按 code 取元数据处必须 `resolve_projection_code()` | 投影未落库，不解析必 404 |

### 4.4 投影 ≠ 第二个数据源

投影**不产生新的数据源**，因此：
- 不计入"数据源个数"（前端 `activeSourceCount` 排除 `is_projection`）
- 不参与采集/同步/去重
- 不改变任何统计口径

## 五、强制落地（三层）

### 5.1 断言层（CI 阻塞）

| 测试 | 覆盖 |
|---|---|
| `backend/tests/test_data_source_naming.py` | name_cn 唯一 / code↔table 一一对应 / 前缀白名单 / 分组登记 / A~E 顺序 / E 标注对账基准 / 停用标注 / 投影合法性 |
| `backend/tests/test_data_source_tree_api.py` | 接口返回的分组顺序与组内顺序 / 投影在列表中且带真身标记 / 投影字段与真身一致 |
| `web/src/views/data/__tests__/Browser.tree.spec.js` | 复合 key（同一 code 多分组不高亮错乱）/ 前端无重复分组定义 / 投影标签与真身声明 / 边界说明存在 / 三层设计说明齐全 |

### 5.2 变更流程

新增/修改数据源时：

1. 在 `DATA_SOURCE_SEEDS`（或 `PROJECTIONS`）登记，填齐 `name_cn` / `category` / `sort_order` / `description`
2. 跑 §5.1 三个测试
3. 若新增**分组**或**前缀** → 同步更新 §二 / §3.2 / §3.5 与本文件版本号
4. 若涉及口径（A~E 或投诉三源）→ 先确认不违反对应 LOCKED 文档，必要时走人工审核

### 5.3 禁止事项

| 禁止 | 说明 |
|---|---|
| ❌ 前端再定义一份分组顺序 | 两份定义必然漂移（A-20260910-004 教训） |
| ❌ 同一张表注册两个 code | 统计口径分裂；需要别名请用投影 |
| ❌ 投影不声明真身位置 | 违反 AGENTS.md 界面纪律第 5 条 |
| ❌ 停用/易误用只写在 description | 显示名是唯一保证被看到的位置 |
| ❌ `name_cn` 出现 code 原文 | 中文名是给使用者看的 |

## 六、边界：本规范不管什么

- **不管"哪些表该进数据查看树"** —— 判据是"是否可下钻的原始业务表"；工作流/配置/日志/维度/中间表各有功能页，边界在界面上以 ⓘ 声明。
- **不管全量表清单** —— 那是 [数据库表结构说明.md](数据库表结构说明.md)（REF）的职责。
- **不管收藏/自选/权限** —— 数据查看树当前全员可见，无按角色裁剪。
