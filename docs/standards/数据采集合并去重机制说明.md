# 数据集采集/合并/去重 机制说明

**性质**：元需求（META） —— 约束**所有采集通道**的去重键


**版本**：v1.0 · 2026-09-08
**适用范围**：系统所有数据采集通道（BMS/SCRM/共享文档/外部推送/文件导入）的数据合并与去重口径
**背景**：共享文档在线采集落地后，需系统梳理"多通道采集同一数据集时如何合并去重"，确保一致性、幂等、不产生脏数据。

---

## 一、总体架构：多通道 → 统一去重层 → 业务表

```
通道(取数方式)                    去重层(写库语义)            业务表
├─ BMS playwright/http   ─┐
├─ SCRM openapi          ─┤
├─ 共享文档(导出xlsx)     ─┼──→ 按 data_type 的"去重键" upsert ──→ refunds / tickets /
├─ 外部推送(workbuddy)   ─┤                                  manual_refunds /
├─ 文件导入(上传xlsx/csv) ─┘                                  external_complaints / ...
```

**核心原则**：
1. 每个 data_type 有一个**稳定的去重键**（唯一约束/指纹/复合键），多通道写同一数据集时按该键 upsert；
2. **通道无关**：同一业务数据无论来自 BMS/共享文档/workbuddy/文件导入，去重键一致 → 不会重复；
3. **幂等**：同一批数据重复采集/重复推送 → 更新而非新增。

## 二、各数据类型去重键与合并语义

### 2.1 投诉（external_complaints / card_complaints）— 指纹去重

| 项 | 值 |
|---|---|
| 去重键 | `dedup_hash` = md5(**投诉日期 \| 投诉手机号 \| 设备SN \| 归一化投诉问题**) |
| 来源 | `upsert._complaint_identity_hash` 与 `complaint_sync._identity_dedup_hash` **同一口径** |
| 写库 | `on_conflict_do_update(index=dedup_hash)` — 冲突则整行更新（含 result/处理时间/关联工单号） |
| 编号处理 | `complaint_no` 不入指纹（上游易丢 53%）；推送无编号时不覆盖库中已有编号 |
| 覆盖通道 | workbuddy push / 共享文档 / 文件导入 / （future OpenAPI） |

> **多源合并要点**：315 的 result=办结类（含重复投诉）算"已处理"；重复投诉同指纹更新到最新状态。
> 注意：同一手机号+SN 但不同日期/不同问题 → 不同指纹 → 各自独立（不误合并）。

### 2.2 手动退款（manual_refunds）— 复合键去重

| 项 | 值 |
|---|---|
| 去重键 | (**登记日期(北京) \| 订单号 \| 设备号 \| 登记人**) — `_manual_dedup_key` |
| 写库 | `on_conflict_do_update`（登记日期按北京 date 归一，兼容时区/历史解析差异） |
| 语义 | 四列确定一笔退款单；金额/状态变化时 UPDATE 同一行，不因金额变化产生新行 |
| ⚠️ 全量对账 | `full_sync=true` 会**删除库中不在本次 payload 的行** → 共享文档在线采集**必须 full_sync=false**（增量），否则误删（血泪教训） |
| 覆盖通道 | workbuddy push / 共享文档 / 文件导入 |

> **D↔E 对账**：manual_refunds 有 `quality_status='dup_residual'` 标记历史重复治理行（A-20260906-001），统计口径已排除。

### 2.3 BMS/SCRM 各源（18 个 data_type）— 各业务唯一键

经 `run_upsert(df, data_type, mapping, db)` → `UPSERT_DISPATCH` 分发，每 data_type 有专属唯一键：

| data_type | 唯一键/去重语义 |
|---|---|
| refund | 退款单号/订单级唯一 |
| wallet | `business_id` 唯一（部分唯一索引处理 device_sn NULL） |
| device_combo | (device_sn, package_name, start_date) 组合 |
| merchant_refund | (trade_time, merchant_order_no) 部分唯一索引 |
| cs_record | `business_id` 唯一（`uq_cs_record_business`） |
| device_flow_usage | (device_sn, stat_month) 唯一 |
| device_tag | tag_name 唯一 |
| shanmao_refund / manual_refund | 各自业务键 |
| device_profile | sn 主键 on_conflict |

> 这些源多由单一通道（BMS）采集，跨通道合并需求低；若未来共享文档也接此类数据，需确认落到对应 data_type 的入库函数（复用其唯一键）即可幂等。

## 三、采集调度频率（现状 + 统一调度方案）

### 3.1 现状

| 通道 | 调度方式 | 频率 |
|---|---|---|
| BMS 高频源 | `bms_scheduler` 主循环，白天整点(8~23,0)触发 `_do_scheduled_sync` | 每小时 |
| BMS 低频源 | 每天 6:00 低频档（A-20260907-001） | 每天 1 次 |
| SCRM | 与 BMS 高频同窗口并发 | 每小时 |
| 共享文档 | `_maybe_sync_shared_docs` 主循环每 60s 检查，各源按 `sync_interval_minutes`(默认60) 自判到点 | 各源独立 |

> **问题**：共享文档目前是"独立自轮询"（每源自己的 interval），与 BMS 高频（整点触发）**不同步** —— 可能共享文档刚采完，BMS 整点又在忙；或反向。用户期望**统一调度**。

### 3.2 统一调度方案（建议，待工单实现）

**目标**：共享文档采集并入白天高频窗口（8~23,0），与 BMS 高频同一调度节奏；未来窗口改为半小时时自然跟随，无需改共享文档代码。

**设计**：
1. **移除** `_maybe_sync_shared_docs` 的独立 60s 自轮询（或保留为兜底但非主路径）；
2. 在 `_do_scheduled_sync` 白天高频触发时，**一并触发共享文档采集**（`source_tier="high"` 时，除 BMS high + SCRM 外，追加"到点的 shared_doc 源"）；
3. 共享文档源仍可配 `enabled`/`sync_interval_minutes`，但 interval 语义改为"高频窗口内的跳过节奏"（如每 N 个窗口采一次），而非独立计时；
4. 互斥：共享文档浏览器导出慢（单源 30~120s），须与 BMS sync 共用 `SyncTaskManager` 互斥，避免并发 playwright 冲突；建议串行执行（每源 `to_thread`，且仅在调度空闲窗）。

> ⚠️ 涉及已锁定架构 A-20260907-001（分频模型）。若采纳需升版本/新增架构注记，并另开工单实现。

## 四、去重/合并一致性核对清单（新通道接入时）

接入一个新共享文档/新数据源时，核对：

1. [ ] 目标 data_type 是否有**稳定去重键**（唯一约束/指纹/复合键）？
2. [ ] 新通道写入是否走**既有入库函数**（complaint_sync/manual_refund_sync/run_upsert），而非自建写库？
3. [ ] 去重键与既有通道是否**同一口径**（避免 workbuddy 用 A 键、共享文档用 B 键 → 双写重复）？
4. [ ] 是否**不删历史**（full_sync 恒 false，除非明确是全量对账场景）？
5. [ ] 空行/脏行是否在读取层过滤（避免污染 failed/统计）？
6. [ ] 登记时间/处理时间是否按"登记日 vs 处理日"双口径（投诉）或北京日期归一（退款）？
7. [ ] 采集后是否失效对应看板缓存？
