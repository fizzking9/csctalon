# 跨项目经验迁移指南

**版本**：v1.0
**日期**：2026-09-06
**性质**：方法论沉淀 / 可迁移最佳实践（非本项目强制约束，供其他项目参考）
**来源**：csctalon 项目实战经验（事故 → 根因 → 修复 → 防复发 闭环提炼）
**用法**：把本文档按需拆给其他项目团队；每章末尾的"可勾选清单"可直接作为落地模板。

> 说明：本文档属于**知识资产**，不是本仓库的开发规范（开发规范见 `AGENTS.md` 及各 standards 文件）。引用其中示例时，请结合目标项目的技术栈取"方法"，勿照抄"参数"。

## 一、迁移优先级（建议按此顺序带走）

| 优先级 | 主题 | 成本 | 收益 | 适用场景 |
|---|---|---|---|---|
| P0 | AI 协作治理三件套（§二） | 低 | 极高 | 有 AI 参与写代码的项目 |
| P0 | 统计口径单一事实源 + 字段可信度审计（§四） | 中 | 极高 | 数据统计/报表类项目 |
| P1 | 事故→回归测试→审查条目闭环（§五） | 中 | 高 | 任何有 CI 的项目 |
| P1 | 采集可靠性三层模型（§六） | 高 | 高 | 对接第三方抓数/拉取的项目 |
| P2 | 缓存显式编排三级加速（§七） | 中 | 中 | 读多写少、聚合查询重的系统 |
| P2 | 发布/部署纪律（§八） | 低 | 中 | 有部署流水线的项目 |
| P3 | 经验落库机制（§九） | 低 | 中 | 团队协作、有 AI 参与的项目 |

## 二、AI 协作治理三件套（P0）

> 背景：AI 大量参与生产开发后，必须建立"防 AI 事故"的护栏。三件套 = 仓库级约束 + 派工单模板 + 审查清单。

### 2.1 仓库级约束单文件（相当于本项目的 AGENTS.md）

让 Copilot/其他 AI 打开仓库即自动加载。铁律只列最重要的，避免冗长失效：

- [ ] 禁止在生产代码使用 `console.log`（前端）/ 裸 `print`（后端），必须走项目封装的 logger（例外：显式 `[TODO:` 前缀标记）
- [ ] 禁止无参数化拼接 SQL（允许 `text()` + 绑定参数，禁止 `f"...{var}..."` 直接拼进 SQL）
- [ ] 禁止硬编码密码/密钥/内网 IP/DB 账号，一律走环境变量
- [ ] 禁止擅自修改已锁定架构文档（LOCKED 标记，修改须人工审核）
- [ ] 禁止绕过迁移工具直接改表结构（本项目 = Alembic）
- [ ] 输出风格：代码块带关键逻辑注释；改现有文件先说明改动意图；金额整数化（分）存储

### 2.2 派工单模板

模糊需求（"写个接口"）必然导致 AI 猜测。模板强制填写以下区块：

```markdown
## 任务        <- 一句话
## 输入        <- 参数名/类型/必填/范围/枚举
## 输出        <- 字段、单位、分页、统一包装格式
## 约束        <- 框架/路径/表名/金额单位/排序/权限/时区
## 参考        <- 指向现有文档，避免重复造轮子
## 禁止事项    <- 明确禁止拼接 SQL、硬编码等
## 测试要求    <- 至少 1 正向 + 2 边界，测试文件命名约定
```

### 2.3 审查清单 + 分级报告

- [ ] AI 初审只输出报告不修改代码，输出分级：CRITICAL（阻塞）/ WARNING（建议）/ INFO（风格）
- [ ] 有 CRITICAL → 切回开发修复 → 重新审查，才可合并
- [ ] 审查维度固定：安全（注入/XSS/硬编码/路径穿越）、正确性（空指针/泄漏/事务/金额整数/时区/ORM 布尔）、一致性（与架构文档/错误码/文档登记/migration）、性能（N+1/分页/缓存）
- [ ] 人工终审重点核对 AI 容易漏的：业务正确性（对照需求）、边界条件（空值/超大分页）、与现有系统兼容性、数据同步口径影响

### 2.4 角色权限隔离（进阶）

- [ ] Architect 只读、Reviewer 只读、Developer 可写（工具权限按身份隔离）
- [ ] 阶段切换新建会话清空上下文，防止 AI 把架构阶段假设带进开发

## 三、工单驱动 + 文档分层（闭环治理）

> 教训来源：本项目的"有审计、有文档、但无工单"断层 → 治理无法闭环（09-02 数据缺口事件）。

### 3.1 工单规则

- [ ] 所有任务先建工单再动手（含需求/事故/治理/缺陷/运维）
- [ ] 工单是唯一入口与唯一闭环凭证；代码提交/PR 携带 `#issue号`
- [ ] 一单一目标；**事故类强制拆两条**：incident（止损/闭环）+ governance（防复发/治理），禁止混单
- [ ] 工单必写"关闭条件"（无关闭条件的工单视为无效）
- [ ] 粒度治理：< 半天无独立验收价值的琐碎改动合并；无法独立验收/跨模块/> 1 天的必须拆分（父+子工单，叶子可独立关闭）
- [ ] 想法/待办先进 backlog 台账，不进工单池（防碎片化）

### 3.2 文档分层（防"锁定"与"草稿"混淆）

| 层 | 含义 | 能否被开发引用 |
|---|---|---|
| standards/ | 规范、清单、模板 | 是（可更新） |
| arch/（LOCKED） | 已锁定架构 + git tag `arch/xxx` | 仅 LOCKED 可引用 |
| arch/_pending/ | 待人工审核草案 | 否（只能参考） |
| design/ | 需求梳理/方案（评审中） | 评审通过后转 arch |

- [ ] AI 开发只能引用 LOCKED 文档 → 避免 AI 边开发边改架构
- [ ] 文档命名统一带类型前缀 + 日期，配套一份"目录职责表"约束归位

### 3.3 单一事实源（SSOT）

- [ ] 一个统计口径只在一处定义（聚合器/service 函数），页面与接口调用它，禁止各自手写 SQL
- [ ] 口径变更时，同步更新口径文档 + 所有调用方回归

## 四、统计口径治理（P0，BI/统计类项目最大坑）

> 教训：统计口径错误比代码 bug 危害更大且更难发现（金额虚高、工作量虚增通常无报错）。

### 4.1 口径编号 + 公式树集中登记

- [ ] 每个统计口径有唯一编号与明确定义（本项目五路退款口径：A 线上直退 / B 用户提现 / C 闪猫 / D 手动 / E 对账基准）
- [ ] 派生指标（对账偏差 = 经营估算 − 实际现金流）写清公式树与各叶子取数规则
- [ ] 口径随业务升级做版本管理（v1 → v4 → v1.1），变更记录保留原因

### 4.2 字段可信度审计并公示

- [ ] 上游/第三方字段并非全可靠，做量化审计而非印象判断
  - 例：本项目审计 `finish_time`：49.6% 被批量覆盖、23% 同步填充、16.7% 同瞬填充 → 仅 10.7% 真实 → 结论 89% 不可靠
- [ ] 不可靠字段在数据源注册/UI 层禁用（`is_filterable=False`），保留数据仅供已知风险的 SQL
- [ ] 维护"时间字段优先级表"：每分析场景推荐字段 vs 不推荐字段，写明证据与替代方案
- [ ] 关注自动写入（如"每日 03:15 批量任务覆盖"）对时间字段语义的污染

### 4.3 值域脏数据强制排除标准

- [ ] 枚举过滤注意大小写与写法变体（本项目 `NOT IN ('sys','system','SYS','System')` 必须 4 种全列——PG 大小写敏感且库中两种写法并存，漏一种金额就错）
- [ ] 用关键词黑名单治理"状态字段不可信、需备注文本二次过滤"的数据（冻结/失败/驳回等）

### 4.4 交叉验证代替单表自查

- [ ] 时区/金额等全局性正确性，用两张独立数据表 join 验证
  - 例：A 路 vs E 路按 `(device_sn, 金额±0.01)` join，1367 对时间差 0h、无 ±8h 集中 → 证明全链路时区正确
- [ ] 对账偏差定期核对，偏差来源要能下钻定位

### 4.5 口径口径变更的联动影响

- [ ] 改口径前盘点所有消费者（页面/接口/缓存 key/导出）
- [ ] 修改后跑全部回归测试 + 前端 build + 缓存预热验证

## 五、"静默错误"事故清单（P1，全是真实踩坑）

> 通用教训：**能自动修 + 影响面大 + 出错静默** 的组合必须有回归测试兜底，且审查清单要有对应显式检查项。

| # | 事故 | 现象 | 为什么难发现 | 防复发 |
|---|---|---|---|---|
| 1 | ORM 列 `X.col is True`（替代 `== True`） | 查询静默返回空、页面空白 | 自动 lint fix（E712）误伤 ORM 列；不报错无异常 | 规范用 `col.is_(True/False)`；审查清单加条目；专门回归测试 |
| 2 | SQL 布尔"批量清理" | 同上（28 处被误改） | 自动修复无法区分 Python 变量与 ORM 列 | 同上 |
| 3 | 裸 `div:has-text("导出")` 当按钮点 | 点中容器空白返回成功 → 假成功真失败 | 子串匹配命中祖先容器 | 点击前校验按钮语义；测试 FakePage 模拟真实 DOM |
| 4 | 模态弹窗未处理 | 后续点击全被拦截，误报"未找到按钮" | 脚本从不点掉"确定"弹窗 | 每次点击前先 dismiss 模态 |
| 5 | 会话失效未识别 | 复用登录态被踢回登录页，连锁失败 | 把"登录"按钮当查询按钮点 | 专用异常类 + 专用 except 分支，不熔断同组后续源 |
| 6 | 缓存 key 与预热/失效不逐字符对齐 | 同步了看板不变 / 首次访问慢 | 三处靠记忆 | 固化"接入清单"文档（见 §七） |

落地动作：

- [ ] 上述每条已发生的事故 → 新增一条对应回归测试
- [ ] 把事故关键词写进 review-checklist（如"禁止对 ORM 列用 `is True/False`"）

## 六、采集链路可靠性三层模型（P1，对接第三方抓数）

### 6.1 架构分层

```
错误分级重试 ── 熔断+半开探测 ── 缺口队列（兜底补跑）
```

- [ ] **错误分级重试**：transient（5xx/429/超时）指数退避；permanent（4xx/凭证错/解析错）不重试；整窗失败按更小片降级重试
- [ ] **滑动窗口熔断 + 半开探测**：连续失败 N 次熔断；定时放短窗试探，成功自动恢复 → 单源故障不永久停摆
- [ ] **缺口队列**：一源一日一行唯一键；补跑只补缺口源；定期全量兜底清零
- [ ] 部分成功 = success + 失败片清单，不整窗判失败

### 6.2 同步纪律

- [ ] 定时窗口硬约束（只拉当天），upsert 幂等天然补漏
- [ ] 手动同步带冷却期（5 分钟），`force` 显式跳过
- [ ] 全局互斥锁保证任意时刻最多一个同步任务
- [ ] **部署与采集互斥**：部署重启会打断采集 → 留僵尸会话 → 后续批次登录互踢；部署前确认无采集任务在跑
- [ ] 浏览器/进程时区必须显式设为业务时区（容器默认 UTC 会静默污染时间标签）

### 6.3 文件/目录配置（重灾区）

- [ ] 目录类环境变量命名单复数统一，且与代码 settings 同名（曾因 `UPLOAD_DIR` vs `UPLOADS_DIR` 不一致致附件静默丢失、登录态不落盘）
- [ ] 安装脚本对非法值（相对路径在容器 = 空目录）加守卫校验（warn 不自动改）
- [ ] 容器内 volume 挂载路径与宿主机路径都要落盘验证

### 6.4 喂给 AI/下游的 feed 段预算

- [ ] 长 JSON feed 要防硬截断把关键段挤出（本事故：成员名单占满 6.5KB → 模型答"未提供"）
- [ ] 次要大字段先精简（去逐人名单），保证关键段不被挤出
- [ ] 空关键段自愈：检测主字段有值但子段全空 → 删缓存重算

## 七、缓存显式编排：三级加速 + 防击穿（P2）

- [ ] **写入后失效 → 预热 → 路由层缓存**三级，全部显式编排
- [ ] **日期感知 TTL**：历史窗口（已定型）长 TTL（24h），含今天的窗口短 TTL（60~120s）
- [ ] **写入高峰期 TTL ×5 放大**（clamp 上限）：同步期间防缓存击穿打爆 DB；同步结束恢复
- [ ] **预热 TTL > 路由 TTL**（如 180s > 60/90/120s），单次预热覆盖更久热窗口
- [ ] 预热节流：仅当 key 剩余 TTL 低才重算；夜间无人省计算；进程级单飞锁
- [ ] **显式接入清单**（新增数据源/接口时逐条勾选，不靠记忆）：
  - [ ] 数据写入入口 → 调用失效 pattern
  - [ ] 新接口 key 前缀 ∈ 失效 pattern
  - [ ] 新接口已纳入预热函数（key 逐字符对齐）
  - [ ] 改了路由 key 同步改 cache_warmer

## 八、发布/部署纪律（P2）

- [ ] **发布纯净性**：多条发布链路（git/tar/package）用同一份排除清单；新增目录时同步改所有清单，否则开发产物进生产目录/镜像
- [ ] 环境变量命名生产只有一套、与代码同名、脚本读旧名会静默回退相对路径 → 加守卫
- [ ] 受限 CI（内网 Git + 自建 runner）经验：
  - runner 容器内 `docker run -v` 是 daemon 视角 → clone 到宿主机共享路径
  - 镜像预拉，避免 CI 内拉 registry 超时
  - 新版前端测试栈需较新 Node（如 jsdom/undici 需 Node 22+）
- [ ] 密码脱敏（git filter-repo）：占位符需以 `<` 开头才躲过扫描规则；中断会残留 `.git/filter-repo` 卡确认，需清理重跑
- [ ] 部署后验证清单：迁移 head 单一 / 新表存在 / 熔断缓存无残留 / 调度器回填正常 / 启动补跑自动验证新代码

## 九、经验落库机制（P3，本仓库最值得复制的一点）

- [ ] 仓库内维护事故/经验笔记，格式统一：**现象 → 根因 → 修复 → 验证 → 教训/防复发**
- [ ] 事故笔记与工单号、架构文档互相引用（`#issue号`、`A-YYYYMMDD-序号`），形成可追溯链
- [ ] 关键生产修复附"验证证据"（实测数据对比：修复前 121 次全量重建 2min → 修复后增量秒级）
- [ ] 新会话自动加载经验笔记 → 避免同一团队/AI 反复踩同一坑
- [ ] 每份经验可上提为"通用规范条目"或"审查清单检查项"（事故 → 门禁的正向循环）
