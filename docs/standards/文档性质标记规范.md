# 文档性质标记规范（Doc Class）

**生效日期**：2026-09-11
**版本**：v1.0
**适用范围**：本仓库**全部**约束性文档（`AGENTS.md`、`docs/standards/`、`docs/arch/`、`docs/` 根级）
**性质**：**元需求（META）** —— 本规范约束"其它文档该怎么被分类与标记"
**关联文档**：[AGENTS.md](../../AGENTS.md)、[issue-workflow.md](issue-workflow.md)、[review-checklist.md](review-checklist.md)、[docs/README.md](../README.md)

---

## 〇、一句话铁律

> **文档必须先说清自己是「需求」还是「需求的需求」，再谈内容。
> 两类文档适用完全不同的规则 —— 混用会导致用错标准审查、用错流程维护。**

---

## 一、为什么要有这个区分

### 1.1 问题的起源

用户提出（2026-09-11）：

> 「我看这些需求条目，**有的是需求，有的是需求的需求**，都需要打上不同的标记。」

这个区分戳中了一个真实混乱：仓库里 60+ 份文档混在一起，
**描述"做一个功能"的**与**约束"所有功能怎么做"的**没有区分，导致：

| 症状 | 后果 |
|---|---|
| 用"需求"的标准要求"元需求" | 要求规范写"验收标准"，但规范的验收标准是"它能否约束住别人" |
| 用"元需求"的稳定性要求"需求" | 需求本就该随迭代演进，被当成"锁定不可改" |
| 找不到"约束源" | 实现者不知道**到底该遵守哪几条**，规范沦为摆设 |
| 目录名误导 | `docs/standards/` 里混着参考说明与接口契约，新人无法判断哪份有强制力 |

### 1.2 实测盘点（2026-09-11）

对本仓库全部约束性文档分类后的真实分布：

| 性质 | 数量 | 典型 |
|---|---|---|
| **元需求（META）** | 11 | `AGENTS.md`、`issue-workflow.md`、`数据时间字段使用规范.md` |
| **需求（REQ）** | 5 + 架构 47 | `workbuddy数据同步接入规范.md`（约束某一具体集成）、`docs/arch/*` |
| **参考（REF）** | 7 | `数据库表结构说明.md`、`API接口文档.md` |

> ⚠️ **发现的严重问题**：11 份元需求中**仅 4 份**被 `AGENTS.md` 显式引用
> （`issue-workflow` / `review-checklist` / `数据时间字段使用规范` / `界面设计说明规范`）。
> 其余 7 份**无任何强制入口** —— 即"标记了但约束不住"。
> 本规范 §五 规定如何修复。

## 二、三分类定义

### 2.1 元需求（META）—— 「需求的需求」

**定义**：约束**所有**需求/实现该怎么做，而非描述某一个功能。

**判定标准**（满足**任一**即可）：

| # | 判据 | 例子 |
|---|---|---|
| 1 | 回答"**任何**新增功能都必须遵守什么？" | `数据时间字段使用规范`：所有时间统计必须 `AT TIME ZONE 'Asia/Shanghai'` |
| 2 | 定义**口径/术语的权威含义** | `投诉渠道口径与对账说明`：什么叫"内部投诉" |
| 3 | 规定**流程/门禁** | `issue-workflow`：所有任务先建工单 |
| 4 | 提供**审查判据** | `review-checklist`：CRITICAL 阻塞合并 |
| 5 | 是**模板**（约束产出物形态） | `task-work-order`：派工单必须含输入/输出/约束 |
| 6 | 约束"**文档/配置自身**如何组织" | **本规范**：文档必须标性质 |

**维护特征**：**极少变动**；改动需评估"全仓库影响面"，通常配合工单 + 人工审核。

### 2.2 需求（REQ）—— 「具体要做什么」

**定义**：描述一个具体功能/模块/集成的设计与实现契约。

**判定标准**：

| # | 判据 | 例子 |
|---|---|---|
| 1 | 有明确的**功能边界**（做什么、不做什么） | `A-20260911-001-投诉分析整体重构` |
| 2 | 有**接口契约**（路径/字段/错误码） | `workbuddy数据同步接入规范`：`/sync/complaints/push` 契约 |
| 3 | 有**验收标准** | 同上，须能逐条核验 |
| 4 | 有**归属工单** | 每份需求文档应关联 issue 号 |

**维护特征**：**随迭代演进**；变更走正常工单流程即可，无需全仓库评估。

> 📌 **易混点**：名为"XX接入规范"的文档通常是 **REQ** 而非 META ——
> 因为它只约束**某一个具体集成**，不是"所有需求怎么做"。
> **判据是"约束范围"，不是文件名里有没有'规范'二字。**

### 2.3 参考（REF）—— 「现状记录」

**定义**：记录系统现状/知识/台账，**不构成约束**（或仅有弱约束）。

**判定标准**：

| # | 判据 | 例子 |
|---|---|---|
| 1 | 以"**代码为准**"的镜像清单 | `API接口文档.md`：~374 端点登记 |
| 2 | 描述**已实现的机制** | `数据同步与加工说明.md`：采集链路现状 |
| 3 | **台账/登记**性质 | `审查行动项登记.md` |
| 4 | 明确的**跨项目方法论**（自述"非本项目强制"） | `跨项目经验迁移指南.md` |

**维护特征**：**随实现同步更新**；过期即失效（不"违反"，只是"不准"）。

## 三、标记方式（三层落地）

### 3.1 ① 文档头部 —— 性质字段

每份约束性文档的头部**必须**含性质标记，紧随标题：

```markdown
# <文档标题>

**性质**：元需求（META）        <!-- 或 需求（REQ） / 参考（REF） -->
**生效日期**：YYYY-MM-DD
**适用范围**：<约束谁>
...
```

> 存量文档**不强制追溯**（避免大批量改动引入风险）；
> **但谁改动、谁补齐**（同 `界面设计说明规范` 的存量策略）。

### 3.2 ② 索引登记 —— `docs/README.md`

全部约束性文档**必须在 `docs/README.md` 的「文档性质索引」表中登记**，
按性质分组，标注：性质 / 强制力 / 是否被 AGENTS 引用 / 一句话职责。

**索引是单一事实来源** —— 新增文档必须同步登记，否则 `review-checklist` 判 WARNING。

### 3.3 ③ 强制链 —— AGENTS.md 引用

**元需求（META）中的"强制类"必须挂进 `AGENTS.md` 的引用链**，
否则标记只是标签、不构成约束（见 §1.2 实测问题）。

判定"强制类 META"：文中含明确禁止/必须条款 **且** 有具体适用场景。

## 四、三类的规则差异（**这是分类的意义所在**）

| 维度 | 元需求 META | 需求 REQ | 参考 REF |
|---|---|---|---|
| **审查标准** | 能否**约束住别人**？有无明确判据？ | 验收标准是否达成？ | 是否与代码一致？ |
| **变更成本** | 高（全仓库影响） | 中（局部） | 低（同步即可） |
| **是否走架构锁定** | ❌ 不走（走规范评审） | ✅ `docs/arch/` 走锁定流程 | ❌ 不走 |
| **是否需关联工单** | 建议 | **必须** | 建议 |
| **是否进 AI 自动加载** | 强制类必须 | 否 | 否 |
| **过期处理** | 修订 | 归档 | 重写 |

## 五、存量问题与修复要求

基于 2026-09-11 盘点，以下 META **无强制入口**，需补进 `AGENTS.md`：

| 文档 | 为什么该挂 | 建议位置 |
|---|---|---|
| `error-code.md` | 所有后端接口的响应格式元规则 | 「绝对禁止」或「输出风格」 |
| `数据采集合并去重机制说明.md` | 约束**所有采集通道**的去重键 | 「绝对禁止」 |
| `投诉渠道口径与对账说明.md` | 投诉口径权威定义，改动影响所有投诉统计 | 「绝对禁止」 |
| `数据源接入与缓存加速规范.md` | 新增数据源/接口的缓存铁律 | 「工具使用」或「绝对禁止」 |

> 其余 META（`alembic-migration管理规范` / `task-work-order`）已由其它规范间接约束，
> 可暂不挂 AGENTS，但**必须进索引**。

## 六、自检（新增/改动文档前）

- [ ] 这份文档约束的是"**某个**功能"还是"**所有**功能"？
- [ ] 若答"所有" → META：是否已进 `docs/README.md` 索引 + `AGENTS.md` 强制链？
- [ ] 若是 META：文中每条要求是否都有**明确判据**（而非"建议"式表述）？
- [ ] 若是 REQ：是否有**验收标准** + **归属工单**？
- [ ] 若是 REF：是否声明了"**以代码为准**"？
- [ ] 头部是否已标 `**性质**`？

## 七、与既有规范的关系

| 规范 | 关系 |
|---|---|
| `docs/README.md` | 管"文档放哪、叫什么名"；**本规范管"文档是什么性质"** —— 正交 |
| `issue-workflow.md` | 管"任务怎么流转"；本规范管"文档怎么分类" |
| `review-checklist.md` | 已加「文档性质」检查项 |
| `AGENTS.md` | META 强制类的唯一挂载点 |
