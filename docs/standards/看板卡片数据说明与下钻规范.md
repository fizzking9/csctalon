# 看板卡片数据说明与下钻规范

**性质**：元需求（META）—— 约束**所有看板类页面**的卡片（强制）
**生效日期**：2026-09-13
**版本**：v1.0
**适用范围**：`web/src/views/dashboards/**` 下全部页面 + 后续新增的看板/图表页面
**关联文档**：[AGENTS.md](../../AGENTS.md)、[界面设计说明规范.md](界面设计说明规范.md)、[review-checklist.md](review-checklist.md)、[数据源接入与缓存加速规范.md](数据源接入与缓存加速规范.md)、[投诉渠道口径与对账说明.md](投诉渠道口径与对账说明.md)

---

## 〇、一句话铁律

> **任何一个卡片，都必须同时回答两个问题：**
> **①「这个数从哪来？」（可说明）**
> **②「觉得不对时怎么查下去？」（可下钻）**
> **答不出任一条的卡片，不许上线。**

---

## 一、为什么要有这条规范

### 1.1 背景（真实案例）

2026-09-13 排查「投诉分析 → 渠道明细 → (外)卡商」页（工单 **#75**）时发现：
「卡商投诉分类」图表 **永久显示「暂无数据」**，但该渠道总数有值、趋势图正常。

**根因不是数据缺失，而是三层断链**：

| 层 | 实际状态 | 后果 |
|---|---|---|
| 后端 | `card.by_category` **硬编码为 `[]`**，注释指向 `complaint_subs` 接口 | 该接口**从未存在**（死引用）|
| 前端 | 只读 `by_category` | 恒为空 → 恒显示「暂无数据」|
| 使用者 | 看到一个空图，**无从判断**是"真没数据"还是"功能坏了" | 只能截图来问 |

**核心教训**：

1. **没有数据说明的卡片 = 使用者无法自证真伪**。看到空图时，他分不清是业务为空还是代码有 bug。
2. **没有下钻的卡片 = 发现问题也追不下去**。看到数字异常，只能截图找人，而不是自己点进去看构成。
3. **注释里的死引用比没有注释更糟** —— 它把后人引向一个不存在的实现。

### 1.2 两个病灶

| 病灶 | 表现 | 后果 |
|---|---|---|
| **无说明** | 卡片只有标题和数字，不写数据来源/统计范围/更新时点 | 使用者无法判断数字口径，也无法识别「空」是故障还是真实 |
| **无下钻** | 数字是纯文本，点了没反应 | 发现异常无法自查，必须转人工；决策链断在最后一厘米 |

---

## 二、强制要求一：卡片必须有「数据说明」

### 2.1 必须写清的三件事

每个卡片（含 KPI 卡、图表卡、列表卡）必须能回答：

| 要素 | 说明 | 例 |
|---|---|---|
| **来源** | 数据取自哪个接口 / 哪张表 | `/complaints/summary` 的 `card` 分源对象 |
| **口径** | 统计范围与判据（含排除项） | 仅补充表侧分类；不含工单侧；NULL 归「未标注」 |
| **时点** | 数据窗口与更新时机 | 跟随顶部时间条；同步后 60s 内失效 |

### 2.2 落地方式

**最小实现**：卡片标题旁一个 ⓘ 图标（`el-tooltip` 或 `el-popover`），内容含上述三件事。

```vue
<!-- ✅ 合规示例 -->
<div class="chart-title">
  卡商投诉分类
  <el-tooltip effect="dark" placement="top" content="来源: card_complaints.problem_category｜口径: 仅补充表侧, NULL 归「未标注」｜窗口: 跟随顶部时间条">
    <el-icon style="color:#b0b4bb;cursor:help"><QuestionFilled /></el-icon>
  </el-tooltip>
</div>
```

**完整实现**：若卡片涉及复杂口径（如跨表去重、软纠正、口径差异），用 `el-popover` 写完整设计说明（**必须含「我们不做什么」段**，见 [界面设计说明规范.md](界面设计说明规范.md) §二）。

### 2.3 关键约束

1. **说明必须与代码同源**：口径若由后端常量决定（如 `_REPEAT_THRESHOLD`），说明文案不得写死数字，应从前端读取的字段渲染，避免两处漂移。
2. **「空」必须可解释**：若卡片可为空，说明中必须写明"什么情况下为空"，让使用者能区分**业务为空**与**功能故障**。
3. **禁止装饰性说明**：不得写「本图展示投诉分类分布」这类同义反复；要写**判据**，不写**形容词**。

## 三、强制要求二：卡片必须可下钻

### 3.1 原则

> **凡是显示了数字的地方，使用者都必须能问「这个数由哪些构成」，并当场得到答案。**

### 3.2 下钻的三种去向（按优先级）

| 优先级 | 去向 | 适用 | 例 |
|---|---|---|---|
| **① 跳到明细页 + 带筛选参数** | 数字 = 某集合的计数 | 投诉来源卡 → `/complaints/detail?source_type=内部投诉&start=…&end=…` |
| **② 弹出抽屉展示构成** | 构成较短、不值得跳页 | 值班人员 chip → 人员审计抽屉 |
| **③ 跳到同页对应区块** | 目标就在本页 | 影响事件横幅 → 本页事件区 |

### 3.3 ★ 下钻必须带上下文（最易被忽略）

**禁止**跳到"空白明细页让用户自己再筛一遍"。必须传递：

- **时间窗口**（`start` / `end`）—— 与当前卡片所见窗口**逐字一致**
- **筛选条件**（如 `source_type` / `status` / `handler`）
- 若是降级（无法透传某条件），必须在代码注释中写明**为什么不能**，而非默默丢掉

```js
// ✅ 合规: 窗口与筛选全带上
function drillToComplaint(sourceType) {
  router.push({
    path: '/dashboards/complaint-analysis',
    query: { tab: 'channel', source: sourceType, start: range.value.start, end: range.value.end },
  })
}

// ❌ 不合规: 只跳页不带上下文 → 用户落到默认近30天, 与刚才看的窗口不符, 数字对不上
function drillToComplaintBad() {
  router.push('/dashboards/complaint-analysis')
}
```

### 3.4 不可下钻的情形 —— 必须显式声明

若某卡片**确实不该下钻**（如"结论条"本身已是终态、或明细涉及敏感数据），
必须在**代码注释 + 页面 ⓘ**中写明理由，禁止沉默：

```vue
<!-- ❌ 不做下钻: 该指标为算法综合评分, 无可展示的单一构成明细;
     若强行下钻只能给出一堆分项权重, 对使用者无行动价值。见 #68 -->
```

### 3.5 交互一致性

| 元素 | 约定 |
|---|---|
| 可点击的数字 | `cursor: pointer` + hover 时轻微视觉反馈（下划线或色深） |
| 可点击的图表 | 支持点击数据点/柱条（ECharts `on('click')`） |
| 提示 | hover 显示 `title` 或 tooltip，说明"点击查看明细" |

```
③ 审查层：docs/standards/review-checklist.md 对应检查项通过
```

## 五、审查清单（并入 review-checklist.md）

新增/改造看板卡片时，逐条核验：

- [ ] 卡片有 ⓘ 说明，且含**来源 / 口径 / 时点**三要素
- [ ] 说明写的是**判据**而非形容词（不写"展示分布"，写"按 X 分类、排除 Y"）
- [ ] 若卡片可为空，说明中写明**什么情况下为空**
- [ ] 卡片**可下钻**，且下钻**带时间窗口 + 筛选条件**
- [ ] 无法带全上下文时，代码注释写明**为什么**
- [ ] 若**不可下钻**，代码注释 + 页面 ⓘ 均声明**理由**
- [ ] 可点击元素有 `cursor: pointer` 与 hover 反馈
- [ ] 说明文案中的动态值（阈值/窗口）**从数据读取**，不硬编码
- [ ] 卡片注释块写明「不做什么及原因」

---

## 六、存量处理

**存量不追溯，改动即补齐**（同 [AGENTS.md](../../AGENTS.md) 铁律）：

- 未改造的存量看板卡片**不强制**追溯补说明与下钻；
- 但**谁改动、谁补齐** —— 只要动到该卡片（改口径 / 改样式 / 挪位置），
  就必须按本规范补齐 ⓘ 说明与下钻，或显式声明不可下钻的理由。
