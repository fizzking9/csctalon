# 界面设计说明规范（Design Rationale）

**生效日期**：2026-09-11
**版本**：v1.0
**适用范围**：所有前端界面（页面 / 标签页 / 独立区块组件）的新增与改造
**性质**：**强制约束**（违反者审查不通过）
**关联文档**：[AGENTS.md](../../AGENTS.md)、[review-checklist.md](review-checklist.md)、[issue-workflow.md](issue-workflow.md)、[docs/README.md](../README.md)

---

## 〇、一句话铁律

> **任何界面，在写代码之前，必须先用一段话说清「这个界面替谁回答什么问题、为什么这样组织」，
> 并把它写进代码、显示给使用者、登记进审查清单。说不清的界面，不许开工。**

---

## 一、为什么要有这条规范

### 1.1 背景（真实案例）

2026-09-11 梳理「投诉分析」页（工单 **#67**）时发现：该页面历经 12 轮口径治理
（#47/#52/#53/#55/#57/#58/#60/#61/#62/#63/#64/#65），**每一轮都按"解决一个口径问题"
追加一个 tab 或一张图**，最终变成 2134 行 / 8 个 tab / 概览塞 12+ 图 的形态。

**口径是对的，界面是乱的** —— 因为从来没有人问过一句：

> 「这个页面到底是给谁看的？他要靠它做什么决定？」

### 1.2 三类典型病灶

| 病灶 | 表现 | 后果 |
|---|---|---|
| **堆图无结论** | 12 张图，没有一个字说明"所以呢" | 决策者看完仍不知该干什么 |
| **重复无边界** | 同指标在概览与子页各画一遍 | 维护者不知改哪处，改漏即数字打架 |
| **无主无人** | 数据治理工具混进决策页 | 目标用户被非目标内容污染 |

### 1.3 本规范要解决的问题

1. **约束作者**：开工前先想清楚，而不是顺手加个图。
2. **告知使用者**：页面上能直接看到"这页为什么这么设计"，而非猜。
3. **保护后续维护者**：哪块能动、哪块不能动、为什么，写在原地，不用考古 git log。

## 二、强制要求：三层落地

一个界面 === **三条记录必须同时存在**，缺一条视为未完成。

```mermaid
graph LR
    A["① 代码层<br/>设计说明注释块"] --> B["② 页面层<br/>使用者可见的 ⓘ 说明"]
    B --> C["③ 审查层<br/>review-checklist 检查项"]
    style A fill:#e0f2fe
    style B fill:#fef3c7
    style C fill:#dcfce7
```

### 2.1 ① 代码层 —— 界面文件头部的「设计说明」注释块

**位置**：`<template>` 之前的文件头部注释（`.vue`），或该区块组件的 props 上方。
**要求**：五要素齐全（见第三节），缺项写「无」并说明原因，**不得留空**。

```vue
<!--
  ┌─────────────────────────── 设计说明（Design Rationale） ───────────────────────────┐
  │ 目的：客服主管每周一晨会前 5 分钟内判断「外部投诉是否失控、该找谁」。               │
  │ 逻辑：外部投诉是「后果」指标，单看总量会骗人 → 故首屏给 ①升级率 ②主体集中度 ③涉诉金额│
  │       三张卡（可控指标）压住总量卡（不可控指标），先归因后看量。                    │
  │ 口径：工单侧 service_category 空白 ⇒ 投诉；外部桶 = 315 平台词 ∪ 监所软纠正(#58)。  │
  │       详见 docs/standards/投诉渠道口径与对账说明.md §1。                           │
  │ 取舍：不做日粒度报警（日波动噪声大，用户 2026-09-11 决策 → 按周/月对齐）。          │
  │       不做比率指标（数据完整度不足，#67 Out of Scope）。                            │
  │ 工单：#67 · 设计：docs/arch/_pending/A-20260911-001-投诉分析整体重构.md            │
  └──────────────────────────────────────────────────────────────────────────────────┘
-->
```

> **无需在代码里重复口径的完整定义** —— 写清"是什么口径 + 文档指针"即可，
> 避免同一口径在多处描述后互相漂移。

### 2.2 ② 页面层 —— 使用者可见的「ⓘ 设计说明」

**这是本规范与普通注释最大的区别**：设计意图必须**给使用者看到**，不能只躺在代码里。

**形态要求**（二选一，优先前者）：

| 方案 | 适用 | 实现 |
|---|---|---|
| **A. 标题旁 ⓘ 图标 + 气泡** | 单个区块/卡片 | `el-tooltip` 或 `el-popover`，内容为「目的 + 逻辑 + 取舍」三段 |
| **B. 页面标题旁「设计说明」按钮 + 抽屉** | 整页（多区块） | 打开 `el-drawer`，展示完整五要素 + 口径文档链接 |

**硬性要求**：

1. **必须包含「取舍」段** —— 明确写出「本页不做什么、为什么」。
   这是最容易被省略、但对使用者最有价值的一段（防止"为什么没有 XX 指标"的反复追问）。
2. **必须标注口径出处** —— 可点击跳转到 `docs/standards/` 对应文档（或复制路径）。
3. 文案用**业务语言**，不用技术语言（不写 `_complaint_source_type_case()`，写"外部投诉口径"）。

### 2.3 ③ 审查层 —— 清单检查项

`docs/standards/review-checklist.md` 已新增 **「界面设计说明」** 检查项，见该文档 §一。
未提供设计说明的界面改造，**审查直接判 CRITICAL**，阻塞合并。

## 三、设计说明必填五要素

| # | 要素 | 必须回答的问题 | ❌ 反例 | ✅ 正例 |
|---|---|---|---|---|
| 1 | **目的** | 替**谁**、回答**什么决策问题**、多久用一次 | "展示投诉数据" | "主管晨会前 5 分钟判断外部投诉是否失控" |
| 2 | **逻辑** | **为什么**这样组织？为什么是这几个指标/这个顺序？ | 无（直接堆图） | "总量是不可控后果指标，升级率才可控 → 可控指标前置" |
| 3 | **口径** | 数据来自哪张表/哪个判据？口径文档在哪？ | 无出处 | "315 平台词 ∪ 监所软纠正(#58)，见口径文档 §1" |
| 4 | **取舍** | **不做什么**？为什么不做？ | 无 | "不做日粒度报警（噪声大），不做比率（数据不全）" |
| 5 | **工单** | 关联 issue 号 + 设计文档路径 | 无 | "#67 · A-20260911-001" |

> **要素 4（取舍）是强制的**，且必须写"为什么不做"，不能只列不做的项。

## 四、判定标准：有用的界面 vs 秀好看的界面

开工前用这 6 条自检，**任一条答不上来就不许动手**：

| # | 自检问题 | 不过关的表现 |
|---|---|---|
| 1 | 这个界面**替谁**解决问题？（写出岗位） | "所有人" / "领导"（等于没说） |
| 2 | 看完它，使用者能做出**哪一个具体决定**？ | 只能"了解情况" |
| 3 | 每个图表都**指向一个动作**吗？（没有就删） | "这个图挺好看的，留着吧" |
| 4 | 哪个是**可控指标**、哪个是**后果指标**？可控的是否前置？ | 只堆后果指标（总量/金额） |
| 5 | 有没有**和别处重复**的展示？谁是真身、谁是投影？ | 同指标两处各画一遍 |
| 6 | 使用者**会不会问"为什么没有 XX"**？设计说明里是否已答？ | 取舍段缺失 |

**一句话判据**：

> **如果一个界面被删掉后，没有任何人的任何决定会改变，那它就是秀好看的。**

## 五、模板（可直接复制）

### 5.1 代码层模板（区块级）

```vue
<!--
  设计说明（Design Rationale）
  目的：<谁> 在 <何时/多久一次> 判断 <什么决定>。
  逻辑：<为什么这样组织；可控指标 vs 后果指标；排序依据>
  口径：<数据来源与判据>，详见 <docs/standards/xxx.md §N>
  取舍：不做 <X>，因为 <理由>；不做 <Y>，因为 <理由>。
  工单：#<N> · 设计：<文档路径>
-->
```

### 5.2 代码层模板（整页级，多区块）

```vue
<!--
  ┌──────────────────────── 设计说明（Design Rationale） ────────────────────────┐
  │ 目的：…
  │ 逻辑：…
  │ 口径：…
  │ 取舍：…
  │ 工单：#N · 设计：<路径>
  │
  │ 区块清单（每块的职责与真身/投影关系）：
  │   ① 结论条    —— 唯一"自动归因"出口，其它区块不得重复做结论
  │   ② KPI 5 卡  —— 总量/登记/处理/积压/涉诉金额，均为"窗口内"值
  │   ③ 趋势区    —— 4 块，粒度由顶部时间条统一控制（禁止各自加粒度开关）
  │   ④ 积压明细  —— 真身；渠道页的积压列表是投影
  └─────────────────────────────────────────────────────────────────────────────┘
-->
```

### 5.3 页面层模板（ⓘ 抽屉文案）

```markdown
## 这个页面为什么这样设计

**给谁用**：<岗位>，<使用频率>
**回答什么**：<具体的决策问题>

**为什么这样组织**
- <可控指标前置的理由>
- <图表顺序的理由>

**数据口径**
- <口径 1> → 详见 <文档链接>
- <口径 2> → 详见 <文档链接>

**我们不做什么（及原因）**
- ❌ <X>：<理由>
- ❌ <Y>：<理由>

**关联**：工单 #N · 设计文档 <路径>
```

## 六、存量界面处理

| 情形 | 处理 |
|---|---|
| **本次要改造的界面** | **必须**补齐三层设计说明（为验收前置条件） |
| 存量未改造界面 | **不追溯**（避免一次性大改）；**下次任何人改动它时必须补齐** |
| 被本次改造"淘汰/搬迁"的界面 | 在搬迁提交中注明「原设计意图 + 新落点」，防止意图丢失 |
| 已锁定架构文档中的界面约定 | 若本规范要求与之冲突，**走人工审核修订**，不得静默绕过 |

> 原则同 `AGENTS.md` 的凭证纪律：**历史不追溯、改动即补齐**。
