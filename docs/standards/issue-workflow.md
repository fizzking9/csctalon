# 工单驱动工作流规范（Issue Workflow）

**生效日期**：2026-09-03
**适用范围**：所有任务（含需求、事故、治理、缺陷、运维动作），不论由人还是 AI 执行
**关联文档**：[AGENTS.md](../../AGENTS.md)（全局约束）、[task-work-order.md](task-work-order.md)（AI 派工单模板）、[arch/README.md](../arch/README.md)（架构锁定流程）、[review-checklist.md](review-checklist.md)（审查清单）

> 目的：把「任务」统一收敛到 Gitea issue 工单，作为唯一入口与闭环凭证，杜绝口头驱动、散文档驱动、无痕开发。
> 背景：2026-09-02 `cs_records` 接待数据缺口事件暴露「有审计、有文档、但无工单跟踪」的断层——审计结论与设计建议没有进入可跟踪的工单，导致治理无法闭环。

---

## 一、铁律

1. **所有任务必须先建工单，再动手**。禁止无工单开发、无工单运维、无工单改数据。
2. **工单是唯一入口与唯一闭环凭证**。口头/聊天/文档只能作为补充说明，不能替代工单。
3. **一单一目标**。事故类必须拆成「止损工单」与「治理工单」两条，禁止混单。
4. **工单必须写「关闭条件」**。没有关闭条件的工单视为无效工单。
5. **代码变更必须关联工单**。提交信息、PR 描述须携带 `#issue号`，否则审查不通过。

---

## 二、工单分类（Label）

| 分类 | Label | 语义 | 责任人 | 示例 |
|---|---|---|---|---|
| 事故处理 | `incident` | 已发生的线上故障，止损/补救/闭环 | 运维 / 业务 / 数据负责人 | 09-02 数据缺口补跑 |
| 治理改进 | `governance` | 系统性缺陷的长效修复，防复发 | 后端 / 采集 / 监控 | 重试、熔断、告警 |
| 功能需求 | `feature` | 新功能或增强 | 架构师 → 开发者 | 新增导出能力 |
| 缺陷修复 | `bug` | 明确代码缺陷 | 开发者 | LIMIT 排序方向错误 |
| 技术债 | `tech-debt` | 重构、清理、基建 | 开发者 | 依赖锁定 |
| 运维动作 | `ops` | 备份、迁移、凭证轮换等人工操作 | 运维 | JWT 密钥轮换 |

> 标签在 Gitea 中按 Label 名称创建；`incident` 与 `governance` 为强约束分类（见第三节）。

---

## 三、事故类工单的强制拆分

当一个事件既造成线上影响、又暴露系统设计缺陷时，**必须拆成两条工单**，禁止合并：

| 维度 | 事故工单（incident） | 治理工单（governance） |
|---|---|---|
| 关注点 | 已经发生了什么、怎么止损 | 为什么会发生、怎么修复系统 |
| 责任人 | 运维 / 业务 / 数据负责人 | 后端 / 采集 / 监控 |
| 产出 | 补跑/回填结果、事件闭环说明 | 设计评审、代码实现、告警上线 |
| 关闭条件 | 数据已补齐或确认不可补、业务确认 | 验收标准全部满足、灰度验证通过 |

> 反例（禁止）：`09-02 缺口处理 + 重试熔断改造` 合成一单——会导致事故无法快速闭环、治理无法独立验收、责任人互相消耗。

---

## 四、工单必填字段

每条工单正文至少包含：

```markdown
## 背景
<发生了什么 / 为什么需要做>

## 影响范围
<涉及对象 / 时间窗口 / 影响程度>

## 根因判断（incident/bug 必填，feature 可略）
<事实与证据，区分「上游故障」vs「本地代码」>

## 处理动作 / 设计要求
- [ ] <可勾选的执行项>

## 验收标准 / 关闭条件
<明确、可验证的完成判据>

## 关联
- 审计/设计文档路径
- 关联工单号
```

## 五、状态流转

```
Open（新建）
  → 认领（指派责任人 + 设 Label）
  → In Progress（执行中，附执行证据）
  → 待验收（提交可验证产出：测试结果/补跑对比/灰度数据）
  → Closed（满足关闭条件，记录关闭日期与结论）
  （任意阶段可回退：验收不通过 → In Progress）
```

| 状态 | 进入条件 | 离开条件 |
|---|---|---|
| Open | 创建 | 指派责任人 |
| In Progress | 认领 | 产出可验证证据 |
| 待验收 | 证据齐全 | 人工/机器验收通过或驳回 |
| Closed | 满足关闭条件 | ——（归档，禁止无痕重开） |

## 六、工单 × 四阶段协同机制（需求 → 架构 → 编码 → 测试）

> 工单是四阶段的「载体」，四阶段是工单的「流转节奏」。每一阶段都有明确的工单状态、通过凭证（Gate）与门禁，缺一不可。缺少钩子 = 工单只是挂个号，不驱动流转。

### 6.1 阶段状态机

| 阶段 | 工单状态 | 通过凭证（Gate） | 产出 |
|---|---|---|---|
| ① 需求分析 | Open → 需求确认 | 需求派工单/用户确认；「关闭条件」已定义 | 工单正文完整（背景/影响范围/验收标准） |
| ② 架构设计 | 设计中 | 架构文档 LOCKED + git tag + 人工审核通过 | `docs/arch/` 锁定文档；工单引用其路径 |
| ③ 编码实现 | In Progress → 待验收 | 提交/PR 关联 `#issue号`；CI 通过（ruff + pytest） | 代码 + 测试，符合派工单约束 |
| ④ 测试验证 | 待验收 → Closed | 审查报告无 CRITICAL + 人工终审通过；满足关闭条件 | 审查报告回写工单；工单关闭并记录日期与结论 |

### 6.2 阶段门禁规则

1. **不可跳阶段**：未完成需求确认不得进入架构设计；未锁定架构不得编码实现。
2. **凭证可追溯**：每个 Gate 的凭证（派工单、架构文档、PR/提交、测试输出、审查报告）都回写到工单，作为流转依据。
3. **回退规则**：任一门禁不通过，工单回退到上一阶段（如审查有 CRITICAL → 回 In Progress 修复）。

### 6.3 双向引用（工单 ↔ 其他资产）

| 资产 | 工单侧 | 资产侧 |
|---|---|---|
| 架构文档 | 工单正文标「架构文档路径」 | 架构文档头标「关联工单 `#号`」 |
| 提交/PR | 工单评论记录 PR 链接 | 提交信息与 PR 描述带 `#issue号` |
| 审查报告 | 工单评论贴审查结论 | 报告注明对应工单号 |
| 审计/台账 | 工单正文引用审计报告 | 审计报告与行动项台账标注工单号 |

### 6.4 自动化钩子（待建设）

- 当前「CI 通过（ruff + pytest）」与「工单状态」之间靠**人工回写**；设计草案已入 `docs/arch/_pending/A-20260903-001-issue-automation-gates.md`（PENDING 待审核），落地后由 CI 自动执行。
- 在自动化钩子落地前，**编码完成者必须手工把 CI 结果与测试结果贴到工单**，否则视为未通过「③ 编码实现」门禁。

## 七、工单粒度治理（防碎片化 / 防巨石单）

> 两个极端都要避免：① 工单碎片化（大量空壳或几行改动就单独开单，无法管理）；② 巨石单（一个工单塞进一堆需求，无法逐步实现、验证、测试）。粒度以「**可独立验收**」为唯一标尺。

### 7.1 合并判定（应合并，不单独开单）

满足**全部**条件时，应并入关联工单或批量工单，禁止单独开单：

- 工作量极小（< 半天），无独立上线/验收价值；
- 与已有工单同模块、同责任人、同时间窗；
- 纯机械性改动（改一个变量名、一行注释、加一个日志等）。

> 例：顺手修一处拼写 → 并入正在做的工单；一批同类小清理 → 合并成一个 `tech-debt` 批量工单。

### 7.2 拆分判定（应拆分，禁止巨石单）

满足**任一**条件时，必须拆成多个工单：

- 无法在一次上线中独立验收；
- 涉及不同模块 / 不同风险面 / 不同责任人；
- 总工作量 > 1 天，或需要分阶段灰度；
- 需求本身「逐步实现、逐步验证、逐步测试」的（先地基后上层）。

> 拆分产物要么是「父工单 + 子工单」，要么是多个并列工单，但**每个叶子工单都必须能独立关闭**。

### 7.3 拆分与验证节奏

1. 先拆出**最小可交付切片**（先跑通主链路 / 先止血），后续工单逐步增强；
2. 每个工单 = 一段可独立测试、可独立上线的增量；
3. 上一个工单关闭（含测试通过）后，再启动下一个；
4. 拆分顺序在父工单里列出，标注依赖关系（A → B → C）。

### 7.4 想法 / 待办池（先不建工单）

未到执行时机的想法、低优先级建议，**不进 issue，先进 backlog 清单**（如 `docs/审查行动项登记.md` 台账），避免工单碎片化；排期确认后再转正式工单。

---

## 八、禁止事项

1. 禁止无工单直接改生产代码 / 数据 / 表结构。
2. 禁止把事故与治理混在同一工单。
3. 禁止创建无「关闭条件」的工单。
4. 禁止工单长期停留在 Open 且无责任人。
5. 禁止用聊天记录替代工单作为变更依据。
6. 禁止为「< 半天、无独立验收价值」的琐碎改动单独开单（应合并）。
7. 禁止创建无法独立验收的巨石单（应拆分）。
