# 数据源接入与缓存加速规范

> 版本：v1.0 · 日期：2026-08-25
> 状态：架构约束文档（开发者必读）
> 关联：[数据同步与加工说明.md](数据同步与加工说明.md) · [workbuddy数据同步接入规范.md](workbuddy数据同步接入规范.md) · [workbuddy手动退款数据同步接入规范.md](workbuddy手动退款数据同步接入规范.md)
> 范围：本文件规定「数据写入 → 缓存失效 → 缓存预热 → 路由缓存 → 前端」全链路的接入约定，重点是**新增数据源 / 新增看板接口时必须完成的缓存接入清单**，避免出现「新数据已入库但看板仍显示旧数据 / 首次访问冷加载」的问题。

---

## 一、为什么需要这份文档

系统已建立「**缓存预热 + 路由层缓存 + 写入后失效**」三级加速机制（2026-08-25 落地）。但该机制是**显式编排**的——缓存 key、失效 pattern、预热函数三者必须**逐字符对齐**，任何一环遗漏都会导致：

| 遗漏点 | 现象 | 用户感知 |
|--------|------|----------|
| 数据写入后未失效对应 pattern | 看板显示旧数据，直到 60s 缓存自然过期 | 「我同步了数据，看板怎么没变」 |
| 新接口加了 `cached_call` 但未纳入预热 | 首次访问冷加载，跑重聚合 SQL | 「今天看板很慢」 |
| 改了路由 key 没同步改 cache_warmer | 预热写到旧 key，路由命中新 key → 永不命中预热 | 「缓存管理显示预热 N 条但访问仍慢」 |
| 新接口 key 前缀不在失效 pattern 内 | 同步后该接口缓存不失效 | 「专项分析数据滞后」 |

**本文档的核心价值**：把上述对齐关系固化为可勾选的接入清单（§七、§八），新增数据源/接口时逐条核对即可，不依赖记忆。

## 二、数据全链路总览

```
┌─────────────┐   ┌──────────────┐   ┌─────────────────┐   ┌──────────────┐   ┌────────┐
│ 1. 数据采集  │ → │ 2. 解析入库   │ → │ 3. 缓存失效      │ → │ 4. 缓存预热   │ → │ 5. 访问 │
│  (3种入口)  │   │ (upsert/去重) │   │ (失效旧 pattern) │   │ (重算写热缓存) │   │ (命中)  │
└─────────────┘   └──────────────┘   └─────────────────┘   └──────────────┘   └────────┘
                                                                     ↑
                                                          6. 管理员强制重建(兜底)
```

| 阶段 | 实现 | 关键约束 |
|------|------|----------|
| 1. 采集 | 3 种入口（见 §三） | 互斥锁 / 冷却 / 增量 |
| 2. 入库 | `upsert.py` 统一解析+去重+时区加工 | naive 北京时间 → UTC |
| 3. 失效 | `cache_invalidate_pattern(pattern)` | **必须在每个写入入口调用** |
| 4. 预热 | `cache_warmer.warm_after_sync()` 等 | key 与路由层逐字符对齐 |
| 5. 访问 | 路由层 `cached_call(key, ttl, fn, ...)` | TTL 60/90/120s |
| 6. 重建 | `cache_warmer.rebuild_cache(scope)` | 管理员手动 / `AdminUser` |

> **铁律**：任何一个数据写入入口（采集→入库）都必须在入库成功后失效对应缓存 pattern，否则看板数据会滞后到缓存自然过期（最长 60s/写入高峰期可达 300s）。当前已有入口的失效情况见 §六。

## 三、采集方式与同步机制

### 3.1 三种数据写入入口

| 入口 | 触发 | 实现入口 | 失效缓存责任点 |
|------|------|----------|----------------|
| **A. BMS/SCRM 主动同步** | 定时(00/08/12/16/20点) / 手动一键同步 | `sync_task_manager.submit_multi` → `bms_sync.sync_all` | `sync_task_manager` finally 块（§6.1） |
| **B. workbuddy 推送** | workbuddy 每 20 分钟检测文件变化推送 | `sync_complaints.push_complaints` → `complaint_sync.sync_complaints_from_payload` | ⚠️ **当前缺失（见 §九缺口 G1）** |
| **C. 手动文件上传** | 用户在「文件上传」Tab 上传 xlsx/csv | `uploads.py` | ⚠️ **当前缺失（见 §九缺口 G2）** |

### 3.2 同步调度（入口 A 细节）

- **定时时刻**（东八区）：`00:00, 08:00, 12:00, 16:00, 20:00` 每天 5 次
- **互斥**：`SyncTaskManager._lock` 全局 asyncio 锁，手动/定时任一在跑则另一路抛错跳过
- **冷却**：上次成功后 5 分钟内非 `force=true` 拒绝（`scheduled` 触发免冷却）
- **增量**：`compute_incremental_ranges` 查 `bms_sync_logs` 最近 SUCCESS 的 `time_end`，从该时刻起算；首次/早于今日 0 点则从今日 0 点起
- **时间范围硬约束**：定时同步强制 `today_start ~ now_cn`，**不同步历史数据**
- **采集并发**：BMS + SCRM 经 `submit_multi` + `asyncio.gather` 并发，BMS 下载冷却期穿插 SCRM

### 3.3 数据源归组（source_groups）

新增数据源时需配置 `group_key`，同域名共享登录态归同组（凭证组级配置，免重复填）：

| 域名特征 | group_key | 组名 |
|----------|-----------|------|
| `wifi.cloud-cat.cn` / `support.cloud-cat.cn` | `bms-wifi` | BMS 主平台 |
| `fast.cloud-cat.cn` | `shanmao` | 闪猫平台 |
| `ai-acc` | `aiacc` | ai-acc 平台 |
| `bilinl` / `baiyinqifu` | `scrm` | SCRM 平台 |
| 其他 | 按域名 | 逐源配置 |

归组规则实现于 [source_group_service.py](file:///Users/tanzk/dev/csctalon/backend/app/services/source_group_service.py) `_group_key_for_base_url`，凭证解析优先级：单源 > 组 > seed/.env。

## 四、缓存机制

### 4.1 路由层缓存（`cached_call` / `cached_json`）

实现于 [redis_client.py](file:///Users/tanzk/dev/csctalon/backend/app/core/redis_client.py)：

```python
# 简单接口缓存（analytics.py 大量使用）
cached_call(key: str, ttl: int, fn: Callable, *args, **kwargs) -> Any
#   - 命中缓存: 直接返回, 跳过 fn（写入高峰期顺带续期短 TTL）
#   - 未命中: 调 fn, 结果非 None 则写缓存, 返回结果

# 装饰器形式（complaints.py 使用）
cached_json(key_fn: Callable[..., str], ttl: int = 60) -> Callable
#   - key_fn(params...) → key 字符串
#   - 可通过 fn.__wrapped__ 取原函数（cache_warmer 预热时绕开装饰器内置 TTL）
```

**TTL 约定**：

| TTL | 适用 | 位置 |
|-----|------|------|
| 60s | 默认（多数看板接口） | analytics.py / complaints.py |
| 90s | `today:staff`（人员效率，重 CTE） | analytics.py:254 |
| 120s | `refund:*` 趋势类（变动较慢） | analytics.py:312/322/334/357/367/376 |
| 180s | **预热写入专用**（`WARM_TTL`，覆盖更长热窗口） | cache_warmer.py |

### 4.2 写入高峰期 TTL 放大（防雪崩）

同步进行时 `mark_sync_writing(True)` 标记写入高峰期，期间缓存 TTL 自动 `×5`（clamp 300~3600s），命中后顺带续期短 TTL 条目，防止同步期间缓存击穿打爆 DB。同步结束 `mark_sync_writing(False)` 恢复。实现于 redis_client.py `_effective_ttl` / `_maybe_extend_hit_ttl`。

### 4.3 缓存预热（cache_warmer）

三时机，全部实现于 [cache_warmer.py](file:///Users/tanzk/dev/csctalon/backend/app/services/cache_warmer.py)：

| 时机 | 函数 | 触发点 | 覆盖范围 | force |
|------|------|--------|----------|-------|
| 同步完成后 | `warm_after_sync` | `sync_task_manager._run_background` finally（失效缓存后） | 今日视图 + 月报看板 | ✅ 强制刷新 |
| 服务启动后 | `warm_on_startup` | `bms_scheduler.start` 延迟 8s | 今日视图 | ✅ 强制刷新 |
| 空闲期 | `warm_idle` | `bms_scheduler._run_loop` 白天每分钟 | 今日 + 本周视图 | ⚪ 节流（TTL≤60 才重算） |

**设计要点**：
- `WARM_TTL=180s` > 路由层 60/90/120s，单次预热覆盖 3 分钟热窗口
- 节流：`force=False` 时仅当 key 剩余 TTL ≤ 60s（或不存在）才重算，白天约每 2 分钟自检一次 → 数据始终 ≤2 分钟新鲜且永不冷加载
- 白天 8~23 点才预热，夜间无人省计算
- 进程级单飞锁 `_warm_lock`（非阻塞）防并发重复计算
- `_can_warm()` 始终检查：Redis 可用 + 非同步中（force 不能绕过，防同步进行中抢 DB）
- **key 与路由层逐字符对齐**：预热直接调 service 函数（`analytics A.*`）与 complaint 路由 `__wrapped__` 原函数，用 `cache_set_json` 写 `WARM_TTL` 缓存

### 4.4 管理员强制重建（兜底）

实现于 [cache_admin.py](file:///Users/tanzk/dev/csctalon/backend/app/api/v1/cache_admin.py)，仅 `AdminUser`：

- `GET /system/cache/info` → 可用范围 + Redis/预热/同步状态
- `POST /system/cache/rebuild` → 按 scope 失效 + 强制重算预热（或仅失效）

| scope | 失效 pattern | 预热函数 |
|-------|--------------|----------|
| `today` | `today:*`, `complaint:*` | `_warm_today_view` |
| `week` | `today:*`, `complaint:*` | `_warm_week_view` |
| `reports` | `op:*`, `cash:*`, `cat:*`, `operator:*`, `summary` | `_warm_reports` |
| `all` | 全部 pattern | today + week + reports |

操作记事务通知（`category=alert, action=cache_rebuild`），含失效/预热条数、耗时、操作人，可追溯。

## 五、缓存 key 命名规范

**新增看板接口必须遵循此命名规范**，否则无法纳入失效/预热体系。

### 5.1 前缀分类（前缀 = 失效/预热的 pattern 单元）

| 前缀 | 业务域 | 失效 pattern | 是否预热 |
|------|--------|--------------|----------|
| `today:` | 今日看板（今日/本周视图共用） | `today:*` | ✅ today/week |
| `complaint:` | 投诉分析（summary/detail/backlog） | `complaint:*` | ✅ |
| `op:` | 运营看板 | `op:*` | ✅ reports |
| `cash:` | 现金流看板 | `cash:*` | ✅ reports |
| `cat:` | 退款分类看板 | `cat:*` | ✅ reports |
| `operator:` | 人员操作看板 | `operator:*` | ✅ reports |
| `summary` | 看板总览（无前缀冒号） | `summary` | ✅ reports |
| `reception:` | 接待分析专项 | ❌ 未在失效 pattern | ❌ 未预热（缺口 G3） |
| `refund:` | 退款分析专项 | `refund:*`（仅同步后失效） | ❌ 未预热（缺口 G4） |

### 5.2 key 拼接规则

```
{前缀}:{子项}:{参数1}:{参数2}:...
```

- 参数用 `:` 分隔，**None 用字符串 `None` 占位**（与路由层 `cached_call` 的 f-string 一致）
- 日期参数用 `YYYY-MM-DD`（analytics 用 naive datetime 内部转换，key 用字符串）
- 示例：`today:staff:None:2026-08-25:2026-08-25:200:0:person:None:None:None`

> **关键**：路由层 key（analytics.py/complaints.py 的 f-string）与预热 key（cache_warmer.py 的 f-string）必须**逐字符相同**。改路由 key 时务必同步改 cache_warmer 的 `_warm_analytics` / `_warm_complaints` / `_warm_reports`。

## 七、✅ 新增数据源接入清单（CHECKLIST）

新增一个数据源（如新增一个 BMS 表 / 一个外部推送源 / 一个新平台 REST API）时，按顺序完成：

### 7.1 采集与入库

- [ ] **1. 确定采集方式**：主动同步（Playwright/HTTP）/ 被动推送（workbuddy）/ 文件上传
- [ ] **2. 注册数据源配置**：`sync_source_configs` 表（data_type / base_url / fetch_mode / default_sync / requires_captcha）；如属新域名，配置 `source_groups.group_key`（见 §3.3）
- [ ] **3. 实现抓取器**：Playwright（`BmsFetcher` 同 base_url 复用 Context）/ HTTP（`ai_acc_fetcher` + 7天分片）/ 推送接收
- [ ] **4. 实现 upsert**：`upsert_*.py`，明确去重策略（upsert 主键 / none 不去重 / fallback 合成键），时区加工走 `_to_datetime`（naive=北京时间→UTC）
- [ ] **5. 接入 SyncTaskManager**（仅主动同步）：在 `bms_sync.sync_all` / `scrm_sync` runner 中加入新 data_type；`DEFAULT_SYNC_TYPES` 是否纳入定时

### 7.2 缓存接入（核心，勿漏）

- [ ] **6. 识别该数据源影响哪些看板接口**（列出受影响的 key 前缀，如新增退款类数据 → 影响 `today:refund`/`today:rr`/`refund:*`）
- [ ] **7. 在该数据源的写入入口添加缓存失效**：
  - 主动同步 → 已由 `sync_task_manager` finally 统一失效 `today:*`/`refund:*`/`complaint:*`，**仅当新数据影响其他前缀（如 `reception:`/`op:`/`cash:`）时**，需在 finally 块补充 pattern
  - **被动推送 → 必须在推送入库后失效对应 pattern**（见 §九 G1，当前投诉推送缺失）
  - **文件上传 → 必须在上传入库后失效对应 pattern**（见 §九 G2，当前缺失）
- [ ] **8. 如新数据源影响看板预热范围**，更新 `cache_warmer` 的预热函数（§八）
- [ ] **9. 记事务通知**：写入入口调用 `record_system_event`，让管理员感知同步结果

### 7.3 文档与验证

- [ ] **10. 更新本文档 §六 覆盖矩阵 + §3.1 入口表**（写明该数据源的失效责任点）
- [ ] **11. 编写数据源接入规范**（参照 `workbuddy数据同步接入规范.md` 格式）
- [ ] **12. 验证**：入库后立即查 Redis（`redis-cli keys "today:*"` 看 TTL 是否刷新）+ 前端看板数据是否及时刷新

## 八、✅ 新增看板接口接入清单（CHECKLIST）

新增一个看板接口（如新增一个分析维度接口）时，按顺序完成：

- [ ] **1. 路由层加缓存**：在 [analytics.py](file:///Users/tanzk/dev/csctalon/backend/app/api/v1/analytics.py) / [complaints.py](file:///Users/tanzk/dev/csctalon/backend/app/api/v1/complaints.py) 用 `cached_call(key, ttl, fn, ...)` 或 `@cached_json(key_fn, ttl)` 包裹
- [ ] **2. key 遵循命名规范**（§5）：`{前缀}:{子项}:{参数}`，None 用 `"None"` 占位；**优先复用现有前缀**（today/op/cash/cat/operator/complaint/refund/reception），便于纳入现有失效/预热 pattern
- [ ] **3. 选择 TTL**：默认 60s，重聚合 CTE 用 90~120s（§4.1）
- [ ] **4. 判断是否需预热**（高热度接口才预热）：
  - 是 → 在 `cache_warmer._warm_analytics` / `_warm_complaints` / `_warm_reports` 的 specs 列表追加 `(name, key, fn, args, kwargs)`，**key 必须与路由层逐字符对齐**
  - 否 → 仅靠路由层 60s 缓存 + 写入后失效（如该接口属新前缀，需在 sync_task_manager finally 补失效 pattern）
- [ ] **5. 若新增了前缀**（如全新业务域 `xxx:`）：
  - [ ] 5a. 在 `sync_task_manager` finally 失效 pattern 列表追加 `"xxx:*"`
  - [ ] 5b. 在 `cache_warmer.SCOPE_PATTERNS` 的 `all` scope 追加 `"xxx:*"`
  - [ ] 5c. 若需管理员可重建，新增 scope 或并入现有 scope
- [ ] **6. 验证 key 对齐**：改路由 key 后，grep 确认 cache_warmer 中同名 key 同步修改（否则预热写旧 key、路由命中新 key → 预热失效）
- [ ] **7. 更新本文档 §六 覆盖矩阵**

## 九、已知缺口与待优化项

> 以下为 v1.0 编写时审计发现的缓存接入缺口，需后续修复。**新增数据源时勿再重复这些遗漏。**

### G1. workbuddy 投诉推送未失效缓存（✅ 2026-08-25 已修复）

- **现象**：workbuddy 推送投诉数据入库后，投诉看板（`complaint:summary/detail/backlog`）与今日看板投诉区块（`today:*`）仍显示旧数据，直到 60s 缓存自然过期
- **根因**：[sync_complaints.py](file:///Users/tanzk/dev/csctalon/backend/app/api/v1/sync_complaints.py) `push_complaints` → [complaint_sync.py](file:///Users/tanzk/dev/csctalon/backend/app/services/complaint_sync.py) `sync_complaints_from_payload` 入库后**仅记事务通知，未调 `cache_invalidate_pattern`**
- **修复**：在 `sync_complaints_from_payload` `db.commit()` 成功后，当 `inserted+updated>0` 时失效 `complaint:*` + `today:*`，并触发 `warm_after_sync`（预热今日视图含投诉区块）；失败静默不影响主流程
- **影响面**：投诉看板、今日看板投诉相关区块

### G2. 手动文件上传未失效缓存（中优先）

- **现象**：用户在「文件上传」Tab 上传 xlsx/csv 入库后，相关看板显示旧数据
- **根因**：[uploads.py](file:///Users/tanzk/dev/csctalon/backend/app/api/v1/uploads.py) 入库后**未调 `cache_invalidate_pattern`**
- **修复方向**：按上传文件类型推断受影响前缀（退款→`refund:*`/`today:*`，投诉→`complaint:*`，etc.），入库后失效
- **影响面**：所有受上传数据影响的看板

### G3. 接待分析专项未预热也未失效（低优先）

- **现象**：`reception:*` 接口有路由缓存但未预热（首次访问冷加载），且同步后未失效（数据滞后到 60s 过期）
- **根因**：`reception:` 前缀不在 `sync_task_manager` finally 失效列表，也不在 `cache_warmer` 预热范围
- **修复方向**：若接待分析访问热度高 → 纳入 `warm_idle`/`warm_after_sync` + finally 补 `reception:*`；否则保持现状（靠 60s 自然过期）
- **备注**：接待数据源 SCRM 若 naive 当 UTC 解析仍有 8h 偏移待验证（见 [数据时间字段使用规范.md](数据时间字段使用规范.md)），预热前应先确认时间语义正确

### G4. 退款分析专项未预热（低优先）

- **现象**：`refund:*` 退款分析专项接口有路由缓存、同步后被失效，但**未预热**，首次访问冷加载
- **根因**：`cache_warmer` v1 未预热 `refund:*`（窗口/格式不统一，曾试 weekly 合并查询因 ISO 周与滚动窗口不对齐回退）
- **修复方向**：统一窗口格式后纳入预热；当前靠同步后失效 + 60s 自然回填兜底，优先级低
