## 二、问题清单（按证据归档）

### 1）上游瞬时 500 被当“确定失败”

- 现象：导出返回 `{"code": 500, ...}` 时，仅执行一轮单次重试。
- 问题：此类 5xx 或 JSON 500 属于“可重试瞬时错误”，却在第一次失败后直接熔断该专项。
- 风险：当天后续全部采集被截断，导致后续窗口无机会补偿。

### 2）熔断后当天不再探活

- 现象：09-03 09:00 上游恢复，但 09-02 午后熔断后不再探测上游状态。
- 问题：即使上游中途恢复，也不会恢复采集，导致“断层持续”。

### 3）缺口无自愈

- 现象：补跑机制只针对“前一天”，并要求当天补跑成功才会回补。
- 问题：一旦前一天补跑失败，后续没有强制回补路径，数据缺口可能永久留存。

### 4）大范围导出一次性失败

- 现象：7 天兜底整窗一次性失败后，整批被直接丢弃。
- 问题：没有按日/按片降级重试，导致“整窗失败”造成“整天数据丢失”。

### 5）缺失数据量骤降监控

- 现象：断层持续到运维人工比对才发现。
- 问题：没有在第一时间触发告警，业务侧无法及时觉察异常。

## 四、设计/代码层改进建议（仅建议，待评审后排期）

### 1. 错误分级 + 重试退避

- 将 `5xx` / JSON 500 归类为“可重试瞬时错误”。
- 大范围导出失败时，应优先按日切片降级重试，再尝试整窗重试。
- 不要因整窗一次性失败而直接放弃单日数据。

### 2. 熔断优化

- 改为“滑动窗口连续失败 ≥ N 次”才熔断，而非“一次失败即熔断”。
- 熔断后增加“半开探测”机制：上游恢复后，自动恢复采集。

### 3. 缺口待补队列

- 记录“业务日期 + 专项”未补齐清单。
- 次日补跑前先清点缺口，再多次重试，避免只判定前一天窗口导致永久丢失。

### 4. 数据量骤降监控

- 对各专项入表量做日统计；若相较近 7 日均值骤降超阈值，触发告警。
- 熔断发生时，直接推送告警，而非依赖人工对比发现。
