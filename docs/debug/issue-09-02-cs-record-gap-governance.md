# [ISSUE] ai-acc 大范围导出失败的重试、熔断与缺口补全机制治理

> 类型：工程治理 / 长期修复
> 状态：已创建为 Gitea 工单 `tanzk/csctalon#2`
> 工单链接：http://192.168.28.11:3000/tanzk/csctalon/issues/2
> 责任人：后端开发 / 数据采集开发 / 监控运维
> 相关审计：docs/debug/debug-cs-record-gap-2026-09-02.md

## 一、背景

本次 2026-09-02 `cs_records` 缺口事件暴露出采集链路在“上游瞬时 5xx + 大范围导出失败 + 熔断后不探活 + 缺口无自愈”四个环节上的治理缺口。

这类问题不属于单次业务事故，而是系统设计层面的可靠性缺陷。

## 二、目标

建立一套稳定的采集治理机制，确保：

1. 上游瞬时错误被正确识别为“可重试”；
2. 大范围导出失败能够按日/按片降级重试；
3. 熔断触发条件更加合理，并具备半开探测恢复机制；
4. 缺口数据可进入待补队列并在下一轮补跑时强制清点；
5. 数据量骤降与熔断事件能第一时间发出告警。

## 三、设计要求

### 3.1 错误分级与重试

- [ ] 将 `5xx` / JSON 500 识别为可重试瞬时错误；
- [ ] 大范围导出失败时优先按日切片重试，而不是直接整窗丢弃；
- [ ] 整窗失败前先执行“单日失败再整窗失败”的策略；
- [ ] 退避机制按指数退避或分段重试参数化实现；

### 3.2 熔断优化

- [ ] 修改熔断条件：采用滑动窗口下连续失败次数阈值；
- [ ] 在熔断后增加半开探测逻辑；
- [ ] 上游恢复后自动恢复采集，避免再次出现“断层持续”；

### 3.3 缺口待补队列

- [ ] 维护“业务日期 + 专项”未补齐清单；
- [ ] 次日补跑前先清点遗漏项；
- [ ] 对缺口日期进行强制补跑触发；

### 3.4 告警与监控

- [ ] 统计各专项每日入表量，并与近 7 日均值对比；
- [ ] 当骤降超阈值时触发告警；
- [ ] 熔断发生时直接推送告警；

## 四、验收标准

以下指标全部满足后，可视为治理工单完成：

- 5xx / JSON 500 不再被直接判定为“确定失败”；
- 大范围导出失败时可按日切片重试，单日成功率显著提升；
- 熔断不会在一次错误后永久停采，而是具备恢复探测；
- 缺口补全流程存在可追踪清单与强制回补触发；
- 数据量骤降告警能在异常发生后及时发送；

## 五、实施步骤

1. 方案评审：确认重试策略、熔断阈值、降级路径；
2. 设计实现：补充错误分类、重试器、半开探测与缺口队列；
3. 单元/集成验证：覆盖重试、熔断恢复、缺口回补场景；
4. 灰度上线：选择低风险专项先验证；
5. 线上观察：确认告警正常、恢复机制生效；

## 六、风险与限制

- 本工单需要在评审后再实施，不应在未确认的情况下直接修改生产逻辑；
- 该类治理需要覆盖采集、补跑和监控三层，不能只改单点重试；
- 对外部平台 5xx 需要保守处理，避免误判造成重复拉取过量；
