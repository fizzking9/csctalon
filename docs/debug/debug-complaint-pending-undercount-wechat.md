## 5 个可证伪假设 (H1-H5)
| # | 假设内容 | 可证伪观测点 |
|---|---|---|
| **H1** | service_tickets 投诉判定 WHERE 过严: st_kws 关键词集 / service_category 匹配逻辑 不能覆盖所有投诉类工单(特别是微信商户号投诉), 导致大量应该进来的工单在第一步就被过滤掉 | 近7天 service_tickets **总行数** vs 我的 WHERE 判定匹配后行数 vs 实际投诉类工单行数 |
| **H2** | `_to_status_bucket` 关键词表把真实未处理的 status 误判成了"已完成/已终止": 微信/商户号投诉同步过来的原始 status 字符串(例:"已受理""受理中""已分派""申诉中") 与我的映射表不吻合, 在后处理阶段被错误过滤掉 | 近7天候选工单 **原始 status 值分布 top20**, 以及每一个按我的规则映射后被归类为"已完成/已终止"的那些原始字符串 |
| **H3** | external_complaints 状态推断规则过于激进: 把"result 含有效→已完成" "有handle_time→已完成" 等推断用于微信投诉时, 把"受理有效(不等于处理完毕)"误判为已完成; 或者微信商户号投诉有独立 platform 但没进来 | external_complaints 近7天 **原始 platform + result 分布**, 以及每张表有多少被我推断为已完成/已终止 而实际未处理完 |
| **H4** | 三张独立投诉表 有大批记录根本没进入我的 UNION (创建窗口/判定口径问题), 13 条只是 service_tickets 一部分未闭环 + external/card 基本为 0 → 真实总数远大于 13 | 三张表分别: 近7天总行数 / 按我的 WHERE 取到多少行 / 状态过滤后剩多少条 (三阶段漏斗) |
| **H5** | LIMIT / 排序截断了前 201(或200) 条中的早期行: 但 13 条远小于 200 所以基本不成立, 仅作为兜底验证 | 最终合并后列表实际条数 & 是否命中截断 |

### Step 3: 证据判定 ✅ (全部落定 2 个根因)

| 假设 | 结论 | 核心证据 |
|---|---|---|
| H1 投诉判定 WHERE 过严 | ❌ **拒绝** | A0=7595 总工单, A1=1276 投诉匹配(17%), WHERE 被过滤的 6319 条 Top20 全部是退款/换货/套餐疑问, 没有投诉漏网 |
| H2 status 映射误判 | ❌ **拒绝** | status 原始值仅 4 种: 已完成/处理中/待处理/终止, 与我的 bucket 映射 100% 一一对应, 没有误判 |
| H3 外部投诉推断激进 | ⚠ 次要 | external_complaints 近7天 **0 行** (最后一条 7/25, 近20天未同步新的), external 表不承载商户号投诉 |
| H4 三表 UNION 漏表 | ⚠ 次要 | external/card 近7天都是 0, 所有投诉都落在 service_tickets, 没漏 |
| **H8 LIMIT 201 排序方向 bug** | ✅ **确认为主根因** | 生产代码 `ORDER BY register_time ASC LIMIT 201` 取到最早 201 行, 其中 **192 条已完成 + 9 条未闭环 + 1 条终止** → 运营实际只看得到 9-13 条. 但全量漏斗真实未闭环=**208 条**! (相差 15 倍) |
| **商户号投诉没显示根因** | ✅ **确认为 H8 连锁效应** | A1 中含"微信/商户"关键词的行共 **177 条**, 其中未闭环 **109 条** (状态=处理中). 它们在 ASC 排序中序号分布 #4 ~ #>201**, #228、#257、#260…已经超出 LIMIT 201 → 被 SQL 直接截断, 列表完全看不到 |

**额外发现**: external_complaints 表虽然有 1312 条历史记录,但最后一条是 2026-07-25,说明近 20 天外部投诉同步没有启用; 用户提到的"微信商户号投诉"实际走的是 BMS→service_tickets 的 `service_item='微信投诉'` 同步链路.

### Step 4: 最小范围修复 ✅
**修改文件**: backend/app/services/analytics.py → complaint_pending 三段查询

修复策略 (一个改变两处受益):
1. **SQL 层 3 个查询全部移除 LIMIT PENDING_LIMIT_ROWS+1**: 只保留 WHERE(倒查7天创建 + 投诉判定) + ORDER BY ASC, 让 ~1276 行候选全部进 Python 层
2. **Python 层先过滤 bucket**: 遍历后处理循环中已有的 `if bucket in ("已完成","已终止"): continue` 把已闭环的剔除 → 得到未闭环全集 (~208 条)
3. **Python 层合并三表 排序 ASC 后统一 LIMIT 200**: 已有的 `complaint_pending.sort` + `len > 200 截断` 逻辑不变, 它作用在未闭环**全集**上, 不再被老已完单抢占 LIMIT 名额

性能评估:
- 旧: 3 条 SQL 各 LIMIT 201 → 取到 ~201 行但 95% 是已完成垃圾行
- 新: 3 条 SQL 各取 ~1276 行 / 0 行 / 0 行 → Python 遍历 1276 次 (亚毫秒级, 完全可接受)
- 实际未闭环返回 ≤200 条 (和原上限一致), 前端无感知
