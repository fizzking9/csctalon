# workbuddy 手动退款数据同步接入规范

> 版本: v1.0 · 2026-08-23
> 适用: workbuddy 定时将 `商户号手机退款处理登记.xlsx` 明细推送到客服中心管理系统
> 配套: 投诉数据同步接入见 [workbuddy数据同步接入规范.md](workbuddy数据同步接入规范.md)

---

## 1. 背景与目的

系统的手动退款台账表 `manual_refunds`(手动退款登记)此前仅支持**本地文件导入**:
客服在商户号(微信商户)后台手动操作的退款登记,登记在《商户号手机退款处理登记.xlsx》中。

该台账是四路经营退款中的 **D 路(手动退款)**:`is_refunded='是'` 的行构成 D 路经营出款,
`is_refunded='否'`(已登记未退款)的行计入"登记蓄水"水位。

**同步方式**: workbuddy 每 20 分钟检查文件是否变化,变化时将该文件明细以 **JSON** 通过 HTTP 推送过来。
系统按 (登记日期, 订单号, 退款金额) 复合键去重 upsert,重复推送不会产生重复数据。

> 说明: 主动监测(腾讯文档)方式暂不覆盖本表;本规范只定义"被动推送"接入。
> 若手动退款台账已有本地文件导入习惯,推送与导入会按同一复合键互相覆盖,二者可并存但建议只保留一种。

---

## 2. 接入总览

| 项目 | 值 |
|---|---|
| 推送接口 | `POST {BASE_URL}/api/v1/sync/manual-refunds/push` |
| 日志查询(内部) | `GET {BASE_URL}/api/v1/sync/manual-refunds/logs` |
| 鉴权方式 | HTTP 请求头 `Authorization: Bearer <WORKBUDDY_SYNC_TOKEN>`(或 `X-Sync-Token` 头) |
| 数据格式 | `application/json` |
| 建议频率 | 每 20 分钟检查文件;文件变化才推送(全量推送文件内全部行即可,系统按复合键去重) |
| 幂等性 | 支持。同一行重复推送不会产生重复数据(按 登记日期+订单号+退款金额 复合键 upsert) |

`BASE_URL` 为系统对外访问地址(如 `https://csctalon.example.com`),由系统管理员提供。

---

## 3. 鉴权

1. 系统管理员在 `.env` 配置(与 315 投诉推送共用同一个 token):
   ```
   WORKBUDDY_SYNC_TOKEN=<随机长字符串,建议 openssl rand -hex 32>
   ```
2. workbuddy 推送时携带请求头:
   ```
   Authorization: Bearer <WORKBUDDY_SYNC_TOKEN>
   ```
3. 未配置 token → 接口返回 `503`;token 错误/缺失 → 返回 `401`。
4. 「数据采集 → 采集方式开关」中"被动推送"关闭时,接口同样返回 `503`。

## 4. 推送接口规范

### 4.1 请求

```
POST /api/v1/sync/manual-refunds/push
Content-Type: application/json
Authorization: Bearer <token>
```

### 4.2 请求体结构

```json
{
  "source_file": "商户号手机退款处理登记.xlsx",
  "manual_refunds": [
    { "登记日期": "2026-08-19", "订单号": "WX123456789", "设备号": "67482454178206", "...": "..." }
  ]
}
```

- `source_file`: 可选,来源文件名(记录到同步日志)。
- `manual_refunds`: **必填**,为数组,元素为对象,字段名与 xlsx 列名一致(见 4.3 字段映射),也可直接使用英文字段名。
- 每次推送建议携带**文件内全部行**(系统按复合键去重更新,全量推送最简单可靠)。

### 4.3 字段映射

| 字段名(推送用,与xlsx一致) | 库字段 | 必填 | 说明/清洗规则 |
|---|---|---|---|
| 登记日期 / 登记时间 | register_time | **必填** | 日期/时间;按北京时间解释后转 UTC 存储;年份笔误自动纠错(见 §5) |
| 订单号 / 订单编号 / 平台订单号 | order_no | **必填** | 去重键之一;缺订单号的行无法定位,跳过 |
| 退款金额 / 实退金额 | refund_amount | 建议 | 去重键之一;数值清洗(货币符号/千分位/中文单位);缺省按 0 参与去重 |
| 设备号 / 设备SN / SN | device_sn | 否 | 关联键;自动维护设备主数据(缺失 SN 建空壳) |
| 商户ID / 商户号 / 商户号ID | merchant_id | 否 | 字符串,超64字符截断 |
| 订单金额 / 订单原金额 | order_amount | 否 | 数值清洗 |
| 登记人 | registrant | 否 | 姓名清洗(纯数字/金额格式视为列错位 → 置空并记警告) |
| 是否已退款 / 是否退款 | is_refunded | 否 | 归一化: 仅 `是` 计为已退款,其余(空/否/其他)一律 `否` |
| 退款操作人 / 操作人 / 处理人 | refund_operator | 否 | 姓名清洗 |
| 操作时间 / 退款时间 / 完成时间 | op_time | 否 | 日期时间清洗 |
| 备注 / 说明 | remark | 否 | 备注=`示例` 的模板行自动跳过 |

### 4.4 响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "log_id": 12,
    "status": "success",
    "total": 1896,
    "inserted": 0,
    "updated": 1896,
    "failed": 0,
    "filtered": 0,
    "warnings": 2,
    "errors": [ { "row": 1936, "level": "warning", "message": "...", "data": {} } ]
  }
}
```

| 字段 | 含义 |
|---|---|
| status | `success`=全部入库;`partial`=有行被丢弃(见 failed);`failed`=整体失败(需看服务端日志) |
| total / inserted / updated | 收到行数 / 新增 / 更新(重复推送时 inserted≈0) |
| failed | 被丢弃的行数(硬失败,如行解析异常或缺登记日期/订单号),会记入 errors 并置 status=partial |
| filtered | 空行/模板行等主动过滤的行数 |
| warnings | 软警告数(行保留但某字段被清洗,如姓名列填了手机号 → 置空),仅记录不影响状态 |
| errors | 前50条 警告/失败明细 |

## 5. 数据清洗与去重规则(系统侧自动处理)

workbuddy **无需自行清洗**,推送原始单元格内容即可,系统会:

1. **列名映射**: 兼容 xlsx 中文列名与英文字段名,推荐按 4.3 中文列名推送。
2. **时间处理**: 日期统一按北京时间解释转 UTC 存储;登记日期超出合理范围
   ([当前年-2 的 1/1, 今天+3天])时,有操作时间佐证 → 按操作时间年份自动修正(auto_fixed),
   无佐证 → 标记 `quality_status=pending` 待人工确认;操作时间早于登记日期超过 1 天(时间倒挂)同样标记 pending。
   **原始数据只有日期没有时间** — 时间部分为 `00:00:00` 北京时间的行,系统自动统一设为 `15:00:00`(北京时间),
   作为合理默认值(非退款完成时间,而是用于数据排序和去重定位的参考时间)。
3. **姓名/金额防御**: 姓名列若是数字/金额(常见列错位)置空并记录警告;金额列支持 `¥1,234.56`、`50%`、`1.2万` 等格式。
4. **去重复合键**: `(register_time, order_no, COALESCE(refund_amount, 0))`(订单号非空的行),
   同键 upsert 更新。**重复推送/重复行不会累积**。同一订单可分期多次退款(不同登记日期/退款金额),复合键能正确区分。
5. **is_refunded 归一**: 仅字面值 `是` 视为已退款,其余一律 `否`(空 → 未退款,计入登记蓄水)。
6. **设备主数据维护**: 推送中出现的新 SN 自动在 `devices` 表建空壳,避免外键失败。

> 注意: 若同一行(同键)的**退款金额**被修改,复合键会变化 → 会产生新记录(旧记录保留为历史)。
> 建议保持"登记日期+订单号+退款金额"稳定,退款状态变更通过 `is_refunded` / `操作时间` 更新。

---

## 6. 错误码

| HTTP | 场景 |
|---|---|
| 401 | token 缺失或错误 |
| 400 | 请求体非 JSON 对象 / `manual_refunds` 缺失或非数组 |
| 413 | 请求体过大(默认受反向代理限制,建议单次 <50MB) |
| 500 | 服务端异常(数据已回滚,重试即可) |
| 503 | `WORKBUDDY_SYNC_TOKEN` 未配置,或"被动推送"采集方式已关闭 |

---

## 7. 建议与约定

1. **频率**: 每 20 分钟检查文件 mtime/内容变化,变化才推送;未变化可跳过(降低负载)。
2. **推送内容**: 建议全量推送(文件内全部行)。若文件很大(>5万行),可改按"最近更新日期"增量推送,但需保证每条记录复合键稳定。
3. **幂等**: 同一行重复推送安全;内容更新(如操作时间/退款操作人变化)会覆盖旧值。
4. **日志**: 每次推送可在系统内 `GET /api/v1/sync/manual-refunds/logs`(需登录)或「数据采集 → 采集日志」页查看,包含行数/新增/更新/失败与错误明细。
5. **与本地导入的关系**: 两者共用同一复合键去重,互相同源;重复推送/导入只会更新不会累积,但建议只保留一种常用方式,避免日志混淆。

## 8. 本地联调示例

```bash
# 1. 配置 token 后启动系统
# 2. 构造 JSON(字段用 xlsx 列名)推送到本地
curl -X POST http://127.0.0.1:8000/api/v1/sync/manual-refunds/push \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <WORKBUDDY_SYNC_TOKEN>" \
  -d '{
    "source_file": "商户号手机退款处理登记.xlsx",
    "manual_refunds": [
      {
        "登记日期": "2026-08-19",
        "设备号": "67482454178206",
        "订单号": "WX123456789",
        "商户ID": "1900000001",
        "订单金额": 1299.00,
        "登记人": "张三",
        "是否已退款": "是",
        "退款金额": 1299.00,
        "退款操作人": "李四",
        "操作时间": "2026-08-19 15:30:00",
        "备注": ""
      }
    ]
  }'
```

成功返回 `"code": 0` 及同步统计;随后即可在「决策看板 → 退款-提现全链路 / 退款看板」的 D 路(手动退款)查看。
