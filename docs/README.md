# docs 目录组织与命名规范

**生效日期**：2026-09-03
**适用范围**：`docs/` 下所有**新增**文档的命名与放置位置
**性质**：约束新增文件；存量文件逐步迁移，不强求一次性重命名（避免破坏既有交叉引用）

> 背景：docs 根目录历史文档中英文混杂、报告/规范/设计/说明混放、无日期前缀，检索与维护困难。本规范只约束「新增」，存量按迁移计划渐进归位。

---

## 一、目录职责

| 目录 | 职责 | 命名规则 |
|---|---|---|
| `docs/arch/` | 已锁定架构设计 | `A-YYYYMMDD-序号-简述.md`（见 arch/README.md） |
| `docs/arch/_pending/` | 待审核设计草案 | 同 arch 编号，状态 PENDING |
| `docs/standards/` | 规范/清单/模板 | 英文 kebab-case（`error-code.md`） |
| `docs/reports/` | 审计/审查/审核报告 | `YYYY-MM-DD-主题-报告.md` |
| `docs/debug/` | 调试会话与故障排查归档 | `debug-<主题>-<日期>.md` 或 `<主题>-<日期>.md` |
| `docs/security/` | 安全事件/凭证整改 | 英文 kebab-case |
| `docs/ops/` | 运维手册/SOP | 英文 kebab-case 或 `<主题>运维手册.md` |
| `docs/` 根目录 | 仅保留全局入口类文档 | `README.md`、`规划设计.md` 等顶层总纲 |

> ⚠️ 报告类（审计报告、审查报告、审核报告）一律进 `docs/reports/`，不再堆在根目录。

---

## 二、命名规则（新增文件强制）

1. **规范/清单/模板** → 英文 kebab-case，不带日期：`issue-workflow.md`、`error-code.md`。
2. **报告/审计** → 带日期前缀：`2026-09-02-接待数据缺口审计.md`。
3. **调试/故障** → `debug-` 前缀 + 主题：`debug-cs-record-gap-2026-09-02.md`。
4. **架构** → 沿用 `A-YYYYMMDD-序号-简述.md`（不重复定义，见 arch/README.md）。
5. **运维手册/SOP** → `<主题>运维手册.md` 或英文 kebab-case，放入 `docs/ops/`。
6. **禁用**：空格、下划线混用、无意义序号（`新建文档.md`、`文档1.md`）。

---

## 三、存量迁移计划（渐进，非强制）

> 迁移会破坏既有 Markdown 交叉引用，必须**分批、先改引用再移动**。当前不执行，仅登记方向：

| 现状（根目录） | 去向 |
|---|---|
| 审计报告-*.md、审核报告-*.md、审查报告-*.md | `docs/reports/` |
| 数据采集运维手册.md | `docs/ops/` |
| *数据接入规范.md、*同步接入规范.md、数据源接入与缓存加速规范.md | `docs/standards/` |
| Group-Specialty双体系设计.md、腾讯云部署迁移方案.md 等设计 | 评审后入 `docs/arch/` |
| 数据时间字段使用规范.md、数据同步与加工说明.md 等成文规范 | `docs/standards/` |

---

## 四、运维手册的分发（不在生产目录）

`docs/` 不随发布包进生产（`package.sh` 排除 `docs`，`upgrade.sh` 清理 `docs`），因此运维手册在**生产服务器上不可见**。运维人员获取方式二选一：

1. **首选**：从代码仓库（Gitea）在线查看——运维手册与代码同仓库，永远是最新版本。
2. **兜底**：将手册同步到团队共享文档/知识库，供无仓库访问权限的现场人员查阅。

> 原则：手册跟随代码仓库，不单独部署到运行环境；如确需服务器现场可查，可在 `.env` 指向的 `logs/` 同级放一份拷贝，但**不要**改发布打包清单。
