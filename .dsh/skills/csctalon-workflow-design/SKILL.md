# CSCTalon 办公流程/工作流设计规范

> 核心原则: 系统第一屏应「推着人走」而非「人到处找事」; 流程要闭环但分级, 不搞一刀切。

## 1. 流程设计五问(任何新流程先回答)

1. **谁发起?** 录入入口是否 ≤30 秒、能自动则自动?
2. **谁处理?** 是否有明确负责人/接收人(缺省=进统一待办中心)?
3. **什么状态?** 状态机是否线性可预期(待处理→处理中→已完成/闭环)?
4. **何时提醒?** 到期/超期/新增是否有通知(站内信+角标)?
5. **如何闭环?** 结束态是否明确(关闭/归档/回看), 结果是否可追溯?

答不上的流程=不完整, 不上线。

## 2. 状态机规范

- 状态用 String 枚举(避免 SA Enum 迁移麻烦), Pydantic 层校验。
- 状态流转线性的: `待处理 → 处理中 → 已完成` 为主轴; `挂起/驳回/退回` 为分支。
- 每个状态变更落时间线记录(谁/何时/从哪到哪/备注), 复用跟进记录表。
- 状态色统一用 `statusColor.js` 色板(黄=需动作/蓝=进行中/绿=结束/红=异常/灰=归档)。

## 3. 统一待办中心(必做)

- 汇聚所有「该我处理的事」: 待办事项 / 待跟进异常 / 待回看措施 / 待审发票报销 / 待读政策 / 被指派工单。
- 每条带: 来源 + 优先级 + 截止 + 一键跳转; 按角色过滤(管理层看全部, 一线看本人)。
- 新模块的"待处理"数据必须接入统一待办中心, 禁止散落各页面。

## 4. 通知提醒(轻量站内信)

- 触发点: 到期(措施回看/异常跟进)、新增(异常登记/政策发布/审计指派)、状态变化(审核通过/被驳回)。
- 落 `notifications` 表(recipient_id/type/title/content/ref_type/ref_id/is_read), 前端角标 + 列表。
- 局域网内站内信即可, 不做外部推送。

## 5. 闭环分级(不过度管理)

| 事项重要度 | 闭环要求 |
|-----------|---------|
| 小事/日常 | 一句跟进记录即闭环(记录>不记录) |
| 中事/影响有限 | 跟进 + 状态流转 + 到期回看 |
| 大事/影响大 | 完整流程: 登记 → 复盘 → 输出措施 → 到期回看 → 结论归档 |

禁止对小事强制走完整流程(会逼人少登记, 数据失真)。

## 6. 跨模块联动(推荐链路)

```
异常事故(登记+跟进)
  ├─→ 转待办(todo_items)        当需要人执行
  ├─→ 转管理措施(measures)       当需要持续改进/到期回看
  └─→ 转跨部门派发(upstream)     当根因在上游
投诉审计 → 审计结论 → 转管理措施
政策发布 → 通知相关角色 + 关联知识库话术同步
发票提交 → 主管审核 → 报销 → 导出
```

## 7. 流程评审清单(梳理流程时逐项过)

- [ ] 五问是否全部可答?
- [ ] 状态机是否线性可预期、流转落时间线?
- [ ] 待处理项是否进统一待办中心?
- [ ] 到期/新增是否有通知?
- [ ] 结束态是否明确、可追溯?
- [ ] 是否按重要度分级闭环而非一刀切?
- [ ] 是否与异常/措施/待办/上游正确联动?
- [ ] 录入是否 ≤30 秒、能自动则自动?
